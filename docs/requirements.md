# Requirements

> AIUP stage 2 of 5: [vision](vision.md) → **requirements** → [entity model](entity_model.md) →
> [use cases](use_cases.puml) → [technical specs](specs/). Index: [docs/README.md](README.md).
>
> **Status** follows the AIUP reference: `Open` (not built),
> `In Progress` (open PR), `Implemented` (on `main`), `Verified` (for an FR: every use case that lists it
> under `Requirements:` is `Tested`, i.e. has tagged tests; otherwise an FR is at most `Implemented`), `Deferred`, `Rejected`, `Obsolete` (retired; Notes name what replaces it). NFRs and constraints are exempt
> from this derivation and from the weakest-requirement rule: an NFR's status reflects its own measurement or test,
> a constraint's is verified by review and the technical specs; only FRs derive their status from their use cases. Planned items carry their issue number.
> Measured values cite their source; numbers taken from code cite the file. Some NFRs deliberately pin **code constants**
> (rates, defaults) so that changing one is a visible spec change; NFRs whose target is not agreed yet say
> "Target not yet set (to measure)". The Status column holds exactly one AIUP status. The **Notes** column holds at most one line: where the
> requirement is specified (use case, spec section), the tracking issue of a planned item, or what replaces a retired one.
> Rules live in the statement, the use cases and the technical specs, never only in Notes; tests trace through the use cases.

## Roles

| Role | Who |
|---|---|
| Player | Holds a PS Move controller and plays. |
| Host | The game host: picks modes, calibrates and starts games from the operator pad (UC-015). |
| Operator | Runs and observes the stack (Pi or laptop), edits flags. |
| Presenter | Runs the "Two Standards Walk Into an Agent" talk demo and the Orange Case booth challenges. |
| Agent | The Go service that observes via OTel and acts via flags (a system actor). |
| Maintainer | Changes the system; owns specs, reviews tier-3 proposals. |
