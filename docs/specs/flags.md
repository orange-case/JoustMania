# Flag catalog (OpenFeature / flagd)

> Technical spec. Part of the [spec tree](../README.md). Also serves #1092 (agent-tunable flag catalog).
> **Generated from the JSON files plus a call-site scan**, then
> hand-verified. Regenerate rather than hand-edit when many rows change.
> **References.** Write a code reference as a full repo path: `path/file.go:Symbol` (survives edits) or `path/file.go:123` (allowed, but it drifts and a growing count warns in CI). `make spec-refs-check` fails on a missing file, an out-of-range line, a missing symbol or a path that is not a full repo path (#1280). <!-- spec-refs: ignore -->

OpenFeature flags served by flagd are the **only** control surface of the system:
human settings, the agent's governor and the agent's own interventions
are all flags (northstar constraint C-002). This catalog lists every flag on `main`. The flag sets and their files are
generated by `make specs` into [generated/flag-counts.md](generated/flag-counts.md) (#1280); the per-set flag counts are not committed, so two PRs that each add a flag do not conflict: `make specs-counts` prints them and CI shows them in the Telemetry Contract job summary (#2152); the `ci/` copies (§12) are not counted. (`services/flagd/controller.ci-rust.json`, loaded by nothing, was deleted in #1416.)

Rule (see [CONTRIBUTING](../CONTRIBUTING.md#spec-driven-development-aiup)): a new flag, a new variant, a
changed default or a new reader/writer updates this file in the same PR.

**Provider readiness (#1329, UC-010 A5 / BR-004).** A named provider is READY only after its first sync from flagd. Until then, every evaluation returns the code default with `ProviderNotReadyError`, and the `TracingHook` records that error on the current span. `lib/feature_flags.py` `wait_for_provider_ready(domain, deadline_seconds)` waits for READY, bounded by the deadline. The SDK runs the READY handler on whichever thread emits the event: the provider's init thread, the flagd watcher thread, or the caller of `add_handler` when the provider is already READY. The waiter is therefore woken on its own event loop with `loop.call_soon_threadsafe`. The handler is removed once the wait ends. The controller manager waits at startup (5 s per domain). The game coordinator waits per game (real and agent-started shadow games), before the game is created: up to 5 s, and only for those of `system`, `controller`, `game`, `agent`, `user`, `interventions` and `observability` that are still NOT_READY. STALE and ERROR are not waited on, because with the in-process resolver they still serve the last-synced flags. `observability` is waited on too (maintainer decision 2026-11-18, #2658): the coordinator reads `telemetry.moment_shape` (§10, UC-100) per game, so a game must not read its code default because that provider had not synced yet. The wait finishes before the game root span is created and its outcome is recorded on that span; the flag is read after it. A game starts with the code defaults only when flagd is not reachable within the 5 s deadline. After a wait the coordinator re-reads its process-wide runtime config in an empty evaluation context, so a shadow session's `game_kind` / experiment targeting cannot leak into it (`services/game_coordinator/flag_readiness.py`). The OpenFeature client used for the wait is reused per domain, and a domain's status is read through that client (`lib/feature_flags.py` `provider_status`). `api.provider_registry.get_provider_status` takes a provider object and reports NOT_READY for a domain string.

**Agent and rust-hid readiness (#1713, UC-045 A3).** Both use the in-process resolver against `flagd:8015` and wait for flagd without a deadline that can end the sync for good. go-sdk-contrib flagd v0.8.0 (re-checked in #1942; v0.6.0 behaved the same) gives `Init` one deadline; when it passes before the first sync, the provider never starts its event loop, its event buffer (5) fills after a few flag changes and the sync stops applying data, so later flips are lost (the in-process form of #1709). `Init` also fails at once on a STALE / ERROR event before the first sync (flagd refusing the stream), with the same result. The agent therefore wraps each provider (`syncedProvider`): a provider is built only once a TCP probe of the sync port succeeds (probes 250 ms apart, doubling to 10 s); its `Init` gets no effective deadline, so it waits for the first sync (logged at WARN every 10 s while it waits); an `Init` that fails on an error event is shut down and a fresh provider is built after a pause of 1 s doubling to 5 min, logged at WARN, with no overall limit. Residual bound: v0.8.0 never frees a failed build (its service `Init` waits on a channel that ignores its context: about one goroutine and 300 KB each), so a flagd that accepts TCP but refuses the stream (for example a wrong selector) costs at most one build per domain per 5 min, about 10 MB per hour for the two domains; a flagd that is down costs only probes. Until the first sync the SDK keeps the domain NOT_READY. While the domain is not READY (before the first sync, and when the sync stream is lost: STALE or ERROR until flagd sends again) every agent read returns its code default, as when flagd was unreachable on the RPC resolver: `enabled` and `interventions_enabled` fail closed, and so do `experiments_enabled` and `experiment_dynamic_enabled` (no env fallback since #1907). Unlike the Python services, the agent does not keep serving the last-synced values while STALE. After flagd sends a configuration the provider cannot parse (ERROR), the next valid configuration, even one identical to the last good one, sends READY again, so the agent's reads are served again at once (v0.8.0; v0.6.0 waited for the next configuration that changed a flag). The sync stream reconnects on its own (backoff 500 ms to 1 s). v0.8.0 also ends the sync stream every 10 min and opens it again at once (`StreamDeadlineMs`, default 600000): this sends no event and the resent configuration changes no flag, so reads stay served; the provider logs `sync stream established` at INFO each time (once per domain per 10 min). Every in-process read runs under a context timeout equal to the `Init` deadline (one timer per read, which never fires with the agent's deadline). Sync keepalive (#1768): flagd v0.16.0's sync server set no keepalive enforcement policy, so grpc-go's default applied (at most one client ping per 5 min, none without an open stream; a faster client collected ping strikes and got GOAWAY `too_many_pings`, which dropped the stream and made the agent fail closed for about a second). Since flagd v0.18.0 (#1945) the sync server is served by connect over net/http, which enforces no minimum ping interval and permits pings without a stream (`--keep-alive-min-time` and `--keep-alive-permit-without-stream` are accepted no-ops), so no client ping cadence draws that GOAWAY any more; the client options below are kept unchanged. v0.6.0 hard-coded a 30 s ping without a stream, which drew that GOAWAY every 2 to 3 min on an idle stream, and v0.8.0's own options still ping without a stream (its default keepalive time 0, documented as off, is raised to grpc's 10 s minimum); the agent therefore dials the sync stream with its own options (`WithGrpcDialOptionsOverride`: plaintext, the retry policy above with at most 4 attempts as in v0.8.0, keepalive ping every 10 min with a 5 s timeout and only while the stream is open), as the Python services do (`keep_alive_time=600000`). Trade-off: flagd sends no heartbeat on an idle stream, so a half-open connection can go unnoticed for up to about 10 min (OS TCP keepalive starts only after 2 h); in that window the agent stays READY on the last-synced values and would miss a kill-switch flip. This is accepted because the agent and flagd share one host and compose network, and a shorter ping (for example 30 s) is what flagd up to v0.16 rejected with GOAWAY `too_many_pings`. rust-hid sends no HTTP/2 keepalive pings (the crate's `keep_alive_time_ms` default is 0; only OS TCP keepalive), so its stream is not affected. The lifecycle holder is reloaded on every `PROVIDER_CONFIGURATION_CHANGED` and, as the safety net, every 1 s. rust-hid builds its provider only once flagd's sync port accepts a TCP connection, retried with backoff (500 ms to 5 s) in the background, and again if the build fails (the crate's own first-sync wait is 5 s); until then `grpc_rpc_spans` reads its code default (off). Every flagd client points at the sync port: each compose file and each image that sets `FLAGD_PORT` sets 8015 (`tests/contract/test_flagd_client_ports.py`, #2090); a client on the RPC port (8013) gets the TCP connection but never a first sync. Once built, the crate's sync stream reconnects on its own (backoff 500 ms to 2 s) and keeps the last-synced values while flagd is away. Tests: `services/agent/flags/synced_provider_test.go` (late first sync, lost stream), `services/agent/flags/latestart_test.go` (a real gRPC sync server that accepts TCP before it serves: one provider build, reads fail closed until READY, then every flip is seen; the identical configuration after a parse error is served again; a DISABLED `enabled` reads off; the opt-in canary `TestUpstreamFlagdLateInit_StillWedges`, run with `FLAGD_UPSTREAM_CANARY=1`, fails once upstream fixes the late-init bug so the wrapper can be re-evaluated), `services/agent/flags/keepalive_test.go` (keepalive within flagd's ping policy, sync over the override dial options), `tests/service/test_agent_flag_live.py` (late flagd, flagd restart mid-run, flips of already-read flags, an idle stream held 150 s without a drop), `tests/service/test_rust_hid_flag_live.py`.

### 1.2 Evaluation context

- API level (Python): `service_name`, `service_namespace`, `language`, `hostname`, `game_kind=real` (`lib/feature_flags.py:115-131`).
- Per game (transaction context): `targetingKey=game_mode`, `game_mode`, `controller_count`, `game_kind`, optional `sensitivity`, `experiment_id`, `arm` (`lib/feature_flags.py:set_game_transaction_context`). Calibration reads add `gameId` (`lib/feature_flags.py:284-295`).
- Interventions are evaluated per live session with `{targetingKey=serial, gameId}` (`services/game_coordinator/interventions.py:InterventionFlagReader.session_context`).
- Every intervention handler (and revert handler and agent cue) runs on the game loop through `GameLoopDispatcher.run`, and the manager sets the game's own transaction context around it (`flag_eval_context` on the game, `services/game_coordinator/intervention_dispatch.py:run_in_game_flag_context`; restored afterwards). A flag read inside a handler therefore sees the API-level context, the game's transaction context (`targetingKey=game_mode`, `game_mode`, `controller_count`, `sensitivity`, `game_kind` (`shadow` in a shadow game), `experiment_id`, `arm`; before the game's run starts only `game_kind`, `experiment_id` and `arm`) and its own invocation context, which wins (#1970; before, handlers saw only the API-level context, #1837, #1872). The handler-read flags are declared in `services/game_coordinator/handler_flag_reads.py` (today `shield.activation`, `shield.charge_expiry_seconds`, `windows` and the `user` flag `agent_intervention_cue`). Targeting on them may use only the variables declared there, checked over `services/flagd/*.json` and `services/flagd/ci/*.json` (`tests/contract/test_flagd_resolution.py`); `services/game_coordinator/tests/test_handler_flag_reads.py` drives every handler and fails for a read that is not declared. Because handlers see the game's context, an experiment-arm value on `windows` reaches the `pacing_profile` read in that arm's games, and the lever is then blocked as `experiment_override` (§4, UC-043 BR-005); real and non-experiment shadow games resolve every handler-read flag as before.
- `game_kind` vocabulary for flags is `real` / `shadow`; the protected value is `real`. An experiment-arm value is rendered by the flag service (`services/flag-service/state/render.go`) as the rung `{"and": [{"!=": [{"var": "game_kind"}, "real"]}, {"==": [{"var": "experiment_id"}, "<id>"]}, {"==": [{"var": "arm"}, "experimental"]}]}` in front of the baseline targeting, so the control arm, every other experiment and every real game fall through (FR-138). The agent's gate checks a dry run of each write before it writes (`services/agent/experiment/gate.go`). Every experiment has an id: a proposer proposal is declared as a registry experiment (`exp_<hex>`); there is no unscoped form. The flag service drops an experiment's arm values once no registered game has carried its id, and nobody wrote them, for `FLAG_SERVICE_EXPERIMENT_IDLE` (default 2 h, NFR-051). Telemetry uses the same `real` / `shadow` since #2646 (before that `primary` / `shadow`); see [entity_model.md](../entity_model.md#game_session).

### 1.3 Reload semantics

| Term | Meaning |
|---|---|
| **live** | Evaluated at use time (each call, cycle or tick). Takes effect once flagd has the new configuration from the flag service. |
| **event-refreshed** | Cached, re-read on OpenFeature `PROVIDER_CONFIGURATION_CHANGED`. Effectively live. |
| **per-game** | Read at game start (menu `StartGameConfig` or game `__init__`) and frozen for that game. |
| **startup** | Read once at process start. **Restart required.** |

Startup-only flags: controller `backend`; observability `metrics_export_interval_ms`,
`otel_bsp_schedule_delay_millis`; user `menu_auto_start`, `audio_volume.lobby_music`,
`audio_volume.menu_sound`, `audio_volume.menu_voice`.

Propagation (write accepted to value served): the flag service pushes the new configuration on the open sync
stream at once; `tests/service/test_flag_propagation.py` measures it for NFR-050. A baseline file change takes
effect only on the next start of the flag service (`scripts/flags.sh restart`).

**Traceability:** C-002, C-033, NFR-050 / UC-015, UC-044, UC-053 / `docker-compose.yml`, `lib/feature_flags.py`, `lib/flag_service_writer.py`, `services/agent/flags/` / `lib/tests/`, `services/agent/flags/*_test.go`, `tests/service/test_flag_propagation.py`.

Parsed by `services/agent/goal/profile.go:Parse`. Each variant is an object with exactly one of `{"terms": [ {"characteristic": <name>, "min": <number|null>, "max": <number|null>, "phase": "whole"|"endgame", "weight": <number>} ]}` or the sentinel `{"from_objectives": true}`. Unknown keys on the object or on a term invalidate the variant (`additionalProperties:false`):

| Field | Rule |
|---|---|
| `characteristic` | One of `duration`, `activity`, `change`, `elimination_pace`, `survival`, `closeness` (decide-contract §14.1); anything else invalidates the variant |
| `min`, `max` | Finite numbers inside the characteristic's hard bounds (`duration` seconds, `activity` and `closeness` and `change` as fractions of the death threshold, `elimination_pace` per minute); `null` = open (at least one edge is set); `min` <= `max`; the hard bounds per characteristic are in decide-contract §14.4 |
| `phase` | `whole` (default when absent) or `endgame` (at most 2 players alive) |
| `weight` | Finite, > 0 and at most 10 (default 1 when absent); the attainment is the weighted mean |
| terms | 1 to 4 per `terms` variant |

`from_objectives` is the sentinel `{"from_objectives": true}`, without terms: the profile is derived from the active `objectives` variant (decide-contract §14.4). A value that fails any rule
falls back to `from_objectives` (WARN once, and a metric). A contract test checks every variant in both `agent.json` files (`services/flagd/`, `ci/`). The flag is human-owned and never written by the agent (C-034); at runtime only Flagsmith may select another declared profile (Flagsmith only, §13, #2705).

## 5. `interventions`

File: [`services/flagd/interventions.json`](../../services/flagd/interventions.json).

The agent's tier-1 write surface: bounded, in-game, reversible. Written only by the agent action sink (gated by `interventions_enabled`) through the flag service, and always for one registered game: every value is rendered as targeting on that game's `gameId` (and on the player's serial for a per-player flag), resolves in no other game, and is dropped when the game ends ([UC-053](../use_cases/UC-053.md) BR-003, FR-136). The game coordinator `InterventionManager` re-reads the set on every flagd configuration change. **State** flags resolve the game's value; **event** flags (`eliminate_player`, `revive_player`, `audio_cue`, `controller_effect`, `end_game`, `group_shield`) resolve the game's event list `{"epoch","seq","events":[last 16]}` and the coordinator applies every event with a seq above the last one it applied, exactly once (UC-053 BR-006, FR-137); a game starts with an empty list, so nothing of an earlier game is replayed. Per-player **level** flags (`player_sensitivity_factor`, `player_handicap_factor`) apply to the players whose level changed during the game, and a player whose level returns to neutral has its factor reset to 1.0 as a revert ([UC-040 BR-017](../use_cases/UC-040.md#br-017-per-player-levels-belong-to-one-game), #1317). Per-player **grant** flags (`shield_seconds`, `toughness_boost_seconds`, `soft_penalty_action`) get a fresh generated variant per write, so a same-value re-grant is a change and fires once ([UC-040 BR-012](../use_cases/UC-040.md#br-012-a-per-player-grant-applies-once-per-decision)). `end_game` is in the deciding game's event list and ends only that game ([UC-040 BR-011](../use_cases/UC-040.md#br-011-end_game-ends-only-the-game-it-was-decided-for)). Value formats and the writer mapping: [decide-contract.md §11](decide-contract.md#11-from-decision-to-game-effect); bounds and scopes: §13.1.

**Consistency with the allow-list after a reconnect** ([UC-053](../use_cases/UC-053.md) A9 step 4, #1552). The coordinator holds `interventions` and `agent` on separate in-process sync streams, which reconnect one by one, in no fixed order, after a flagd restart. The flag service therefore stamps every `interventions` flag and `agent/interventions_allowed` (no other flag) with the snapshot it rendered them from: flag metadata `snapshotEpoch` (its boot epoch) and `snapshotVersion` (its snapshot version), so every write moves both stamps. After reading an intervention, and before it moves any baseline, the coordinator compares the stamp of `end_game` (its interventions set) with the stamp of `interventions_allowed`. While the allow-list is from another epoch, older or unstamped, the intervention is deferred: nothing is applied, blocked or recorded, and no baseline moves. The `agent` stream's catch-up fires a configuration change, which re-evaluates it against the current allow-list (applied, or blocked `not_allowed`). A stale allow-list therefore never decides an intervention, wider (fail closed) or narrower (nothing is lost). An unstamped `interventions` set (file-sourced flagd, as in the contract tier) is not gated. A probe that fails is treated as a lag (fail closed). The probe and the allow-list stamp are resolved through the provider, bypassing the OpenFeature hooks, so they do not appear in the evaluation metrics; the allow-list stamp is read at most once per evaluation pass unless the probe moves past it. A deferral that lasts longer than 5 s is visible as a rate-limited WARNING. The flag service refuses to start when `FLAG_SERVICE_SETS` serves `interventions` without `agent`, since every intervention would then be deferred for good. Because every write moves both stamps, one write fires a configuration change on the written set, on `interventions` and on `agent`. Code: `services/flag-service/state/render.go` (`snapshotStamped`), `services/game_coordinator/intervention_deferral.py` (`AllowListGate`).

## 13. Mutable-flag registry

> Enforced by the flag service since PR #1417 (epic #1407, [UC-053](../use_cases/UC-053.md), FR-132, FR-133;
> design: [architecture/flag-service.md](../architecture/flag-service.md)).

A flag changes at runtime **only** if it has a row here,
only within its bounds and only in its scope. Every other flag of every set is the **read-only baseline**: it
changes by a reviewed edit of the flag file and a restart of the flag service (C-033). The registry file
`services/flag-service/registry.yaml` encodes this table; a change to one updates the other in the same PR.

**Writers** is the canonical place that says who writes each flag (the human surfaces: the menu for the operator pad,
the operator and stage scripts, Flagsmith; the agent: `agent` for its game-scoped interventions, `agent
experiment arm` and `agent promotion` for the two gated `game` writes of OWNERSHIP_MODEL §1); other documents link
here instead of listing writers. A key whose Writers cell names none of the three agent writers is never agent-written (C-034).
There are **no writer roles and no authorization** (local party game; architecture note D11): the column states the
contract the writers' code keeps, not a check.

**Kinds:** `state` = one value per scope; `level` = per-player value, re-applied as a whole; `grant` = per-player
value with a fresh variant per write (the coordinator fires on a variant change); `event` = per-game event list
`{"epoch","seq","events":[last K]}` written with `POST` (UC-053 BR-006); `overlay` = stack-wide value rendered as a
`defaultVariant` substitution, so baseline targeting still wins.

**Scopes:** `game` = targeting on `gameId` of a registered game; `game+serial` = `gameId` and `targetingKey`
(a serial of that game); `stack` = the default for every reader; `experiment+arm` = `game_kind != "real"` and
`experiment_id` and `arm`; `real` = the real default (promotion).
Game-scoped values are dropped when the game ends (FR-135).

**Persist (#2803):** persistence is a property of the flag, not of the request. `yes` = an admin setting: **every**
stack-scope write of it is persisted, whoever writes it (the menu for the operator pad, a script, a stage beat,
Flagsmith). A `PUT` without scope parameters sets the persisted value in the service's own state file, a `DELETE`
without scope parameters clears it, and the value is restored at start (FR-018, C-030). The flag has one stack value:
there is no in-memory overlay over a persisted value. A stack write of it takes no `ttl_seconds` (`400 malformed`: a
persisted value never expires). A stored value the registry no longer accepts (an unknown flag, a flag no longer
persistable, a variant no longer declared, such as the retired `openai` of `decision.backend`, #2788) is skipped and
logged as stale, and the flag serves its baseline. `no` = every stack value lives in memory only (architecture note
§10.1). Other scopes (`game`, `experiment+arm`, `real`, ...) are never persisted, also on a `yes` row. The request's
`persist` (the `PUT` body field, `DELETE ?persist=`) is optional and changes nothing: it is accepted where it was valid
before #2803 (a stack write of a `yes` row; `?persist=` on any stack `DELETE`) and stays `400 malformed` on a stack
`PUT` of a `no` row, in another scope, with `ttl_seconds` or on a dry run, so an older caller that expects
persistence is refused loudly instead of silently getting an in-memory value. A writer reset
(`DELETE /{flagSetId}?writer=`) never clears a persisted value (PR #1417 review): only a per-flag `DELETE` does.

**Session-only variants (#2803, maintainer decision):** a variant of a `yes` row may be session-only. A stack write of
it is never persisted: it lives in memory over the persisted value, which stays as it was, and a restart, a `DELETE`
of the flag or a writer reset of its writer returns to the persisted value; a later persisted write replaces it. It
is never sent to Flagsmith (the link sees the persisted value beneath it), and a write of it with `"persist": true`
or from Flagsmith is `400 malformed`. The set is fixed in the flag service's code (`registry.sessionOnly`, like
`registry.killSwitches`): `agent/interventions_allowed` = `shadow_group` (the
level `agent-group-ab.sh` sets for a run), so a run killed with `SIGKILL` never widens the host's kill switch
across a restart.

**Which store wins (#2803, FR-215, UC-054 A2, A3, BR-006):** with the Flagsmith link `off`, the state file is the
persisted store. With the link `on`, Flagsmith is the persisted store and the state file is its offline cache: every
value of a `yes` row the link applies is also persisted, so an offline start serves the last value Flagsmith gave.
When the link connects, Flagsmith is the full backend (#2804): it wins wherever it holds a value, a kill switch too,
and an empty Flagsmith is seeded from the local value:

| When the link connects | Flagsmith holds a value | Flagsmith holds none |
|---|---|---|
| after a reconnect (no restart), for a stack value changed while the link was not connected | the Flagsmith value is applied and persisted; the local change is discarded | the baseline applies and the persisted value is removed |
| at a start, for the value in the state file | the Flagsmith value is applied and persisted | Flagsmith is seeded: the persisted value stays and is sent to Flagsmith, which holds it from then on |

The two rows differ because the mark "changed while not connected" lives in memory only (F5): at a start the state
file's value cannot be told apart from Flagsmith's last value, so it is kept and sent (flagsmith-sync.md §5.1, §6). A
value a person cleared in Flagsmith while the flag service was down therefore comes back from the state file at the
next start; clear it locally too (a `DELETE`, or the pad's reset) or set it in Flagsmith.

**Failed save, kill switches (#2368, UC-053 A12):** when the state file cannot be saved (or was unreadable at
start), a stack `PUT` or `DELETE` of a `yes` row is refused with `500 persist_failed` and nothing changes in
memory, also for a stage script, which before #2803 wrote such a row in memory; with a state file unreadable at start that includes a `DELETE` with no persisted value in memory, because
the file may still hold one (a `no` row cannot be in the file: its `DELETE` stays a plain `204`, uncounted). The exception covers the persisted kill-switch flags, a fixed set in the flag service's
code (`registry.killSwitches`), not a registry.yaml attribute (released images parse the checkout's registry.yaml
strictly). This list is its single source of truth, kept in sync by a test: `agent/interventions_allowed`. A safety
stop must take effect now, so a write or clear of it applies in memory and answers `persisted: false` (`PUT`) or
`204` with `X-Flag-Persisted: false` (`DELETE`), counted in `flagservice_admin_persist_errors_total` and not
counted as persisted in `flagservice_overlays`; a restart brings back what the file holds (services.md §7.2). Only a
row with persist `yes` can be in the set: `enabled` is a kill switch too, but its row is persist `no`, so a failed
save never affects it.

**Stage beats and scripts on a `yes` row (#2803, replaces "persisted vs overlay" of #1682):** a stage beat
(`talk-stage.sh`) or a script (`agent-group-ab.sh`) that writes a `yes` row replaces the host's value, and the
replacement survives a restart; there is no temporary value over it, except a session-only variant (above). `talk-stage.sh reset` applies the stage
baseline after deleting the persisted decision backend and models (#1682), and writes a `yes` row only where its value in force differs;
`agent-group-ab.sh` snapshots the
stack value of the rows it writes (the persisted one of a `yes` row) and puts it back with its writer (a value from
Flagsmith under `group-ab-restored`) when the run ends. After a `SIGKILL` the run's `interventions_allowed` =
`shadow_group` is session-only, so a restart returns the host's level; its persisted `decision.backend` stays until
`agent-group-ab.sh restore --out DIR`. `talk-preflight.sh` WARNs while a
remote backend is persisted.

Renamed grant flags carry no persisted state (`toughness_boost_seconds`, formerly `partial_shield_seconds`, is not `persist`, is game-scoped and is dropped with its game): there is nothing to migrate. The persisted `interventions_allowed` stores a variant name only, so its content follows the baseline file (#1838).

**Real write (#2096, #2810, UC-043 A17, C-034):** a `PUT` or `DELETE` in scope `real` (the promotion overlay) is never refused because a real game is registered: every flag with scope `real` is read once per game, at its start (UC-048 BR-011; the menu's game config and the coordinator's init flags otherwise), so a write or a revert applies from the next game. The flag service keeps that list as a Go set (`latchedAtGameStart` in `services/flag-service/registry/latched.go`, not a `registry.yaml` key, so released images still load the checkout's registry), and `TestRealScopeIsLatched` fails the build when a row with scope `real` is not in it. `shield.activation` is not latched (an instant or trigger game reads it at each grant, UC-048 BR-004), so it has no `real` scope and the agent never promotes it (UC-043 A17 step 3; maintainer decision on #2810); `TestShieldActivationIsReadPerGrant` fails the build if it is listed as latched or given scope `real`. Operator flips (stage, pad, scripts) keep working per grant. A `real` write may carry `ttl_seconds` like a stack write. An older agent's `?unless_real_game=true` is ignored. **Compare-and-delete (`?if_writer=<label>`, #1877, UC-043 A18):** a `DELETE` of the `real` overlay may carry this opt-in precondition (like If-Match): the overlay is cleared only when its stored writer equals the label, compared and cleared under one lock, else `412 writer_mismatch` and nothing changes. A missing overlay is a `204` that clears nothing. It is evaluated after every other check. It is valid in scope `real` and, since #2755 (maintainer decision D14), in scope `stack`: the in-memory stack overlay of a `DELETE` without scope parameters and without `persist`, so the menu's reset of a pad row clears only its own overlay (UC-016 BR-013); elsewhere, and empty, `400 malformed`. It is not the informational writer label, which is never checked (D11). Every revert of the agent sends `if_writer=promotion`, the kill switch's included: every overlay the agent writes carries writer `promotion`, so it never blocks the kill switch from clearing one, and another writer's overlay is never removed. **Write precondition (`?if_writer_in=<labels>`, #2260, UC-043 A19):** a `PUT` of the `real` overlay may carry a comma-separated list of writer labels (opt-in, like If-Match): the overlay is written only when the stored real overlay's writer is in the list, or when no real overlay is present and the list holds an empty entry (`if_writer_in=promotion,` = the promotion's own overlay or none), compared and written under one lock, else `412 writer_mismatch` and nothing changes. An overlay without a writer label matches no entry. It is evaluated after every other check (a dry run included). It is valid only in scope `real` (elsewhere, repeated, over 16 entries or an entry over 80 characters, `400 malformed`). A `PUT` without it writes unconditionally, as before. The agent's promotion write sends `if_writer_in=promotion,`, so a promotion never overwrites a real overlay another writer (a script, a maintainer on the API) set; it maps the `412` to outcome `discarded` (reason `real_overlay_owned_by_another_writer`). A mid-game `DELETE` is harmless for the running game: it latches its hold values and its activation at game start, and a game latched to `hold` stays `hold` (UC-048 BR-011), so the revert applies from the next game. Other scopes are not affected.

The seven hold sub-parameters of §13.3 (`shield.energy_max_seconds`, `shield.energy_budget_seconds`, `shield.energy_initial_seconds`, `shield.recharge_per_second`, `shield.min_burst_seconds`, `shield.hold_rumble_intensity`, `shield.empty_pulse_ms`) have scope `stack or experiment+arm or real` since FR-162 (#2096 PR-7b-2a); `shield.activation` has `stack or experiment+arm` (#2810).

**Flagsmith only (#2705, FR-226, UC-053 A14, UC-054 BR-011):** a registry row may be marked Flagsmith only, so that the operator can change a baseline flag from Flagsmith while no writer on the network can. Such a flag changes at runtime only through the Flagsmith link's in-process write (writer `flagsmith`, §13.6). Every `PUT`, `POST` and `DELETE /{flagSetId}/{flagName}` over HTTP, a dry run included, is refused with `403 flagsmith_only`, whatever writer label the caller sends; the check runs right after the registry lookup (`404`, `422 flag_read_only` first) and before every other check, and an HTTP write labelled `flagsmith` stays `400 malformed` (UC-053 BR-002, checked before it). A writer reset (`DELETE /{flagSetId}?writer=`) skips the row, also with `writer=flagsmith`. The trust boundary is the process: no HTTP caller reaches the in-process path, so neither the agent nor any other writer of UC-053 can write the flag; whoever can change the stack's Flagsmith environment can (the operator, holding its keys, C-016). Otherwise the row is an ordinary row: it is a Flagsmith feature (§13.6), and kind, scope and bounds are checked as for any write. A marked row must be kind `overlay`, scope `stack` only and persist `no` (the flag service refuses to start otherwise), and is never an `interventions` row or a flag the agent writes (C-034). With the link off or offline the flag changes only by a reviewed edit of its flag file (C-033); a value from Flagsmith lives in memory and comes back from Flagsmith at a restart (UC-054 BR-006). The marker is a fixed set in the flag service's code (`registry.flagsmithOnly`), not a registry.yaml attribute: released images parse the checkout's registry.yaml strictly (#2403). This list is its single source of truth, kept in sync by a test: `agent/goal.profile`. A flag-service image older than the marker serves the row as an ordinary registry row, writable over HTTP, until a release that carries the marker runs.

**Description (`description`, #2345):** one line, in game terms, of what the flag does, at most 120 characters (the cap bounds the experiment proposer's prompt). **Required** on every row whose scope includes `experiment+arm` (the experiment catalog, §13.3, and the one `agent` row with that scope, `decision.prompt_profile`, §13.2, #2530): the flag service refuses to start when such a row has none, or when a description is longer or spans lines; optional on every other row. It is served in the row's `policy` by the read endpoints and is informational: no write is checked against it.

**Bounds** are the declared variants of the baseline file unless a range, a payload schema or `free string` is
given. Ranges are inclusive and pinned to the reader's own clamp (`difficulty_handlers.py` factors 0.5 to 2.0, `lifecycle_handlers.py` toughness boost and soft penalty, `games/base.py` ramp_tempo 15 s and tempo ramp 0.1 to 10 s), so the registry never rejects a value the game would apply.
`free string` accepts any string value up to 512 characters (a declared variant name still selects that
variant); it exists for values only a test fixture or an operator knows, such as a fake server's URL (re-review N5).
A `variant` naming a declared variant is always within bounds (restricted to the listed variants where a list is
given); a `value` equal to a declared variant's value selects that variant. Event payloads are checked by the
service for shape and serials (a serial of the game); whether the player is still alive and whether a sound id
exists in the audio catalog are checked by the game coordinator and the audio service, which hold that state.

## 14. Ownership composition: invalidation and visibility

> [OWNERSHIP_MODEL.md](../OWNERSHIP_MODEL.md) holds the ownership principle and invariants (section 1) and the
> composition of the two contested runtime parameters (section 4: sensitivity, grace/shield); it points here for the
> two rules below.

### 14.1 The invalidation rule

> **A human baseline change invalidates the active agent override for that parameter.**

The human is the source of truth for intent. When the admin changes a baseline the agent is currently overriding, the
human's new value wins **immediately** and the agent's active override for *that parameter* is dropped (caveat: no
production code path calls `set_baseline_sensitivity`, so today this invalidation is reachable only through the
game-object API; a mid-game admin flag edit is not pushed into a running game):

- The agent does not keep an override pinned over a fresh human decision. Otherwise the admin's deliberate change would
  silently no-op while the agent's transient delta persisted.
- Invalidation is **per parameter**, not global: changing `sensitivity` cancels an active `global_sensitivity_override`
  but leaves an active `shield_seconds` untouched.
- After invalidation the agent may **re-propose** against the new baseline on its next decision. The human change resets
  the baseline the agent composes against; it is not a veto of the agent.

Implementation for `sensitivity` (verified against the code): the game keeps a human `baseline_sensitivity` and an agent
`sensitivity_override` layer; `game.sensitivity` is the effective value. `BaseGameMode.set_baseline_sensitivity` (the
target of assigning `game.sensitivity`) sets the baseline and clears the override; clearing the override from the agent
path (`handle_global_sensitivity_override`, value -1) returns to the **current** baseline, never to the game-start
snapshot (`configured_sensitivity`, telemetry only). The same shape applies to any future contested parameter.
Grace/shield needs no invalidation: it composes with `max(grace_until, invincible_until)` (OWNERSHIP_MODEL section 4.2).

**Traceability:** C-008 / UC-015, UC-040 / `services/game_coordinator/games/base.py`,
`services/game_coordinator/difficulty_handlers.py`.

### 14.2 The visibility contract

The human admin must be able to tell agent activity apart from a malfunction. A conforming implementation provides at
least:

- a **distinguishable signal** when the agent applies an in-game delta (an LED pattern, audio cue or dashboard
  indicator that is clearly agent action, not a game event and not "the settings are broken");
- a signal that identifies **what** changed at the granularity of one registry key (§13.1), so the
  admin can reconcile observed behaviour with the baseline.

Agent actions are already audited as spans (`agent.decision`, intervention events) and metrics
(`game_interventions_total`); the contract is the human-facing, on-device surfacing of that activity, not new
instrumentation.

Surfaces (#818):

1. **Truthful admin announcement (removed, #2819).** The controller admin mode announced the EFFECTIVE value of an
   option it selected and followed a step with the magenta agent cue when an agent overlay won (#1739, UC-012 BR-006).
   It is gone with the admin mode. The operator pad announces the value it commits, and its live preview and knob start
   read the effective value from `GetMenuStatus` (UC-015 BR-017, BR-018).
2. **On-device cue.** When the coordinator applies a **HARD-class** intervention (`spec.weight >= WEIGHT_HARD`, in
   `services/game_coordinator/interventions.py`; `end_game` is excluded because its game has just ended, UC-040
   BR-018) it emits a short magenta `GAME_EFFECT_PULSE` on the affected controller(s), broadcast for non-targeted
   actions (`InterventionManager._emit_agent_cue`). It is gated by the `agent_intervention_cue` toggle in the `user`
   set (§9; default on, off in `ci/`), so it can be muted for demos, and is best-effort: a failure never breaks the
   intervention path. MEDIUM and SOFT interventions are silent so gameplay is not disrupted.

**Traceability:** C-008 / UC-015, UC-040 /
`services/game_coordinator/interventions.py`.

### 15.1 Registry entries (extends §13.2 and §13.5)

Each key above is added to the mutable-flag registry as a stack-scoped `overlay`, `Persist` no (except `inference.backend`, which persists like `decision.backend`, #1682), with the bounds of its variants (seconds: int within the variants' declared range; `inference.model` a free string), writer: operator scripts and the integration fixtures. The agent writes none of them. The `agent` rows are in the registry (§13.2: `inference.timeout_seconds` int 30 to 120, `effect.window_seconds` 10 to 40, `promotion.rewatch_interval_seconds` int 30 to 120, `promotion.rewatch_timeout_seconds` int 1800 to 7200, `promotion.revert_cooldown_seconds` int 300 to 1200, `inference.model` free string, `inference.effort` its declared variants, `decision.probe_decisions` variants `on` / `off`); the `observability` rows (`log_level`, `debug`) are in the registry too (§13.5). #1810 adds `experiment_completed_grace_seconds` (int 0 to 600) and `experiment_proposer_enabled` (`on`, `off`); #1907 adds `experiment_dynamic_candidates` and `experiment_dynamic_denylist` (free strings), `experiment_dynamic_objective` (its variants); `experiment_tick_seconds` already had a row (int 1 to 1000).

### 15.4 Agent-limiting settings (FR-152)

Every setting that limits the agent is an operator ceiling no agent write can loosen (C-034): the env var is the ceiling and the human-owned flag may only tighten it. The flags are operator-written (§13.2), never agent-written. Per setting:

- **(a) Autonomous promotion** runs only when `AGENT_AUTONOMOUS_ENABLED` is true AND `code_improvement.mode` is `autonomous` AND `enabled` is on.
- **(b) Issues.** Opening an issue needs `AGENT_CODE_IMPROVEMENT_ENABLED` true AND `enabled` on; `code_improvement.mode` (default `issue`) then selects issue or autonomous only within that ceiling.
- **(c) Remote-call budget** = `min(AGENT_LLM_MAX_REQUESTS_PER_MINUTE, llm.max_requests_per_minute)` (NFR-011), shared by the decide path, the retro and the proposer. An in-game decide call on a paid backend (claude) also needs a slot under that backend's `decision.<backend>.max_requests_per_minute` in the same window: the cap can only tighten (`inherit` = no cap of its own, 0 or a negative value closes the backend, a value above the global cap does nothing). The jev backend, the retro and the proposer stay on the global budget only.
- **(d) Proposer gate** (the M7-4 proposer) is open only when `AGENT_EXPERIMENT_PROPOSER_ENABLED` is true AND `experiment_proposer_enabled` is on. A missing flag or a lost sync reads false (closed), so a deployment with the env set and an `agent.json` without the flag has no proposer.
- **(e) Concurrent-experiment budget** = `min(AGENT_EXPERIMENT_DYNAMIC_MAX_CONCURRENT, experiment_dynamic_max_concurrent)`, clamped to the shadow capacity. An unset, invalid or non-positive env is no ceiling (logged at WARN when set but not positive).
- **(g) Validated objectives.** An autonomous promotion (a) also needs its experiment's objective in `AGENT_AUTONOMOUS_VALIDATED_OBJECTIVES`, the operator's attestation that the objective's shadow substrate meets the validity bar (UC-043 A23, FR-203): a comma list of `objective@release` entries (`balanced@0.14.0`). An entry counts only when its objective has a fitness function (`endurance`, `balanced`, `accelerate`) and its release equals the agent's `SERVICE_VERSION`, which must be a release (`X.Y.Z`; `latest`, `main`, `dev` or a sha never count). Unset or empty validates no objective; an empty objective is never validated; no flag can widen it. An autonomous promotion of any other objective is a recorded no-op `substrate_not_validated objective=<objective>`. Read once at startup; `code_improvement.mode` and `enabled` stay the runtime tighteners. Not passed through compose (D-A6).

**Unset env.** For the boolean gates unset is closed (false); for the budgets (c), (e) unset means no env ceiling and the flag governs.

**Fail values.** A missing flag or a lost sync resolves each flag to its code default: `enabled` off, `code_improvement.mode` `issue`, `llm.max_requests_per_minute` 6 (not the lowest variant 3), `decision.claude.max_requests_per_minute` 30 (so the global 6 binds), `experiment_proposer_enabled` false, `experiment_dynamic_max_concurrent` 3. The boolean gates therefore fail closed and the budgets fall to their defaults, still capped by a set env value.

**Not agent-limiting.** `decision.probe_decisions` and `inference.backend` are tuning flags (§15 rows): the probe only swaps in a rules engine that emits synthetic `noop` decisions, and `inference.backend` only chooses between the stub and the Claude text backend of the retro and the proposer. Every egress ceiling stays with the operator: the Claude client exists only with `ANTHROPIC_API_KEY` set and a valid `AGENT_INFERENCE_BASE_URL`, the call count is (c), and the M7-4 proposer also needs the proposer gate (d), so no flag alone switches on model-chosen experiment declaration.
