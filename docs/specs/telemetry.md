## 3. Spans

### 3.1 gRPC (all Python services, rust-hid)

| Span | Kind | Gate | Source |
|---|---|---|---|
| `{Service}/{Method}` (e.g. `GameCoordinatorService/ForceEndGame`) | CLIENT / SERVER | flag `grpc_rpc_spans` (default variant `enabled`), evaluated per RPC; when flagd is unreachable or the flag is missing the Python check falls back to **false** (no RPC spans) | `lib/grpc_tracing.py` (`_rpc_spans_enabled`) |
| `grpc.server` (rust-hid) | SERVER | same flag | `services/rust-hid/src/grpc_tracing.rs:105-115` |
| renamed: `StreamButtonEvents`, `StreamGameplayData` (CM); `PlaySound:{sound}`, `PlayMusic:{dir}`, `ChangeTempo:{x}x`, `SetVolume:{pct}` (audio) | SERVER | | `services/controller_manager/servicer.py` (`StreamButtonEvents`, `StreamGameplayData`); `services/audio/servicer.py` (`PlaySound`, `PlayMusic`, `ChangeTempo`, `SetVolume`) |

Audio span attributes: `PlaySound:{sound}` carries `audio.file`; `PlaySound` and `PlayMusic` carry `audio.muted=true` when `play_audio` is off (read at use time); `PlaySound` carries `audio.silent=true` when `play_audio` is on but the audio hardware is not open yet, so nothing is heard. `PlaySound` carries `audio.duration_seconds`, the clip length it returns in `PlaySoundResponse.duration_seconds` (0 when nothing is heard; UC-020 A5). `StopSound` (server span, unrenamed) carries `audio.stopped`, the number of channels it stopped (UC-020 A5).

Python `{Service}/{Method}` CLIENT spans cover the whole call: a unary call ends at its status, a server-, client- or bidi-stream when the RPC terminates (completed, failed, or cancelled by `call.cancel()` or a cancelled read task; a stream the caller drops ends when it is garbage collected; closing the channel alone does not end an open stream, its reader keeps waiting), with no work per message. A unary call in flight does end when its channel closes. `rpc.grpc.status_code` is the final code; a non-OK status sets the span status ERROR, except a cancel by the caller (cancelled call or task, garbage collection, a unary call ended by closing its channel), which leaves it unset; a `CANCELLED` sent by the server is ERROR. Covers the async channels from `lib/grpc_utils.create_channel` and the HID adapters' sync unary calls; the sync `StreamIO` stream has no span. When `grpc_rpc_spans` is on, the `traceparent` sent with the call carries the CLIENT span, so the receiving SERVER span (Python `{Service}/{Method}`, the renamed audio/CM spans, rust-hid `grpc.server`) is its child, as with connect-proxy's `otelgrpc` client. With no CLIENT span (`grpc_rpc_spans` off or flagd unreachable), the caller's current span is sent. The sync `StreamIO` stream has no CLIENT span and still sends the caller's span.

Python `{Service}/{Method}` SERVER spans record the status the RPC really ended with. `rpc.grpc.status_code` is the code of `context.abort(code)` (read from the servicer context, the `AbortError` is re-raised), the code a handler set with `context.set_code(X)` before returning normally, or OK. A non-OK code sets the span status ERROR; a handler that fails with any other exception (including a downstream call's error that escapes it) records the code set on the context, else UNKNOWN (ERROR, exception event recorded). The span status description is the handler's `details` text when set, else the code name. A handler cancelled because the client cancelled the call (or the server stops) records `CANCELLED` and leaves the span status unset, the same convention as the CLIENT span above. This holds for unary, server-, client- and bidi-stream handlers and is decided once per RPC, with no work per message.

connect-proxy: `otelhttp` server spans (`/health` filtered) and `otelgrpc` client spans only.

**gRPC health checks are not traced**: the collector's `filter/grpc_health` processor drops every span whose `rpc.service` is `grpc.health.v1.Health` (Go, Rust) or `Health` (the package-stripped form `lib/grpc_tracing.py` records for the Python services) from the `traces` pipeline (Jaeger and the agent), whatever service recorded it. Docker healthchecks and watchdog probes call the RPC as before; on the stage Pi 1362 of 1500 Jaeger spans were health checks.

### 3.2 game-coordinator

Flag-provider readiness at game admission (UC-010 A5 / BR-004): the game root span carries `feature_flag.providers_wait_ms`, the time spent waiting for the coordinator's NOT_READY flag providers (`system`, `controller`, `game`, `agent`, `user`, `interventions`, `observability`; STALE / ERROR are not waited on) to be READY before the game was created. The wait runs before the root span starts, so the span's start time and duration do not include it and its warnings carry no game trace id in OTLP logs (accepted). When that bounded wait (5 s) runs out, the root span gets the event `feature_flag.providers_not_ready` (attrs `feature_flag.domains`, the domains still not READY; `feature_flag.wait_seconds`; `feature_flag.fallback` = `code_defaults`). Flag reads of those domains then fall back to code defaults and show as `ProviderNotReadyError` exceptions on the span where they were read.

**Agent log events (FR-250, UC-100 BR-012, UC-041 A8).** In every game, without a flag, the coordinator sends the agent these log records on its SDK `Logger` (the one the booth's `log_event` shape uses; never through Python `logging`), each with the attribute `orangecase.audience` = `agent`. The collector routes on that attribute alone: `logs/agent` passes them, `logs/gateway` drops them (§1), so no backend gets them. signal, so a FFA or NonStop death shows once, as the `player_death` moment below.

**`player_death`: exactly one moment per death.** Every death that reaches the base kill path (`BaseGameMode._kill_player`) records exactly one `player_death` moment, in the game's moment shape (by default a span event on that player's lifecycle span, appendix A), in every mode. The one record carries, in every shape:

- always: the identity `moment.id`, `game.id`, `game.kind`, and `player.serial`, `player.name` (once the controller reported one), `death.reason` (`motion` for a threshold death, `agent_intervention` for `eliminate_player`), `accel_magnitude` (0.0 for a non-motion death), `alive_remaining` (alive players after this death), `sensitivity`, `sensitivity_factor`, `music_speed`;
- when the player's last shield (a hold activation, an instant shield, an activated charge) ended less than 3 s before the death: `shield.since_end_ms` (UC-048 BR-015; the fairness measure of the shield end grace);
- mode extras, added through `_player_death_event_attributes()` and computed as if the player were already out: Teams / Random Teams `team`, `team_eliminated`; Traitor `team_eliminated` (secret team), `is_traitor`, `visible_team`, `secret_team`; Werewolf `is_werewolf`, `was_revealed`; NonStop `kills`, `deaths` (including this death), `score`; `death.eliminated` (bool, UC-041 BR-008) in the modes where a death can keep the player in the game: Fight Club (false for a round loss, where the loser stays in the game; true when the death takes a disconnected player out of the rotation; UC-025), NonStop (false for a respawn death, true for a disconnect death; UC-026 BR-004), Swapper (false for a swap, true for a disconnect death, next to the Teams attributes `team`, `team_eliminated`; UC-024 BR-005) and Zombies (always false: a conversion, a zombie death and a disconnect all keep the player in the game; UC-023 BR-008); the mode's outcome of the death: Zombies `respawn_delay` (seconds, a killed zombie only; the delay its respawn timer uses), Fight Club `round` and `winner` (a death that decides a round), Tournament `match_id` (a death that decides a match).

A mode's `_kill_player_impl` never adds its own `player_death` span event. Swapper's `team_swap_out` stays a separate span event in every shape. The event-bus `player_death` in §5 is a different channel and reaches stream subscribers only. Consumers that count or order eliminations from the death record count one moment id as one death, and one record as one elimination unless it carries `death.eliminated` false (a Fight Club round loss; a NonStop respawn death, a Swapper swap or any Zombies death). The agent is not one of them: it reads `game_player_elimination_order`, which the coordinator sets for exactly the deaths that take the player out (`_kill_records_elimination_order`), in every shape (§4.4, UC-041 BR-008, BR-009).

**Pinned conventions.** The GenAI rows follow `open-telemetry/semantic-conventions-genai` **v0.1.0**
(2026-11-21, status Development), the *Invoke agent internal span* for the decide span: name
`{gen_ai.operation.name} {gen_ai.agent.name}` = `invoke_agent joustmania-agent`, kind `INTERNAL`, `gen_ai.operation.name`
Required, the sampling-relevant `gen_ai.operation.name`, `gen_ai.agent.name` and `gen_ai.request.model` set at span
creation. Deviations from v0.1.0:

- **`invoke_agent`, not `invoke_workflow`.** v0.1.0 keeps `invoke_agent` for an LLM that drives the control flow
  through tool calls and `invoke_workflow` for an application-defined flow; the agent's loop is application-defined,
  but the model chooses the intervention, and GenAI agent views look for the agent conventions.
- **Rules path without a model.** The rules path records the same span name and `gen_ai.operation.name=invoke_agent`
  although no model is called (`decide.backend=rules`, no `chat {model}` child, no `gen_ai.request.model`, no
  `gen_ai.output.type`), so one query sees every decision of either path. Cost per decision therefore filters
  on `gen_ai.request.model` being present, not on `decide.backend`: a rules-path span carries no model and no tokens,
  while a remote call that fell back (timeout, error, invalid answer) ends with `decide.backend=rules` but keeps its
  model and its billed `chat {model}` child, and counts.
- **No tool spans.** The decide backends return JSON and call no tools, so there are no `execute_tool` spans; the
  model calls are the `chat {model}` CLIENT children of the remote-path span.
- **`gen_ai.conversation.id` is the game id.** Each decide request is a stateless single-turn prompt and the agent
  keeps no conversation history, so this is a grouping key rather than a conversation in the sense of v0.1.0
  (notes [4] and [5] tie the attribute to managed history). It is kept so a backend's conversation view groups one
  game's decisions.
- **`gen_ai.request.model` with a per-decision model.** Note [12] says not to populate it for an agent that supports
  multiple models or dynamic selection. The backend, and with it the model, is chosen per decision by flag
  (`decision.backend`, `decision.*.model`), but each invocation calls exactly one model, so the span carries that
  invocation's model (from its start) and the rules path carries none.
- **Jev's finish reason is derived.** Jev reports no finish reason; the agent records `stop` for a decoded valid
  answer and `error` otherwise (no response, or an answer that failed to decode), matching its captured output
  message.
- **Cache-write tokens on the chat span under two names.** The claude `chat {model}` spans (decide, retro and proposer) carry v0.1.0's
  `gen_ai.usage.cache_write.input_tokens` and, for consumers that read it so far, the same value as the Go semconv
  package's (v1.41.0) `gen_ai.usage.cache_creation.input_tokens`; the old name goes with the other transition
  alternatives (#2729). The decide span carries only `cache_write`.

v0.1.0's invoke_agent table lists only `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`; the cache and
reasoning totals are registry attributes added on top.

**Spend.** The decide span's totals cover the decide calls only; the retro's and the proposer's model calls
are only on their own `chat {model}` spans (told apart by the instrumentation scope and the parent span: under
`agent.llm.retro`, or the proposer). The totals repeat the per-call values of the decide span's `chat {model}`
children, so count one or the other, never both: a backend that rolls child usage up into the agent span, or a
query that sums `gen_ai.usage.*` over every span, counts a remote decision twice. In every backend's mapping the
cache read and cache write tokens are included in `gen_ai.usage.input_tokens` (claude adds them to its
`input_tokens`) and the reasoning tokens in
`gen_ai.usage.output_tokens` (claude's `output_tokens` include thinking); jev reports input and output only. So price the cached share at the cache rate and the rest of
`input_tokens` at the input rate, and never add `cache_*` or `reasoning` on top. The response model and the provider
(`gen_ai.response.model`, `gen_ai.provider.name`) are on the chat children, not on the decide span: price by those.
The counting rules:
- **Per decision:** the decide span's totals.
- **Per game:** the sum of `gen_ai.usage.*` over the spans with `gen_ai.conversation.id=<game id>`: the game's decide
  spans and its retro's `chat {model}` span. The decide spans' `chat {model}` children carry no conversation id, so
  nothing counts twice.
- **Proposer:** cross-game; its `chat {model}` spans carry no conversation id and count only toward the agent's
  total.

The span name contains a space; Jaeger query strings URL-encode it (an exception to this spec's dot-notation rule,
§8).

**Old span name.** `agent.decide` is the decide span's old name; older agent images still emit it and the stores hold its
history. These accept both names: the collector's `filter/agent_decide`, the Grafana span-metrics panels
(`span_name=~` both names; one agent emits only one name, so nothing counts twice), the talk pre-flight (falls back to
`agent.decide` with a WARN) and `scripts/agent_group_ab.py`. The dashboard SPA reads only the new name. The old-name
alternatives are removed in #2729 (planned).

Content capture: `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.output.messages` only when
`decision.capture_content` is on (default off; on in `ci/`), decide backends only, 16 KiB per part
(`services/agent/decide/llmio/genai.go`). Not gated: the retro span always carries the capped prompt in
`llm.retro.user`, and the system prompt is logged once per SHA (`agent.llm.system_prompt`) (#2838); the once-per-SHA seen-sets (this and `agent.llm.retro_response`) are LRU-capped at 1024 fingerprints each, so an evicted SHA is logged again if it recurs.

Metrics `gen_ai.client.operation.duration` (s) and `gen_ai.client.token.usage` come from the decide backends
(claude, jev; semconv advisory buckets) and from the offline proposer / retro backend
(`services/agent/inference/metrics.go`: every call the Anthropic API answered records duration and tokens,
refusals, truncations and empty replies included; a call without an API key records nothing). The series are told
apart by `otel_scope_name`: `github.com/joustmania/agent/inference` for the offline calls,
`github.com/joustmania/agent/decide/backends/<backend>` for decide. VictoriaMetrics stores them as
`gen_ai_client_operation_duration_seconds_{bucket,sum,count}` and `gen_ai_client_token_usage_{bucket,sum,count}`
(prometheus_remote_write adds `_seconds` for the unit `s`, nothing for `{token}`), with labels
`gen_ai_operation_name`, `gen_ai_provider_name`, `gen_ai_request_model`, `gen_ai_response_model`,
`server_address`, `server_port`, `gen_ai_token_type` (token usage), `error_type` (failed calls only) and the
pipeline's `otel_scope_name`. The Agent Decisions & Interventions dashboard shows latency, calls and tokens by
`caller` (the last segment of `otel_scope_name`) and `gen_ai_request_model` (§6.1).

**Elapsed game time.** The agent's in-game elapsed time (`elapsed_s` in the decide state, `duration` in the rules
and the `agent.evaluate` log line) is `game_duration_seconds` while that gauge is fresh, i.e. its value advanced
within the last 5 s. When the gauge is missing or stale during an active game, the agent derives the elapsed time
from when it saw `game_active` go 0 → 1, never going below the last gauge value. Within a game the value never
decreases. At game end the duration every game-end consumer (experiment conclusion, retro, summary, proposer) sees is
the larger of the gauge and the agent's own start → end time, because the coordinator's final set can arrive after
`game_active` 0 (UC-041 A3, BR-003; `services/agent/gamecontext/store.go` `effectiveDurationLocked`).

**Game end.** The agent ends a game on the first of three signals (UC-041 A4, BR-005): the `game_active`
1 → 0 datapoint; the game root span arriving (OTLP exports a span once it ended, and the root span ends with the
game's session; the duration bracket then closes at the span's end time and a later `game_active` 1 for that game id
is ignored); or the game's `game_active` series staying silent for 60 s (`gameActiveStaleAfter`; the coordinator
exports every 100 ms, so this leaves margin for a collector restart; the bracket closes at the last datapoint).
`OnGameEnd` fires once per game whichever comes first, so a dropped 0 no longer keeps the game's partition from being
evicted. In a game-id partition every end latches: game ids are never reused, so a later `game_active` 1 for an ended
game id is ignored, also after the partition was evicted (the multiplexer remembers the last 512 ended ids). The
timeline's "end" phase event is stamped at the game's own end, so the start → end bracket game-end consumers derive
from it (`experiment_loop.go` `withEffectiveDuration`) matches the store's. The snapshot carries the end reason
(`GameContext.EndReason`: `zero`, `root_span`, `stale`, `end_event`: the `game.end` log event, a normal end). A `stale` end means the agent's telemetry for the game broke:
it increments `agent_game_end_stale_total{game_kind}` (`real` / `shadow`), the experiment loop releases an experiment game without a
fitness sample (and records no recent-real sample for a real game), and the retro, game summary and proposer skip it
(`services/agent/gamecontext/store.go` `endGameLocked`, `EndGameFromRootSpan`, `EvictStale`; `gamecontext/multiplexer.go`;
`services/agent/gameend.go`).

**Jaeger query API.** Every Jaeger reader in this repository, the dashboard SPA (`services/dashboard/src/jaeger.ts`), the talk pre-flight and the integration tests (`tests/integration/jaeger_v3.py`), uses the query API v3 through `/jaeger/api/v3` (gRPC-gateway JSON; Jaeger 2.21 removes the legacy `/api/services` and `/api/traces` search). A search is `GET /jaeger/api/v3/traces` with `query.serviceName`, `query.operationName`, `query.attributes` (a JSON object of string tags, AND), `query.searchDepth` (traces) and the required `query.startTimeMin` / `query.startTimeMax` (RFC 3339, UTC). The dashboard still never sends a browser-clock time: `query.startTimeMin` is the Unix epoch on a cold start, then the span-derived start of the incremental window (agent clock), and `query.startTimeMax` is the fixed bound `2100-01-01T00:00:00Z`; the talk pre-flight and the tests run on the Jaeger host and send their own clock. The answer is OTLP JSON (`result.resourceSpans[].scopeSpans[].spans[]`, all matching traces in one list, ids in hex, times in ns as strings); the readers group it by `traceId` into the span fields they used before (operation = `name`, parent = `parentSpanId`, tags = `attributes`, span events = `events`, service = the resource's `service.name`). `404` with `No traces found` is an empty answer, not an outage. Grafana's Jaeger datasource (`services/grafana/provisioning/datasources/jaeger.yml`, URL `http://jaeger:16686/jaeger`, base path included) reads services, operations and single traces through v3 (`[feature_toggles] jaegerEnableGrpcEndpoint`), but Grafana 13.0.2 still sends its trace search to the legacy `/api/traces` (jaeger#7594), which Jaeger 2.22 (the pinned version) no longer serves. No panel searches traces; the decision panels (Agent Decisions & Interventions, Talk) therefore read VictoriaMetrics `agent_decisions_total` instead: a time-range table by `game_kind`, `action`, `blocked`, `block_reason` and a decisions / min time series by `action` and `game_kind`; single traces are opened in the Jaeger UI at `/jaeger/`.

**A metric needs a named consumer**. A Python metric stays only while something reads it: a Grafana
dashboard, the dashboard SPA, the agent, a script or tool, or a document whose procedure queries it (a runbook, a
test case, a challenge doc, a service-tier test). The consumer scans below find Grafana, the SPA, the agent and
`scripts/` / `tools/` source; there are no alert rules. Any other reader is recorded in [notes/telemetry-metric-catalog.yaml](notes/telemetry-metric-catalog.yaml) as `reader: <path>` (a path outside
`docs/specs/`, which names every metric), and `test_every_python_metric_has_a_named_consumer` fails when a metric
has neither, or when the named file no longer contains the metric name. A new metric names its consumer in the same PR; a metric "for later" is not
added, and a future reader (a challenge, an agent signal) adds or restores the metric itself. `tests/contract/test_telemetry_contract.py` checks the agent's and the dashboards' names against the producers. The §6.2 catalog and its counts are **generated** from the same scans (the counts are printed by `make specs-counts` and the Telemetry Contract job summary, not committed): one row per Python metric name, each Consumers cell equal to what the consumer scans find (Grafana and SPA PromQL, the agent's ingest constants, the name as a word in non-test `tools/` and `scripts/` source), and the **no** rows in Emitted equal to the metrics nothing records. A metrics PR runs `make specs`; `make specs-check` fails CI when the generated file is stale. The scans prove a name is referenced, not that the query using it is right.

## 8. Naming rules

Rules (from `.claude/rules/development.md`): metric names prefixed with the service (`game_`, `controller_`,
`menu_`, `audio_`, `agent_`), counters end in `_total`, histograms in `_seconds` / `_bytes` (or a base unit),
span names in dot notation for new spans, attributes namespaced as in §2.1.
Every Go `Span*` / `Attr*` constant value must appear in this spec as its exact string (a `ns.*` mention or a
`.suffix` shorthand does not document a key, so write the full key); `make spec-refs-check` fails on a new
undocumented one, and `docs/specs/notes/spec-refs-baseline.json` lists the ones still open (it only shrinks:
a new entry fails).

Known violations on `main` (do not copy them; fix opportunistically, #2837):
`games_*` and `bluetooth_*` without a service prefix; histograms
`game_accel_distribution`, `agent_intervention_effect_delta`; `game_loop_jitter_ms` in milliseconds; most
coordinator / menu spans in snake_case; rust `grpc.server` vs Python `{Service}/{Method}`. Not a violation but an
exception: semconv-defined span names keep their convention's format (`chat {model}`, `invoke_agent joustmania-agent`, §4.2).

**Traceability:** NFR-030, NFR-031 / UC-035 / `.claude/rules/development.md`.

**Signal hash:** FNV-1a/64 over the controller's delivered frames in order, each frame encoded as the signed
32-bit little-endian integer ⌊intensity · 1000 + 0.5⌋ (milli-g, rounded half up); for an archetype with a
`trigger_policy` (UC-046 BR-018) each frame adds one byte after the value, 1 when the trigger is pressed on that
frame and 0 otherwise, so the hash of an archetype without a policy is unchanged; rendered as 16 lowercase hex digits.
intensity is computed in IEEE-754 double precision; the milli-g rounding keeps the hash stable across Python builds,
and golden tests pin it. **Checkpoints:** the hash value after every r delivered frames (one per second of game time).
The total number of delivered frames depends on wall-clock lag (a dead player leaves the stream filter a few frames
after its death; the winner's stream runs until the game is torn down), so replays compare the checkpoints on their
common prefix, not the final hash.

**Journal:** the experiment journal records the same facts: a `pattern_pinned` event (selection, pinned names,
parameter objects, parameter digests, safety cap and a note when the cap fell back to 300), `archetype`,

again or an archetype is skipped (UC-046 BR-015); a rerun after a real game preempted the pair
(`preempted_by_real_game`) is noted as `pattern_pair_rerun_preempted` instead, and one after a stale end (UC-041 A4) as
`pattern_pair_rerun_stale`; all three share the pair's one budget of 10 reruns.
The experiment's conclusion (`outcome` event) reports the timeout count and rate per arm and whether one arm timed out
clearly more often (UC-046 BR-013), followed by the `agent_ended` count and rate per arm when any game ended that way;
both rates are over the arm's pattern games that ended with a sample (`winner`, `tie`, `timeout`, `agent_ended`).

**Liveness check (BR-008):** the runner asks the agent's telemetry multiplexer at the game's start, once per
second while it runs and at its end whether another partition reports `game_active` with an update in the last
10 s; stale partitions are ignored.

**Replay check:** read `pattern.archetype`, `pattern.params_digest`, `game.rng_seed`, `pattern.stream_rate_hz`, the
game mode and sensitivity off the trace, run one shadow game with them (`SHADOW_GAME_ARCHETYPE`, `SHADOW_GAME_SEED`),
and compare: per-slot checkpoints equal on their common prefix (NFR-040), `pattern.elimination_order` and
`pattern.winner_slot` equal (NFR-041), and the sequence of rules decisions as (`intervention` type,
`pattern.target_slot`) equal (NFR-042). Only games with `pattern.replay_exact=true` and the same
`pattern.params_digest` and `pattern.flag_digest` on both sides are compared. `scripts/pattern-replay-check.sh
<archetype> [seed]` runs the archetype twice with the one-shot runner and performs this comparison on the two runs
(it reads the `PATTERN_REPLAY_RECORD` line the one-shot runner prints), and `scripts/pattern-replay-check.sh --against
<record>` replays one recorded game: the record is a saved `PATTERN_REPLAY_RECORD` JSON or a `pattern_game_ended`
journal event (a line of the experiment's `events.jsonl`). The checkpoint hashes prove identical input; the
elimination order, winner and decisions are the evidence that the game played out the same (UC-046 BR-001).

## Appendix A. Booth profile

Booth-only telemetry for the challenges in [docs/challenges/](../challenges/) (UC-100, UC-101). It changes what the backends behind the gateway see, never what the agent reads: the agent's death channel is `game_player_elimination_order` in every shape (§4.4, UC-041 BR-008, BR-009), and no record of this appendix passes the collector's `filter/agent_events`. Off the booth every value here is at its default (`span_event`), which is the telemetry of §3.2.

### A.1 Moment shapes

**Moment shapes (UC-100, FR-216, FR-217, NFR-060; implemented for the warning and the death in `lib/moments.py` `record_moment`, called from `games/base.py` `_warn_player` and `_run_kill`).** The warning (`death_warning`) and the death (`player_death`) are *moments*: one record per happening, with one identity, sent in a shape chosen by the flag `telemetry.moment_shape` ([flags.md §10](flags.md#10-observability)). The coordinator reads the flag once (`lib/moments.py` `read_moment_shape`, called in `game_session.py` `_run_game_loop_async`), inside the game root span when it starts, and holds it for the game (`BaseGameMode.moment_shape`), for every game kind (UC-100 BR-002); the root carries the shape in effect for every moment of the game as `telemetry.moment_shape`. Default, and fallback for an absent, unknown or unreadable flag (also when the `observability` provider is not READY yet, not READY within the 5 s admission deadline, UC-010 A5): `span_event`. The agent reads no moment in any shape (UC-041 BR-009): its elimination order comes from `game_player_elimination_order` alone, which the coordinator sets in every shape (§4.4, UC-100 BR-007). The value `both` is not a shape: like any unknown value it runs as `span_event` (UC-100 A6 Obsolete). The shape is a stack overlay that persists until it is cleared (flags.md §10): a booth leaves it at the default afterwards. A moment never raises into the game: when the log channel fails, `record_moment` reports it once per process on stderr and goes on (the span event is sent as before).

| Shape | What is sent | Parent / correlation | Exported |
|---|---|---|---|
| `span_event` (default) | span event `death_warning` / `player_death` on the player span, as now | the player span | with the player span: at the death in FFA, Teams, Traitor, Swapper and for the Tournament loser (they end the player span there); at game end in NonStop, Fight Club and Zombies |
| `span` | span `game.death_warning`, started at the warning and ended at once with end time = start + `WARNING_DURATION` (no open span, no timer); `game.player_death` with start = end = the death | child of the player span | at once (traces batch 2 s) |
| `log_event` | log record with `event_name` = `death_warning` / `player_death` (the same name as the span event), severity INFO, the moment's attributes as log attributes; emitted on the SDK `Logger` of the coordinator's `LoggerProvider`, not through Python `logging`, so `log_level` never drops it. A process without OTLP logging (not initialised, tests) falls back to `span_event` and records that shape on the root | trace and span id of the player span | SDK batch (up to 1 s) plus the collector's logs batch (5 s): up to about 6 s; never to the agent (`filter/agent_events`) |

Attributes: the moment's own attributes are the same in every shape; every shape adds the identity attributes `moment.id`, `player.serial`, `player.name` (once known), `game.id` and `game.kind` (on `player_death` the player keys were already there; it gains `moment.id`, `game.id`, `game.kind`). `moment.id` is the same in every record of one moment and unique within the game: `<game.id>/<player.serial>/<n>`, where `n` counts the player's moments from 1 per serial within the game, kept by the game (`BaseGameMode._moment_identity`), not by the player record, so a recreated player never reuses one (e.g. `game_abc123/00:06:f7:c9:a1:01/2`). Readers that count moments count one per `moment.id`. The agent ignores every span that carries `moment.id` (§4.4, UC-100 BR-010).

Not moments, unchanged in every shape: the event-bus game event `player_death` of §5 (NonStop, FFA; stream subscribers only); the INFO log lines the coordinator writes for a warning and a death; the controller manager's `effect_player_death` span and `player_warning` event (§3.3). Only a record with the moment's name and a `moment.id` counts as the moment (UC-100 BR-009).

### A.2 Ground truth

Ground truth (FR-219, UC-100 step 6, BR-006): at a normal game end the coordinator records on the game root span one span event `challenge.ground_truth` per player of the game (and per serial with a recorded moment that left the game), with `player.serial`, `player.name` (once known), `challenge.warning_times_ns` (int array: the time of each warning, in order) and `challenge.death_times_ns` (int array: the time of each death, in order). An array is left out when the player has no such moment: a player never warned has no `challenge.warning_times_ns`, a player who never died (the winner, a survivor) no `challenge.death_times_ns`. In FFA, Teams and Traitor a player dies at most once; NonStop, Fight Club, Zombies and Swapper record every death of a player (respawn, round loss, conversion, swap), each one that reaches the base kill path. A warning sent by the agent's `warn_player` counts like a motion warning. Times are wall-clock epoch nanoseconds from `time.time_ns()`, the clock the OTel SDK stamps span events (and log records) with by default, read once per moment and used as the record's own timestamp (`record_moment` `timestamp_ns`: the span event's timestamp, the moment span's start and end, the log record's timestamp; `services/game_coordinator/games/motion.py:_warn_player`, `services/game_coordinator/games/elimination.py:_run_kill`), so a ground-truth time equals its record's timestamp in every shape; `game_clock` is not wall time and is not used. Kept per game and serial, not on the `Player` object, and independent of `analytics.enabled`. Recorded after the teardown step, every mode passing through the base `run()`; a force-ended game (`game.outcome` = `force_ended`) or one whose `run()` raised records none (UC-100 A5); the outcome, its latching and the span ending order are unchanged. Source: `services/game_coordinator/games/ground_truth.py`, `services/game_coordinator/games/outcome.py:_record_ground_truth`.

### A.3 Intervention moment

**Intervention moment (UC-101, FR-220, FR-221, NFR-061).** Each agent intervention the coordinator applies to one player is a third moment, named `intervention`, in the game's moment shape (`telemetry.moment_shape`, as the warning; the root's `telemetry.moment_shape` names the shape of every moment of the game: the warning, the death and the intervention): span event `intervention` on the player span, span `game.intervention` (child of the player span, start = end = the apply), or log event `intervention` with the player span's trace context. `intervention.type` is the decision's intervention name, as on `agent.intervention.effect` and in `game_interventions_total{type}`: `grant_shield`, `grant_group_shield`, `toughness_boost`, `adjust_player_sensitivity`, `set_player_handicap` (a changed factor, a return to 1.0 included), `revive_player`, `soft_penalty`, `eliminate_player` (UC-101 BR-001). Attributes in every shape: `intervention.type`, `intervention.id` (the id served with the value at the read that found the change, carried per target in the dispatch context to the handler; left out when the write carried none, UC-101 A3, BR-004), the identity attributes of the moments (`moment.id`, `player.serial`, `player.name` once known, `game.id`, `game.kind`). The handler records it where it records the lever's own effect (`shield_granted`, `shield_charge_granted`, `shield_energy_granted`, `toughness_boost_armed`, `sensitivity_factor_applied`, `handicap_factor_applied`, `player_revived`, `soft_penalty_tighten`, the `player_death` with `death.reason` `agent_intervention`; a soft-penalty warning has no lever event of its own); an effect that lands late (`game_loop_late`) is recorded when it lands, a handler refusal (`InterventionNotApplied`) or a `handler_error` before the effect lands records none (UC-101 BR-005); once the effect landed, the moment stays even if a later step of the same handler (its feedback) raises and the outcome is recorded as `handler_error` ("effect landed" rule). A soft-penalty warning records the intervention moment after the warning's own `death_warning` moment, with its own clock read; a tighten records one moment after `soft_penalty_tighten` only when it lengthened the window or strengthened the factor, and its warning cue adds a `death_warning` but no intervention moment; an elimination's moment follows its `player_death` and carries the death's timestamp. A trigger-mode charge records at `shield_charge_granted`, hold-mode energy at `shield_energy_granted` (a full pool is refused before, so energy was added); a kept grant (a longer protection runs) records none. Mechanism: the manager reads the id with the value (`decisionId.<variant>` of the resolved `details.variant`, or the event entry's `decision_id`; anything missing, empty, not a string or raising is no id), never compares it for change detection (a grant's identity stays `(variant, value)`), and runs the handler in an intervention scope (a `ContextVar`, no game method signature changes) naming the target serial, a level's changed serials or, for a group shield, any player; each named player records at most once per scope, and the scope closes when the handler returns. `record_intervention` never raises into the lever. Source: `services/game_coordinator/games/intervention_moment.py`, `services/game_coordinator/interventions.py`, `services/game_coordinator/games/rubberband.py:record_intervention`. Every game kind records it (UC-101 BR-001). Not the moment, and unchanged: the lever events above and the `agent_intervention` game event of §5, which the event bus also records as a span event on the current span; none carries an intervention id (UC-101 BR-008). Not recorded: a blocked, refused, failed or superseded intervention, or one that changed nothing (UC-101 BR-005); a deferred one (UC-053 A9) only once the re-evaluation applies it, with the id served at that read; game-wide levers, `controller_effect`, `audio_cue`, and the coordinator's auto-rubberband boosts. A group shield records one moment per shielded player with the one intervention id (UC-101 A4). At most one moment per player per applied intervention; interventions are bounded by the agent's rate limit and the coordinator backstop (decide-contract §11).

Ground truth of the interventions (FR-222, UC-101 BR-006, BR-007): at a normal game end, after the per-player ground truth of FR-219, the coordinator records on the game root span one span event `challenge.intervention_ground_truth` per applied intervention, in apply order, with `intervention.type`, `intervention.id` (left out without one), `player.serial`, `player.name` (once known), `moment.id` (the `moment.id` of its intervention moment; left out when no moment was sent: no player span, a failed record; the presenter asks only about entries with a `moment.id`, UC-101 BR-009), `challenge.applied_at_ns` (int, epoch ns: the intervention record's own timestamp, one clock read as for FR-219) and `challenge.first_death_at_ns` (int, epoch ns: that player's first death at or after the apply time; left out when the player did not die from then until the game ended; for `eliminate_player` the death it caused, equal to the apply time). The entry is recorded with the moment, also when the player has no span. None after a force-end or a failed run (UC-101 A7). Accepted gap: an effect that lands late (`game_loop_late`) after the game's teardown recorded the ground truth gets its moment but no entry. Source: `services/game_coordinator/games/ground_truth.py`, `services/game_coordinator/games/outcome.py:_record_ground_truth`. **Span event limit:** the Python SDK keeps at most 128 events per span by default and, past the limit, drops the OLDEST events (a bounded deque), so on the game root the FR-222 events (recorded last) would push out the FR-219 ones. The game root carries the §5 game events, the FR-219 events (one per player, up to 64) and the FR-222 events (interventions are bounded by the agent's rate limit and the coordinator backstop: a 10-minute NonStop or shadow game can reach a few hundred); the player span carries the warnings and, in the span-event shape, the intervention moments. The game coordinator's compose service sets `OTEL_SPAN_EVENT_COUNT_LIMIT=1024` (`docker-compose.yml`, and `docker-compose.ci.yml`, whose environment replaces the base one; read by the SDK when `lib/telemetry.py` builds the `TracerProvider`); every other service keeps 128. The bound is per span, events are held only until the span ends and is exported, so the extra memory is that of one long-lived game root and its player spans (on the Pi a few hundred small events, well within the coordinator's 256 MB, NFR-003). Tests: `services/game_coordinator/tests/test_intervention_moment_uc101.py` (the provider honours the limit; the compose contract).
