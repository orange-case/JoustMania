# Use Case: Decide an In-Game Intervention

## Overview

**Use Case ID:** UC-040
**Use Case Name:** Decide an In-Game Intervention
**Primary Actor:** Agent
**Secondary Actors:** Model API, Player
**Goal:** Nudge a running game toward the active objectives with a bounded, reversible intervention
**Trigger:** A telemetry batch updates a game's context (UC-041) while the game is active and at least one player is fresh; the [glossary](../glossary.md) owns the definitions of **Fresh player** and **Evaluation gate** (a context that fails the gate is not evaluated and nothing is recorded)
**Status:** Tested
**Requirements:** FR-043, FR-044, FR-046, FR-047, FR-048, FR-049, FR-050, FR-051, FR-052, FR-053, FR-069, NFR-010, NFR-011, NFR-012, NFR-013, NFR-015, NFR-050, C-002, C-004, C-018, FR-253
**Planned:** FR-096 (Implemented: BR-044; stays here until a rehearsal on the stage hardware lets it be Verified), FR-098 (Implemented: BR-045; stays here until a rehearsal on the stage hardware lets it be Verified), FR-200 and FR-201 (Implemented: A44, A45, BR-034; stays here, not under Requirements, until a coverage check with the test bodies read and an integration test of the path from a decision through its prediction to the outcome span let it be Verified, because a Tested use case would derive Verified)
**See also:** Shield application and feedback are [UC-048](UC-048.md); how the rules engine picks its candidates is [decide-contract.md](../specs/decide-contract.md) §15. The ids of the flows and rules that moved there (A16, A17, A30 to A34, A36 to A39, A41 to A43, A46 to A48, A51, A52) are not reused.

## Preconditions

- The agent observes the game and holds one context per game id (UC-041).
- The game coordinator registered the game with the flag service, so the game has a scope there ([UC-053](UC-053.md)).

## Main Success Scenario

1. System reads the live flag snapshot (objectives, policy, `decision.*`) and finds `enabled` at `watch` or `act`, not `off` (A28); this scenario follows a remote backend (rules: A1). The agent evaluates flags without a resolver cache, so a flip is seen on the next read ([flags.md §1.3](../specs/flags.md#13-reload-semantics)); this applies to every flag read in this use case (steps 1 and 7, A6, A7, A28).
2. System sees `decision.backend` = jev (the main in-game backend), or claude (the manual backup), and the backend is available (jev: `JEV_API_KEY`; claude: key + model).
3. System checks that no remote call is in flight for this game, that the game kind is eligible (`llm.eligible_game_kinds`, default `real_only`: real games only), that the allow-list offers at least one intervention besides `noop` (BR-005), that `decision.min_interval_ms` (default 3 s) has passed since the previous call of this game started and `decision.min_gap_after_answer_ms` (default 1 s) since it ended (an answer, a timeout or a failure ends a call), and that the global budget (`llm.max_requests_per_minute`, default 6) has room and, for claude, the backend's own cap (`decision.<backend>.max_requests_per_minute`, default 30, tighten-only) too.
4. System builds the state (narrative, players with the danger signals, `shielded` and `shield_charged`, and in a hold game the energy fields instead of `shield_charged`, `shield_limited` for a player the agent would refuse another shield on the cap, the cooldown or the hold pool or budget, and the per-player factors the agent already applied ([decide-contract.md](../specs/decide-contract.md) §1.2), the game-wide levers in their cooldown (A53), digest) and the FFA questions: which intervention (noop or an allowed type), which target, what magnitude within the game's ranges (`decision.magnitude_bounds`, BR-045) (questions, answers and validation: [decide-contract.md](../specs/decide-contract.md)). The group lever `grant_group_shield` is offered only while its gate is open for this game (`policy.group_grant.enabled` on, a shadow game or `real_games` on, 2 to `max_targets` alive players, fewer than `max_per_game` group shields applied in this game, `game_shield_group_grants`); then the target question also offers the group options `group:all` and, with three or more alive, `group:all_except:<serial>` (UC-048 A13, BR-014). No rule proposes it.
5. System calls the backend asynchronously with `decision.<backend>.timeout_ms` (claude 5000 ms, jev 2500 ms by default); the game keeps running. The request describes the levers by their effects (BR-036), carries the goal lines when the game's goal profile has terms ([decide-contract.md](../specs/decide-contract.md) §14.4) and the operator brief when `decision.operator_brief` is set (BR-044).
6. The backend answers; System parses and validates the answers strictly, each answer on its own and the answers together (no target on `noop`, a player on a player lever, none on a session lever, a group only on the group lever).
7. System re-reads the live flags (step 1 caveat): `enabled` is still not `off` and `decision.backend` is unchanged.
8. System checks that the intervention is not `noop`.
9. The `ffa.intervention` confidence is at least the answering backend's act threshold `decision.<backend>.act_confidence_threshold`, read now: jev 0.6, claude 0.8 by default. Outcome `act`; the span records the threshold.
10. System re-reads the current context: it exists, the game is still active, the target (if any) is still present and, for a lever that needs fresh readings, has fresh readings (A50, BR-039), and the state the request was built on is not older than `decision.max_state_age_ms`.
11. System runs the permission chain: allow-list, battery threshold, the experiment-flag check (a lever of the flag under test in an experiment game: A40, BR-028), the already-applied check (a state or level intervention only, when suppression is on: A35, BR-023), the lever cooldown (a game-wide lever whose last write is younger than the effect window: A53, BR-046), the shield gate (a targeted `grant_shield` only: UC-048 A4, A6), per-game weighted rate limit.
12. System writes the intervention to the flag service for this game (`interventions` set, scoped to the game id, and to the player's serial for a per-player intervention; a one-shot intervention is appended to the game's event list) ([UC-053](UC-053.md)); the write is made only while `enabled` is `act`, never at `watch` (A11), and can fail (A27).
13. The game coordinator picks up the flag change, re-checks the allow-list, the mode's capabilities, battery and its global backstop, and applies the intervention through the game's own code (e.g. tempo change, a shield ([UC-048](UC-048.md)), elimination; a toughness boost lasts at most 30 s and its boost is clamped to 1.0 to 2.0), publishing `agent_intervention`; after an applied HARD-class intervention it pulses the targeted controller (or every active player for a game-wide intervention) unless `agent_intervention_cue` is off or the game is ending (the pulse is magenta (255,0,192), the colour of the helped cue; no cue once the outcome is latched, so it never cuts the winner rainbow short, UC-020 BR-004); a player-targeted intervention is also recorded as an event on that player's span carrying `player.serial` and `player.name`. A one-shot intervention applies once, and only in the game whose event list holds it (BR-006). `end_game` ends only the game it was decided for (BR-011), and a per-player grant (`grant_shield`, `toughness_boost`, `soft_penalty`) applies once per decision to each player it targets (BR-012). The intervention's side effect runs on the game's own event loop (BR-018, A26). How a `grant_shield` or `grant_group_shield` is applied, limited and shown is [UC-048](UC-048.md).
14. System records `invoke_agent joustmania-agent`, `chat {model}`, `agent.decision` and `agent.action` spans (a player-targeted decision names the player with `player.serial` and, when known and the game is not a shadow game, `player.name`) and later measures the effect of each dispatched decision (`agent.intervention.effect`, correlated by that decision's own `decision.intervention_id`; a cycle has no id), all inside the game's trace (BR-013). This holds on every path: a decision that lands on the remote path, including its rules fallback, takes its fitness baseline from the current context at landing. Only a written decision is measured: a gated no-op (A11) or a failed write (A27) gets no effect span and no id. The rationale on the spans keeps its first 256 runes and appends `...` when longer. Interventions a player can perceive give feedback in the game: an audio cue plays a real sound (BR-007), and a shield plays a sound and shows on the player's LED and on the dashboard ([UC-048](UC-048.md)).

## Alternative Flows

### A1: Rules backend (default)

**Trigger:** `decision.backend` is `rules` (step 2)
**Flow:**

1. System ranks rule candidates by objective weight × urgency × fitness pressure and emits up to two decisions per evaluation (at most one evaluation per second).
2. System records the rules answers as the first emitted decision (intervention and target, even one the allow-list will block), with `outcome=act` and no confidence.
3. If the ranking emitted nothing, System records no span and counts the cycle in `agent_evaluations_total{outcome=idle}`; use case ends.
4. Otherwise use case continues at step 11 (no confidence routing).

### A2: Remote timeout, error or invalid answer → rules fallback

**Trigger:** The call times out, fails (HTTP error including 429) or the answer fails validation, inconsistent answers included (step 5 or 6)
**Flow:**

1. After the kill-switch and backend checks (step 7), System records `outcome=fallback` with `fallback_reason` = timeout, error or invalid_answer.
2. System lets the rules engine decide on the **current** context. If the context is gone or the game has ended, nothing is decided and the span carries `outcome=discarded`, `discarded_reason=stale` (detail `context_missing` or `game_ended`) with the `fallback_reason` kept, and use case ends; it also ends when the rules emit nothing.
3. Otherwise use case continues at step 11.

### A3: Backend unavailable, ineligible or over budget → rules now

**Trigger:** Unknown backend (any `decision.backend` value other than rules, claude and jev, including the retired `openai`), missing key / model, no re-validation source, ineligible game kind or exhausted budget, global or (claude) the backend's own `decision.<backend>.max_requests_per_minute` cap (step 2 or 3)
**Flow:**

1. After the in-flight check (A4), System checks in this order: the backend (`unknown_backend`, `backend_unavailable`; `async_not_wired` when the loop has no context provider to re-validate a late answer, which the shipped agent always wires, so only a hand-built loop in a test produces it), the game kind (`llm_not_eligible`), then the allow-list (A14), the cadence (A4) and the budget (`llm_budget_exhausted`). So an unknown, unavailable or ineligible backend falls back to rules even when the allow-list is empty; the allow-list then blocks their decisions (A10).
2. System records `outcome=fallback` with the reason (`unknown_backend`, `backend_unavailable`, `async_not_wired`, `llm_not_eligible`, `llm_budget_exhausted`) on the cycle's `invoke_agent joustmania-agent` span and counts it in `agent_llm_gated_total{reason}`. When the rules emit nothing in that cycle, only the configuration fallbacks (`unknown_backend`, `backend_unavailable`, `async_not_wired`) still emit the span, at most one per reason per `decision.throttle_seconds`; `llm_not_eligible` and `llm_budget_exhausted` are then counted only. A game entering or changing a configuration fallback logs a WARN `agent.decide.backend_misconfigured`, and an INFO when it clears.
3. Rules decide in the same cycle (A1); when they emit nothing, use case ends.
4. Otherwise use case continues at step 11.

### A4: Cadence or in-flight gate

**Trigger:** A call is in flight for this game, the minimum interval has not passed since the previous call started, or the gap has not passed since it ended (step 3)
**Flow:**

1. System makes no decision this cycle (rules stay quiet; not a fallback) and records no span. A call in flight is not counted; an unmet interval or gap counts `agent_llm_gated_total{reason=decide_interval}` and logs `agent.decide.cadence_wait` at debug level. The gap clock starts when the previous call returns, whatever its outcome: an answer, a timeout or a failure, before the answer is checked or acted on. Two calls of one game are never in flight together.
2. Use case ends.

### A5: Low confidence → held

**Trigger:** Confidence below the threshold (step 9)
**Flow:**

1. System records `outcome=held` and does nothing. The context is not checked first, so a low-confidence answer that lands after the game ended is `held`, not `discarded`.
2. Use case ends.

### A6: Kill switch mid-flight → discarded

**Trigger:** `enabled` was turned off while the call was in flight (step 7, the first check on landing)
**Flow:**

1. System records `outcome=discarded`, `discarded_reason=kill_switch`; neither the answer nor a rules fallback acts. When the call had failed or timed out, the span also carries its `decide.fallback_reason`.
2. Use case ends.

### A7: Situation changed → discarded

**Trigger:** The backend changed (step 7), or, for an answer that would act, the context is missing, the game ended, the target is gone, a lever that needs fresh readings targets a player whose readings are stale (A50, BR-039) or the state the request was built on is older than `decision.max_state_age_ms` (default 10 s) (step 10)
**Flow:**

1. System records `outcome=discarded` with `backend_changed` (step 7) or `stale` (step 10, with `decide.discarded_detail` = `context_missing`, `game_ended`, `target_gone`, `target_stale` or `state_too_old`), and counts it in `agent_decide_discarded_total{reason}` (every remote `invoke_agent joustmania-agent` span that carries a `discarded_reason` is counted).
2. Use case ends.

### A8: Inconsistent answers → invalid (retired)

**Trigger:** None: inconsistent answers (e.g. `noop` with a target, or a player intervention without a target) fail validation at step 6 and fall back to the rules like any invalid answer (A2); the outcome `invalid` and `decide.invalid_reason` are gone. The ID is kept so it is not reused (step 6)
**Flow:**

1. System falls back to the rules as in A2: `outcome=fallback` with `fallback_reason=invalid_answer`.
2. Use case ends.

### A9: Noop

**Trigger:** The backend chose `noop` (step 8)
**Flow:**

1. System records `outcome=noop`.
2. Use case ends.

### A10: Blocked

**Trigger:** Not allowed, battery below `policy.battery_threshold`, refused by the shield gate (`already_charged`, UC-048 A4; `shield_cap_reached` or `shield_cooldown`, UC-048 A6), the same value already applied (`already_applied`, A35), a game-wide lever changed again inside its effect window (`lever_cooldown`, A53) or rate limit reached (step 11)
**Flow:**

1. System records the decision as blocked with the reason on `agent.decision` and as `decide.blocked` / `decide.block_reason` on `invoke_agent joustmania-agent`; the outcome stays `act`; nothing is written. A scarce budget is spent in rank order (A20, BR-014); a repeat the budget already refused emits no new `agent.decision` span (A21).
2. Use case ends.

### A11: Agent watching

**Trigger:** `enabled` is `watch` at the write (step 12; FR-051)
**Flow:**

1. Nothing is written and no write is counted; the decision has already charged the per-game budget and its `agent.action` span is recorded. `agent_interventions_applied_total` does not increment: it counts only interventions that were written. The decision gets no effect sample and no `decision.intervention_id`.
2. System records the drop on the `agent.decision` and `agent.action` spans as `decision.applied=false` with `decision.not_applied_reason=watch` (a written decision carries `decision.applied=true`; a failed write A27 carries `decision.applied=false` with `write_failed`), so the dashboard shows `not applied: agent in watch` and never `allowed` for a write that did not happen. Behaviour is unchanged: only the record differs.
3. Use case ends.

### A12: Noul questions (retired)

**Trigger:** None: the decide contract has no `noul` question kind. The noul is a detail of Jev's wire format, asked only by Jev's gate (A13, [decide-contract.md §3.1](../specs/decide-contract.md)). The ID is kept so it is not reused (step 4)
**Flow:**

1. No request carries a noul; Jev's gate asks its own (A13 step 1).
2. Use case continues at step 6.

### A13: Two-stage Jev round (gated)

**Trigger:** `decision.backend` is jev (step 5)
**Flow:**

1. System's first Jev call asks the gate noul "Does the game need an intervention right now?" and `ffa.intervention` without `noop` in the same call.
2. System synthesises the `ffa.intervention` answer as `{noop: 1 − p_yes, Jev's pick: p_yes, others: 0}` when the gate opens (step 3) and as `noop` with certainty when it stays closed, so its confidence is p_yes when acting and 1 − p_yes for noop, and records Jev's real p_yes and distribution on the stage-1 span.
3. If p_yes is below the act threshold (`decision.jev.act_confidence_threshold`, read when the call fires; the gate opens no lower than 0.5) the answer is `noop` and no second call is made; use case continues at step 6 (then A9).
4. Otherwise, if the chosen intervention needs a target or a magnitude, System makes a second Jev call conditioned on it (target among alive players described by suitability; magnitude levels of that intervention only, no neutral level, the most likely level wins with ties going to the gentler level; for two-way levers Go picks the direction from the danger signals and Jev picks the strength).
5. Both calls share the `decision.jev.timeout_ms` deadline; a stage-2 failure fails the whole round (A2).
6. Use case continues at step 6; at step 9 p_yes is compared with the same flag read again at landing (default `gate` 0.6, calibrated for p_yes: collapsing and near-threshold act, calm and dragging are noop), so the answer is `held` (A5) only when the flag was raised while the call was in flight.

### A14: No interventions allowed → no remote call

**Trigger:** The effective allow-list is empty: `interventions_allowed` resolves to `none` (or to a list that holds only `noop` or empty ids, e.g. `probe`; or, in an experiment game, only levers of the flag under test, A40 step 5), so `noop` would be the only `ffa.intervention` option, while a remote backend is selected, available and the game kind eligible (step 3). On the rules backend, and when A3's backend or eligibility fallback applies first, this flow does not apply: the rules run and the allow-list blocks what they emit (A10).
**Flow:**

1. System makes no remote call: no Jev or Claude request is built or sent, and neither the cadence (`decision.min_interval_ms`) nor the global budget (`llm.max_requests_per_minute`) is charged.
2. System does not run the rules engine either (nothing it could emit would pass the allow-list) and records no fallback and no `invoke_agent joustmania-agent` span.
3. System increments `agent_llm_gated_total{reason=no_interventions_allowed}` and writes a debug log `agent.decide.no_interventions_allowed` only when the game enters or leaves this state.
4. As soon as the allow-list offers an intervention again, the next cycle continues at step 3.

### A15: One-shot interventions of an earlier game

**Trigger:** A game starts after one-shot interventions (`audio_cue`, `controller_effect`, `eliminate_player`, `revive_player`, `end_game`) were applied in an earlier game, and a later flag change makes the coordinator re-evaluate during the new game (step 13)
**Flow:**

1. The earlier game's event list was dropped with its scope when that game ended ([UC-053](UC-053.md) BR-003); the new game is registered with an empty event list.
2. On the re-evaluation the new game's list holds no event, so nothing is applied and no `agent_intervention` is published.
3. An event appended for the new game has the next sequence number and is applied once. Use case continues at step 13.

### A18: `end_game` evaluated in another game

**Trigger:** The agent writes `end_game` for one game while other games are live, real or shadow (step 13)
**Flow:**

1. The agent appends `end_game` to the event list of the game whose decision loop decided it. Without a coordinator game id it writes nothing (BR-002).
2. The flag service renders the event list on that game's id only; every other live game resolves its own list, so it sees no new event: no force-end, no `agent_intervention` event, no backstop budget used.
3. The addressed game is force-ended through the same path as `ForceEndGame` for that `game_id`, real or shadow. An `end_game` for a game whose end is already under way waits for that end and publishes no second `game_force_ended` (the intervention itself is still recorded as `agent_intervention`) ([UC-027](UC-027.md) A4). Use case continues at step 14.

### A19: Per-player grant from an earlier decision or game

**Trigger:** A per-player grant flag (`shield_seconds`, `toughness_boost_seconds`, `soft_penalty_action`) holds the grant of an earlier decision for player A, and the agent grants player B, or a new game starts (step 13)
**Flow:**

1. The agent writes each grant for (game, player); the flag service gives every write a fresh generated variant, so one decision is one change for one player, even when the value repeats.
2. On every re-evaluation the coordinator applies a grant only to a player whose resolved variant or value changed since the last read in this game and is not neutral. Player A's unchanged grant is not applied again when B is granted.
3. A new game starts with no grant: the earlier game's grants were dropped with its scope ([UC-053](UC-053.md) BR-003).
4. Use case continues at step 13 for player B only.

### A20: Scarce intervention budget

**Trigger:** The per-game budget (`policy.max_interventions_per_minute`) cannot admit every decision of the cycle (step 11)
**Flow:**

1. System offers the cycle's decisions to the rate limit in rank order (BR-014).
2. The first decision that passes the allow-list and battery checks but does not fit the remaining budget ends admission for the cycle: it and every lower-ranked decision of the cycle are blocked with `rate_limit` and charge nothing, so a cheaper, lower-ranked decision never spends the budget ahead of it. A decision that costs more than the whole budget can never fit and does not end admission.
3. A `send_controller_effect` decision is admitted only if the protective reserve is still free after charging it (BR-015). When it is not, it is blocked with `rate_limit` and the lower-ranked decisions are still offered.
4. Blocked decisions are recorded as in A10. Use case continues at step 12.

### A21: Decision already refused for the same reason

**Trigger:** A decision with the same intervention and target (or group set) was already blocked with the same reason, any block reason of A10, and the budget has not changed since: nothing was admitted and nothing left the 60 s window (step 11)
**Flow:**

1. System blocks it with that reason again and records it in the cycle's layer state and in `agent_decisions_total{blocked="true",block_reason=<reason>}`, and logs `agent.decision_<reason>_repeat` at debug level.
2. System emits no `agent.decision` / `agent.action` span, no `agent.decision_blocked` warning (or info log, for `already_applied` and `lever_cooldown`) and no narrative-timeline entry for the repeat. The cycle's `invoke_agent joustmania-agent` span still reports `decide.blocked=true` / `decide.block_reason=<reason>`. The dashboard Agent tab therefore takes its blocked tallies (total, by intervention, by reason) from `agent_decisions_total{blocked="true"}` over its 10-minute window, not from the warning lines; when VictoriaMetrics is unreachable it shows them as `n/a`, and with no samples as zero. The timeline keeps the first refusal per budget state.
3. Once the budget changes, the next refusal of that decision is recorded in full again (A10).
4. Use case ends.

### A22: Coordinator blocks the intervention

**Trigger:** The coordinator's re-check fails for an intervention the agent dispatched (step 13)
**Flow:**

1. The coordinator does not apply it and publishes `agent_intervention` with `blocked=true` and the reason: `not_allowed` (not in its allow-list), `mode_unsupported` (the mode's capability matrix denies it, e.g. `revive_player` in FFA), `low_battery`, `rate_limited` (global backstop) or `handler_error` (the handler failed). `already_charged` (a `grant_shield` to a player who holds a shield charge, UC-048 A4). `shield_pool_full` and `shield_budget_exhausted` (a `grant_shield` in a hold game that could add nothing, UC-048 A9; nothing applied, the backstop reservation is refunded, not counted against UC-048 BR-007). `shield_cap_reached` and `shield_cooldown` (a `grant_shield` refused by the shield limits per player per game, UC-048 A7, BR-007; nothing applied, the backstop reservation is refunded). `revive_refused` (the mode refused a `revive_player`: the game is decided or not running, or the player is unknown or already alive; the handler applies nothing, the backstop reservation is refunded; UC-023 BR-004, UC-026 BR-003). `eliminate_refused` (an `eliminate_player` that killed nobody: the player is unknown or already dead, a kill of the same player is in flight, the game is force-ended (every mode, UC-030 step 9; the force-end is applied on the game's loop, so an `eliminate_player` there is either counted before it or refused), or the mode declined the kill (UC-030 step 9, e.g. every mode with the default kill gate once the game's outcome is latched, Swapper once its win is latched, UC-024 BR-004, Tournament for a waiting player, a fighter in grace, between matches or after the champion is latched, or Fight Club for a waiting player, a combatant in its invincibility, between rounds or after the winner is latched, UC-025 BR-006); the handler applies nothing, the backstop reservation is refunded). `experiment_override` (a `pacing_profile` in an experimental-arm shadow game whose experiment sets `windows` to a value other than the requested preset: the experiment's windows stay, the handler applies nothing and the backstop reservation is refunded; a preset whose value equals the experiment's is applied; a failed flag read on either side is a flag error, never an override, and the handler applies what it read, as before; [UC-043](UC-043.md) BR-005). The agent's spans still read `act`, not blocked. While the allow-list the coordinator holds is older than the intervention (after a flagd reconnect, [UC-053](UC-053.md) A9 step 4), the intervention is deferred rather than checked, and checked once the allow-list catches up, so a stale allow-list never blocks or applies it.
2. Use case ends.

### A23: Probe mode

**Trigger:** The flag `decision.probe_decisions` is on (agent set, default off; read every decision cycle, so a flip changes the next cycle; off while flagd cannot resolve it, no env fallback), which replaces the rules engine with the probe engine for that cycle (never in a pattern game, UC-046), and the rules engine decides: on the rules backend (A1) or in a rules fallback (A2, A3). While a remote backend is selected, available and eligible, an allow-list of only `noop` (`probe`) leads to A14 instead: no remote call, no rules, so no probe decision (step 1)
**Flow:**

1. The probe engine emits one synthetic `noop` decision at most every 5 s and nothing else; there are no rules answers, so the cycle records no `invoke_agent joustmania-agent` span.
2. The `noop` passes the allow-list only when the list names `noop`, as the `probe` variant of `interventions_allowed` does (otherwise it is blocked `not_allowed`, A10); it then charges the per-game budget like a medium intervention (1.0), and the decision is recorded on `agent.decision` and `agent.action` spans.
3. The writer treats it as a successful write that changes no flag and calls no flag service; `agent_interventions_applied_total{action=noop}` increments. The whole decide and act path is exercised without a game effect.
4. Use case ends.

### A24: Per-player levels return to neutral

**Trigger:** During a game, a player whose `player_sensitivity_factor` or `player_handicap_factor` resolved to a non-neutral value resolves to neutral again because the agent cleared the player's value, including the last such player (step 13)
**Flow:**

1. The coordinator reads the player's level as neutral where its baseline for this game holds a non-neutral level.
2. The coordinator dispatches the neutral value as a revert: it resets that player's factor to neutral (1.0) without the permission chain or the backstop, so a kill switch or an exhausted budget can never leave the factor stuck (BR-017). Players whose level changed to another non-neutral value in the same read go through the permission chain (step 13).
3. A later non-neutral value for any player is a change again and is applied (step 13).
4. Use case continues at step 14.

### A25: A game ends and its per-player values are dropped

**Trigger:** A game ends, real or shadow, after per-player interventions were written for it (step 12)
**Flow:**

1. The game coordinator reports the end to the flag service ([UC-053](UC-053.md) step 7).
2. The flag service drops every value and event list of that game, including every per-player entry, and pushes the configuration once (BR-016).
3. The game's players resolve the neutral value in no other game: a serial belongs to one game, and other live games' values are untouched, so nothing is dispatched for them.
4. Use case ends.

### A26: Intervention side effect runs on the owning game's event loop

**Trigger:** The coordinator applies or reverts an intervention for a live game, real or shadow (step 13)
**Flow:**

1. The coordinator detects the change, updates the game's last-applied state and runs the enforcement chain on its own event loop, as in step 13 (BR-006, BR-012).
2. It hands the intervention's effect (the handler, a revert, the on-device agent cue) to that game's dispatcher, which runs it on the event loop of the game's own thread, where the game's audio and controller-manager clients and its gameplay stream were created (BR-018).
3. Effects for one game run one at a time, in the order the coordinator decided them: an effect starts only after the previous one has finished. Each game, real or shadow, uses its own loop.
4. The coordinator waits for the effect at most 5 s without blocking its own loop. An effect that has started is never cancelled, so it is never left half-applied.
5. If the effect did not complete, the coordinator logs a warning, counts it in `game_intervention_dispatch_failures_total{type,reason}`, records the outcome on the apply's `agent_intervention` event and goes on with the next flag and game. Not started because the game's loop is closed, not running or stopped first: skipped for good, blocked with `block_reason=game_loop_unavailable`. Not started within 5 s (queued behind a slow effect of the same game): skipped for good, blocked with `game_loop_timeout`. Started but not finished within 5 s: left to finish on the game loop, outcome unknown, recorded as not blocked with `block_reason=game_loop_late` and no agent cue. The on-device agent cue is best-effort: it is not sent for `end_game` (the game has just ended) or when `agent_intervention_cue` is off, and a cue that cannot run is only logged at debug level, not counted.
6. Use case continues at step 14.

### A27: The intervention write fails

**Trigger:** The flag service cannot be reached, does not answer within 500 ms, or refuses the write (503, an unknown game, any other non-success status) (step 12)
**Flow:**

1. System does not retry, except once after 100 ms when the flag service answers that the game is not live yet (`game_not_live`).
2. System counts `agent_intervention_writes_total{result=error}`, logs `agent.action_write_failed` (ERROR) and `agent.apply_failed`, and marks the `agent.action` span as an error; `agent_interventions_applied_total` does not increment, and the decision gets no effect sample and no `decision.intervention_id`. A refused game id (A18) is recorded the same way, without a flag-service call.
3. The decision has already charged the per-game budget and is recorded as dispatched; nothing reaches the game, so the game continues unchanged.
4. Use case ends.

### A28: Kill switch off at the start of a cycle

**Trigger:** `enabled` is off when System reads the flag snapshot, or flagd cannot be read, which resolves it to off (step 1)
**Flow:**

1. System decides nothing and calls no backend; it records a throttled `agent.disabled` span with the flags in effect ([UC-045](UC-045.md)).
2. Use case ends.

### A29: Agent shuts down while a remote call is in flight

**Trigger:** The agent receives SIGTERM or SIGINT while a remote decide call is in flight (step 5)
**Flow:**

1. The shutdown cancels the call; an answer that lands after the cancellation is dropped as well.
2. System records `outcome=discarded`, `discarded_reason=shutdown` on the `invoke_agent joustmania-agent` span; there is no rules fallback and no action. The agent waits for in-flight calls before it flushes its spans.
3. Use case ends.

### A35: The same value is already applied

**Trigger:** The agent decides a state or level intervention (BR-023) whose target and value equal the last one it wrote to this game, within the last 30 s (step 11)
**Flow:**

1. After the allow-list and battery, and before the shield gate and the rate limit, the agent compares the decision with its applied-value record for this game, keyed by intervention and target: the value is compared as a number when it parses as one, else as the trimmed string. An empty value matches only an empty value.
2. On a match the agent blocks the decision `already_applied`: nothing is written, no budget is charged, rank-order admission continues (BR-014) and no effect is measured. `agent.decision` carries `decision.blocked=true`, `decision.block_reason=already_applied`; `invoke_agent joustmania-agent` carries `decide.blocked` / `decide.block_reason` and its outcome stays `act` (or `fallback`).
3. The suppression is emitted with its spans, an info log `agent.decision_already_applied` (not the `agent.decision_blocked` warning) and a narrative-timeline entry that reads "already in place", not "blocked". A repeat is quiet (A21).
4. The rules engine drops a candidate whose value is already applied after ranking, so it does not take a decision slot every second; an already-applied candidate still holds its intervention and target against lower-ranked candidates with another value (decide-contract.md §15.6), and the engine may rank an intervention on another key instead, and that may be a stronger one (for example a `grant_shield` for the same near-threshold player). Shields stay bounded by the cap and cooldown of UC-048 BR-007 (UC-048 A6). The decide state carries the per-player factor the agent already applied when it is not neutral (`sensitivity_factor=0.80`, step 4), so a remote backend sees the help is in place.
5. The record holds only values the agent wrote (`applied=true`). While a write to the key is in flight the check finds no match, since a different value may land last. A failed write (A27) or two writes to the same key in flight at once delete the entry, a gated write (A11) leaves it as it was, an entry whose target is no longer among the game's players is dropped, and an entry expires 30 s after its write, so the value is written again. A new game starts with an empty record.
6. Use case ends.

### A40: The lever would change the game's experiment flag

**Trigger:** The agent decides an intervention in a game that belongs to an experiment, in either arm (experimental or control), and the intervention changes the game value that experiment's flag sets (step 11; BR-028)
**Flow:**

1. After the allow-list and battery, and before the already-applied check, the shield gate and the rate limit, the agent looks up the flag of the game's experiment: first by the game id the experiment registry bound at spawn, then by the game's `experiment_id`. It blocks the decision `experiment_flag` when the intervention is a lever of that flag (BR-028).
2. Nothing is written and no budget is charged; rank-order admission continues (BR-014) and no effect is measured. `agent.decision` carries `decision.blocked=true`, `decision.block_reason=experiment_flag`, the narrative timeline records it as blocked, and `agent.decision_blocked` is logged.
3. The rules engine never proposes these levers (they are remote-backend only), so the check acts on remote decisions; a blocked one does not end rank-order admission, so the next decision of the same answer may still apply.
4. A game with no experiment, a game whose experiment the registry does not know (another agent's, or one torn down), and a lever of another flag are decided as before. The coordinator's `experiment_override` (A22, UC-043 BR-005) stays the backstop in the experimental arm.
5. A remote decide request for the game does not offer the levers of the flag under test: they are dropped from the `ffa.intervention` options ([decide-contract.md](../specs/decide-contract.md) §3.1). When no intervention besides `noop` is left, no remote call is made (`no_interventions_allowed`, A14, BR-005). The block of step 1 stays as defence in depth (a backend that answers an intervention it was not offered).
6. An `experiment_flag` block is emitted with its spans, warning and timeline entry; a repeat is quiet (A21).
7. Use case ends.

### A49: A Fight Club or Tournament player waits for its fight

**Trigger:** A Fight Club or Tournament player goes back to waiting (before its first round or match, or between its fights): the coordinator removes its `game_player_*` gauges ([UC-041](UC-041.md) BR-006), so the agent evicts it from the game's context after `lifecycle.player_ttl_seconds` (step 2; rules, rules fallback and the decide state; BR-038)
**Flow:**

1. The agent remembers the evicted player as waiting until a signal brings it back (it is seated for its next fight) or the game ends ([UC-041](UC-041.md) BR-007).
2. R1, R2 and R4's elimination path compute the elimination fraction as eliminations / players in the game. Players in the game is the game's `game_active_players`, the roster the coordinator sets when the game starts (waiting players included), when it is larger than eliminations + alive players in the context; else eliminations + alive players, as in every other mode. In an 8-player Tournament after match 1 the fraction is 1/8 = 0.125, not 1/3 (1 elimination, 2 fighters). A Fight Club round loss is not an elimination (the loser stays in the game, [UC-025](UC-025.md) step 4 of the Fight Club flow); only a player who leaves the rotation for good (A4 there) is one, so in a 4-player Fight Club where every player has lost a round the fraction is 0.
3. The decide state lists each waiting player with `waiting`: not alive, so it is not a target option and has no danger signals; no readings (its gauges are gone); no elimination order (a Fight Club round loss and a Tournament player still in the bracket have none). The narrative's session line adds `waiting=<n>` and the player line reads `waiting`; the LLM system prompt defines both in one sentence that describes the state only, and jev describes the player as "waiting for its fight, still in the game."
4. The other rules act on the fighters only: R3, R4 (both paths), R6, R8 and R9 need fresh readings (decide-contract.md §15.4). A player who just went back to waiting keeps its last alive state in the context until it is evicted (up to `lifecycle.player_ttl_seconds`), but its readings stop with its gauges, so within 3 s it is stale and no rule targets it. R6 keeps its "more than two alive players" guard, counting the players with fresh readings (it does not eliminate a fighter of a duel), R9 picks a fighter, and the battery policy reads the alive players.
5. Use case continues at step 11.

### A50: The decide state marks a player whose readings stopped or froze

**Trigger:** The decide state is built for a remote backend (claude, jev) or the rules' decide record (step 4) while an alive player's movement readings are not fresh (decide-contract.md §15.4 step 1; BR-039)
**Flow:**

1. The state keeps the player, alive, and marks it `readings_stale`. Its movement intensity, movement variance and skill level are left out, so it has no danger signals (no `danger`, `margin` or `intensity_rank`), is never `most_headroom` or `struggling`, and its narrative line shows no `movement=` sparkline. Its battery, shield fields and the agent's applied factors stay. The narrative's player line reads `<serial> alive readings_stale`; a player that is not alive (eliminated, waiting) is never marked.
2. The claude system prompt defines the marker and says that `adjust_player_sensitivity`, `grant_shield`, `send_controller_effect` and `eliminate_player` targeted at the player are refused (BR-039). Jev describes the player as having stale readings and does not offer it as a target candidate of those four levers; every other player lever still offers it. While no alive player has fresh readings, Jev does not offer those four levers at all.
3. When a remote answer that would act applies one of those four levers to a player whose readings are stale in the current context when the answer lands, the decision is discarded `stale` with detail `target_stale` (A7).
4. Use case continues at step 5.

### A53: A game-wide lever changes again inside its effect window

**Trigger:** The agent decides a game-wide lever of BR-046 (`adjust_global_difficulty`, `adjust_global_sensitivity`, `adjust_music_tempo`, `adjust_volume`, `set_pacing_profile`) with a value other than the one it last wrote to this game, while that write is younger than the effect window (`effect.window_seconds`, default 20 s), or a write to the lever is in flight or another decision for it is in the permission chain (step 11)
**Flow:**

1. After the already-applied check (A35) and before the shield gate and the rate limit, the agent looks up when it last wrote the lever in this game (the applied-value record of A35, keyed by the intervention with no target). A decision that repeats the written value is `already_applied` (A35), which is checked first.
2. While that write is younger than the effect window, resolved at this moment, and the decision names another value, or while a write to the lever is in flight or another decision holds it, the agent blocks the decision `lever_cooldown`. A decision that passes holds the lever until it finishes, so two decisions for one lever running at once (a remote answer landing during a rules cycle) cannot both write inside one window. Re-asserting the last written value is never refused: once the 30 s TTL of A35 has expired inside a longer window (`effect.window_seconds` `long`, 40 s), the same value is written again (BR-046). A refused decision: nothing is written, no budget is charged, rank-order admission continues (BR-014) and no effect is measured. `agent.decision` carries `decision.blocked=true`, `decision.block_reason=lever_cooldown`; `invoke_agent joustmania-agent` carries `decide.blocked` / `decide.block_reason` and its outcome stays `act` (or `fallback`).
3. The refusal is emitted with its spans, an info log `agent.decision_lever_cooldown` (not the `agent.decision_blocked` warning) and a blocked entry on the narrative timeline. A repeat is quiet (A21).
4. The decide state's session line names the levers in their cooldown (`lever_cooldown=adjust_global_difficulty`, step 4), so a remote backend can see that a change would be refused. The rules engine drops a candidate the cooldown would refuse before emission, from one snapshot per ranking (as A35 step 4), so a cooling lever takes none of the two emission slots and a dropped difficulty candidate does not re-arm the movement-variance cooldown; a lower-ranked candidate ranks instead.
5. Once the window has passed, the lever may change again, and that write starts the next window. Only a write the agent made (`applied=true`) starts a window: a failed write (A27) or a gated write (A11) does not, and a new game starts with none.
6. Use case ends.

### A44: A decision carries a prediction and is scored

**Trigger:** A decision that is not a `noop` acts (the permission chain passed and the intervention was applied, steps 11 to 13; the rules path A1 the same) and reaches the record step (step 14) with a prediction: from the rules table (R1 to R9, R4d), from the lever default of the chosen intervention (the ask off), or stated by the model (A45)
**Flow:**

1. The prediction is a closed template with a closed horizon over a measurable characteristic (`survives`, `no_elimination`, `elimination`, `activity_rises`, `closeness_rises`, `game_ends`; [decide-contract.md §14.2](../specs/decide-contract.md#14-characteristics-predictions-goals-2479)). It rides on the decide record, not on the decision, and the decision, the permission chain and the allow-list are unchanged by it (BR-034). Noop carries none.
2. The agent registers it with the values its template needs at that moment, stamped `acted`: one prediction per acting decision, also when an identical one is still pending. A decision that was held (A5), discarded (A7), blocked (A10) or dropped by the actuation gate (A11) registers nothing, and neither does a game that ended. `invoke_agent joustmania-agent` carries `decide.prediction.*`.
3. At the horizon plus a 3 s grace, or at the game's end, the prediction is scored `hit`, `miss` or `unscorable` (with a reason) from the game's telemetry, once (in a respawn mode, `survives`, `no_elimination` and `elimination` are `unscorable` `respawn_mode`, BR-043); an `agent.prediction.outcome` span linked to the decide span records the result and the `agent_prediction_*` metrics count it. A prediction decidable earlier is scored then. The game summary, the retro and the dashboard Agent tab read the result (UC-042 A12): the Agent tab shows on the decision's row what it expected and how it was scored ("expects: survives 15 s (p 0.70, rules R4) → hit", pending until the outcome span exists, `unscorable` with its reason), joined to the decide span by prediction id inside the same trace, and a per-game strip with the hit rate against the controls' base rate per source, acted predictions only. The outcome spans come with the decide search's game traces, so an outcome exported after the query window moved on (a 60 s or 120 s horizon, or the end-of-game score after the last decide) is not fetched: a row still without one then reads `unknown`, not `pending`.
4. Per game and every 15 s of play, control predictions are registered and scored the same way, to give each template its base rate; a hit rate is reported with its base rate, its unscorable rate and `game_kind`.
5. With `decision.predictions_enabled` off, nothing new is registered and no control is added (a prediction already pending still scores); the decision path is unaffected either way. A restart loses the pending predictions, which shows as registered minus scored.
6. Use case ends.

### A45: A model prediction is invalid and dropped

**Trigger:** `decision.predictions.ask_model` and `decision.predictions_enabled` are on, the backend is claude or jev, and the model's `ffa.prediction` answer is missing (for jev also: its prediction call failed), not one of the offered options, has a confidence that is not a finite number in [0,1], names a target template without a target, or contradicts the chosen intervention
**Flow:**

1. `Parse` (jev: a separate call after the decision's stages) splits the prediction off before validation ([decide-contract.md §4.1](../specs/decide-contract.md#41-parse-remote-only-decidellmioparsego)). The remaining answers are validated exactly as before, so the decision is valid and acts or is held as it would have been.
2. The prediction is dropped: `Response.PredictionDropped` carries the reason, `decide.prediction.dropped_reason` is set on `invoke_agent joustmania-agent` and `agent_prediction_dropped_total{backend,reason}` counts it. The lever default is not substituted: this decision has no prediction and nothing is registered.
3. With the ask off (the default) the request carries no ask and this flow cannot occur.
4. Use case continues at step 7 (every later check applies as usual; a dropped prediction never skips one and never lets a decision through that would have failed).

## Postconditions

### Success Postconditions

- The intervention is written for the deciding game only, the game coordinator has applied it through the game's own code, and its decision is recorded in the game's trace (`agent.decision`, `agent.action`).

### Failure Postconditions

- The game was never paused or slowed by the agent (BR-001), no other game was changed (BR-002), and nothing was written to the flag service outside the allow-list, the per-game budget and `enabled` = `act` (BR-004, FR-051).

## Business Rules

### BR-001: The game never waits

Remote calls are asynchronous; nothing in the game coordinator waits for the agent.

### BR-002: Interventions are game-scoped

Every intervention is written for the game whose decision loop decided it and resolves only in that game (FR-069, FR-136, [UC-053](UC-053.md)); a decision without a coordinator game id is not written. This rule is the owner. The writer refuses an intervention whose game id is empty or is not a coordinator game id (`game_…`), such as the `session-<n>` id of the partition for unlabeled signals ([UC-041](UC-041.md) A5), and records the refusal as a failed write (`agent_intervention_writes_total{result=error}`, `agent.action` span error), with no flag-service call and no retry.

### BR-003: Backend roles

See [C-018](../requirements.md#constraints).

### BR-004: Double enforcement

The allow-list is checked by the agent and again by the coordinator, and the coordinator applies nothing unless the agent's `enabled` is `act`: `off` (the stop), `watch` and an unreadable value all apply nothing ([UC-045](UC-045.md) BR-001: the stop writes `enabled` alone, so the coordinator's own check of it holds a stopped agent); the coordinator also enforces a global backstop (default 60 per minute), and it caps and paces the agent's shields per player per game whoever wrote them (UC-048 BR-007, A7).

### BR-005: No paid call without a possible action

A remote decide call is made only when the effective allow-list (deduplicated, empty ids and `noop` dropped, as for the `ffa.intervention` options) holds at least one intervention; otherwise the call could only answer `noop` (A14, NFR-011). The check sits before cadence and budget are charged. An answer already in flight when `interventions_allowed` flips to `none` is still blocked at landing by the live allow-list (`not_allowed`, A10). This covers in-game decide calls only: the post-game retro and the experiment proposer are governed by the kill switch and the LLM budget, not by the allow-list.

### BR-006: A one-shot intervention fires once, only in its game

A one-shot intervention is an event in its game's event list (FR-137, [UC-053](UC-053.md) BR-006). The coordinator applies, in order, every event with a sequence number above the last one it applied for that game and flag, exactly once; a game starts with an empty list, so an event of an earlier game, or from before a coordinator restart, is never applied in a new game. Fail closed on flagd errors: a read that returns an evaluation error applies nothing and does not move the last applied sequence number. A new, non-empty epoch (a flag-service restart) restarts the count. State flags are not affected: a game converges on its current value.

### BR-007: Every intervention sound resolves

Every sound id an intervention plays exists in the audio registry. The writer default `agent_cue` (`play_audio_cue`) and the shield sound `shield_up` are registry **aliases**: `agent_cue` plays the lobby ready ping (`Joust/sounds/beep_loud.ogg`, the sound a controller makes when it readies in the lobby), `shield_up` plays the Commander power-up sting (`Commander/sounds/power_ready.ogg`; an alias names an exact asset path). The audio service logs a WARNING for any sound id that is not in the registry.

Now [UC-048](UC-048.md) BR-001 (Shield LED schedule).

### BR-009: Moved

Now [UC-048](UC-048.md) BR-002 (Toughness boost is the weaker variant).

### BR-010: Moved

Now [UC-048](UC-048.md) BR-003 (Feedback follows the protection, never the other way round).

### BR-011: `end_game` ends only the game it was decided for

`end_game` is an event in the deciding game's event list. The coordinator force-ends only the session whose list holds it; it never resolves "the current game" or "the primary game" on the agent's behalf. A shadow game's decision can therefore never end the real game, and a real game's decision never ends a shadow. The agent never writes an intervention without a coordinator game id (BR-002).

### BR-012: A per-player grant applies once per decision

A per-player grant applies once per decision to each player it targets. The per-player grant flags `shield_seconds`, `toughness_boost_seconds` and `soft_penalty_action` are one-shot, time-boxed effects. Each write gets a fresh variant from the flag service; the coordinator change-detects grants per player on the resolved variant and value within the game and dispatches one intervention per changed player with `target` = that serial, so the battery guard and the backstop apply per grant. Fail closed: a per-player read that returns an evaluation error does not move that player's last-seen grant. The coordinator sees what flagd serves after each push: two grants to the same player pushed in one configuration collapse to the later one, which is applied once. A cleared grant resolves to the neutral value, which is never applied. The level flags `player_sensitivity_factor` and `player_handicap_factor` are not grants: re-applying an unchanged factor is a no-op (BR-017).

### BR-013: Agent spans sit under the game cycle

The agent's in-game spans belong to the running game cycle. The rules-path `invoke_agent joustmania-agent` and `agent.decision` (and the `agent.action` under it) and the remote path's async `invoke_agent joustmania-agent` are remote children of the coordinator's `game_cycle` span. The agent learns that span's id only from the span id of the `game.phase.start` log record sent when the span opens (UC-041 BR-004, A8). When it is not known, the parent is `gameplay_phase`, then the game root span; with no game ids at all the span is its own root. The game's trace id comes from `game.start` or, when that record was lost, from any `game.phase.start` (its span is in the game's trace); the root span id comes only from `game.start`. A lost record leaves the parent to the same order: with `game.start` lost but a phase record received, the trace id is known and the root span id is not, so the parent is `game_cycle` or `gameplay_phase` when known; only with no record carrying the trace id is the span its own root (accepted). For such a game, with the root span id unknown, `agent.decision` has no Link to the game root and the agent's spans carry no `game.trace_span_id` (accepted). Each `agent.decision` keeps its Link to the game root whenever the root span id is known, and the spans keep their backdated start times. In a game there is no `agent.signal_received` span: the triggering OTLP Export is an `agent.signal_received` event on `invoke_agent joustmania-agent` / `agent.disabled`; only without game ids does the cycle keep the span (and the remote `invoke_agent joustmania-agent` its `link.kind=fire_cycle` Link to it).

Each `agent.intervention.effect` span is a direct child of the `agent.decision` that dispatched the intervention: one span per intervention, carrying every evaluated fitness signal as attributes (`intervention.signals`, plus the objective's primary signal as `intervention.fitness_delta`), backdated to dispatch time and ended when the follow-up is read, with no effect span parenting another. The follow-up is read when the window elapses (`effect.window_seconds`, default 20 s) or, when the game ends inside the window, at game end: every effect sample still open for the game is then read at once, its span ends at game end and records the window it actually measured (`intervention.window_seconds`) and why it closed (`intervention.window_end_reason` = `game_ended`, else `elapsed`). The effect span outlives its decision by design; a child that ends after its parent is valid in OTel and keeps the cause one click away, whereas a `game_cycle` parent with a Link would hide the cause behind a Link.

### BR-014: A scarce budget goes to the highest-ranked decision

Within one cycle, decisions reach the per-game weighted rate limit in rank order (rules: the engine's score order; remote: the single answer). Admission stops at the first decision that passes the allow-list and battery checks but does not fit the remaining budget, unless its cost exceeds the whole budget: every lower-ranked decision of that cycle is blocked with `rate_limit` and charges nothing (A20). A decision the budget refused is reported in full once per budget state (the state changes when an intervention is admitted or one leaves the 60 s window); repeats in between are counted and logged at debug level but emit no `agent.decision` span (A21). When the budget covers every decision of the cycle nothing changes: every decision is admitted in rank order, so the rules ranking and the rules path golden are unchanged.

### BR-015: Nudges keep a reserve for protective interventions

A `send_controller_effect` decision (R8 statue nudge, R9 random effect, or a remote answer) is admitted only when the window still has room for one medium intervention (1.0, the cost of `grant_shield` and `adjust_player_sensitivity`) after charging it. The reserve does not apply when `chaos` is the strictly dominant objective weight (the decision's weights, else the `objectives` flag): then the operator asked for chaos and a nudge is the most valuable decision. It also does not apply when `interventions_allowed` permits no protective intervention (`grant_shield`, `toughness_boost`, `adjust_player_sensitivity`, `set_player_handicap`; e.g. the shipped `ambient`): nothing could use the reserve, so nudges may spend the whole budget. With the default budget of 2 and a protective intervention allowed, nudges spend at most 1.0 per minute (two nudges) and a shield or handicap finds 1.0 free; with `conservative` (1) no nudge applies unless chaos dominates.

Accepted limit: only `send_controller_effect` keeps the reserve. The other soft interventions, `play_audio_cue` and `adjust_volume` (also 0.5), do not, so they can still take the last 0.5 or 1.0 before a shield fires in a later cycle. In the same cycle BR-014 still ranks them below a higher-ranked shield. Today R2's calming cue is the only rule that emits one, and only early in an endurance session.

Why a reserve and not a new rule priority or a per-player cooldown: under the stage objectives `balanced_focused` (balanced 0.7, chaos 0.1) R8 scores at most 0.1 × 1.0 = 0.1, the `minScore` floor, while R3 (handicap) and R4 (shield) score 0.7 × urgency, so the ranking already puts shield and handicap first. The starvation came from cost: a 0.5 nudge fits a half-free budget that a 1.0 shield does not, so nudges took every freed half slot. A fixed priority would override the operator's weights under `chaos_focused`, and a per-player cooldown does not bound six statue players, who are six different targets.

### BR-016: Per-player entries live only as long as their game

Per-player values exist only in a live game's scope on the flag service, so the rendered configuration and flagd's evaluation cost grow with the games currently running, not with the history of games. When the game ends the flag service drops every value of the game in one push (A25, [UC-053](UC-053.md) BR-003); a game scope older than 1 h is dropped as well (UC-053 A11). No agent-side pruning is needed.

### BR-017: Per-player levels belong to one game

A game starts with neutral factors: a level is written for one game and dropped with it (BR-016), so a new game never inherits an earlier game's level. During the game the coordinator dispatches a level change only for the players whose resolved level differs from the last read in this game (alive players that pass the battery guard); a player whose level moves to neutral is reset to neutral (A24). The reset is a revert to neutral: it runs without the permission chain and does not count against the backstop. Fail closed: a per-player read that returns an evaluation error is ignored and never moves the last-seen level.

### BR-018: Intervention side effects run on the owning game's event loop

Each game runs on its own thread and event loop, and its gRPC clients (audio, controller manager) and gameplay stream belong to that loop; awaiting them from another loop fails with "attached to a different loop". The coordinator therefore keeps change detection, baselines and the enforcement chain on its own loop, and runs every intervention side effect (apply handler, revert handler, agent cue) on the loop of the game it was evaluated for, one at a time in decision order per game. `end_game` is the exception: it ends the session through the servicer's force-end path on the coordinator's loop, because that path joins the game's thread, and it sends no agent cue. The coordinator waits at most 5 s per effect and never blocks its own loop or deadlocks. An effect that has not started by then, or whose game loop is closed or stopping, is never applied (`game_loop_unavailable` / `game_loop_timeout`, recorded as blocked). An effect that has started is never cancelled, because cancelling it midway could leave the game half-changed; if it is still running at 5 s its outcome is unknown (`game_loop_late`, not recorded as blocked). Each such case is logged and counted (A26). A side effect's flag reads see the evaluation context of the game it runs for (game mode, controller count, sensitivity, `game_kind`, and experiment and arm for an experiment game), set around the effect on the game's loop and restored after it; before the game's run starts, that is its session kind and experiment. A key the read passes itself still wins. So in an experimental-arm shadow game an experiment value on a flag a handler reads resolves there too, and a real or non-experiment shadow game resolves as before. The flags handlers read are declared in `handler_flag_reads.py` and checked by a contract test and a census test (flags.md §1.2).

Accepted limit: the wait is per game but sequential across games. A game whose loop is stuck delays the interventions of the games evaluated after it in the same pass by up to 5 s per pending effect (head-of-line delay); its own later effects are skipped as `game_loop_timeout`. A stuck shadow game can therefore delay the real game's interventions, but never block or corrupt them.

### BR-023: An intervention that cannot change the game is not written

### BR-038: Players waiting for their fight are still in the game

### BR-043: In a respawn mode no elimination measure is scored

- In NonStop, Zombies, Swapper and Fight Club a death keeps the player in the game (a respawn, a turn, a swap, a round loser back in the queue), so the elimination sequence holds only the players who left for good (BR-038) and stays empty for a normal game, however many deaths there are. The game mode is the coordinator's `get_game_name()` (`Nonstop Joust`, `Zombie`, `Swapper`, `Fight Club`) or a menu alias; a contract test pins the names on both sides.
- There the elimination-based templates `survives`, `no_elimination` and `elimination` are scored `unscorable` with the reason `respawn_mode` (decide-contract §14.2), at the first check that sees the mode, whatever their source (rules, lever default, model, control). Without this an `elimination` would always miss and a `no_elimination` or `survives` would always hit.
- `elimination_pace` has no value there, so a goal term on it is not measured: it is left out of the attainment, the now line and `off_band` (decide-contract §14.4). The other characteristics and templates are scored as in every mode.
- A game whose mode is not observed yet is scored as before; a prediction still pending when the mode arrives is scored `respawn_mode` then. R1, R2 and R4's elimination path read the elimination fraction, which stays 0 in these modes, so they do not fire there; that is unchanged. A rare real elimination there (a disconnect, a Fight Club forfeit) does not make the templates scorable.

### BR-044: An operator brief steers the model's choice, never what it may do (FR-096)

- `decision.operator_brief` is a free text of at most 512 bytes (the flag service's free-string bound) an operator writes (stack scope, `agent` set, human-only: the agent never writes it, C-034), for example "keep the red player alive". Default and fallback: empty (a missing, unreadable or blank flag), and then the request and the prompts are byte-identical to the request without it. Writers: `scripts/flags.sh set-value`, Flagsmith ([UC-054](UC-054.md)), `talk-stage.sh reset` (`off`); planned (FR-263): also the operator pad's `RETRO` row 3 `BRIEF` through the menu ([UC-016](UC-016.md) BR-012), in memory, only the declared presets (`off`, `unkillable`, `protect_weakest`), never a free text and never over one (a free text shows as `CUSTOM`; the pad neither edits nor clears it, its reset is a no-op, D13). The pad changes which brief is in force, never this rule: a brief steers the model's choice, so a pad change of it is no raise (UC-016 BR-014).
- The agent reads it per remote request (step 5, at fire time), trims it, keeps at most 512 characters, turns control characters other than a line break, format characters and line / paragraph separators into spaces and `<` / `>` (and their full-width forms `＜` / `＞`) into `‹` / `›` (so the text cannot close or open a prompt block, nor fake one with a look-alike), and sets it on every claude and jev request.
- claude renders it as a delimited `<operator_brief>` block before the game state, and the system prompt gains one fixed paragraph (the same for every brief): the brief is the operator's wish, the model pursues it only by choosing among the offered options and ranges, and noop stays valid. jev gets it as `operator_brief` in the typed state of every stage; its criteria, the gate's included, are unchanged.
- It changes only the text the model reads. The questions, the offered interventions, the options, the ranges, the answer schema, validation, the act threshold, the permission chain and every policy cap are the same with and without a brief: a brief can make the model prefer `grant_shield` or a lower `adjust_player_sensitivity` for one player, but never a factor below the offered range (0.7 at least) or a shield beyond `policy.max_shields_per_player_per_game` and `policy.shield_cooldown_seconds`. "Make the red player unkillable" therefore stays out of reach, and the refused attempts show as blocks with their reason (UC-048 A7, BR-014).
- Telemetry: `decide.operator_brief.present` (true) and `decide.operator_brief.length` (characters after the clean-up) on the remote `invoke_agent joustmania-agent` span when a brief was sent; absent without one. The text itself is only in the GenAI content capture (`gen_ai.input.messages` on the backend's chat span), so only under `decision.capture_content=on`.

### BR-045: The operator sets the magnitude ranges, inside hard limits (FR-098)

- The range each numeric intervention's magnitude is chosen from (decide-contract §2.1) comes from `decision.magnitude_bounds`, an object in the `agent` set an operator writes (stack scope, human-only: the agent never writes it, C-034). It maps an intervention to `{"min": x, "max": y}`; an intervention it does not name keeps the code default range. Its baseline default is the code default table, so nothing changes until an operator writes it.
- Hard limits stay in code: the agent's absolute table (`decide.HardMagnitudeLimits`), equal to the flag service's `interventions` registry ranges and inside the game coordinator's clamps. The flag service refuses a value with an unknown intervention, an entry that is not `{min, max}` numbers, `min >= max`, a bound outside the hard limits, a fraction on `adjust_global_sensitivity`, or a range of `adjust_player_sensitivity`, `set_player_handicap` or `adjust_global_difficulty` that leaves out their neutral 1.0 (`422 out_of_bounds`).
- The agent reads it per decide request (step 4, rules and remote paths) in the game's flag context and builds one bounds table that the request carries: the magnitude question's text, the resolution of the answer into the written value, the jev ladders, the rules answer and the clamp of the rules decision's value, and the per-player factors of the state all use it. An entry that fails the same checks at read time (a value written before a check existed, a baseline edit) falls back to the code default for that intervention only and is recorded; an unreadable flag gives the code defaults. The decision never fails because of it.
- A default (the value written for an empty magnitude) outside a narrowed range is clamped into it; the neutral value is unchanged.
- Each range line of the magnitude question names what its lowest and highest value do (for example "lowest 0.7 (target harder to eliminate)"), so the model can tell which end helps; jev's ladder ends say the same (decide-contract §2.1).

### BR-046: A game-wide lever changes at most once per effect window

- The game-wide levers `adjust_global_difficulty`, `adjust_global_sensitivity`, `adjust_music_tempo`, `adjust_volume` and `set_pacing_profile` change at most once per effect window (`effect.window_seconds`, default 20 s, the follow-up delay of the effect sample, step 14) in a game: the agent refuses another value `lever_cooldown` until the window since its last write to the lever has passed (A53). The same value stays `already_applied` (A35, BR-023), and the cooldown never refuses the last written value, so the 30 s TTL still re-asserts a lost value inside a longer window.
- Why: the magnitude score maps to an absolute value (BR-045), and two close scores can resolve to two values (0.5 and 0.75 give 1.25 and 1.625 for `adjust_global_difficulty`). BR-023 blocks only an exact repeat, and a high budget (`lively`, 8 per minute) no longer damps the alternation, so a lever flipped between two values every few seconds and each effect sample measured a mix of changes.
- The window is the effect window, read at each check, not a separate tunable. The check uses the applied-value record, so it runs only while the loop's suppression is on (A35). Per-player levers (`adjust_player_sensitivity`, `set_player_handicap`), `ramp_tempo` and `auto_rubberband`, grants and events have no cooldown.
- The per-player sensitivity factor has the lowest hard limit, 0.2 (the death threshold times 5, so a player is practically unkillable; never 0, the factor divides the threshold): the flag service accepts `player_sensitivity_factor` from 0.2 to 2.0, and the game coordinator clamps the per-player factor to [0.2, 2.0] and lowers the floor of the combined sensitivity x difficulty factor (0.5) only by that factor itself, so global difficulty alone keeps its 0.5 floor (UC-030 step 5). The agent can reach it only when an operator widens `adjust_player_sensitivity` down to it; the default range stays 0.7 to 1.5.
- Telemetry: `decide.magnitude_bounds.source` (`default` or `flag`) on every `invoke_agent joustmania-agent`, `decide.magnitude_bounds.invalid` (the interventions that fell back, sorted, comma-separated) when one did, and a WARN `agent.magnitude_bounds_invalid` when the set of invalid entries changes.
