# Use Case: See a Swing at Full Density

## Overview

**Use Case ID:** UC-102
**Use Case Name:** See a Swing at Full Density
**Primary Actor:** Presenter
**Secondary Actors:** Player, Gateway, Observability Backend
**Goal:** Show, per observability backend, whether it keeps each player's motion at the density the case sends it (a point about every 100 ms), rolls it up to a coarser step, or loses it, around a death the presenter picks
**Trigger:** Presenter starts the "Can you see the swing?" booth challenge
**Status:** Implemented
**Requirements:** [FR-223, NFR-022, NFR-029](../requirements.md)

A booth challenge of the Orange Case (epic #2569, #2586); UC-100 to UC-199 are the booth challenges, one per challenge. The case already sends each player's acceleration as a metric with a point about every 100 ms; most backends store or draw metrics at a 10 to 60 s step by default, so a swing that lasts a fraction of a second is averaged away. The question is density, not the exact shape of the curve: does the backend keep the points the case sent? The challenge adds no telemetry (BR-005). The reference is the same series in the case's own VictoriaMetrics (BR-003). Every enabled backend gets the same game through the gateway, and the results are shown side by side, never ranked. Steps 1 to 3 are system behaviour that tests check; steps 4 to 6 are the presenter's check at the booth, done by hand.

## Preconditions

- The gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The game coordinator exports its metrics every 100 ms: the observability flag `metrics_export_interval_ms` serves `realtime` to `game-coordinator-service`, the stack default by targeting (NFR-022, [flags.md §10](../specs/flags.md#10-observability)). The flag is read at service start.
- Game analytics are on (`analytics.enabled`, on by default), so the coordinator sends the per-player motion metrics.
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter starts a game ([UC-010](UC-010.md)); any mode with motion deaths.
2. While the game runs, System sets each player's acceleration magnitude, `game_player_accel_magnitude{serial, game_id}`, from the game loop about every 100 ms (BR-001).
3. System exports the metric every 100 ms to the case's VictoriaMetrics and, unchanged, through the gateway to every enabled backend (BR-002).
4. Presenter picks a player's death from the game's trace (the `player_death` moment of [UC-030](UC-030.md), its time and the player's serial) and a window around it, 10 s by default (BR-004).
5. Presenter reads the player's `game_player_accel_magnitude` for that game and window in the case's VictoriaMetrics (the reference) and in each backend's own view of the metric, and records per backend the number of points and the step between them (BR-003).
6. Presenter compares each backend with the reference, records one of the three results (BR-004) and shows the results of all backends side by side.

## Alternative Flows

### A1: The coordinator does not export every 100 ms

**Trigger:** The reference shows a step longer than about 100 ms for the game (the coordinator started with another `metrics_export_interval_ms` variant, or game analytics are off and there is no series) (step 5)
**Flow:**

1. Presenter does not count the game: the case did not send the density the challenge asks about.
2. Presenter restores the preconditions; a change of `metrics_export_interval_ms` applies only after the coordinator restarts.
3. Use case continues at step 1 with a new game.

### A2: A backend does not receive the game

**Trigger:** The gateway or a backend cannot be reached or refuses the data (step 3)
**Flow:**

1. System keeps playing the game and keeps feeding the case's own backends and the agent unchanged (NFR-029).
2. Presenter records the backend as *not received*, not as one of the three results (BR-004).
3. Use case continues at step 6 for the other backends.

### A3: No death to pick

**Trigger:** The game ended without a motion death (force-ended, or every death came from an agent intervention) (step 4)
**Flow:**

1. Presenter picks a window of play of one player instead, by the game's start and end times on its trace.
2. Use case continues at step 5.

## Postconditions

### Success Postconditions

- Post-S-1: Each backend that received the game has one of the three results for the picked window, next to the reference's point count and step.
- Post-S-2: The game was played and recorded like any other game; the challenge sent nothing extra (BR-005).

### Failure Postconditions

- Post-F-1: A game that did not meet the preconditions is not counted (A1); a backend that did not receive the game is *not received* (A2).
- Post-F-2: Neither the game nor the case's own backends nor the agent were affected by a backend or the gateway failing (NFR-029).

## Business Rules

### BR-001: The motion series is a sample at about 10 Hz

`game_player_accel_magnitude` is a gauge per player and game (`serial`, `game_id`). The game loop sets it every `analytics.metrics_emit_interval_frames` frames (6: about every 100 ms at the 60 Hz loop) to the raw acceleration magnitude of that frame. It is a sample: the frames in between are not sent, so the curve need not reach the `accel_magnitude` recorded on the death. The challenge is about density, not about the peak value; the series is compared only with itself in the reference (BR-003).

### BR-002: Every backend gets the points the case sent

The gateway's metrics pipeline takes the same OTLP metrics as the in-case pipeline, with the same processors (batching and resource attributes only): the case aggregates and drops nothing before the gateway (FR-086). Whatever coarsening a backend shows comes after the gateway.

### BR-003: The reference is the case's own series

The reference is `game_player_accel_magnitude{serial, game_id}` in the case's VictoriaMetrics, which stores the received points without downsampling (7-day retention). It is read for the same player, game and window as the backend (raw samples, or a query at a 100 ms step). The `accel_magnitude` on the death is not the reference (BR-001).

### BR-004: The three results

For each backend, for the picked player, game and window (10 s by default, wide enough to hold about 100 reference points):

| Result | Meaning |
|---|---|
| full density | The backend shows a point about every 100 ms: its point count in the window is at least 90 % of the reference's |
| rolled up | The backend shows the window, but with fewer points: record the step it shows (for example 10 s, 60 s) |
| gone | The backend shows no point of the series in the window (dropped, or past its retention) |

A backend that did not receive the game is *not received* (A2), not a result. There is no score and no order.

### BR-005: The challenge adds no telemetry

The challenge uses only what the case sends in every game. It adds no metric, no flag and no work in the game loop.
