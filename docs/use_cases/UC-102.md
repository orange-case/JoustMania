# Use Case: See a Swing at Full Density

## Overview

**Use Case ID:** UC-102
**Use Case Name:** See a Swing at Full Density
**Primary Actor:** Presenter
**Secondary Actors:** Player, Gateway, Observability Backend
**Goal:** Show, per observability backend, whether it keeps a player's motion at the density the case sends it (a new value about every 100 ms), rolls it up to a coarser step, or loses it, in the seconds before a death the presenter picks
**Trigger:** Presenter starts the "Can you see the swing?" booth challenge
**Status:** Implemented
**Requirements:** [FR-223, NFR-022, NFR-029](../requirements.md)

A booth challenge of the Orange Case (epic #2569, #2586); UC-100 to UC-199 are the booth challenges, one per challenge. The case already sends each player's acceleration as a metric with a new value about every 100 ms; many backends store or draw metrics at a 10 to 60 s step by default, so a swing that lasts a fraction of a second is averaged away. The question is density, not the exact shape of the curve: does the backend keep the values the case sent? The challenge adds no telemetry (BR-005). The reference is the same series in the case's own VictoriaMetrics (BR-003). Every enabled backend gets the same game through the gateway (FR-086), and the results are shown side by side, never ranked. Steps 1 to 3 are system behaviour that tests check; steps 4 to 6 are the presenter's check at the booth, done by hand.

## Preconditions

- The full stack runs: the case's VictoriaMetrics and envoy are up (the lite stack has neither).
- The gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The game coordinator started with a 100 ms metric export: the observability flag `metrics_export_interval_ms` serves `realtime` to `game-coordinator-service`, the stack default by targeting (NFR-022). The coordinator reads it once at start and logs the value it got (`metrics_export_interval_ms from flagd: 100ms`); a coordinator that could not read flagd at start exports every 1000 ms until it restarts.
- The game loop runs at 60 Hz: the flag `game_loop.update_frequency_hz` serves `high`, the default ([flags.md](../specs/flags.md)).
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter starts a game ([UC-010](UC-010.md)); any mode with motion deaths.
2. While a player is alive, System sets the player's acceleration magnitude, `game_player_accel_magnitude{serial, game_id}`, on every 6th controller frame of the gameplay stream, about every 100 ms at 60 Hz (BR-001).
3. System exports the metric every 100 ms to the case's VictoriaMetrics and, through the same processors, through the gateway to every enabled backend (BR-002).
4. Presenter picks a player's motion death (`death.reason` = `motion` on its `player_death` moment) and its time: from the player's `challenge.death_times_ns` in the game's ground truth on the root span after a normal game end ([UC-100](UC-100.md) step 6), or else from the player's `player_death` moment in the game's moment shape (on the trace, or in the logs for `log_event`). The window is the 10 s ending at the death (BR-004).
5. Presenter reads the player's raw samples for that game and window from the case's VictoriaMetrics (the reference) and the same series in each backend's own view of the metric, and counts in each how often the value changes (BR-003, BR-004).
6. Presenter compares each backend with the reference, records one of the three results (BR-004) and shows the results of all backends side by side.

## Alternative Flows

### A1: The case did not send the density

**Trigger:** In the reference, the median time between value changes in the window is longer than 150 ms, or there is no series (step 5): the coordinator exports at another interval (another `metrics_export_interval_ms` variant, or flagd was not reachable when it started), or the game loop runs below 60 Hz
**Flow:**

1. Presenter does not count the game: the case did not send the density the challenge asks about.
2. Presenter restores the preconditions; an export interval change applies only after the coordinator restarts, a loop rate change from the next frame.
3. Use case continues at step 1 with a new game.

### A2: A backend does not receive the game

**Trigger:** The gateway or a backend cannot be reached, refuses the data, or drops it after the gateway export's bounded retry or with a full queue (step 3)
**Flow:**

1. System keeps playing the game and keeps feeding the case's own backends and the agent unchanged (NFR-029).
2. Presenter records the backend as *not received*, not as one of the three results (BR-004).
3. Use case continues at step 6 for the other backends.

### A3: No motion death with 10 s of play before it

**Trigger:** The game ended without a motion death (force-ended, or every death came from an agent intervention, which has no swing), or every motion death came less than 10 s after the game started (step 4)
**Flow:**

1. Presenter picks instead the last 10 s of play of a player who was alive in them, by the times on the game's trace.
2. Use case continues at step 5.

## Postconditions

### Success Postconditions

- Post-S-1: Each backend that received the game has one of the three results for the picked window, next to the reference's count of value changes.
- Post-S-2: The game was played and recorded like any other game; the challenge sent nothing extra (BR-005).

### Failure Postconditions

- Post-F-1: A game that did not meet the preconditions is not counted (A1); a backend that did not receive the game is *not received* (A2).
- Post-F-2: Neither the game nor the case's own backends nor the agent were affected by a backend or the gateway failing (NFR-029).

## Business Rules

### BR-001: The motion series is a sample about every 100 ms while the player is alive

`game_player_accel_magnitude` is an observable gauge per player and game (`serial`, `game_id`), in g. On every `analytics.metrics_emit_interval_frames` controller frames of the gameplay stream (6; about every 100 ms at the 60 Hz default, every 200 ms at 30 Hz) the coordinator sets it to the raw acceleration magnitude of that frame. It is a sample: the frames in between are not sent, so the curve need not reach the `accel_magnitude` recorded on the death. Every export sends the gauge's last value, so after the player's death the series repeats one value until the game ends, when the game removes it; in Fight Club and Tournament it is also removed while the player waits for the next fight. Only the seconds before a death show the swing.

### BR-002: Every backend gets the values the case sent

The gateway's metrics pipeline takes the same OTLP metrics as the in-case pipeline, with the same processors: the memory limiter, batching and resource attributes. Neither filters, aggregates nor changes the temporality of this metric (FR-086). The gateway copy is best effort: what its exporter cannot deliver within its bounded retry and queue is lost for the backends only (NFR-029, A2). Whatever coarsening a backend shows otherwise comes after the gateway.

### BR-003: The reference is the case's own raw samples

The reference is `game_player_accel_magnitude{serial, game_id}` in the case's VictoriaMetrics, which stores the received samples without deduplication or downsampling (7-day retention). It is read as raw samples (`/api/v1/export`) for the same player, game and window, never through a range query: a range query fills every step with the last stored value, so it would show a coarse series as dense. The `accel_magnitude` on the death is not the reference (BR-001).

### BR-004: The three results

For each backend, for the picked player, game and window (the 10 s ending at the death), count how often the value changes, in the backend at a zoom that shows the whole window and nothing wider, and in the reference. Points that only repeat the previous value (the step-filling of a query or a graph) are not changes.

| Result | Meaning |
|---|---|
| full density | The backend's count of value changes is at least 90 % of the reference's |
| rolled up | The backend shows the series in the window with fewer than 90 % of the reference's changes: record the step it shows (for example 10 s, 60 s) |
| gone | The backend shows no value of the series in the window (dropped, or past its retention) |

A backend that did not receive the game is *not received* (A2), not a result. There is no score and no order.

### BR-005: The challenge adds no telemetry

The challenge uses only what the case sends in every game. It adds no metric, no flag and no work in the game loop.
