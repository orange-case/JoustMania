# Use Case: Generate the Game Dashboard with a Backend's Assistant

## Overview

**Use Case ID:** UC-104
**Use Case Name:** Generate the Game Dashboard with a Backend's Assistant
**Primary Actor:** Presenter
**Secondary Actors:** Player, Gateway, Observability Backend
**Goal:** Show, per observability backend, whether its own AI assistant builds a working game dashboard from the published prompts and the games the case sent, checked panel by panel against what really happened
**Trigger:** Presenter starts the "What is happening?" booth challenge
**Status:** Draft
**Requirements:** [FR-237, FR-238, NFR-029](../requirements.md)

A booth challenge of the Orange Case (epic #2569, #2585); UC-100 to UC-199 are the booth challenges, one per challenge. The case seeds every enabled backend with games played through the normal pipe: the case's collector and the gateway (FR-086). Then the same published prompts are run in each backend's own AI assistant, which builds the game dashboard from the telemetry it holds. A checklist of required panels is checked on the seeded games against the case's own stores, so a dashboard that looks right but shows wrong numbers is caught. The dashboard is then used for "Can you see the swing?" ([UC-102](UC-102.md)). The results are shown side by side as a gallery, never ranked. The prompts are published before the booth and rehearsed; the challenge page says so. Steps 1 and 2 are system behaviour that tests check; steps 3 to 6 are the presenter's check at the booth, done by hand.

## Preconditions

- The full stack runs, and the gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The prompts and the checklist are published in a version that names the attributes and metrics the prompts may use (FR-237).
- The backends hold no game dashboard from an earlier run of the challenge, generated or hand-built.
- For each backend taking part a hand-built dashboard is prepared and kept outside the backend (BR-006).

## Main Success Scenario

1. Presenter plays the seeding games on the case: a pattern game driven by `stowaway` and one match with real controllers ([UC-010](UC-010.md)), and notes the game id of each (BR-001).
2. System sends each seeding game through the gateway to every enabled backend, like any other game (FR-086).
3. Presenter runs the published prompts in each backend's own AI assistant, in the published order and unchanged (BR-002).
4. The backend's assistant builds a dashboard; Presenter records the time it took and the retries it needed, and does not edit the dashboard (BR-002).
5. Presenter checks each panel of the checklist on the seeded games against the reference values from the case's own stores (BR-003, BR-004).
6. Presenter records each backend's result and shows the dashboards and their checklists side by side (BR-005).

## Alternative Flows

### A1: A seeding game did not end normally

**Trigger:** A seeding game was force-ended or failed, so it has no ground truth to check against (step 1)
**Flow:**

1. Presenter does not use the game for the checklist.
2. Use case continues at step 1 with a new game of the same kind.

### A2: A backend does not receive the seeding games

**Trigger:** The gateway or a backend cannot be reached, refuses the data, or drops it after the gateway export's bounded retry or with a full queue (step 2)
**Flow:**

1. System keeps playing the games and keeps feeding the case's own backends and the agent unchanged (NFR-029).
2. Presenter records the backend as *not received*, not as one of the results (BR-005).
3. Use case continues at step 3 for the other backends.

### A3: The backend has no assistant that builds dashboards

**Trigger:** The backend's assistant cannot build a dashboard, or the backend has no assistant (step 3)
**Flow:**

1. Presenter loads the backend's prepared hand-built dashboard into the backend, labelled *hand-built* (BR-006).
2. Use case continues at step 5.

### A4: The assistant asks a question

**Trigger:** The assistant asks the presenter a question before or while building the dashboard (step 4)
**Flow:**

1. Presenter answers only with the published answer to that question, or with the published default answer when none fits (BR-002).
2. Use case continues at step 4.

### A5: The assistant fails

**Trigger:** After the allowed retries the assistant has built no dashboard, refused, or built one that does not open (step 4)
**Flow:**

1. Presenter records the backend's result as *failed*, with the reason and the last answer of the assistant.
2. Presenter loads the backend's prepared hand-built dashboard into the backend, labelled *hand-built* (BR-006), for the checklist and for [UC-102](UC-102.md).
3. Use case continues at step 5.

## Postconditions

### Success Postconditions

- Post-S-1: Each backend that received the seeding games has a result: *generated*, *hand-built* or *failed*, with its checklist, the time it took and the retries, all with the prompt version.
- Post-S-2: Each backend has a dashboard for [UC-102](UC-102.md): the generated one or, labelled, the hand-built one.

### Failure Postconditions

- Post-F-1: A hand-built dashboard is never shown as generated.
- Post-F-2: A backend that did not receive the seeding games is never given a checklist result (A2).
- Post-F-3: Neither the games nor the case's own backends nor the agent were affected by a backend or the gateway failing (NFR-029).

## Business Rules

### BR-001: The seeding games

Every backend is seeded with the same games played on the case and sent through the normal pipe: a pattern game whose players are driven by `stowaway` in players mode (#2576), so its motion and its deaths are repeatable, and one match with real controllers. Both are free-for-all games that end normally. In the pattern game `stowaway` only drives the controllers: the game's telemetry comes from the case's own services, like any game, and carries no `orangecase.synthetic` mark, so it reaches the case's Jaeger and VictoriaMetrics and BR-004 has its reference there; only `stowaway`'s own spans are synthetic and stay out of the case's backends (#2577). The presenter notes the game id of each; the checklist is checked on those games. A recorded reference dataset (#2582) would make the values fixed; until then the reference is the seeded games themselves (BR-004).

### BR-002: How the prompts are run

- The backend's own assistant only; no other model, no plug-in the backend does not ship.
- The published prompts, in the published order, word for word, all in the same conversation: one new conversation of the assistant per backend, so a later prompt builds on the answers to the earlier ones.
- At most two retries per prompt, each the same prompt again; a retry is recorded.
- A question of the assistant gets only the published answer to it, else the published default answer ("Use the telemetry of the game with this game id and choose yourself").
- Nobody edits the generated dashboard. A change the presenter makes turns it into *hand-built*.
- The time is from the first prompt to the last panel shown.

### BR-003: The checklist

A game dashboard has these panels, each checked on the seeded games:

| Panel | What it must show |
|---|---|
| players alive | the players alive over the game's time |
| deaths | each player's death, with its time |
| elimination order | the order in which the players went out, and the winner |
| last knock-out | the player of the last death and its time |
| motion | each player's acceleration over the game's time, with the death threshold |

The motion panel is the one [UC-102](UC-102.md) uses. A panel is *correct* when it shows the reference values of BR-004 for the seeded game, *wrong* when it shows other values, and *missing* when the dashboard has no such panel.

### BR-004: The reference values

The reference comes from the case's own stores, never from a backend: the deaths, their times, the elimination order and the winner from the game's ground truth on its root span ([UC-100](UC-100.md) BR-006) and its death moments in the case's Jaeger; players alive and the elimination order also from `game_player_alive` and `game_player_elimination_order` in the case's VictoriaMetrics; the motion from `game_player_accel_magnitude` as raw samples ([UC-102](UC-102.md) BR-003). A time counts as correct within 1 s, the motion panel when it shows the series of each player of the game.

### BR-005: The result per backend

| Result | Meaning |
|---|---|
| generated | the assistant built the dashboard from the prompts |
| hand-built | the backend has no assistant that builds dashboards (A3); the dashboard was built by hand from the checklist |
| failed | the assistant built no usable dashboard within the allowed retries (A5); the checklist is that of the hand-built dashboard, labelled as such |

With the result the presenter records the prompt version, the time, the retries and the checklist (each panel *correct*, *wrong* or *missing*). A backend that did not receive the seeding games is *not received* (A2), not a result. There is no score and no order.

### BR-006: The hand-built dashboard is prepared before the booth

Before the booth the presenter builds, for each backend taking part, a game dashboard by hand from the published checklist, with the panels of BR-003 and the title marked *hand-built*, and exports it from the backend, so the backend holds no game dashboard when its assistant starts (the assistant cannot copy it). It is loaded into the backend only in A3 or A5, after the assistant's run.
