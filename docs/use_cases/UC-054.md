# Use Case: Manage Runtime Flags from Hosted Flagsmith

## Overview

**Use Case ID:** UC-054
**Use Case Name:** Manage Runtime Flags from Hosted Flagsmith
**Primary Actor:** Operator, Presenter
**Secondary Actors:** Flagsmith
**Goal:** Change a runtime flag in hosted Flagsmith, for the whole stack, one live game or one player of a live game, so that the stack applies it through the flag service while it is online, and keeps playing on its own while Flagsmith cannot be reached
**Trigger:** The operator or presenter changes a JoustMania flag in the hosted Flagsmith environment of the stack
**Status:** Draft
**Requirements:** [FR-206, FR-208, FR-209, FR-210, FR-212, FR-213, FR-214, FR-215, NFR-050, NFR-058, C-008, C-015, C-016, C-030, C-031, C-032, C-034, C-036, C-037](../requirements.md)

## Preconditions

- The flag service serves the stack's flags to flagd ([UC-053](UC-053.md)).
- The stack is linked to its own Flagsmith environment (stage, CI and dry run each have one), and the flag service holds that environment's credentials as a secret (C-016).
- Flagsmith lists the live games and their players ([UC-055](UC-055.md) A1).

## Main Success Scenario

1. The operator changes a JoustMania flag in Flagsmith: switches its stack-wide value on or off, sets a new stack-wide value, or sets a value for one live game or one player of a live game.
2. The flag service notices the change at its next look at the Flagsmith environment, at most 30 seconds later, or sooner when Flagsmith announces the change.
3. The flag service compares the Flagsmith state with the last state it saw from Flagsmith and with its own state, and recognises the change as a new change made in Flagsmith, not as an echo of a change it sent itself (BR-004).
4. The flag service checks the change like any other write: the flag is runtime-mutable, the value lies within its bounds, the scope is one Flagsmith may set (BR-003), a game or player value names a live game and a player of it, an event's content is valid for the game (UC-053 A4), and flagd is connected (UC-053 step 3).
5. The flag service applies the change as a write with writer label `flagsmith` and pushes the new configuration to flagd (UC-053 steps 4 and 5); a value of a flag the registry marks as an admin setting is persisted like the host's own setting.
6. flagd serves the new value, and the game coordinator, the menu and the agent see it as they see any runtime change (UC-053 step 6).
7. The flag service records the applied change and marks the flag as in sync with Flagsmith; the operator sees in Flagsmith that the stack runs the value.

## Alternative Flows

### A1: Flagsmith not reachable

**Trigger:** The flag service cannot reach Flagsmith, or Flagsmith does not answer within 5 seconds (step 2)
**Flow:**

1. The flag service marks the link as offline and keeps serving the current configuration; every local write, game and kill switch keeps working (BR-007).
2. The flag service tries again with growing waits, up to 60 seconds between two tries.
3. When Flagsmith answers again, the flag service reconciles both sides (A2) and marks the link as online.
4. Use case continues at step 3.

### A2: Same flag changed on both sides while offline

**Trigger:** On reconnect, a flag changed both in Flagsmith and locally since the last state seen from Flagsmith (step 3)
**Flow:**

1. For a kill switch, the more restrictive of the two values wins (BR-005); the flag service applies it locally if needed and sends it to Flagsmith if Flagsmith holds the other one.
2. For every other flag the Flagsmith value wins and is applied as in steps 4 to 7; the local value is discarded and the conflict is recorded with both values.
3. Local changes to flags that did not change in Flagsmith are sent to Flagsmith ([UC-055](UC-055.md)).
4. Use case continues at step 4.

### A3: Flag service starts or restarts

**Trigger:** The flag service starts (step 2)
**Flow:**

1. The flag service starts from the baseline and the persisted admin settings and serves flagd at once; it never waits for Flagsmith (BR-007).
2. If Flagsmith cannot be reached, the stack runs on the baseline and the persisted admin settings, and the use case continues as in A1.
3. Otherwise the flag service creates in Flagsmith every registry flag that is not a feature there yet (BR-002).
4. It applies the restart rule (BR-006): a value a person (a Flagsmith user) set in Flagsmith, and the value of an admin setting, is applied as a change from Flagsmith (steps 4 to 7), except for a kill switch (BR-005): the flag service has no last state seen from Flagsmith for it after a restart, so a Flagsmith value that differs from the local value (the baseline, or the persisted value of an admin setting) is a conflict, the more restrictive value wins, and a local value that wins is sent to Flagsmith and the feature is marked out of sync until then; a value made with any API key (the flag service's own in-memory writes, Terraform, the Flagsmith MCP server) is cleared in Flagsmith, except a kill switch, whose more restrictive value wins even over the clear (BR-005) and is recorded as a conflict; an admin setting made with an API key is replaced by its persisted value (or the baseline), which is sent to Flagsmith, and one made by a person is applied and persisted; a value on a game that is not registered yet is neither applied nor refused, and applies once the game registers; games and players that are not live are removed from Flagsmith, but never at the moment of start: only after the game coordinator has registered its games again, or 45 seconds after start, whichever is later, and never a game that is registered.
5. If the flag service cannot determine who made a value (Flagsmith has no record of it), it treats the value as a person's and reports the restart rule as degraded; it never treats an unknown author as an API key.
6. If the Flagsmith project cannot hold the games' overrides (it has no edge identities), the flag service keeps the link offline and says why.
7. A registry flag that cannot be created as a feature (its name differs from an existing feature only in case, the feature is archived, or Flagsmith keeps failing) is refused with a warning; the other flags are created and the start continues.
8. Use case continues at step 7.

### A4: Change refused by the flag service

**Trigger:** The change from Flagsmith fails a check of step 4: the flag is not runtime-mutable, the value is out of bounds, the scope is not one Flagsmith may set, the game is not live, the serial is not a player of the game, or an event's content is not valid (step 4)
**Flow:**

1. The flag service keeps the current value and records the rejection with its reason, like any refused write (UC-053 A5, A6).
2. The flag service marks the feature in Flagsmith as unhealthy with the reason, so the operator sees in Flagsmith that the stack does not run that value.
3. The refusal stays until the operator changes the flag again in Flagsmith.
4. Use case ends.

### A5: flagd not connected

**Trigger:** flagd has no open sync stream when the change from Flagsmith arrives (step 4)
**Flow:**

1. The flag service does not apply the change and does not record it as seen, so it is tried again at its next look at Flagsmith.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- flagd serves the value set in Flagsmith to the readers it was set for, and to no other game or player.
- Flagsmith shows that the stack runs the value.
- The change is recorded as a sync span naming the flag, scope and writer `flagsmith`, and counted in the Flagsmith link metrics.

### Failure Postconditions

- The configuration flagd serves is unchanged, or is the value of a successful local write; a failure of Flagsmith never changes or blocks a local value.
- A kill switch is never loosened by a conflict between the two sides, a restart or an echo; only a deliberate change of it in Flagsmith loosens it.
- No baseline flag file has changed.
- The game keeps playing.

## Business Rules

### BR-001: Flagsmith is a writer, flagd still evaluates

The flag service treats Flagsmith as one more writer of UC-053 with the writer label `flagsmith`: every value from Flagsmith passes the mutable-flag registry, the game scope and the sync stream checks (C-032). No OpenFeature client resolves against Flagsmith; every client keeps resolving through stock flagd (C-031).

### BR-002: One feature per registry flag

Every flag of the mutable-flag registry is one Flagsmith feature, named after the flag key (keys are unique across flag sets), tagged with its flag set and described by its registry description. The flag service creates a missing one at each start. Read-only baseline flags are not features in Flagsmith.

### BR-003: What Flagsmith may set

From Flagsmith the operator may set a stack-wide value, a value for a live game, a value for a player of a live game, and an event for a live game. Experiment-arm, `real` and fraction values are shown in Flagsmith ([UC-055](UC-055.md) BR-002) but changed only by their local writers; such a change made in Flagsmith is refused (A4), so a Flagsmith value never competes with an agent experiment or promotion.

### BR-004: No echo

A change is new only if it differs from the last state the flag service saw from Flagsmith for that flag and scope. A value the flag service sent itself and Flagsmith confirmed is that last state, so it is never applied a second time and never creates a new variant.

### BR-005: Flagsmith wins, kill switches tighten

When Flagsmith and the flag service disagree after both changed, the Flagsmith value wins, except for the kill switches: `agent/enabled`, `agent/interventions_allowed` and the agent-limiting flags of FR-152 and the other agent gates of flags.md §13.6 (`interventions_enabled`, `experiments_enabled`, `rollout_enabled`, `remediation_allowed`). For those the more restrictive value wins: off before on; the lower number, and a number before `inherit`; `issue` before `pr` before `autonomous`; `local` before `github`; for the other agent gates of flags.md §13.6, off before on; for `interventions_allowed` the variant whose allowed actions are contained in the other's. When neither variant's actions contain the other's, the local value stays, because it was set on stage. A deliberate change in Flagsmith, with a last state seen from Flagsmith and no local change since, is applied as any change (step 5), also when it loosens a kill switch; without a last state (after a restart, or at the first sighting of the flag) the tighten rule applies to any difference between the two values, and a persisted kill switch counts with the value of its state file as the local value; the environment ceilings of C-034 still cap the agent-limiting flags.

### BR-006: What a restart brings back

After a restart, Flagsmith brings back only values a person set in Flagsmith and the values of admin settings; Flagsmith records who made each change. A person is a Flagsmith user. Values made with any API key (the flag service's own in-memory writes from stage scripts, tests and the agent, and values made with Terraform or the Flagsmith MCP server) are cleared in Flagsmith at start, except that a kill switch follows BR-005: the more restrictive value wins even over the clear, so a kill switch tightened by an in-memory write before the restart stays tightened and is recorded as a conflict (safety over reset); an admin setting made with an API key is replaced by its persisted value (or the baseline) and that value is sent to Flagsmith, so a restart still drops every in-memory overlay (UC-053 BR-004) and a stage reset stays a reset. When the flag service cannot tell who made a value, it counts it as a person's and reports the rule as degraded, never as an API key.

### BR-007: Offline first

Flagsmith is a hosted service on the internet; the stage stack must work without it. The flag service never waits for Flagsmith: not at start, not on a write, not on a game. While Flagsmith cannot be reached the stack runs its current configuration; after a restart while offline it runs the baseline and the persisted admin settings. The flag service keeps no copy of the Flagsmith state on disk (C-030), so a value set in Flagsmith that is not an admin setting is not in force after an offline restart until Flagsmith can be reached again.

### BR-008: The stage device only connects out

The flag service reaches Flagsmith; Flagsmith never connects to the stage device. The stack needs an outbound internet link for the link to be online, and no open port (C-015, C-037).

### BR-009: Operator in-game changes

A game or player value set in Flagsmith is an in-game change by a human, allowed by C-008 under the same registry bounds as the agent's interventions. It carries the writer label `flagsmith`, so the agent never counts it as its own decision, its budget or its experiment.
