# Use Case: Manage Runtime Flags from Hosted Flagsmith

## Overview

**Use Case ID:** UC-054
**Use Case Name:** Manage Runtime Flags from Hosted Flagsmith
**Primary Actor:** Operator, Presenter
**Secondary Actors:** Flagsmith
**Goal:** Change a runtime flag in hosted Flagsmith, for the whole stack, one live game or one player of a live game, so that the stack applies it through the flag service while it is online, and keeps playing on its own while Flagsmith cannot be reached
**Trigger:** The operator or presenter changes a JoustMania flag in the hosted Flagsmith environment of the stack
**Status:** Tested
**Requirements:** [FR-206, FR-208, FR-209, FR-210, FR-211, FR-212, FR-213, FR-214, FR-215, NFR-050, NFR-057, NFR-058, C-008, C-015, C-016, C-030, C-031, C-032, C-034, C-036, C-037](../requirements.md)

Known gap (live SaaS only, non-blocking per maintainer decision D1, 2026-11-15): the link is tested against an in-process fake Flagsmith in the service tier ([TC-021](../test_cases/TC-021-operator-steers-stack-from-flagsmith.md), [TC-022](../test_cases/TC-022-flag-service-restart-with-flagsmith-link.md)) and the Go tests of `services/flag-service/flagsmith/`; edge-document identity overrides, the `__future__` feature-state API and the request limits under 8 live games are not yet checked against the hosted Flagsmith SaaS (#2592).

## Preconditions

- The flag service serves the stack's flags to flagd ([UC-053](UC-053.md)).
- The stack is linked to its own Flagsmith environment (stage, CI and dry run each have one), and the flag service holds that environment's credentials as a secret (C-016).
- Flagsmith lists the live games and their players ([UC-055](UC-055.md) A1).

## Main Success Scenario

1. The operator changes a JoustMania flag in Flagsmith: switches its stack-wide value on or off, sets a new stack-wide value, or sets a value for one live game or one player of a live game.
2. The flag service notices the change at its next look at the Flagsmith environment, at most 30 seconds later, or sooner when Flagsmith announces the change.
3. The flag service compares the Flagsmith state with the last state it saw from Flagsmith and with its own state, and recognises the change as a new change made in Flagsmith, not as an echo of a change it sent itself (BR-004).
4. The flag service checks the change like any other write: the flag is runtime-mutable, the value lies within its bounds, the scope is one Flagsmith may set (BR-003), a game or player value names a live game and a player of it (a value for a game that is not registered is neither applied nor refused: it waits and is applied once the game registers), an event's content is valid for the game (UC-053 A4), and flagd is connected (UC-053 step 3).
5. The flag service applies the change as a write with writer label `flagsmith` and pushes the new configuration to flagd (UC-053 steps 4 and 5); a value of a flag the registry marks as an admin setting is persisted like the host's own setting.
6. flagd serves the new value, and the game coordinator, the menu and the agent see it as they see any runtime change (UC-053 step 6).
7. The flag service records the applied change and marks the flag as in sync with Flagsmith; the operator sees in Flagsmith that the stack runs the value.

## Alternative Flows

### A1: Flagsmith not reachable

**Trigger:** The flag service cannot reach Flagsmith, or Flagsmith does not answer within 5 seconds (step 2)
**Flow:**

1. The flag service marks the link as offline and keeps serving the current configuration; every local write, game and kill switch keeps working (BR-007).
2. The flag service tries again with growing waits, up to 60 seconds between two tries.
3. When Flagsmith answers again, the flag service reconciles both sides (A2) and marks the link as online.
4. Use case continues at step 3.

### A2: Reconnect after local changes while offline

**Trigger:** On the first connect after a start or on a reconnect, a flag was changed locally while the link was not connected (step 3)
**Flow:**

1. Obsolete (#2621): kill switches no longer take the more restrictive value; they follow step 2 like any flag (BR-005).
2. A stack-wide value changed locally while the link was not connected (menu admin, stage script, operator write; before the first connect too) is discarded: the Flagsmith value is applied as in steps 4 to 7, also for a kill switch, and the discarded local value is recorded as a conflict with both values. It is never sent to Flagsmith. When Flagsmith holds no value for the flag, the flag goes back to the baseline, an admin setting too (its persisted value is removed from the state file) (BR-007). A value changed while the link was online whose sending had not been confirmed when the link went offline is not discarded: it is sent as in [UC-055](UC-055.md), unless Flagsmith changed that flag meanwhile (then Flagsmith wins, step 2 of A2 as a conflict).
3. A game or player value changed locally (interventions, shields, per-player values, events of a running game) is live game state and is sent to Flagsmith ([UC-055](UC-055.md)).
4. Use case continues at step 4.

### A3: Flag service starts or restarts

**Trigger:** The flag service starts (step 2)
**Flow:**

1. The flag service starts from the baseline and the persisted admin settings and serves flagd at once; it never waits for Flagsmith (BR-007).
2. If Flagsmith cannot be reached, or a start check fails (the Flagsmith project cannot hold the games' overrides because it has no edge identities, it is not the configured project, or it does not serve identity overrides in local evaluation; services.md §7.3 Start), the stack runs on the baseline and the persisted admin settings, the link stays offline (in the second case with the reason), and the use case continues as in A1.
3. Otherwise the flag service creates in Flagsmith every registry flag that is not a feature there yet (BR-002); a registry flag that cannot be created as a feature (its name differs from an existing feature only in case, the feature is archived, or Flagsmith keeps failing) is refused with a warning, and the other flags are created and the start continues.
4. Flagsmith wins at a restart (BR-006): the flag service has no last state seen from Flagsmith, so every value Flagsmith holds that differs from the local value (the baseline, or the persisted value of an admin setting) is applied as a change from Flagsmith (steps 4 to 7), whoever made it (a person in the Flagsmith UI, the flag service's own pushes of in-memory writes, Terraform, the Flagsmith MCP server); a kill switch takes the Flagsmith value like any flag (BR-005); an admin setting's Flagsmith value is applied and persisted like the host's own setting (step 5); a persisted admin value with nothing in Flagsmith is sent to Flagsmith, while a value changed before the first connect is discarded as in A2; game and player overrides are applied only when their game registers; games and players that are not live are removed from Flagsmith, but never at the moment of start: only after the game coordinator has registered its games again, or 45 seconds after the start sequence ended, whichever is later, and never a game that is registered. An event list a game's override holds is the flag service's own copy from before the restart and is not brought back.
5. Obsolete (#2621): the flag service no longer reads who made a value at start, so there is no degraded restart rule.
6. Use case continues at step 7.

### A4: Change refused by the flag service

**Trigger:** The change from Flagsmith fails a check of step 4: the flag is not runtime-mutable, the value is out of bounds, the scope is not one Flagsmith may set, the serial is not a player of the game, or an event's content is not valid (step 4)
**Flow:**

1. The flag service keeps the current value and records the rejection with its reason, like any refused write (UC-053 A5, A6).
2. When a feature-health webhook is configured, the flag service marks the feature in Flagsmith as unhealthy with the reason, so the operator sees in Flagsmith that the stack does not run that value.
3. The refusal stays until the operator changes the flag again in Flagsmith.
4. Use case ends.

### A5: flagd not connected

**Trigger:** flagd has no open sync stream when the change from Flagsmith arrives (step 4)
**Flow:**

1. The flag service does not apply the change and does not record it as seen, so it is tried again at its next look at Flagsmith.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- flagd serves the value set in Flagsmith to the readers it was set for, and to no other game or player.
- Flagsmith shows that the stack runs the value.
- The change is recorded as a sync span naming the flag, scope and writer `flagsmith`, and counted in the Flagsmith link metrics.

### Failure Postconditions

- The configuration flagd serves is unchanged, or is the value of a successful local write; a failure of Flagsmith never changes or blocks a local value.
- A kill switch is never changed by an echo; once online it takes the value Flagsmith holds, like any flag (BR-005).
- No baseline flag file has changed.
- The game keeps playing.

## Business Rules

### BR-001: Flagsmith is a writer, flagd still evaluates

The flag service treats Flagsmith as one more writer of UC-053 with the writer label `flagsmith`: every value from Flagsmith passes the mutable-flag registry, the game scope and the sync stream checks (C-032). No OpenFeature client resolves against Flagsmith; every client keeps resolving through stock flagd (C-031).

### BR-002: One feature per registry flag

Every flag of the mutable-flag registry is one Flagsmith feature, named after the flag key (keys are unique across flag sets), tagged with its flag set and described by its registry description. The flag service creates a missing one at each start. Read-only baseline flags are not features in Flagsmith.

### BR-003: What Flagsmith may set

From Flagsmith the operator may set a stack-wide value, a value for a live game, a value for a player of a live game, and an event for a live game. Experiment-arm, `real` and fraction values are shown in Flagsmith ([UC-055](UC-055.md) BR-002) but changed only by their local writers; such a change made in Flagsmith is refused (A4), so a Flagsmith value never competes with an agent experiment or promotion.

### BR-004: No echo

A change is new only if it differs from the last state the flag service saw from Flagsmith for that flag and scope. A value the flag service sent itself and Flagsmith confirmed is that last state, so it is never applied a second time and never creates a new variant.

### BR-005: Flagsmith wins a conflict

When Flagsmith and the flag service disagree after both changed since the last state seen from Flagsmith, the Flagsmith value wins, for every flag, the kill switches of flags.md §13.6 included (`agent/enabled`, `agent/interventions_allowed`, the agent-limiting flags of FR-152 and the agent gates `interventions_enabled`, `experiments_enabled`, `rollout_enabled`, `remediation_allowed`): once online, Flagsmith is the source of truth. The kill switches are applied first in a round. A deliberate change in Flagsmith is applied as any change (step 5), also when it loosens a kill switch; without a last state (after a restart) a kill switch takes the Flagsmith value like any flag (BR-006). The agent still never writes its own limits, and the environment ceilings of C-034 still cap the agent-limiting flags, also a value from Flagsmith. Decided by the maintainer 2026-11-16 (#2621), replacing the "more restrictive wins" rule of #2590.

### BR-006: What a restart brings back

At a restart Flagsmith wins: the flag service takes every value Flagsmith holds, whoever made it. Values made with any API key (the flag service's own pushes of in-memory writes from stage scripts, tests and the agent, and values made with Terraform or the Flagsmith MCP server) come back like a person's; a kill switch takes the Flagsmith value like any flag (BR-005); an admin setting takes the Flagsmith value and persists it, as for a change made while running (step 5). So a restart is no stage reset while Flagsmith is reachable: an in-memory write the flag service sent to Flagsmith before the restart is in force again after it (a reset is a change in Flagsmith, or a restart with Flagsmith unreachable, BR-007). Game and player overrides apply once their game registers (A3); event lists are one-shot payloads and are not brought back. Decided by the maintainer 2026-11-16 (#2621), replacing the restart rule by authorship of #2587.

### BR-007: Offline first

Flagsmith is a hosted service on the internet; the stage stack must work without it. The flag service never waits for Flagsmith: not at start, not on a write, not on a game. While Flagsmith cannot be reached the stack runs its current configuration and accepts every local write, so the case stays playable offline; after a restart while offline it runs the baseline and the persisted admin settings. Once Flagsmith can be reached, after a reconnect or for the first time after an offline start, Flagsmith is the source of truth: a stack-wide value changed while the link was not connected is discarded in favour of the Flagsmith value (A2); with no Flagsmith value it goes back to the baseline, an admin setting too; game and player values of running games are sent (decided by the maintainer 2026-11-16, #2621). A local write made while online is sent to Flagsmith as before, also when its sending was cut by the link going offline ([UC-055](UC-055.md)); a stack-wide value Flagsmith refuses is reverted to the Flagsmith value ([UC-055](UC-055.md) A4). The flag service keeps no copy of the Flagsmith state on disk (C-030), so a value set in Flagsmith that is not an admin setting is not in force after an offline restart until Flagsmith can be reached again.

### BR-008: The stage device only connects out

The flag service reaches Flagsmith; Flagsmith never connects to the stage device. The stack needs an outbound internet link for the link to be online, and no open port (C-015, C-037).

### BR-009: Operator in-game changes

A game or player value set in Flagsmith is an in-game change by a human, allowed by C-008 under the same registry bounds as the agent's interventions. It carries the writer label `flagsmith`, so the agent never takes it for a write of its own (its rollout stage, a promotion's real overlay).
