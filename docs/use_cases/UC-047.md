# Use Case: Calibrate the Shadow Players Offline from Real Games

## Overview

**Use Case ID:** UC-047
**Use Case Name:** Calibrate the Shadow Players Offline from Real Games
**Primary Actor:** Operator
**Secondary Actors:** Agent
**Trigger:** The operator wants the archetypes that drive shadow games ([UC-046](UC-046.md)) to move and die more like the real players, for example after a realism characterization ([UC-043](UC-043.md) A22) found them divergent
**Goal:** Fit the shadow-game archetypes to recent real games with a script over data that already exists, and propose the result as a change to the `experiment.mock_archetype` variants in a pull request that a human reviews, so that experiment verdicts ([UC-043](UC-043.md)) rest on a substrate that resembles real play (#1055, #1017, #2813)
**Status:** Implemented
**Requirements:** FR-204, FR-205 (Obsolete, #2813), C-022, C-019, C-020, C-021

Context: the first realism characterization of the stage Pi ([UC-043](UC-043.md) A22, FR-203) found shadow games matching real games on mean movement intensity, but with about 20 times less movement variance, far fewer deaths and longer games. Many real games on the Pi are test games: one person shakes a controller while the others lie still. This use case leaves those games out and refits the archetypes to the rest (maintainer idea, 2026-11-01).

Simplification (#2813, spec-simplification epic #2818): the earlier draft of this use case recalibrated automatically inside the agent every N games, validated each candidate with 72 shadow games against a holdout, and kept a per-device calibrated set with rollback and reset (C-019 amendment). Only its game journal (step 1, BR-009) and an unwired selection core were built. The calibration is now offline: the archetypes stay git-versioned in the flag files (C-019), a calibration is a reviewed flag-file change that ships with a release, and git history is the rollback. The automatic triggers, the `calibration.test_session` mark, the evidence store, the rollback and reset commands and the `substrate_calibrated` branch of the validity bar are gone; their flows and rules below are Obsolete.

## Preconditions

- **Pre-1:** Obsolete (#2813): the fit runs offline and starts no shadow game, so it needs no agent gate.
- **Pre-2:** The operator has the inputs as files: a realism dataset of the window (`scripts/agent-shadow-realism.sh --save`, [runbook](../agent-shadow-realism-runbook.md) §4), a copy of the agent's experiments directory (`AGENT_EXPERIMENT_DIR`, the experiment journals of the shadow games in that window), and optionally a copy of the game journal (BR-009).
- **Pre-3:** The flag file's `experiment.mock_archetype` variants are valid archetypes ([UC-046](UC-046.md) BR-003); they are the ones fitted.

## Main Success Scenario

1. A real game ends. The agent appends one record for the game to its game journal: the game id, mode, end time and duration, per player the inputs of BR-002, and the per-game metrics (BR-009).
2. The operator collects the inputs of Pre-2 for a window with real play and with shadow games of a running or finished experiment.
3. The operator runs `scripts/agent_archetype_fit.py --dataset <dataset> --experiments <dir>`.
4. System keeps the eligible real games (BR-002) and the usable shadow games, each labelled with its archetype (BR-010).
5. System splits the eligible real games into 3 bands by elimination pace and scales each archetype's parameter groups by the ratio of its band's median to the archetype's own shadow median (BR-005). It prints the proposal: the counts, the excluded games per reason, the band medians, and per archetype the ratios, any note and every changed value.
6. The operator runs the script again with `--write services/flagd/agent.json --write services/flagd/ci/agent.json`, which rewrites only the changed values of the variants in both flag files, and opens a pull request with the report in its body (runbook §4).
7. A human reviews the pull request and merges it. The new parameters reach a device with the next release that includes them (C-019); experiments pinned from then on use them, experiments already pinned keep theirs ([UC-046](UC-046.md) A5).
8. Use case ends.

### A10: Too few eligible real games

**Trigger:** Fewer than 24 eligible real games are in the input (step 4)
**Flow:**

### A11: An archetype has too few usable shadow games

**Trigger:** An archetype has fewer than 4 usable shadow games (BR-010) (step 5)
**Flow:**

1. System keeps that archetype's parameters and reports it as `insufficient_shadow`.
2. Use case continues at step 5 with the other archetypes.

### A12: A ratio is undefined or would leave the bounds

**Trigger:** A band median or the archetype's shadow median is 0 or missing, or a ratio would move a slot value outside the [UC-046](UC-046.md) BR-003 bounds (step 5)
**Flow:**

1. An undefined ratio is 1: the parameters of that group keep their values, and the report notes `ratio_undefined:<metric>`.
2. A ratio that would leave the bounds is reduced to the largest one that keeps every slot value inside them, and the report notes `clamped:<metric>`.
3. The new values are rounded field by field (BR-005), which can put a slot just outside a bound; the ratio is then reduced in steps of 0.01 % until every rounded value is inside the bounds, and the report notes `rounded:<metric>`. When 100 steps do not suffice, that parameter group keeps its values and the report notes `unrepresentable:<metric>`. The fitted archetype is therefore always valid.
4. Use case continues at step 5.

### A13: Real games from the game journal

**Trigger:** The window the operator needs is longer than the metrics store keeps, or the operator prefers the device's own record (step 3)
**Flow:**

1. The operator adds `--journal <copy of real_games.jsonl>`.
2. System takes the real games from the journal instead of the dataset (per player the mean intensity and the last movement variance, the values the realism dataset holds); the shadow games still come from the dataset.
3. Use case continues at step 4.

### A14: An input cannot be read

**Trigger:** The dataset, the experiments directory, the journal or a flag file is missing or not valid JSON, or a variant or value to rewrite is not found exactly once in a flag file (step 3 or 6)
**Flow:**

1. System prints the error, writes no file (with several `--write` files, none) and exits with status 2.
2. Use case ends.

### A15: The reviewer rejects or reverts a calibration

**Trigger:** The reviewer does not accept the proposal (step 7), or a merged calibration makes shadow play less realistic
**Flow:**

1. The reviewer closes the pull request, or opens a revert pull request of the merged one.
2. Use case ends. Git history is the rollback: the earlier parameters return with the next release.

## Business Rules

### BR-001: Trigger and retry - Obsolete (#2813)

Obsolete. There is no automatic trigger, so no `calibration.every_n_games` flag and no retry wait.

### BR-002: Eligible real game

A real game is eligible only when all of these hold, the reasons checked in this order, the first failing one counted:

- `other_mode`: its mode is `JoustFFA` (`FFA` in the realism dataset), the only mode pattern games run (C-021);
- `metrics_missing`: it has a finite duration and a finite elimination pace;
- `too_short`: it lasted at least 10 s (on the stage Pi the median real game lasts 16 s; shorter games are mostly false starts);
- `too_few_moved`: at least 2 players moved, a player having moved when their movement variance (the dataset's final value, the journal's `last_movement_variance`) is at least 0.005 g² (a controller lying still stays far below);
- `dominant`: no player dominates: the highest movement variance is less than 10 times the second highest (the "one person shaking a controller" test pattern).

The operator excludes a known test session by choosing the window (step 2). Agent interventions and the player count are not filtered: a real game is fitted as it was played.

### BR-003: Test session mark - Obsolete (#2813)

Obsolete. The `calibration.test_session` flag and the journal's `test_session` field are removed; BR-002 and the choice of window (step 2) leave test games out.

### BR-004: Holdout split - Obsolete (#2813)

Obsolete. Without validation games there is nothing to hold out; every eligible game is fitted.

### BR-005: Fit per band

The eligible real games are split into 3 bands by elimination pace (low, middle, high; ties in input order), the low and high band each a third of the games rounded down, the rest in the middle band. A fit needs at least 24 eligible games (3 bands of 8, A10). Each archetype has a fixed band, so its meaning does not swap between calibrations: `calm_long` and `slow_cascade` low; `close_race` and `quick_cascade` high; any other name middle. Several archetypes share a band; the fit scales each one's own parameters, so they keep their shape and stay distinct.

Fit method (one ratio step, deterministic: the same inputs give the same proposal): per metric, r is the band's median over the archetype's median in its usable shadow games (BR-010), a game's value being the mean over its players. `base` and `d_base` are multiplied by the `intensity` ratio; `amp`, `d_amp` and `burst_h` by the square root of the `movement_variance` ratio; `drift` and `d_drift` by the `elimination_pace` ratio. A parameter that is 0 stays 0. `period_s`, `phase`, `d_phase`, `burst_period_s`, `players`, `stream_rate_hz` and a `trigger_policy` keep their values, because 1 Hz gauges cannot resolve sub-second motion and near-death frequency is not measured. Undefined and out-of-bounds ratios: A12. New values are rounded to 4 decimals.

### BR-009: Game journal

Implemented (#1055 PR 1). At each real game end (`game_kind` `real`) the agent appends one record to `<AGENT_EXPERIMENT_DIR>/calibration/real_games.jsonl` on its `agent-experiments` volume ([services.md](../specs/services.md#agent)): `schema_version`, `game_id`, `mode`, `ended_at`, `duration_seconds`, `eliminations`, `history_truncated`, and per player, without a serial (C-009): the mean movement variance and the mean intensity over the game's 1 s samples up to the player's elimination (later samples are left out, as A22 leaves out dead players) with their sample counts, kept across a silence eviction ([UC-041](UC-041.md) BR-007), the last movement variance and whether the player was eliminated. `metrics` holds per-game values from the agent's game context: `intensity` and `movement_variance` (the mean over the players), `elimination_pace` (eliminations per game minute), `activity` and `change` (A22's definition, from the agent's 1 s history, which holds the last 32 s per player: `history_truncated` marks a game where they cover less than the whole game). `near_death_rate` is `null`: the agent does not ingest the coordinator's near-death counter. A metric the agent cannot measure is `null`. Records written before #2813 may hold a `test_session` field; readers ignore it.

Not journaled: shadow games, games of unknown kind, and games the agent ended on the stale `game_active` backstop ([UC-041](UC-041.md) A4: their telemetry broke). A game id is journaled once.

Bounded and durable: the journal keeps the newest 500 records; one more evicts the oldest. It outlives the metrics store's retention, which is why A13 can read it. Every append rewrites the file with a durable atomic write (temporary file, fsync, rename, fsync of the directory), from a single writer off the telemetry ingest path. Fail-soft: a failed write, a full write queue, a game end during shutdown (the writer is joined with a bounded wait) or an unreadable file at start never affects the game or the decide path; it logs `agent.calibration.journal_write_failed` (or `agent.calibration.journal_load_failed`) and counts `agent_calibration_journal_write_failures_total{reason}` ([telemetry.md](../specs/telemetry.md#6-metrics)). A record whose write failed stays in memory and is written with the next one; an unreadable file, or one holding a record with a newer `schema_version` (a downgrade), is never replaced: the journal then refuses writes. Other invalid lines are dropped on the next write.

### BR-010: Usable shadow game

A shadow game of the realism dataset is usable for archetype a only when all of these hold, else it is skipped with the reason:

- `unlabelled`: a `game_assigned` event in one of the experiment journals names the game and its archetype (one-shot shadow games are not in an experiment journal);
- `experimental_arm`: it is a `control` arm game, so the flag under test does not change how it plays;
- `unknown_archetype`: its archetype is a variant of the flag file;
- `params_changed`: the parameters its experiment pinned for a (the `pattern_pinned` event's `params_json`) equal the flag file's current variant, so the ratio measures the parameters being scaled.
