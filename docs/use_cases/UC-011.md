# Use Case: Select the Game Mode

## Overview

**Use Case ID:** UC-011
**Use Case Name:** Select the Game Mode
**Primary Actor:** Host
**Secondary Actors:** Player, Operator
**Goal:** Choose which game mode the next game uses
**Status:** Tested
**Requirements:** FR-011, FR-036, FR-037

## Preconditions

- The menu is RUNNING.
- The host uses the operator pad ([UC-015](UC-015.md)), or the dashboard / `ProcessInput` (A1), or a CONNECTED player in the lobby presses SELECT (A2). Before #2819 the main scenario was Cross in the controller admin mode ([UC-012](UC-012.md), Obsolete); the pad's K1 + knob, formerly A4, replaces it.

## Main Success Scenario

1. Host holds K1 of the operator pad and turns the knob, then releases K1 ([UC-015](UC-015.md) step 4).
2. System steps through the playable modes by the net turns (the ten implemented modes, wrapping past the last mode to the first and back; a whole number of turns of the modes selects nothing and announces nothing; UC-015 BR-005, A7, [UC-016](UC-016.md) BR-007).
3. System pulses the mode's lobby colour on every lobby controller (CONNECTED or READY) and announces the final mode name in the selected voice ([UC-015](UC-015.md) BR-015).
4. System persists the choice as the `current_game` default variant in `user.json`.
5. System publishes a `selection_changed` menu event (`source: operator_pad`); the web command of A1 also publishes `game_selection_changed`.
6. System switches the lobby colour of every CONNECTED and READY controller to the new mode's colour at once, keeping dim for connected and bright for ready (BR-005); a pulse running at the time ends on the new colour.

## Alternative Flows

### A1: Select via the web command

**Trigger:** A client calls `ProcessInput` with `web_command` `select_game` and a game name (step 1)
**Flow:**

1. System selects that mode, announces it and persists it.
2. Use case continues at step 5.

### A2: Select from the lobby with the SELECT button

**Trigger:** A CONNECTED player presses SELECT (step 1)
**Flow:**

1. System advances to the next playable mode (the ten implemented modes, wrapping around) through the same selection path as the pad: the menu's current selection (read by the game start) and the lobby game mode.
2. System persists the choice as the `current_game` default variant in `user.json`.
3. System publishes a `selection_changed` menu event with `source: controller` and the controller serial (no `game_selection_changed`).
4. System announces the mode name in the selected voice (A3 is mode-specific and moved to UC-023 and UC-026).
5. Use case continues at step 6.

### A3: Mode without voice or colour (moved)

**Trigger:** None in this use case since the FFA cluster split: the lobby announcement and colour of Zombies and NonStop are mode-specific and documented in their own use cases (Zombies UC-023, NonStop UC-026). The ID is kept so it is not reused (step 3)
**Flow:**

1. No steps: this flow moved to UC-023 and UC-026 in #1500. The ID is kept so it is not reused.
2. Use case continues at step 4.

### A4: Select with the operator pad (merged into the main scenario)

**Trigger:** None since #2819: the pad's K1 + knob is the main scenario now that the controller admin mode (Cross) is removed. The ID is kept so it is not reused (step 1)
**Flow:**

1. No steps: this flow moved into the main scenario in #2819.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- `current_game` holds the new mode; the next lobby entry (StartMenu or the `menu_auto_start` boot, UC-010 BR-003) restores it.

### Failure Postconditions

- The previous selection stays.

## Business Rules

### BR-001: Playable modes only

Commander, Ninja and Random are never offered.

### BR-002: The dashboard mode selector offers and starts playable modes only

The dashboard builds its mode selector from the menu's `ListGameModes`, so it offers exactly the playable modes of BR-001, with JoustFFA preselected (FFA alone while the menu is unreachable; the dashboard keeps retrying `ListGameModes` with backoff until it answers, #2387). Its Start Game sends `start_game` with the chosen `mode`; the menu selects that mode (as A1, without the announcement), which also persists it as `current_game` in `user.json`, and starts that mode even if the lobby selection changes while the start is pending (UC-010 A6); while a game is starting or running the start is refused with `game_active` and the mode is not selected (UC-010 A8). An unknown or unimplemented mode is rejected: `ProcessInput` answers `success=false` with the error, a `game_start_rejected` menu event is published, the selection stays and no game starts (D-M9, #1278).

### BR-003: A button handler error never drops the stream

A handler error while processing a button press is logged; it does not drop the button stream or clear the lobby's ready state (#1272).

### BR-004: Cycle order

The pad (one mode per net knob step) and SELECT in the lobby step through the playable modes in `Games` enum order (`lib/types.py`), skipping the modes of BR-001, and wrap around: JoustFFA, JoustTeams, JoustRandomTeams, Traitor, Werewolf, Zombies, Swapper, FightClub, Tournament, NonStop (`services/menu/utils/settings.py` `GAME_MODES`).

### BR-005: Every selection repaints the lobby

Every selection path (lobby SELECT, the web `select_game` / `start_game` with a mode, the operator pad) goes through the menu's single selection path (`MenuServicer.select_game_mode`), which sets the new mode's lobby colour on every CONNECTED (dim) and READY (bright) controller; IDLE controllers are not repainted (#2105). A selection that fails (unknown or unplayable mode) repaints nothing. The colour is a base colour, so a pulse running at the time (step 3, UC-015 BR-015) ends on the new colour.
