# Use Case: Reach the Stage Pi over its own Hotspot

## Overview

**Use Case ID:** UC-061
**Use Case Name:** Reach the Stage Pi over its own Hotspot
**Primary Actor:** Host
**Secondary Actors:** Operator
**Goal:** At a venue without a wired network the Host still reaches the dashboard, Jaeger, Grafana and SSH from a laptop or phone, while the hotspot never takes the place of a working wired network or a known Wi-Fi network and never slows the controllers
**Trigger:** The uplink (`eth0` by default) has no connection, at boot or later
**Status:** Implemented
**Requirements:** FR-184, FR-185 (Obsolete, #2785), FR-186 (Obsolete, #2785), FR-187 (Obsolete, #2785), FR-189 (Obsolete, #2785), NFR-008, NFR-028, C-043, C-044, C-045

Simplification (#2785, spec-simplification epic #2818): the host-OS detail of this use case (NetworkManager events and delays, the profile, the setup command and its self-test, the password handling, the status line and the ACT LED cue) moved without a behaviour change to the ops spec [stage-host.md](../specs/stage-host.md) §6, with an acceptance checklist (SH-11 to SH-16). This use case keeps its goal and the flows of FR-184 (hotspot fallback); the other flows and every rule are retired here, their ids kept, and live on in the ops spec under their former ids.

Known gap (main step 4): reaching the stack at `10.42.0.1` from a joined device is checked only on the Pi (#2088, SH-16); no automated check exists, because it needs a real access point and a joined client.

## Preconditions

- **Pre-1:** NetworkManager manages `wlan0` and the uplink, and `dnsmasq-base` is installed.
- **Pre-2:** The Wi-Fi radio can run a 5 GHz access point (country set, channel allowed, radio on, a chip with 5 GHz).
- **Pre-3:** The Operator ran the hotspot setup with a password and its forced self-test passed ([stage-host.md](../specs/stage-host.md) §6).
- **Pre-4:** UC-060 is installed; its offline start (FR-180) is what makes convention play possible. The hotspot itself does not depend on it.

## Main Success Scenario

1. The uplink loses its connection, or the Pi boots without one. System (a NetworkManager event or the timer) starts the check.
2. System waits until the uplink has not been stably connected for the up delay (20 s, 60 s while it is still connecting), and longer just after boot so that a known Wi-Fi network can connect first ([stage-host.md](../specs/stage-host.md) §6).
3. System finds no Wi-Fi client up or connecting on `wlan0` and the uplink not connected, and brings up the password-protected 5 GHz hotspot at `10.42.0.1`, with no internet sharing (C-043, C-044).
4. Host joins the hotspot and opens `http://10.42.0.1/`: the dashboard, `/jaeger/`, `/grafana/` and SSH work, offline, with the agent on the rules backend (convention play).
5. Use case ends.

## Alternative Flows

### A1: The cable returns

**Trigger:** The uplink is connected again while the hotspot is up (step 4)
**Flow:**

1. System waits until the uplink has been connected for 15 s without a break; a short connection inside a flap does not count.
2. System takes the hotspot down within the NFR-028 bound; its clients drop.
3. Use case ends. The Host switches to the LAN.

## Postconditions

### Success Postconditions

- With the uplink not connected and no Wi-Fi client on `wlan0`, the hotspot is up and the Host reaches `http://10.42.0.1/`; with the uplink stably connected, the hotspot is down.
- The status file names the state (`on`, `off`, `waiting`, `failed`, `disabled`, `not-set-up`) and its reason, with no secret.

### Failure Postconditions

- The hotspot is down, the reason is in the journal and the status file, and the game stack is unaffected.
