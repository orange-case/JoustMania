# Use Case: Run Synthetic Load with stowaway

## Overview

**Use Case ID:** UC-106
**Use Case Name:** Run Synthetic Load with stowaway
**Primary Actor:** Presenter
**Secondary Actors:** Operator, Gateway
**Goal:** Generate the synthetic load a booth challenge needs on the stage Pi, attached to the live match where it belongs, without slowing the game, reaching the agent or filling the case's own backends
**Trigger:** Presenter runs `stowaway run --challenge <name>`, or switches the `stowaway.*` flags with the `stowaway` compose service running
**Status:** Implemented
**Requirements:** [FR-285, FR-225, FR-248, NFR-062](../requirements.md)

A tool of the Orange Case (#2576, epic #2569), not a challenge of its own: it feeds UC-102, UC-103 and UC-104. `stowaway` runs on the Pi as a service of the case behind the `stowaway` compose profile and sends OTLP to the case's collector like every game service, so vendors get synthetic and real data through the same processors and the same gateway export (BR-001). It has three modes: `telemetry` (synthetic telemetry attached to the live match), `players` (drives a pattern game through the mock controllers) and `both`. Steps 1 to 6 are system behaviour that unit tests check; the Pi measurements of BR-004 are booth tasks.

## Preconditions

- The full stack runs, with the collector's synthetic routing (telemetry.md §1.1).
- `stowaway.enabled` is on ([flags.md §10](../specs/flags.md#10-observability)); it is off by default.
- For `telemetry`: a real match runs or will start. For `players`: no real match runs, and the controller manager's mock control API is up.

## Main Success Scenario

1. Presenter starts `stowaway` (the compose service, or `stowaway run --challenge span-rounds` in its container) (BR-007).
2. System reads `stowaway.enabled`, `stowaway.challenge`, `stowaway.mode` and `stowaway.intensity` at use time, at most 200 ms old (BR-003, BR-004).
3. System follows the primary game's `StreamGameEvents`; on `game_started` it takes the match from the event's `game_id` and `_traceparent` (BR-002).
4. System runs the challenge's generator in the match: one `CONSUMER` span in the match trace under the event's `_traceparent`, and the challenge's load beneath or beside it, everything marked `orangecase.synthetic=true` (BR-001, BR-006).
5. System ends the generator's span when the match ends (`game_ended`, `game_force_ended`, `game_error`), when the challenge reached its target, or when a flag stops it, with the stop reason on the span (BR-003, BR-006).
6. The collector sends the synthetic telemetry to the gateway, never to the agent, and to Jaeger and VictoriaMetrics only with `ORANGECASE_SYNTHETIC_IN_CASE=true` (BR-001).

## Alternative Flows

### A1: The kill switch is turned off

**Trigger:** `stowaway.enabled` serves `false`, cannot be read, or its flag set is not ready (step 2)
**Flow:**

1. System stops every generator within one second: no new span, data point or mock-controller game; the open span ends with `stowaway.stop_reason` = `kill_switch` (BR-003).
2. In `players`, System force-ends its own pattern game and removes its mock controllers.
3. Use case continues at step 2 once the flag is on again; nothing restarts the process.

### A2: Players mode

**Trigger:** `stowaway.mode` is `players` or `both` (step 2)
**Flow:**

1. While no real match runs, System reserves the mock controllers of the built-in pattern archetype, starts a shadow JoustFFA game through `StreamGameEvents` and lets the archetype drive it to its end (BR-005).
2. In `both`, the challenge's generator follows that game as in steps 3 to 5.
3. When a real match starts, System force-ends its own game (BR-005).
4. System removes its mock controllers and waits 10 s.
5. Use case continues at step 2.

### A3: A challenge without a generator

**Trigger:** `stowaway.challenge` or `--challenge` names `cardinality-bomb`, `hostile-wifi` or `clock-skew` (step 4)
**Flow:**

1. System logs once that the challenge is not implemented and emits nothing for it (BR-006).
2. Use case continues at step 2.

### A4: No challenge

**Trigger:** `stowaway.challenge` is `none` and no `--challenge` is given (step 2)
**Flow:**

1. System emits nothing; it keeps following the matches (and runs players mode if A2 applies).
2. Use case continues at step 2.

### A5: The challenge flag changes during a match

**Trigger:** `stowaway.challenge` serves another value while a generator runs (step 4)
**Flow:**

1. System ends the generator with `stowaway.stop_reason` = `challenge_change`; the new challenge starts at the next `game_started`.
2. The game coordinator records the flip on the match trace (UC-035 BR-018, `WATCHED_CHALLENGE_FLAGS`).
3. Use case continues at step 3.

### A6: Development against a plain OTLP endpoint

**Trigger:** Presenter runs `stowaway run --challenge <name> --endpoint <url>` off the case (step 1, BR-007)
**Flow:**

1. System sends to that endpoint instead of the case's collector. With `--no-flagd` (only with `--endpoint`) the command-line values replace the flags and Ctrl-C is the kill switch.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- Post-S-1: The match trace holds the challenge's synthetic spans as `CONSUMER` spans (and their children) of the match, each with `orangecase.synthetic=true`.
- Post-S-2: The agent received none of it, and the case's backends none with `ORANGECASE_SYNTHETIC_IN_CASE` off.

### Failure Postconditions

- Post-F-1: With the flags at their defaults `stowaway` emits nothing, even when its container runs.
- Post-F-2: The game, the agent and the case's backends are unaffected by `stowaway` stopping, crashing or hitting its caps.

## Business Rules

### BR-001: One pipe, always marked

`stowaway` sends OTLP to the case's collector (`OTEL_EXPORTER_OTLP_ENDPOINT`, compose `http://otel-collector:4317`); it has no gateway token, endpoint or exporter of its own. Its resource carries `orangecase.synthetic=true` (bool), and so does every span it attaches to a match trace. The collector's routing (telemetry.md §1.1, UC-041 BR-011) does the rest.

### BR-002: Follow the match, never the gameplay stream

`stowaway` is a consumer of `StreamGameEvents` of the primary game (an empty request), like the dashboard. A match starts for it at `game_started`, published inside the game's trace, so the event's `_traceparent` names a span of the match trace; a match it joins after `game_started` is skipped. It never subscribes to `StreamGameplayData` or `WatchGameplayData`.

### BR-003: The kill switch

`stowaway.enabled` is read at use time, at most 200 ms old, every generator tick (at most 100 ms). It fails closed: an unreadable flag, an error or a set that is not ready reads `false`. Off stops all generation within one second, without a restart.

### BR-004: Never slow the game

The compose service is behind the `stowaway` profile (off by default), with `cpus: 1.0`, `cpuset` `${STOWAWAY_CPUSET:-3}` (the last core of the Pi 5) and a 256 MiB memory limit, `oom_score_adj` +500 (expendable, NFR-081). `stowaway.intensity` multiplies each generator's rate; it is clamped to [0, 4], the ceiling in code (`INTENSITY_CEILING`) until the collector's CPU at maximum intensity is measured on the stage Pi (NFR-062). The collector's memory limiter (NFR-021) refuses data rather than growing.

### BR-005: Players only outside a real match

Players mode starts a pattern game only while the primary game is neither starting nor running (`GetGameState`), as a shadow game (origin unspecified) on reserved mock controllers tagged `stowaway`, with the built-in archetype `quick_cascade` (a copy of the `experiment.mock_archetype` variant of the same name, UC-046; `tests/contract` keeps them equal). It checks the primary game every second and force-ends its own game when a real match starts; the coordinator's shadow policy applies as for any shadow game (UC-043). The pattern game's own telemetry is the game coordinator's, not synthetic: it is the repeatable seeding game of FR-248.

### BR-006: The challenges

| Challenge | Generator |
|---|---|
| `span-rounds` | `CONSUMER` span `stowaway.padding` under the match, with `INTERNAL` children `stowaway.padding.span` until `stowaway.span_target` children were emitted (UC-103 BR-002), at the larger of 500 spans/s × intensity and the target over 100 s |
| `swing-density` | `CONSUMER` span `stowaway.swing` for the match, and the gauge `stowaway_swing_accel_magnitude{serial, game_id}` for 4 × intensity synthetic players (at least 1), a swing every 3 s, exported every 100 ms (the density of UC-102 BR-001, as load of its own: UC-102 itself adds no telemetry) |
| `cardinality-bomb`, `hostile-wifi`, `clock-skew` | selectable, not implemented: logged once, nothing emitted (#2579, #2578, #2580) |

Stop reasons (`stowaway.stop_reason`): `target`, `match_end`, `kill_switch`, `challenge_change`.

### BR-007: The command line

`stowaway run [--challenge <name>] [--mode telemetry|players|both] [--intensity <x>] [--span-target <n>] [--endpoint <url>] [--no-flagd]`. A command-line value overrides its flag; the kill switch always comes from flagd, except with `--no-flagd`, which is refused without `--endpoint`. The compose service runs `stowaway run` with the flags only.
