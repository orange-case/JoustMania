# Use Case: Force-Start a Game

## Overview

**Use Case ID:** UC-014
**Use Case Name:** Force-Start a Game
**Primary Actor:** Host
**Goal:** Start a game now, without waiting for every connected player to ready up
**Status:** Tested
**Requirements:** FR-013, FR-007

## Preconditions

- The menu is RUNNING and the operator pad is in use ([UC-015](UC-015.md) Pre-1 to Pre-3).

## Main Success Scenario

1. Host taps the game key K8 on the operator pad in the lobby ([UC-015](UC-015.md) steps 1 and 2; K1 in the first layout).
2. The pad sends `ProcessInput` `force_start` (no generation guard, [UC-015](UC-015.md) A5); the pad refuses a tap whose status shows `lifecycle_live` itself, and the menu refuses with `game_active` under [UC-015](UC-015.md) A1 (A4).
3. System builds the roster: all connected controllers if `force_all_start` is on (read now, at the force start), otherwise the ready controllers; no serial stands for the pad ([UC-015](UC-015.md) BR-008).
4. System asks the controller manager for the live roster and drops serials that are no longer connected (BR-001).
5. System publishes `game_requested` and starts the game (UC-010 from step 5).

## Alternative Flows

### A1: Released early (obsolete)

**Trigger:** None: it described the admin trigger hold (charge cancelled, white admin LED restored). The pad's force-start is a K8 tap, so no hold time applies; the pad's gesture rules decide ([UC-015](UC-015.md) BR-007, [UC-016](UC-016.md) BR-011). The ID is kept so it is not reused (step 1)
**Flow:**

1. No steps.
2. Use case ends.

### A2: Live roster unavailable

**Trigger:** GetConnectedControllers fails or does not answer within 2 s (step 4; `LIVE_ROSTER_RPC_TIMEOUT_SECONDS`, a code constant)
**Flow:**

1. System keeps the roster as is.
2. Use case continues at step 5.

### A3: Fewer players than the mode's minimum

**Trigger:** Roster has fewer controllers than the selected mode's minimum, two at least (step 5; UC-010 BR-001, BR-002)
**Flow:**

1. System publishes `game_start_cancelled`, announces "not enough players" by voice and returns to the lobby (UC-010 A3).
2. Use case ends.

### A4: A game is already starting or running

**Trigger:** The menu's game lifecycle is live when `force_start` arrives, becomes live during the live roster lookup, or a start wins the race inside the start path (step 2 or 5)
**Flow:**

1. System refuses with `game_active` and changes nothing ([UC-015](UC-015.md) A1); a start that loses the race inside the start path is refused as in UC-010 A8 (`game_start_rejected`, reason `game_active`); the live game is not cancelled.
2. System restores the menu state it held before the request (it is never left in `GAME_STARTING`, which would drop every button event).
3. Use case ends.

### A5: Force-start from the operator pad (merged into the main scenario)

**Trigger:** None: the pad's force start is the main scenario now that the controller admin mode is removed. The ID is kept so it is not reused (step 1)
**Flow:**

1. No steps: this flow moved into the main scenario.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- A real game runs with the forced roster.

### Failure Postconditions

- No game starts.

## Business Rules

### BR-001: Ghost pruning

A controller missing from the controller manager's live roster is never part of a forced roster.

### BR-002: Force-start skips the ready check, not the minimum

A force-start starts without waiting for every connected controller to be READY, but the forced roster still needs the selected mode's minimum (UC-010 BR-001): a forced Traitor game with three controllers is cancelled (A3) like a ready-path start.
