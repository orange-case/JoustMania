# Use Case: Find How Deep a Backend Shows a Trace

## Overview

**Use Case ID:** UC-103
**Use Case Name:** Find How Deep a Backend Shows a Trace
**Primary Actor:** Presenter
**Secondary Actors:** Player, Gateway, Observability Backend
**Goal:** Show, per observability backend, the largest round (10 thousand, 100 thousand or 1 million padding spans on top of the game's own spans in one game's trace) for which it still shows the whole trace
**Trigger:** Presenter starts the "How deep can you go?" booth challenge
**Status:** Draft
**Requirements:** [FR-224, FR-225, FR-246, NFR-062, NFR-029, NFR-024, NFR-003](../requirements.md)

A booth challenge of the Orange Case (epic #2569, #2574); UC-100 to UC-199 are the booth challenges, one per challenge. Each round is one game and so one trace; each round carries more spans than the last. A real game is a few thousand spans; the challenge adds one span per motion sample of each player (BR-001) and synthetic padding up to the round's target (BR-002), so the game's trace grows to a size where backends meet their per-trace limits, their sampling or the limits of their trace view. The case records how many spans it delivered in the trace (BR-003), and every enabled backend gets the same game through the gateway (FR-086). The result of a backend is the last round it showed whole; results are shown side by side, never ranked. The game's root span ends only when the game ends, so a round is judged after the game end. Steps 1 to 6 are system behaviour that tests check; steps 7 to 9 are the presenter's check at the booth, done by hand.

## Preconditions

- The full stack runs, and the gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The case's own ceiling for this stack version is measured and recorded in NFR-062 (BR-008).
- `stowaway` runs in telemetry mode behind its compose profile on the stage Pi and, for the rounds above the case's ceiling, on a laptop that sends to the gateway (BR-002).
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter sets the round's span target for the next game ([UC-053](UC-053.md)); the first round is the smallest (BR-007). Before the first round Presenter also switches on the per-sample spans, which stay on for the whole run unless A5 switches them off (BR-001).
2. Presenter starts a game ([UC-010](UC-010.md)).
3. While a player is alive, System records one span per processed motion sample of that player in the game's trace (BR-001).
4. System pads the game's trace with synthetic spans until the padding reaches the round's target or the game ends (BR-002).
5. At a normal game end, System records how many spans the case delivered in the game's trace, the game's own and the padding, on the trace and in the case's metrics (BR-003).
6. System sends the whole trace through the gateway to every enabled backend; the synthetic padding never reaches the agent (BR-004, BR-005).
7. Presenter opens the game's trace in each backend by its trace id and reads whether it opens, how many spans it shows and how long it took to show (BR-006).
8. Presenter records the backend's result for the round against the delivered count (BR-006).
9. Presenter repeats the steps with the next round's target until every backend has failed a round or the largest round is done, and shows each backend's last whole round side by side (BR-007).

## Alternative Flows

### A1: The game did not end normally

**Trigger:** The game was force-ended or failed, so no delivered count was recorded (step 5)
**Flow:**

1. Presenter does not count the game for any backend.
2. Use case continues at step 2 with a new game for the same round.

### A2: The padding falls short of the round's target

**Trigger:** The game ended before the padding reached the target, or `stowaway` stopped on its kill switch or at its CPU or memory cap (step 4)
**Flow:**

1. System records the delivered count as in step 5; the trace holds fewer spans than the round's target.
2. Presenter does not count the game for this round.
3. Presenter plays a longer game, or moves the padding to the laptop when the round is above the case's ceiling (BR-002).
4. Use case continues at step 2.

### A3: The case loses spans on its own way out

**Trigger:** The case's collector refused or dropped spans of the game, or the gateway export dropped them after its bounded retry or with a full queue (step 6)
**Flow:**

1. System keeps playing the game and keeps feeding the case's own backends and the agent unchanged (NFR-029).
2. Presenter records the round as *not delivered* for every backend, not as a backend's failure (BR-004).
3. Presenter moves the padding to the laptop for this round (BR-002).
4. Use case continues at step 2 with a new game for the same round.

### A4: A backend does not receive the game

**Trigger:** The gateway reports that it could not deliver the game's spans to a backend: the backend cannot be reached or refuses the data (step 6)
**Flow:**

1. Presenter records the backend as *not received* for the round, not as one of the results (BR-006).
2. Use case continues at step 7 for the other backends.

### A5: The game loop misses its rate

**Trigger:** With the per-sample spans on, the game loop on the stage Pi falls below its rate (step 3)
**Flow:**

1. Presenter does not count the game: the case changed the game it measures (NFR-062).
2. Presenter switches the per-sample spans off for the remaining rounds; the padding then carries the whole target.
3. Use case continues at step 2.

### A6: The presenter ends the run early

**Trigger:** The booth slot ends before every backend has failed a round or the largest round is done (step 9)
**Flow:**

1. Presenter shows for each backend still passing its last whole round with the note *not tested further*.
2. Use case ends.

## Postconditions

### Success Postconditions

- Post-S-1: Each backend that received the rounds has, next to the delivered count of each round, its result per round and its last whole round.
- Post-S-2: The games were played like any other game: the game loop held its rate and the agent took nothing from the per-sample spans or the padding (NFR-062).

### Failure Postconditions

- Post-F-1: A round the case did not deliver in full is never counted as a backend's failure (A2, A3).
- Post-F-2: Neither the game nor the case's own backends nor the agent were affected by a backend or the gateway failing (NFR-029).
- Post-F-3: With the challenge flags at their defaults, the case sends no per-sample span and no padding.

## Business Rules

### BR-001: One span per motion sample, only when switched on

With the flag `telemetry.per_sample_spans` on, the game coordinator records one span per processed motion sample of each alive player, a child of the player's span, with the sample's acceleration magnitude, the death threshold, the player and the game. At 60 Hz that is 60 spans per second per player: 8 players over 2 minutes are about 58 thousand spans. The flag is read once per game, off by default; off, the trace is that of a game without the challenge. The agent never receives these spans (BR-005). With them on, a round's trace holds its padding plus the game's own spans: about 70 thousand spans in the first round for 8 players over 2 minutes.

### BR-002: The padding fills the trace up to the round's target

`stowaway` in telemetry mode follows the live game through the game events and attaches synthetic spans to the game's trace, under one padding span that is a child of the game's root, until it has delivered the round's target or the game ends. The padding is the target itself, not the target minus the game's own spans, so the trace always holds at least the target. Every synthetic span carries `orangecase.synthetic=true`. Up to the case's measured ceiling (NFR-062) the padding runs on the stage Pi and goes through the case's collector; above it, `stowaway` runs on a laptop, follows the same game and sends the padding to the gateway, which the round's record names.

### BR-003: The delivered count is the reference

The reference is the number of spans of the game's trace that the case delivered: the spans the game coordinator exported and the padding `stowaway` exported, each counted by its producer after a successful export, so a span dropped inside a producer is not counted. Each producer records its count after the game end, on the trace and as a metric per game in the case's VictoriaMetrics, and the case dashboard shows both counts and their sum per round. The other spans in the game's trace are not counted: the agent's (its decisions, the summary and the retro), the audio service's and the controller manager's. So a backend is compared per producer, by service: the game coordinator's spans against its count, `stowaway`'s against the padding count (BR-006). A game that was not ended normally has no delivered count (A1).

### BR-004: The gateway gets the whole trace

The gateway's traces pipeline takes the same spans as the in-case pipeline, with the same processors; neither samples nor filters the game's spans (FR-086). Spans the case's collector refused or dropped, or the gateway export dropped (its bounded retry and queue, NFR-029), are the case's loss: the collector's own counters for the game's time show it, and the round is *not delivered* (A3).

### BR-005: The agent and the case's own backends are protected

The synthetic padding goes to the gateway only, never to the agent; the case's Jaeger gets it only when a flag allows it (#2577). The per-sample spans go to the case's Jaeger and the gateway, never to the agent. Today the collector's one traces pipeline sends every span to both Jaeger and the agent, so this needs a planned collector route with #2574: the agent's copy of the traces drops the per-sample spans by their span name before its exporter, while the Jaeger and gateway copies keep them. Without that route the challenge does not run, because about 60 spans per second per player would crowd the agent's bounded queue (NFR-024) and push out the game spans it reads. Neither flag changes the game loop's work beyond recording the per-sample spans (NFR-062).

### BR-006: A backend's result for a round

The presenter opens the trace by its trace id in the backend's own trace view, first 2 minutes after the game end and once more 10 minutes after it, and keeps the better result.

| Result | Meaning |
|---|---|
| whole | The trace opens within 60 s of the request and shows, for the game coordinator and for `stowaway` each, at least the producer's delivered count of spans (BR-003) |
| partial | The trace opens and shows fewer spans of either producer than its delivered count: record the counts it shows |
| too slow | The trace has not opened 60 s after the request |
| not found | The backend finds no trace with that id |

A backend that shows only the trace's total span count, not a count per service, is judged on the total minus every span of that trace whose service is neither the game coordinator nor `stowaway` (the agent, the audio service, the controller manager), counted per service in the case's Jaeger; its result carries the note *total only*. A backend that did not receive the round is *not received* (A4), and a round the case did not deliver is *not delivered* (A3); neither is a result. A backend passes a round only with *whole*.

### BR-007: The rounds

The rounds are 10 thousand, 100 thousand and 1 million spans of padding, the variants of the span-target flag, played smallest first. A backend's result is the largest round it showed *whole*, or *none* when it failed the first. A backend that fails a round is not tested at larger rounds. There is no score and no order.

### BR-008: The case's ceiling is measured before the booth

Before the booth, once per stack version on the stage Pi, the maintainer runs the rounds with the padding on the Pi in the booth's setup: the gateway export on, to a gateway or a test sink that accepts everything, and the synthetic-telemetry flag of #2577 as at the booth (padding to the gateway only, not into the case's Jaeger), so the Pi carries the same load as at the booth. The maintainer records in NFR-062 the largest round for which the game loop held its rate with 0 dropped frames, the case's collector refused and dropped no span, and the delivered count reached the target. Rounds above that ceiling take their padding from the laptop (BR-002). A stack without a recorded ceiling for its version does not run the challenge.
