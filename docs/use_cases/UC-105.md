# Use Case: Find What the Game Master Cost

## Overview

**Use Case ID:** UC-105
**Use Case Name:** Find What the Game Master Cost
**Primary Actor:** Presenter
**Secondary Actors:** Player, Agent, Model API, Gateway, Observability Backend
**Goal:** Show, per observability backend, how far down it can answer what the agent's model calls cost, from the total spend to the spend per decision, checked against the tokens the case recorded and a published price table
**Trigger:** Presenter starts the "What did the game master cost?" booth challenge
**Status:** Implemented
**Requirements:** [FR-249, NFR-029](../requirements.md)

A booth challenge of the Orange Case (#2718); UC-100 to UC-199 are the booth challenges, one per challenge. The agent, the game master, calls a model to decide in a game, to review a game after it ends (the retro) and to propose experiments (the proposer). Each call records its tokens on its span, and the agent's token metrics count them too ([telemetry.md §4.2](../specs/telemetry.md#42-genai-semantic-conventions)). The OTel GenAI conventions define no cost attribute, so turning tokens into money is each backend's own work, and that difference is what the challenge shows. Every enabled backend gets the same games through the gateway (FR-086) and the same questions, from coarse to fine; the case's own spans give the token reference and a published price table frozen on a date gives the money reference. The results are shown side by side, never ranked. Steps 1 and 2 are system behaviour that tests check; steps 3 to 6 are the presenter's check at the booth, done by hand. The guide, with the questions, the price table and the reference queries, is [what-did-the-game-master-cost.md](../challenges/what-did-the-game-master-cost.md); `scripts/genai_cost_reference.py` computes the reference of step 3. No backend has been run yet (#2718).

## Preconditions

- The full stack runs, and the gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The agent is on with interventions allowed and decides through a model backend in real games (`decision.backend` serves `claude`, `llm.eligible_game_kinds` includes `real`).
- The retro and the proposer call a model: `inference.backend` serves `claude` and the agent has its model key (otherwise the stub answers and records no usage).
- The agent's spans follow the OTel GenAI agent conventions (#2584).
- The questions, the price table with its date and the reference queries are published (FR-249).

## Main Success Scenario

1. Presenter plays the challenge games ([UC-010](UC-010.md)) and, between two of them, switches the decide backend once ([UC-044](UC-044.md)), and notes each game's id and the time of the switch (BR-001).
2. System records the usage of each model call of the agent on its spans and in the agent's usage metrics, and sends them through the gateway to every enabled backend, like any other telemetry (BR-002).
3. Presenter reads the reference usage per game, caller and model from the case's own spans and turns them into money with the published price table (BR-003).
4. Presenter asks each backend the published questions in order, from the total spend down to the spend per decision, the pricing detail and the switch (BR-004).
5. Presenter checks each answer, usage first, then money, against the reference (BR-005).
6. Presenter records for each backend the answer to each question and how far down it got, and shows the results of all backends side by side (BR-006).

## Alternative Flows

### A1: A game has no model call

**Trigger:** The agent made no model call in a game: it decided on the rules path only, a model call was gated by budget or interval, or the model backend was unavailable (step 2)
**Flow:**

1. Presenter does not use the game for the per-game questions; it has no spend.
2. Use case continues at step 1 with a new game.

### A2: A backend does not receive the games

**Trigger:** The gateway or a backend cannot be reached, refuses the data, or drops it after the gateway export's bounded retry or with a full queue (step 2)
**Flow:**

1. System keeps playing the games and keeps feeding the case's own backends and the agent unchanged (NFR-029).
2. Presenter records the backend as *not received*, not as one of the results (BR-006).
3. Use case continues at step 3 for the other backends.

### A3: The case's reference does not add up

**Trigger:** For a game, the token totals on the agent's decide spans differ from the sum of their model calls, or the game's spans have left the case's Jaeger (step 3)
**Flow:**

1. Presenter does not use the game for the per-game and per-decision questions.
2. Use case continues at step 3 with the next game; with no game left it continues at step 1.

### A4: A backend answers in usage only

**Trigger:** The backend shows the usage of a question but no money (step 5)
**Flow:**

1. Presenter checks the usage and records the money of that question as *usage only* (BR-005).
2. Use case continues at step 5 with the next question.

## Postconditions

### Success Postconditions

- Post-S-1: Each backend that received the games has an answer to each question, *matches*, *differs*, *usage only* or *cannot answer*, and the last question it answered in order, all with the date of the price table.
- Post-S-2: The games were played like any other game; the challenge added no model call and no telemetry (BR-007).

### Failure Postconditions

- Post-F-1: An answer is never checked against a game whose reference did not add up (A3).
- Post-F-2: A backend that did not receive the games is never given a result (A2).
- Post-F-3: Neither the games nor the case's own backends nor the agent were affected by a backend or the gateway failing (NFR-029).

## Business Rules

### BR-001: The challenge games

At least two real games end normally with model decisions in each, one before and one after the switch of the decide backend, so that question 6 has a step to find. Every game ends with a retro. Shadow games and the proposer's calls count when they run in the same time (experiments on); they are not required. Shadow games get model decisions only when `llm.eligible_game_kinds` includes `shadow` (the default is `real` only); otherwise the shadow half of question 2 has a reference of zero, and the presenter says so with the question. Jev, when it decides, charges no tokens and is priced at zero, with the note *compute, not priced*.

### BR-002: What the case sends

The challenge uses the telemetry the agent sends in every game ([telemetry.md §4.2](../specs/telemetry.md#42-genai-semantic-conventions)):

- each model call's span with its provider, requested and answering model, and its tokens: input, output, cache read, cache write and reasoning;
- the decide span with the totals of its model calls and the game id as its conversation id; the retro's model call also carries the game id; the proposer's calls carry none;
- the token metrics by provider, model and token type, with no game id, so a backend that prices only from metrics cannot answer per game; their instrumentation scope tells the decide backends apart from the offline calls, but one scope covers both the retro and the proposer, so metrics alone cannot split those two (question 2).

### BR-003: The reference

The token reference is read from the case's own Jaeger, never from a backend, with the counting rules of [telemetry.md §4.2](../specs/telemetry.md#42-genai-semantic-conventions): per game, the sum over the spans with the game's id as conversation id (its decide spans and its retro's model call); per decision, the decide span's totals; per caller, decide, retro and proposer by the model call's parent. For questions 1, 2 and 6 the reference covers every model call of the agent in the challenge window, from the start of the first challenge game to the end of the last game's retro, whatever game it belongs to: the decide spans' totals plus the retro's and the proposer's model calls, by the answering model and provider; the proposer's calls, which carry no game id, count only here. Real against shadow games is told apart by the kind of the game the conversation id names, on that game's root span; a call without a game id is neither. A decide span and its model calls are never both counted. The money reference is those tokens times the published price table, frozen on a date: per model, a price for input, output, cache read and cache write tokens; cached input at the cache price and the rest of the input at the input price, reasoning within output, by the answering model.

### BR-004: The questions

| # | Question |
|---|---|
| 1 | What is the total spend, per provider and model? |
| 2 | What is the spend per caller: decide, retro, proposer; and real games against shadow games? |
| 3 | What did each of the challenge games cost? |
| 4 | What did each decision cost, what did the interventions that changed the game cost, and what did the decisions cost that were held or blocked and had no effect? |
| 5 | Are cache and reasoning tokens priced apart; is the price that of the answering model or the requested one; do refused, cut-off and failed calls count? |
| 6 | Does the spend change at the switch of step 1, and does the backend show the switch next to the change? |

The questions are asked in this order, each with the game ids and the time window of the challenge.

The reference for the subsets of question 4 comes from the agent's decision spans in the case's Jaeger, each priced by the decide span it came from (one decide span can hold several decisions; its cost is counted once per subset it falls into):

- *changed the game*: a decision whose intervention was applied (`decision.applied` true), the entries of the game's intervention ground truth ([UC-101](UC-101.md) BR-006);
- *held*: a remote answer below the act threshold, whose decide span carries the event `gen_ai.evaluation.result` with the label `fail`;
- *blocked*: a decision a gate refused (`decision.blocked` true).

### BR-005: Checking an answer

| Answer | Meaning |
|---|---|
| matches | the tokens equal the reference, and the money is within 5 % of the reference |
| differs | the tokens or the money is off: record the backend's number and, when known, why (for example, a decide span counted with its model calls, or its own price list) |
| usage only | the tokens match, but the backend shows no money (A4) |
| cannot answer | the backend cannot show the tokens or the money of the question |

Question 5 is answered by what the backend shows or documents; question 6 *matches* when the backend shows the step at the switch's time, and the presenter notes whether it shows the switch itself. A span event at the moment of a flag change is #2572 (open).

### BR-006: How far down a backend got

A backend's result is its answer to each question and the last question it answered with *matches* while every question before it was answered with *matches* or *usage only*. A backend that did not receive the games is *not received* (A2), not a result. There is no score and no order.

### BR-007: The challenge adds nothing

The challenge makes no model call of its own and adds no telemetry: the spend is what the agent spends in the games anyway. The stretch ideas of #2718 (a deliberate cost spike, the cost of the GenAI telemetry itself, the cost of the backend's own assistant, local model compute) are not part of this use case.
