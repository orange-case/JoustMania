# Use Case: Play Joust Free-for-All

## Overview

**Use Case ID:** UC-020
**Use Case Name:** Play Joust Free-for-All
**Primary Actor:** Player
**Goal:** Be the last player standing
**Status:** Tested
**Requirements:** FR-014, FR-020, FR-027, FR-030, FR-032, FR-033, FR-035, FR-036

This use case is Free-for-All and also the **base game lifecycle** of every game mode (BR-005 to BR-009, A2, A4, A5): UC-021 to UC-026 state only their delta from it.

## Preconditions

- A JoustFFA game was started with at least two players (UC-010).

## Main Success Scenario

1. System assigns every player to team 0, publishes `players_initialized` and gives each player a unique colour in the `color_assignment` phase (shown when the gameplay stream starts).
2. System starts the game music at `audio_volume.countdown_music`, publishes `game_started`, plays the countdown (UC-010 step 6) and then raises the music to the game volume.
3. Players try to jostle each other's controllers while keeping their own still.
4. System alternates the tempo intensity between normal-speed (1.0×) and 1.3× windows (UC-031 step 3): the intensity ramps slowly between them, the thresholds follow it every frame and the music follows it.
5. System eliminates any player whose movement exceeds the threshold (UC-030) and publishes `player_death` with the serial and the number of players left.
6. When one player is left, System publishes `game_winner` with the serial, shows a rainbow on the winner for `winner_rainbow_duration_ms` (default 3 s, played in full, BR-004) and plays "congratulations".
7. System publishes `player_analytics` for each player (when `analytics.enabled` is on) and `game_ended` with the duration.

## Alternative Flows

### A1: Tie

**Trigger:** No player is left at a win check, which happens only when an agent elimination (UC-040, `eliminate_player`) and another death fall between two win checks (step 6)
**Flow:**

1. System publishes `game_tie` instead of `game_winner`; no rainbow is shown.
2. Use case continues at step 7.

### A2: Player disconnects

**Trigger:** A controller disconnects during the game (step 3), including during the countdown or the EMA warmup; such a disconnect is handled before the first gameplay frame. A controller that stays connected but sends no report for `silent_disconnect_seconds` (default 3 s, out of range) is a disconnect too (UC-002 BR-007); if it comes back during the game it shows the out state, not its game colour (UC-002 BR-008)
**Flow:**

1. System eliminates the player through the normal death path (`player_death`, explosion, death effect; no motion involved) and checks the win condition at once (BR-001).
2. Use case continues at step 6 when one player is left, otherwise at step 3.

### A3: Agent intervention

**Trigger:** The agent applies an intervention (UC-040) (step 3)
**Flow:**

1. System applies it through the game's own code paths (e.g. tempo change, shield, elimination) and publishes `agent_intervention`. In trigger mode (Free-for-All only, `shield.activation`) a shield is a charge the player activates with the trigger (UC-048 A3, UC-030 A6). `revive_player` is denied in FFA by the coordinator's mode capability matrix (`mode_unsupported`).
2. Use case continues at step 3.

### A4: Force-ended

**Trigger:** The game is force-ended (UC-027: operator Stop, `ForceEndGame`, agent `end_game`, a real game preempting a shadow game) while the game loop still runs, whatever the alive count (step 3)
**Flow:**

1. System stops the game loop without a winner: no `game_winner`, no rainbow, no "congratulations". A force-end before the game has started (during colour assignment or the instruction wait) skips the start (no `game_started`, countdown, stream or music) and ends with exactly one `game_ended`, outcome `force_ended`.
2. System records outcome `force_ended` with the force-end reason (BR-003). Every survivor's span gets `player_survived`, not `victory`, and no player has `winner = true`.
3. System publishes `player_analytics` for each player and `game_ended` with the duration, `outcome = force_ended` and the reason, then `game_force_ended` (UC-027 step 3).
4. Use case ends.

### A5: Instructions on

**Trigger:** The host has switched spoken instructions on (`game_instructions`, user set; FR-014, the pad's K6, UC-015 BR-011) when the game starts, after colour assignment and before the music and the countdown (step 2)
**Flow:**

1. System reads `game_instructions` at game start (use time, not cached). When it is off, or cannot be read, or the game is a shadow game (no audience), the main scenario runs unchanged: no clip, no wait.
2. System plays the mode's instruction clip (JoustFFA: `FFA-instructions`; every other mode names its clip in its delta table, BR-005, and its own "Instructions on" flow: UC-021 A3, UC-022 A3, UC-023 A2, UC-024 A2, UC-025 A5, UC-026 A3) before it starts the game music, and waits until the clip has finished: it waits for the clip length the audio service reports in `PlaySoundResponse.duration_seconds`, capped at 60 s. A clip that is not heard (`play_audio` off, audio hardware not open, file missing) reports 0 s, so the game does not wait. During the wait the controllers show that the game is starting, for players who cannot hear the clip in a loud venue: the gameplay stream is open (a mode without a streamed intro opens it when the clip starts, so the controllers take their player colours at once) and drained (frames discarded, disconnects kept), and every player's controller pulses slowly in its colour (`GAME_EFFECT_PULSE`, 1 Hz) for the length of the wait; the countdown then follows on the same stream. Opening the stream for the clip is best effort: a failure is logged, and the stream opens after the clip as without instructions. A force-end during the wait stops it at once, and the game does not start: no music, no `game_started`, no `countdown_start`; the game ends as in A4 steps 2 to 4 (`outcome = force_ended`, BR-003), and the gameplay stream is released when the game ends. The system also sends the audio service `StopSound` (best effort and bounded to 2 s: a failure or timeout is logged and never blocks the end), so the clip does not keep playing after the game has ended. A mode that opens the gameplay stream before the clip (its delta table says "streamed intro": Random Teams, Traitor, Werewolf, Zombies, Tournament, Fight Club) plays the clip after its intro phase, on the stream its intro opened. In the modes with their own `run()` (Werewolf, Zombies, Tournament, Fight Club) a force-end during the intro phase also skips the clip.
3. System records `game.instructions` on `game.phase.initialization` (`played`, `off`, `shadow`, `no_audio` when there is no audio client, `failed` when `PlaySound` fails, or `no_clip` for a mode without a clip: only Non-Stop Joust, which has no recording (UC-026 A3), records `no_clip` and does not wait; only `played` waits) and, when played, a `game.instructions_played` event with the clip and its length (telemetry.md §3.2).
4. Use case continues at step 2.

## Postconditions

### Success Postconditions

- The game session is ENDED, the outcome (`winner`, `tie` or `force_ended`, BR-003) and the winner, if any, are in the event stream, and the lobby is restored.

### Failure Postconditions

- On an internal error, System publishes `game_error` once (the game for a base-run mode, else the session) and ends the session. A base-run mode (Free-for-All, Teams, Random Teams, Swapper, Traitor, NonStop) also stops the game music and ends every running shield effect (UC-048 A2) on that path, and when the game task is cancelled; the modes with their own `run()` (Fight Club, Tournament, Werewolf, Zombie) do the same in their `finally`.

## Business Rules

### BR-001: Win condition

The game ends when at most one player is alive; win detection runs after every controller sample of a frame and after every disconnect, so the last player standing can never die through motion.

### BR-002: Grace period

`death_grace_period_seconds` has no effect in FFA (no respawn).

### BR-003: End-of-game outcome

Every JoustFFA game ends with exactly one outcome:

| Outcome | When | Recorded |
|---|---|---|
| `winner` | the loop ended on BR-001 with one player alive | `game_winner` (serial); `victory` with `winner = true` on the winner's span only |
| `tie` | the loop ended on BR-001 with no player alive (A1) | `game_tie`; no `victory` event |
| `force_ended` | the game was force-ended (A4), whatever the alive count | the force-end reason; `player_survived` on each survivor's span; no `victory`, no winner |

`force_ended` takes precedence while the game loop runs: a force-end that lands while one player is left but before the loop ended still records `force_ended`, because the game did not reach its win condition. The outcome is latched when the loop ends (win condition met, or loop stopped): a force-end that arrives afterwards (during the post-win hold, the winner rainbow or teardown, e.g. `preempted_by_real_game`) stops the effects early but does not change a `winner` or `tie` outcome. Neither does a gameplay stream the controller manager has ended after the win: the winner rainbow is skipped with a warning and the game ends with its `winner` outcome, not `game_error` (UC-030 BR-006). The result is latched once, in the same win check that decides it (BR-001) and before `game_winner` or `game_tie` is published, together with the root-span outcome; the root-span outcome is latched first, so a force-end that lands before it (also while the last kill awaits its explosion or the end of a shield charge) latches `force_ended` and nothing is published, and a later win check does not publish the result again. Once the outcome is latched no kill is taken (UC-030 step 9): an `eliminate_player` of the winner during the post-win hold or teardown is refused (`eliminate_refused`, UC-040 A22), and it, like a disconnect then, records no death, `player_death` event or death effect, so the winner stays alive. Once the game is force-ended no kill is taken either, in any mode, also for the controllers later in the frame the force-end landed in and for a kill awaiting its explosion: they count no death, `player_death` event, death effect or score (UC-030 step 9). The force-end is applied on the game's own loop, so it never lands between a kill's gate check and its count: a kill counted before it, or is declined (UC-027 step 3). The 1 s post-win hold follows a latched outcome only: a loop that ends on a mode error kept for `run()` (a Tournament bracket step, UC-025) latches none and ends at once with `game_error`. The outcome is on the game root span (`game.outcome`, `game.end_reason` for `force_ended`, `game.winner` for `winner`), on a `game.outcome` event of `game.phase.teardown`, in the `game_ended` event (`outcome`, `reason`) (telemetry.md §3.2, §5), and as the `outcome` label of `game_completed_total` (telemetry.md §6, shown by the Game & Players dashboard's "Games by Outcome" panel). The label has five bounded values: these outcomes, `completed` (also for an unknown or unreadable outcome) and `error` for a session that published `game_error` (gRPC clients not initialized, mode creation failed, or the game loop raised: a gameplay stream still failing after three reconnects, or at once an error while a frame is processed, UC-030 BR-006), so a failed start never shares a slice with a natural end.

After the latch the game stays active for a post-win hold of 1 s (`_hold_win_display`) so the winner shows; a mode that ends its loop on an error latches no outcome and has no hold. UC-023 step 3 relies on this 1 s.

Other modes: the latch, the force-end precedence, the no-kill-after-force-end rule, the root-span and `game_ended` recording and the `game_completed_total` label apply to every mode (BR-007); the outcome values of the other modes are in BR-006, and their result events in their delta tables (BR-005).

### BR-004: The winner rainbow plays in full

From the latched win (BR-003) until the rainbow ends, the winner's LED belongs to the rainbow:

- The game coordinator sends no agent cue once the game is ending (outcome latched, force-ended, or ENDING / ENDED): neither the "agent acted" pulse of an applied HARD-class intervention (UC-040 step 13) nor the shield help cue (a `grant_shield` is refused `game_ending`, UC-048 A12 step 3).
- The controller manager never lets a `GAME_EFFECT_PULSE`, `GAME_EFFECT_FLASH` or `GAME_EFFECT_SHOW_BATTERY` take over a running `WINNER_RAINBOW` on the same controller: the overlay is skipped and the rainbow plays to its end, then the base colour is restored. A lifecycle effect (death, warning) still takes over, and an overlay after the rainbow plays as usual.
- The rainbow is not lost behind a death: the controller manager applies the game's commands without waiting on an effect hold (the loser's death red hold no longer delays the winner's rainbow), and when the game closes its gameplay stream, the commands the controller manager has already received, the rainbow included, are still applied ([services.md](../specs/services.md) controller-manager notes). A starting rainbow owns the LED from the moment it is sent, so a pulse or flash from the other stream that lands while the replaced effect ends yields to it too.
- The game-end shield cleanup stays as before: `SHIELD` 0 to every player with a shield or hold command, before the rainbow, ends every layer, hold rumble and cue on every controller (UC-048 A11, BR-010).

Seen on the Pi (0.13.0, hold mode): a player held the trigger past empty and died, and the other player's rainbow was not visible. The controller manager received and started the rainbow (its `controller.effect.winner_rainbow` span, 3000 ms), and neither reported game had an agent cue in the end window, so the observed cause is still open (suspects: Bluetooth LED write stalls on the winner's controller or a re-registration during the rainbow). This rule is a defensive fix: a short overlay landing during the rainbow, such as the agent cue that every applied HARD-class intervention sends to each alive player, is a possible path that removes a running rainbow, and it is closed here.

### BR-005: Base game lifecycle and the mode delta

Every game mode (UC-020 to UC-026) runs this base lifecycle. A mode use case states only its delta, in one "Delta from the base lifecycle" rule with a table of the same rows as below, plus the flows and rules that exist only in that mode:

| Row | Free-for-All (this use case) |
|---|---|
| Win condition | at most one player alive (BR-001) |
| Teams | none: every player on team 0, one colour each |
| Thresholds | the tempo-driven thresholds (UC-030, UC-031) |
| Start cues | colour assignment, countdown (UC-010 step 6), game music |
| Result event and end cues | `game_winner` + winner rainbow + "congratulations" (BR-004); `game_tie` (A1) |
| No-winner value in `game_ended` | no `winner` field: the outcome is `tie` or `force_ended` (BR-003) |
| Instruction clip (A5) | `FFA-instructions` |
| Streamed intro (A5) | no |
| `run()` | base |
| Mode grace (BR-009) | none |
| Eliminations (BR-008) | every death |

The parts every mode shares, written once here:

- **Start.** Spoken instructions (A5), the countdown (UC-010 step 6), the EMA warm-up of the startup guard (UC-030 BR-003) and the game's flag evaluation context. A mode with its own `run()` (Werewolf, Zombies, Tournament, Fight Club) starts like the base `run()`: it publishes `game_starting`, refuses fewer than two players with `ValueError` before the gameplay stream opens (the session publishes `game_error`, UC-010 BR-001), sets the flag evaluation context and runs the EMA warm-up after the countdown (D-G3).
- **Disconnect.** A disconnect goes through the normal death path (A2); what that death means for the player is the mode's (BR-008).
- **Force-end.** A4 and BR-007.
- **Outcome.** BR-003 (FFA) and BR-006 (every mode).
- **Grace.** BR-009.
- **Failure.** The failure postcondition: `game_error` once, the game music stopped and every shield effect ended, the run-end cleanup on every exit.

### BR-006: Root-span outcome in every mode

Every game records exactly one outcome on its root span as in BR-003 (`game.outcome`, `game.end_reason` for `force_ended`; the `game.outcome` event of `game.phase.teardown`, the `game_ended` event and the `game_completed_total` label; telemetry.md §3.2, §5, §6). Free-for-All records `winner`, `tie` or `force_ended` (BR-003); every other mode records `completed` for a natural end (a winner, a tie or no winner) or `force_ended` with the force-end reason. This holds for the modes on the base `run()` (Free-for-All, Teams, Random Teams, Traitor, Swapper, Non-Stop Joust) and for those with their own `run()` (Werewolf, Zombies, Tournament, Fight Club, which play on the base game loop). A force-end after the outcome is latched (BR-007) or after the loop ended does not rewrite it.

### BR-007: Force-end declares no winner; the result is latched

In every mode:

- A force-end (UC-027) while the game runs declares no winner: no result event, no winner rainbow, no win voice and no rainbow wait; the surviving player spans (and team spans) end without a win (`winner=false`, Tournament `is_champion=false`), and `game_ended` carries the mode's no-winner value with `outcome` `force_ended` and `reason`. The result event and the no-winner value of each mode are in its delta table.
- The result (a winner, or a tie or no-winner result where the mode has one) is latched once, in the same synchronous step that decides it, before its result event is published, together with the root-span outcome (BR-006). The root-span outcome is latched first: a force-end that lands before it (also after the win check started) latches `force_ended` and no result, so nothing is published, even when the win condition is met. A force-end that lands afterwards (the same tick, the publish, the post-win hold, the rainbow or the teardown) keeps the result, its end-of-game effects and its outcome, and a later win check publishes nothing again.
- Once the game is force-ended or the result is latched, no kill is taken (UC-030 step 9; BR-003).
- In the modes other than Free-for-All, a gameplay stream that ends before a result ends the game with the no-winner value, `outcome` `completed` and no winner effects (Free-for-All: BR-003).

Where the step that decides the result is mode-specific (Zombies' win-check precedence, Swapper's frozen winners, the 1v1 decision paths, Non-Stop's time limit), the mode's own rule says so and refers here.

### BR-008: Only an elimination is an elimination

In every mode a death is an elimination only when it takes the player out of the game for good ([UC-041](UC-041.md) BR-008): the player's `game_player_elimination_order` is recorded once and its `player_death` carries `death.eliminated` true. A death the player comes back from (the mode's delta table: a Zombies conversion or zombie death, a Swapper swap, a Fight Club round loss, a Non-Stop respawn death) sets no elimination order and its `player_death` carries `death.eliminated` false, so the agent's elimination sequence and elimination fraction leave it out; the death is still counted (`dead_count`, `game_player_deaths_total`). A player taken out without a death (a Tournament match lost on time, UC-025 A1) gets its order with no `player_death`. No order is recorded once the game no longer takes kills (BR-007).

### BR-009: Grace

A player cannot die through motion while in grace: until `effective_grace_until`, the maximum of `grace_until` and, in Tournament and Fight Club, the match or round invincibility `invincible_until` (UC-025 BR-001), so neither shortens the other. Two sources only ever extend `grace_until`: the 0.3 s start grace of the game loop takes the maximum with a longer grace already granted, such as an agent shield (UC-030 BR-003, FR-033), and an agent shield (UC-040) extends and never shortens it. The mode's own grace after a death, from its delta table (the conversion and respawn grace of Zombies and the swap grace of Swapper, both `death_grace_period_seconds`), sets `grace_until` to now plus that period and so replaces the current grace, also a longer one. Non-Stop's spawn protection runs on its own deadline (UC-026 step 2). Grace stops motion deaths only: an agent `eliminate_player` still kills a player in grace or with a shield (UC-040). Free-for-All has no mode grace (BR-002).
