# Use Case: Observe the System

## Overview

**Use Case ID:** UC-035
**Use Case Name:** Observe the System
**Primary Actor:** Operator, Presenter
**Goal:** See what the game, the controllers and the agent are doing, from one URL
**Trigger:** An operator or the presenter opens `http://<host>/` in a browser (the stack's single entry point, BR-001)
**Status:** Tested
**Requirements:** FR-043, FR-059, FR-080, FR-081, FR-084, FR-085, FR-086, FR-103, FR-122, FR-255, NFR-002, NFR-003, NFR-021, NFR-022, NFR-023, NFR-024, NFR-029, C-014, C-015, C-016
**Planned:** FR-161 (#2096, In Progress: the hold-mode energy bar, BR-008, is implemented; FR-161 stays here, not under Requirements, until its other PRs of #2096 land, because a Tested use case would derive it Tested)

## Preconditions

- The full stack runs (not the lite stack, which has no Jaeger, VictoriaMetrics or Grafana).

## Main Success Scenario

1. System (envoy on port 80) serves the dashboard and, under the same host, Jaeger (`/jaeger/`), Grafana (`/grafana/`), VictoriaMetrics (`/victoria-metrics/`), the agent's experiment dossier (`/experiments`) and its read-only live state (`/experiments/state`, BR-011) and the browser API, which connect-proxy translates to the services' gRPC calls (C-014, BR-001).
2. System shows the dashboard's Controllers view: a live controller grid (each card's title is the controller's human-readable name from `GameplayData.name`, UC-004, with the short id `P<last 4 of the serial>` as a smaller subtitle; it follows a rename in the stream and falls back to `P<short id>` as title when the name is empty; LED colour, acceleration, connection-quality badge with its p95 and longest report gap, BR-005; the HCI adapter the controller is connected through (`hci0`, `hci1`, ..., a badge from `controller_adapter_info` in VictoriaMetrics, hidden while only one adapter is seen or the adapter is unknown, and a per-adapter count in the grid header, BR-009); an agent-shield badge, FR-084: "Charged" (with the seconds to expiry, or none when the charge never expires) while the player holds a shield charge, UC-048 A3; the shield countdown while a shield runs; both, "Shield 4.2s · Charged", when a charge waits under a running shield) fed by the dashboard's own gameplay stream, an observer that never claims a controller (BR-006); and the game state, alive count and event feed (game start on `game_start` and end, with the winner from `game_winner` or the `game_ended` `winner` (a controller serial shows the controller, a team name "team <name>", `none` "No winner" with the `reason` or non-result `outcome`, e.g. "(force-ended)"; without a `winner` field: Swapper, Traitor, Teams and Random Teams `winning_team` as "Team <index>" with `-1` or `none` "No winner", Tournament `champion` as the controller, a plain "Game ended!" for neither, as does a stringified `None` or empty `winner` or `champion`); the Running state on `game_start` and `game_started`, the Starting state on `countdown_start` and Running again on `countdown_end` (the base modes send `game_started` before the countdown; Werewolf, Zombies, Tournament and Fight Club send it after the countdown); the Ended state on `game_ended`, `game_force_ended`, `game_error` ("Game ended with an error") or `game_start_error` (with its error message); eliminations; agent shields and shield charges, with feed lines for a charge, its trigger activation and its expiry; in a hold game the energy bar of each player, BR-008) from the game event stream, which connect-proxy relays from the game coordinator (A4 when either stream drops).
3. Operator opens the Agent tab; System shows, from the agent's read-only state (`GET /experiments/state`, BR-011), the decision feed (`invoke_agent joustmania-agent`; decisions recorded under the older `agent.decide` span are not shown, telemetry.md §4.2; each linked `agent.decision` reads `allowed`, `blocked`, or `not applied: <reason>` when the agent was at `watch` or the write failed), the activity feed (blocked decisions from the `agent.decision` spans of the same answer) and the effective flags of the followed game (the agent's flag state of that game, recorded on every evaluated cycle: decision backend, act threshold, battery threshold, max interventions per minute, game mode, the agent state `enabled` (`off` / `watch` / `act`), objectives, allow-list, `experiments_enabled` and `llm.eligible_game_kinds` (the stage fallback, UC-070 A9, shows as `on` and `real,shadow`, BR-013), with a hint while the agent is at `watch`; the game is chosen like the current-backend strip, UC-070 BR-005, so a shadow game never replaces the stage game; while a real game is live it is that game's own flag state, also before its game has decided, and the "no flag state" hint until the agent has evaluated it, never the previous game's), and the applied and blocked intervention counts from VictoriaMetrics (`agent_intervention_writes_total` and `agent_decisions_total`, by `game_kind`): the real-game (`real`) counts lead, the shadow-game counts sit on their own labelled line, and the blocked-by-action and blocked-by-reason breakdowns cover real games only; a series without `game_kind` (from an older agent image) counts as real (A3 when a source is down). Every row links its trace in Jaeger, the drill-down (BR-011); no request carries a browser-clock time.
4. Operator opens the Experiments tab; System shows the cohort experiments and their arms from the agent's progress snapshot of each experiment (`GET /experiments/state`, BR-011; recorded after every state change): per arm the samples, mean fitness and games in flight, Δ (experimental minus control mean), the verdict (running while `proposed` / `running`; `verdict.outcome` once it concluded (`concluded`, `promoting`, `done`, `discarded`), else that status; an `aborted` experiment shows `aborted`, its interim verdict outcome only as "(interim: <outcome>)") and how it ended (the status and the end reason); each card names what is tested (the flag, the experimental value, the objective and the thesis) and links the experiment's `agent.experiment` trace in Jaeger (BR-013); when the experiment's promotion was refused because another writer owns the real overlay (UC-043 A19), the card also shows "would promote <flag>=<value>; real value owned by <writer>" from the snapshot's recommendation; live experiments plus the newest 10 finished ones (A1 for one experiment's dossier, linked from the tab).
5. Operator follows a game in Jaeger (the dashboard's Traces tab embeds the Jaeger search `service=game-coordinator-service` with the tag filter `game.kind=real`, which only game root spans carry, so the gRPC `Health/Check` spans that dominate the service by volume never fill the list, and shadow games are left out; on Jaeger's api/v3 the UI search URL is unchanged, only a direct `/api/traces` caller would move to `/api/v3/traces` with attributes in place of `tags`): the game's root span (named after the mode), its phases, one span per player, and the agent's in-game spans as remote children of `game.cycle` (UC-040 BR-013); coordinator and agent spans name the game kind in one vocabulary (BR-002).
6. Operator watches the Grafana dashboards, in four folders: Game (game and players, including the per-player acceleration against the warning and death lines; controllers and Bluetooth, including the connection quality per controller, BR-005, and each adapter's identity, HCI error counters and link roles, FR-122), Agent (decisions by backend and outcome, remote-model latency and usage, interventions and their measured effect, shadow games), Platform (infrastructure and services; flags and the flag service) and Talk (one dashboard for the talk, `Talk: Two Standards`, UC-070). Every latency panel reads histograms with their declared buckets (BR-004). The dashboards, their panels and the metric names are listed in [telemetry.md §6](../specs/telemetry.md#6-metrics).
7. Operator finds a game's errors in Jaeger (span status and exception events, by `game.id` or trace id), and the raw lines with `docker compose logs --since/--until` around the span's time (the container logs are no longer shipped anywhere).

## Alternative Flows

### A1: Experiment dossier

**Trigger:** Operator opens `/experiments` or `/experiments/<id>` (step 4)
**Flow:**

1. System (the agent) answers `/experiments` with the list of experiments from its journal: for a browser (`Accept: text/html` without `application/json`, or `?format=html`) an HTML table of id, status, flag, candidate, verdict, start and thesis; JSON otherwise (id, hypothesis, flag, candidate, objective, status, verdict, start and, once concluded, end) and `/experiments/<id>` with that experiment's dossier as JSON (thesis, arms, games with their outcome and fitness, verdict, decision, notes and trace hints). The decision follows how the experiment ended, not only its verdict: `promoted` when it ended `done`, `reverted` when it ended `done` but its journal holds a `promotion` event with outcome `reverted` (the kill switch undid the real default, [UC-043](UC-043.md) A1; the status stays `done`), `discarded` also when it ended `done` but its last `promotion` event is `discarded` (an older journal whose deferred hold-key write was dropped), `discarded` when it ended `discarded` (also a promote verdict whose promotion could not act, [UC-043](UC-043.md) A4, A9), `refined` when it ended `discarded` on an inconclusive verdict, `aborted` when it was aborted, and empty while it runs, including while a promotion runs (status `promoting`; a journal left at `concluded` keeps its verdict label, since the journal cannot tell it from a live one). The `/experiments` list and the dashboard's Experiments tab show the verdict, not the decision. An unknown id is answered 404 `experiment not found`; with the agent down, envoy answers with its own error.
2. Use case continues at step 5.

### A3: A telemetry backend or the agent is down

**Trigger:** Jaeger, VictoriaMetrics, Grafana, the collector or the agent is unreachable while the operator uses the dashboard (step 3 and step 4; Grafana and the agent also at step 6 and A1)
**Flow:**

1. The collector keeps exporting to the others: each backend has its own exporter, the agent fan-out is best effort and never blocks the pipeline (NFR-024), and the collector's memory limit bounds what queues up for a down backend (NFR-021). The collector starts and runs without its backends (no `depends_on` on them, restart `unless-stopped`); data for a backend that is not up yet is queued in memory and retried with the collector's default bounded retry (about 5 min), so a backend that comes up later than that loses the early data; the queue is bounded by NFR-021 (UC-060 BR-004).
2. The dashboard shows what it can still read. A panel that has rendered keeps its last data and marks it `stale — last updated <n>s ago`; a panel that never rendered shows `Could not reach the agent for its decisions (/experiments/state).` (decide feed, strip and flag panel) or `Could not reach the agent for its experiments (/experiments/state).` (Experiments tab) when the agent's state cannot be read (the request fails, times out, answers non-2xx such as envoy's 503 with the agent down, or no JSON). Jaeger down does not touch these panels; only the trace links and the Traces tab need it. An agent that answers without a flag state or an experiment yet is not an error: the panel says what it waits for (`No flag state yet …`, `No experiments yet …`). With VictoriaMetrics down (request failed or HTTP error) the Applied and Blocked counts show `n/a` ("VictoriaMetrics unreachable"); an empty answer from a reachable VictoriaMetrics is `0` (no interventions yet). Both counts cover the same last 10 minutes; Blocked leaves out `already_applied` (the value was already in place, not a refusal, UC-040 A35); the counts are split by the `game_kind` label of the agent counters, real games (`real`, an unlabelled series counts as real) first and shadow games on their own line; with Jaeger down and VictoriaMetrics up they still show. With the collector down the agent receives no telemetry: the Agent and Experiments tabs show no new agent rows. With the agent down `/experiments` also fails (A1). With VictoriaMetrics down the adapter badges and the header counts keep their last value and are marked stale (the badge title and the header say `stale`); if they never rendered, no adapter is shown and the grid is unaffected (BR-009). The stage settings strip (BR-010) keeps its last values marked `stale` when both its sources fail, and shows `—` for a value no source reports; one source down only blanks what only it carries. With Grafana down the dashboard's embedded Grafana view (its Metrics tab) and its outbound Grafana links fail; the rest of the dashboard is unaffected.
3. Use case continues at step 3.

### A6: The dashboard is opened or reloaded while a game runs

**Trigger:** The operator opens or reloads the dashboard while a real game is STARTING, RUNNING or ENDING, or the game event stream missed `game_ended` during a reconnect (A4); the coordinator's event bus has no replay (step 2)
**Flow:**

1. The follow poll (`GetGameState` every 2 s, BR-012) seeds the Start and Stop buttons and the status line from the real game's state: STARTING, RUNNING or ENDING (the winner ceremony still holds the stage) disables Start and the mode choice, enables Stop and reads `Game: Starting`, or `Game: Running` for RUNNING and ENDING.
2. The poll acts on its first answer and on every change of the real game's live-ness, never on a repeat. An answer whose request went out before the latest game event (`game_start`, `game_ended`, ...) or Start / Stop click is dropped (each request is stamped with a counter that every such event bumps), so a stale RUNNING cannot re-enable Stop after `game_ended` and a not-live first answer cannot undo a Start click in flight; the next poll answers again. When the real game is no longer live and the status line still reads Starting or Running, it reads `Ended` and Start is enabled again; an idle status line stays as it is. A failed poll changes nothing.
3. Events keep driving the buttons and the status line as before (step 2).
4. Use case continues at step 2.

### A7: The game telemetry also goes to the gateway (opt-in)

**Trigger:** The operator wants external backends to show the same games and starts the collector with `docker-compose.gateway.yml` and its two environment variables, or on the Pi sets the two variables in `.env.local` (BR-015) (step 5)
**Flow:**

1. Without `docker-compose.gateway.yml` (the default): System (the collector) loads `config.yaml` only; every exporter targets a service of the compose network, so no telemetry leaves the case.
2. With it: System loads `config.gateway.yaml` as a second configuration and sends the traces, metrics and logs that the services push over OTLP once more, to one remote OpenTelemetry Collector (the gateway, deployed outside this repo), which forwards them to the external backends: OTLP/HTTP with gzip to `<endpoint>/v1/traces`, `/v1/metrics` and `/v1/logs`, authenticated with the bearer credential of BR-015. Each gateway pipeline runs the processors of its in-case twin, so the gateway receives what Jaeger and VictoriaMetrics receive from the services (no health-check spans). Host, container, scraped and span metrics are not sent.
3. The in-case pipelines are unchanged: Jaeger, VictoriaMetrics and the agent receive everything as in the main scenario, and steps 1 to 7 work without an uplink.
4. When the gateway is unreachable or answers 429, 502, 503 or 504, System retries a batch for at most 5 min and then drops it; batches waiting for the gateway are queued up to 16 MiB per signal and a full queue drops the new batch at once. When the gateway refuses the credential (401, 403) or answers any other error, System drops the batch without a retry. The collector logs each failure. In every case only the gateway copy is lost; the in-case pipelines deliver as before (NFR-029).
5. Operator switches the export off by recreating the collector without `docker-compose.gateway.yml` (on the Pi: removes the two variables from `.env.local` and recreates the collector through the wrapper); batches still queued for the gateway are dropped.
6. Use case continues at step 5.

2. 5. When a source cannot be read, System keeps the last picture and shows "no data" for that source; it never shows an error page.

## Postconditions

### Success Postconditions

- The operator can find one game's spans in Jaeger and its series in VictoriaMetrics by its game id, and the spans of its trace, with their error events, in Jaeger by the game's trace id.

### Failure Postconditions

- With any telemetry backend, the collector or the agent down, the game services never wait on telemetry: recording a span, a metric or a log line neither blocks nor raises on the game path (export runs on background threads, NFR-024), so a game starts, runs its loop at the NFR-003 rate and ends as it does with telemetry up. Telemetry recorded while a backend was down may be missing from that backend.


## Business Rules

### BR-001: One entry point

Envoy on port 80 is the only host entry for the UIs and the HTTP and browser APIs. Every other published port, and the interface it is published on, is listed in C-015; docs that say `:8080` are stale (D-E1). The pairing daemon's unpair port is narrowed by UC-005 BR-003.

### BR-002: One `game.kind` vocabulary

Coordinator and agent spans and metrics all say `real` / `shadow` (D-T7), so a search for one game kind in Jaeger or VictoriaMetrics reads the same value from either service. Older series that carry `primary` keep it until retention drops them, and the agent still maps a `primary` it ingests to `real`. The rule that an empty or unknown kind is never real is owned by the entity model (GAME_SESSION `game_kind_telemetry` / `game_kind_flags`).

### BR-003: Dead alerts (retired)

Retired: the alert rules were removed together with Prometheus alerting (A2), so the dead `GameCrashRate` / `ServiceUpdatePending` rules (D-T3) are gone. The ID is kept so it is not reused.

### BR-004: Histograms export their declared buckets

Every histogram is exported with the bucket boundaries it declares: a Python `Histogram(..., buckets=[...])` in `lib/otel_metrics.py` passes them to the OTel SDK as explicit bucket boundaries, and the Go agent histograms set `WithExplicitBucketBoundaries` (`gen_ai.client.*` use the GenAI semantic-convention advisory boundaries). Without them the SDK defaults (0, 5, 10, 25, ...) put every sub-second latency into the first bucket, so each latency p95 reads about 4.75 s. The collector's `span_metrics` connector sets explicit buckets (5 ms to 32 s) on the `invoke_agent joustmania-agent` duration histogram. A histogram records only values in the unit its buckets are sized for: `agent_intervention_effect_delta_ratio` records the deltas of the 0..1 progress-type fitness signals only (`*_progress`, `*_ratio`, `balanced.skill_gap`); the elapsed-time and constant-threshold keys stay on the `agent.intervention.effect` spans.

### BR-005: Connection quality per controller

The controller manager classifies each controller's link from the gaps between consecutive fresh frames (a poll that returns a new report) over a rolling 10 s window: the p95 gap (nearest rank) is good at ≤ 22 ms, fair at ≤ 30 ms and poor above 30 ms; the longest gap, including the still-open gap since the last fresh frame, is good at ≤ 30 ms, fair at ≤ 50 ms and poor above 50 ms. The controller's class is the worse of the two. A controller that delivered frames before and has been silent for the whole window is poor (its open gap is the longest gap), though a controller silent for `silent_disconnect_seconds` (default 3 s) is disconnected before that and its badge and series go with it (UC-002 BR-007); only a controller that has not yet delivered two fresh frames is unknown, and then no badge or quality series is shown. The thresholds are the upstream JoustMania gameplay-derived ratings (provisional, not yet validated on Pi hardware with this measurement). Gaps are taken at the controller manager's poll pick-up (monotonic clock), so they are quantised to the 10 ms poll interval and sub-poll jitter is invisible; time the poll loop itself runs late (event-loop contention; discovery, LED and health work run on their own tasks, NFR-002) is subtracted from every gap that spans it, so a loop stall does not rate every controller worse; the same subtraction applies to the health span's `bluetooth.event_gap_ms`; a link gap that overlaps a controller-manager loop stall is understated by up to the stall's length (FR-122).

### BR-006: The dashboard's gameplay stream is an observer

A gameplay stream that never sent colours (an observer: the dashboard's `WatchGameplayData`) never consumes a game signal. Mid-game disconnects (`GameplayDataUpdate.disconnects`), the per-controller health counters (`GameplayData.health`) and the mock death latch's frame budget are read once, so only game streams (those that sent colours in their config) drain them (every open game stream gets each disconnect, UC-002 BR-004), also while their alive filter is empty (NonStop's respawn window, a reconnect with nobody alive), and then only for the controllers of their own roster (the empty filter means every controller in a frame, but a game never consumes another game's mock latches, health counters or trigger latch); an observer's frames carry no `disconnects` and no `health` and do not count against a death latch. An observer stream runs at its requested rate capped at `game_loop.update_frequency_hz` (the dashboard asks for 30 Hz), while a game stream runs at the flag rate, except a pattern game's stream, which is pinned to its archetype's `stream_rate_hz` for the whole game and ignores the flag ([UC-046](UC-046.md) step 4, FR-103). connect-proxy forwards only the browser's rate (missing or 0 and below = 30 Hz, capped at 30 Hz), never colours or a filter, so a browser cannot claim controllers, set their LEDs or open a game stream.

Known gap (Post-F-1, e2e only): on the running stack the outage is exercised with the agent down (`tests/integration/test_uc035_a3_backend_down.py`: the loop keeps at least half its configured rate); with the collector or a single backend down the clause is asserted at the SDK level only (`lib/tests/test_telemetry_fail_open.py`: spans, metrics and log lines neither block nor raise against a dead collector), not by a stack run with that container stopped.

### BR-007: The battery scale on the controller card

The gameplay stream's `GameplayData.battery` carries the controller's last-known battery. On the Rust HID path (the shipped path, `proto/psmove_hid.proto`) the value is a percentage in steps of 20 (0, 20, 40, 60, 80, 100); the psmoveapi path and older fixtures use 0-5. The dashboard card reads both the way `battery_to_pct` does (`controller_manager/metrics.py`): a value of 5 or less is a 0-5 level times 20, anything above is already a percentage, clamped to 0-100, so a Rust 40 does not show as 100 %. The bar colour is `high` above 50%, `medium` above 20%, otherwise `low`. Charging and charged both arrive as 100 (the HID layer maps 0xEE and 0xEF to 100), so a charging controller reads 100% (gap, no proto change). The separate battery roster that also used this scale was removed (A5 Obsolete). The lobby's low-battery warning reads the same scale: 20 % or less is low ([UC-002](UC-002.md) A8, BR-010); it gets the value from the button stream (connect, button and the 30 s battery-only events), not from this stream.

### BR-008: Hold energy tile

- In a hold game (UC-048 BR-008) each player's tile shows a bar of the energy against the cap, a thin second bar of the budget remaining against the budget, the text `Hold <energy>s/<cap>s · budget <left>s` and the state, with the levels of the controller LED (UC-048 BR-010): `empty` (below the minimum burst), `low` (below a third of the cap), `charged`, `full` (at `min(cap, budget remaining)`), `active` (draining, highlighted), plus `recharging` while the pool fills by itself and `budget used up` once less than a minimum burst of budget is left. A marker names the last source of energy: `agent` after a grant, `recharge` while recharging. A game that is not a hold game publishes no energy event, so its tiles show no bar.
- Source: the game event `player_shield_energy` ([telemetry.md](../specs/telemetry.md) §5), published at every transition the controller gets a hold command for (UC-048 BR-010: the start of the game loop, an activation, the end of an activation, a grant, a reconnect), from the coordinator's outbound hold task, never from the frame path. Between two transitions the energy is a linear function of time (UC-048 BR-008), so the event carries the rate and the dashboard computes the rest. A keyframe re-publishes a living player's state when that player had no energy event for 2 s, so a dashboard opened mid-game, a reopened stream (A4) or a dropped event gets the bar back within about 4 s (twice the 2 s keyframe interval: the keyframe timeout restarts on every wake, and a dropped keyframe adds one more interval). Events of one player coalesce like the controller commands; at most two per minimum burst per player plus one per grant, plus one keyframe per 2 s. The event is droppable on the event bus: a subscriber whose queue is a quarter full or more loses it on its own loop, so energy events never hold more than a quarter of a queue and at least three quarters stay for `player_death`, `game_ended` and `game_winner` (a full queue still drops any event); the menu logs it at DEBUG. A shadow game publishes none: a shadow game can be a hold game only when its archetype presses the trigger (UC-048 BR-004, UC-046 BR-018), and then it still sets the agent's hold gauges and sends the hold layers to its mock controllers, but no `player_shield_energy` event (no dashboard bar for a game without an audience, and no energy events on the shared bus queues).
- Why not VictoriaMetrics: dashboard data comes from telemetry where it can, but a live bar cannot use it. The coordinator exports metrics every 100 ms, yet VictoriaMetrics (v1.144) answers an instant query 30 s late by default (`-search.latencyOffset`) and 2.5 to 4 s late with `nocache=1` (measured on a throwaway instance): a 5 s pool would be drawn after it emptied. The per-player shield gauges stay planned for the agent's view (telemetry.md §6), where seconds of lag are acceptable.
- The bar interpolates linearly from the last event's `energy_ms` and `rate_ms_per_s`, measured against the browser's monotonic receipt time (`performance.now()`); no wall-clock timestamp is compared, so no browser clock is trusted; the same holds for the timed shield badge (UC-040 step 4, from the event's `seconds`) and for every elapsed-time measure of the dashboard's pollers, decide window and fallback pacer (`performance.now()`). A draining bar stops after `remaining_ms` (the activation's end), a filling bar at `full_ms`; values are clamped to [0, cap]. When the end of an activation is not followed by an event (a dropped one), the bar shows the idle state at the drained level. Every event resets the state. The bar is cleared on `game_start`, game end, `player_death` and a lost event stream (A4); `ShieldStore` clears its shield entry on `player_shield_energy`, and a hold activation publishes no `player_shielded` (UC-048 BR-010).

### BR-009: Adapter on the controller card

- Each controller card shows the HCI adapter its link runs on (`hci0`, `hci1`, ...), so an operator sees an unbalanced Bluetooth load without opening Grafana. The grid header shows a count per adapter ("hci0: 5 · hci1: 4"), also with one adapter ("hci0: 9"). The per-card badge is hidden while only one adapter is seen.
- Source: the existing `controller_adapter_info{serial,adapter}` series ([telemetry.md](../specs/telemetry.md) §6), read from VictoriaMetrics through envoy's `/victoria-metrics/` with `timestamp(controller_adapter_info)` and `nocache=1`, polled every 10 s while the page is visible. No proto field and no new metric. The join key is the controller manager's serial, the same one the gameplay stream carries.
- One adapter per serial: OTLP writes no staleness marker, so after a controller moved adapter both series can answer for a short time; the series with the newest sample timestamp wins.
- A serial without a series (mock controllers, USB, a failed sysfs lookup) shows no adapter badge and is left out of the counts. A reconnect whose adapter lookup returns an empty name clears the controller manager's stored adapter (UC-002 A4), so the series goes instead of keeping the old `hciN`.
- Why VictoriaMetrics and not the stream: the adapter changes only on reconnect, and seconds of lag are acceptable (contrast with BR-008): the label can trail a reconnect by 2.5 to 4 s with `nocache=1`, so at worst about 14 s (10 s poll plus that lag). Polling runs only while the Controllers tab is shown and the page is visible. The badge names the adapter, not the link health (BR-005 is the live signal). The lite stack has no VictoriaMetrics (Pre-1) and shows no adapters.
- Known gap: the real adapter path (sysfs walk to `hciN`) is verified on Pi hardware only; mock controllers report none, so no e2e test asserts a label.

### BR-010: Stage settings strip

- A one-line strip above the controller grid shows what the operator pad changes (UC-015 BR-018): the shield activation mode (`instant`, `trigger`, `hold`; in hold mode the latched `shield.energy_max_seconds` as `max` and `shield.energy_budget_seconds` as `budget`), the sensitivity (index 0 to 4 (`ultra slow` first)) and the team count. Shield, sensitivity and teams carry `(operator)` when the pad persisted a value and `(automatic)` when it did not (the flag file default or an agent promotion applies); a value the source does not report shows `—` with no tag.
- Sources: VictoriaMetrics first, `last_over_time({__name__=~"game_shield_activation_mode|game_shield_hold_setting|game_sensitivity",game_kind=~"real|primary"}[1m])` with `nocache=1` ([telemetry.md](../specs/telemetry.md) §6): the live primary game's latched values; the one-minute window drops the series of an ended game. No gauge carries the team count and, in the lobby, no game gauge exists, so the dashboard also calls `GetMenuStatus` through connect-proxy (unary, services.md §3.1): `num_teams`, `sensitivity`, `shield_activation` and `operator_settings`. One game only: of the series in the window the game (`game_id`) with the newest sample wins (`tlast_over_time` with the same selector), never a mix of two. A live game's gauge wins over the menu value; when the menu reports no live lifecycle (`lifecycle_live` false, the lobby after a game) the menu value wins over a lingering gauge; the origin tag always comes from `operator_settings`.
- Polled every 5 s with the single-chain poller (backoff to 30 s), only while the Controllers tab is shown and the page is visible. Either source down leaves the other's values; both down keeps the last strip marked `stale`.

### BR-011: The Agent and Experiments tabs read the agent's state, not Jaeger

- Source: one read-only JSON answer of the agent, `GET /experiments/state` through envoy's `/experiments` route ([services.md](../specs/services.md) §5). It holds what the two tabs render: the newest decide spans the agent recorded with their `agent.decision` spans, the scored predictions and the game summaries (in OTLP/JSON, folded like a Jaeger answer), the effective flags of the newest games, and the progress snapshot of every live experiment and of the newest finished ones. It is a read path for humans and changes nothing (C-005).
- Poll: the Agent tab every 1.5 s, the Experiments tab every 5 s, each one small answer (single-chain poller, 4 s timeout, backoff on errors and slow answers). No Jaeger search feeds these panels, so there is no pacing, no settle window, no search lane and no shadow search.
- Shadow games cannot crowd out the stage game: the agent keeps the decides of shadow games apart from the others (30 each), so a burst of shadow games never evicts the real game's rows; the dashboard keeps them all (60) and picks the followed game as before (UC-070 BR-005).
- Drill-down stays in Jaeger: every decide row, flag state and experiment card carries the trace id its link opens.
- Memory, not history: the agent holds this state in memory; after an agent restart the tabs start empty (live experiments come back with their rehydrate snapshot), and finished experiments from before it are in the dossier (A1). A prediction outcome or a game goal the dashboard has seen stays on screen after the agent dropped its span.
- Hidden: no poll runs while its tab is not shown, the page is hidden or it sits in the back/forward cache; showing it again polls at once.
- Retired with this rule: the decide poll's 512 KiB/s pacing, the 62 s settle window, the `game.id` lane with a `game.kind=shadow` search every fourth poll and their 4 s per-lane timeouts, the flag-state fallback search with its 30 s pacer, the goal summary search, and the `agent.flag_state` and `experiment.progress` spans ([telemetry.md](../specs/telemetry.md) §4.1).

### BR-012: Background load of an open dashboard

- Hidden page: the Controllers gameplay stream (30 Hz) is aborted when the page is hidden (`document.visibilityState`) or parked in the back/forward cache (`pagehide`), shows no `Connection lost. Retrying...` for it (also when the page is shown again before the aborted call has settled) and is reopened on show (`pageshow`); a page that starts hidden opens no stream. The pollers of BR-009 and the Agent and Experiments tabs already pause the same way (PageGate).
- Follow poll (`GetGameState` + `ListGames`, every 2 s): runs only while the Controllers or Agent tab is shown and the page is visible; other tabs, a hidden page or the back/forward cache stop it, and showing the tab polls at once.
- Iframes: the Grafana Metrics iframe gets its `src` on the first open of its tab and is blanked (`about:blank`) 60 s after its tab is left, or at once when the page is hidden or parked in the back/forward cache, so its 5 s refresh costs nothing in the background (returning to the tab within 60 s keeps the loaded Grafana, no reload); the Jaeger search iframe loads on the first open of the Traces tab and then stays.
- The Agent and Experiments tabs read the agent's state (BR-011); the stage settings poller (BR-010) pauses the same way. The game event stream stays open on every tab (low rate, drives the status bar).

### BR-014: One writer per metric series

Every process that exports metrics has its own `instance` (`service.instance.id` = container id plus a per-process random suffix, [telemetry.md](../specs/telemetry.md) §1 resource attributes), so two processes never write one series and a counter only resets when its process starts. A restart therefore starts new series; a query that spans restarts aggregates `instance` away.

### BR-015: The gateway export is an overlay that only adds

- One compose file switches it on: `docker-compose.gateway.yml` replaces the collector's command with the base `--config` followed by a second `--config` for `services/otel-collector/config.gateway.yaml`, mounts that file and passes two environment variables. The collector merges the two files key by key (maps are merged, a list in the later file replaces the earlier one), so the overlay only adds map keys and restates no list of `config.yaml`: one exporter `otlp_http/gateway` and the pipelines `traces/gateway`, `metrics/gateway` and `logs/gateway`. Every receiver, processor, connector, exporter, extension and pipeline of `config.yaml` is the same after the merge.
- Game telemetry only: the three gateway pipelines read the `otlp` receiver and nothing else, and no other pipeline names the gateway exporter.
- `ORANGECASE_GATEWAY_HOST` is the host name of the gateway (e.g. `otlp.example.org`; `host:port` for a port other than 443), and the overlay builds the endpoint as `https://<host>`, so the export is always OTLP/HTTP over TLS; `ORANGECASE_GATEWAY_TOKEN` is the bearer token. Both come from the environment only (the shell or `.env.local`), never from a flag or a file of this repo (C-016), and compose refuses to render the overlay when one is missing. The case holds no name and no key of an external backend. The scheme is not configurable: the case only ever dials `https` (C-016). The gateway must answer `/v1/traces`, `/v1/metrics` and `/v1/logs` directly, without a redirect: the collector follows redirects (no option turns that off) and sends the token to the target, even over plain `http`. With a value that carries a scheme (`http://host`) the exporter still speaks `https`, to a host that does not exist, so every export fails and nothing is sent (checked by hand on 2026-11-16 with collector v0.164.0 and a plain-HTTP sink: no request arrived).
- Bounds (NFR-029): 10 s per attempt, retries for at most 300 s, a queue of 16 MiB of serialized data per signal measured in bytes (48 MiB in total, about 200 MiB of collector memory when all three are full: a full queue costs about four times its serialized size, measured on 2026-11-16 as about 65 MiB for one full 16 MiB traces queue; a queue counted in batches has no memory bound and could reach the memory limiter of NFR-021, which refuses data for every pipeline), a full queue drops. The queue is in memory: a collector restart loses it (persistent queue: #2578).
- The export is switched by recreating the collector container. On the Pi the two variables are the switch: `scripts/setup/joustmania-compose.sh`, which every compose call of the Pi goes through (the autostart of UC-060, upgrades and manual calls, C-041), adds `-f docker-compose.gateway.yml` exactly when both `ORANGECASE_GATEWAY_HOST` and `ORANGECASE_GATEWAY_TOKEN` have a non-empty value and compose renders the stack with the overlay. The wrapper reads the two itself, in compose's order: the shell first (a variable set there wins, also when empty), else `.env.local`, else `.env`; in a file it reads the last `NAME=value` line (also `NAME = value`, `NAME: value`, an `export` prefix and one pair of surrounding quotes). It does not interpolate, so with both read as set it asks compose (`config -q` with the overlay, which prints nothing) and adds the overlay only when compose accepts: a value compose reads as empty (empty quotes followed by a comment, `${UNSET}`, a value that starts with `$name`) would otherwise make compose refuse the overlay on every call and the stack would not start. With both set, a reboot, a restart of the unit and an upgrade keep the export on; with none set nothing changes, compose is not asked and no telemetry leaves the case. With only one of the two set, or when compose refuses, the wrapper does not add the overlay and writes one line to stderr, so a broken gateway configuration never stops the stack from starting. Keep both in `.env.local`: a variable set only in a `systemctl edit` drop-in (`Environment=`) reaches the autostart and the upgrade but not a compose call from a login shell, which would recreate the collector without the overlay. The wrapper never prints a value. A call that names the overlay itself gets it once.
- Known gap: delivery is checked by hand, not in CI. On 2026-11-15 the pinned collector image (v0.164.0) with both files delivered traces, metrics and logs with the bearer token to a local OTLP/HTTP sink over plain HTTP (with the endpoint still a full URL; since then the scheme is fixed to `https`); with the sink down and with the sink answering 401 the in-case traces exporter still received every span. TLS to a deployed gateway is not exercised in this repo.

### BR-016: Message hand-offs carry a messaging span kind

A span that puts its trace context into a message for another process is `PRODUCER`, and a span that starts from a trace context received in a message is `CONSUMER`; every other non-gRPC span of a Python service stays `INTERNAL`. A kind-based filter (OTelFeature's `telemetryLevel=IO`) then keeps the hand-offs between services. The spans and their kinds are listed in [telemetry.md](../specs/telemetry.md) §3.3 (span kinds): `menu.event.publish` is `PRODUCER`; `controller.effect.player_death`, `controller.effect.winner_rainbow`, `controller.effect.countdown` and `controller.shield_effect` are `CONSUMER`. Only the kind changed: names, attributes, events and parents are as before.

### BR-017: The stage view reads what the agent reads

The stage view shows only OpenTelemetry data from the stack's own stores (VictoriaMetrics, Jaeger), never the game's gRPC streams, so on stage it shows exactly what the agent senses. It is read-only, polls at most once per second per source, uses the same queries as the Game & Players acceleration panel (mocks left out), and keeps every query free of browser-clock times (subqueries relative to the server's now; Jaeger v3 bounds as in jaeger.ts), because the stage Pi may run without NTP.

### BR-018: A challenge switch is marked on the match trace

When a challenge flag (a key starting with `challenge.` or `stowaway.`, [flags.md §1.4](../specs/flags.md#14-challenge-flags)) gives a different value or variant during a match than it last gave in that match, the evaluation that saw the change records one `feature_flag.evaluation` span event on the span current at that evaluation, which is on the match's trace; an evaluation that gives the same value again records nothing. The first evaluation in a match counts as a change. The match root span records `orangecase.challenge.start` when a challenge becomes active and `orangecase.challenge.end` when it becomes inactive, changes to another challenge, or the match ends. A watched challenge flag is evaluated once per gameplay frame, so a flip shows within one game-loop tick. The detection never raises into the game loop and adds no label to the `feature_flag.evaluation_*` metrics (FR-255).
