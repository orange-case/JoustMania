# Use Case: Trace an Agent Intervention to its Effect

## Overview

**Use Case ID:** UC-101
**Use Case Name:** Trace an Agent Intervention to its Effect
**Primary Actor:** Presenter
**Secondary Actors:** Player, Agent, Gateway, Observability Backend
**Goal:** Show, per observability backend, whether it joins an intervention that landed on a player to the agent decision that sent it, across the agent's trace and the game's trace, and whether the player survived it, when the intervention arrives as a span, a span event or a log event
**Trigger:** Presenter starts the "Who saved them?" booth challenge
**Status:** Draft
**Requirements:** [FR-220, FR-221, FR-222, FR-216, FR-217, NFR-061, NFR-060, NFR-003](../requirements.md)

A booth challenge of the Orange Case (epic #2569, #2665); UC-100 to UC-199 are the booth challenges, one per challenge. The agent decides in its own trace (`agent.decision` → `agent.action`); the effect lands in the game's trace, on the player. The one key both sides carry is the intervention id. The booth question: "player X got a shield: which agent decision gave it, and was the player still alive 10 s later?" One game per shape, as in [UC-100](UC-100.md); the case records the ground truth, every enabled backend gets the same game through the gateway, and the results are shown side by side, never ranked. Steps 1 to 7 are system behaviour that tests check; steps 8 to 10 are the presenter's check at the booth, done by hand.

## Preconditions

- The gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The agent is enabled, its intervention writes are on (`interventions_enabled`) and its allow-list names at least one lever of BR-001 that can save a player; in a real game `standard` names two, `grant_shield` and `adjust_player_sensitivity` (BR-001, [flags.md §3](../specs/flags.md#3-agent)).
- The game's shields are instant: the shield mode is neither trigger nor hold ([UC-040](UC-040.md) A30, A36), so a shield protects from the moment it is applied (BR-007).
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter chooses the moment shape for the next game: span, span event or log event ([UC-100](UC-100.md) step 1).
2. Presenter starts a game ([UC-010](UC-010.md)); System fixes the moment shape for the whole game and records it on the game's trace (UC-100 BR-002).
3. Agent decides an intervention on a player ([UC-040](UC-040.md)), gives it an intervention id before it writes, records the id on its decision, and writes the intervention with the id through the flag service ([UC-053](UC-053.md)) (BR-003).
4. The flag service serves the written value together with its intervention id (BR-003).
5. System applies the intervention to the player and, where it records the lever's own effect, records the intervention moment on the player, in the game's shape, with the intervention id it read with the value (BR-002, BR-004).
6. System sends the moments with the rest of the game's telemetry, and the agent sends its decision, through the gateway to every enabled backend.
7. When the game ends, System records on the game's trace, per applied intervention, the ground truth: its id, type, player, the time it was applied and the time of the player's first death at or after it, if any (BR-006).
8. Presenter picks a player who got an intervention whose survival the question can ask about (BR-001) and asks each backend which agent decision gave it and whether the player was still alive 10 s later (BR-007).
9. Presenter compares each answer with the ground truth and records, per backend, one of the three results (BR-008, BR-009).
10. Presenter repeats steps 1 to 9 for the other two shapes and shows the results of the three games side by side.

## Alternative Flows

### A1: The game runs in another shape than chosen

**Trigger:** The shape recorded on the game's trace differs from the chosen one (step 2)
**Flow:**

1. System records the intervention moments in the recorded shape, as for the warning ([UC-100](UC-100.md) A1). The same holds when the shape is `both` (UC-100 A6), and a shape change during the game applies from the next game (UC-100 A2).
2. Presenter does not count a game whose recorded shape differs from the chosen one, or is `both`.
3. Use case continues at step 1 for the next game.

### A2: The coordinator does not apply the intervention

**Trigger:** The coordinator blocks the written intervention (allow-list, mode capability, battery guard, backstop budget; [decide-contract.md §11](../specs/decide-contract.md#11-from-decision-to-game-effect)), its handler refuses it (shield limits, [UC-040](UC-040.md) A34; a refused revive or elimination; the game ending) or fails, a later write superseded it before the coordinator read it, or the value was already in place, so nothing changed (step 5)
**Flow:**

1. System records no intervention moment and no ground truth for it; the agent's decision keeps its intervention id (BR-005).
2. Presenter does not ask about that intervention.
3. Use case continues at step 6.

### A3: The written intervention carries no intervention id

**Trigger:** The write that set the value carries no id: written by someone other than the agent (stage scripts, the validation harness, tests), or by an agent that predates FR-221 (step 5)
**Flow:**

1. System applies the intervention unchanged and records the intervention moment and its ground truth without an intervention id (BR-003, NFR-061).
2. Presenter does not ask about that intervention, because no decision is behind it.
3. Use case continues at step 6.

### A4: One decision lands on several players

**Trigger:** The agent's decision is a group shield ([UC-040](UC-040.md) A47; in a real game only with the group allow-list and `policy.group_grant.real_games` on, UC-040 BR-033) (step 5)
**Flow:**

1. System records one intervention moment per shielded player, each with its own moment id and the decision's one intervention id, and one ground truth entry per player (BR-004).
2. Use case continues at step 6; the presenter may ask about any one of the players.

### A5: A backend does not receive the game or the decision

**Trigger:** The gateway or a backend cannot be reached or refuses the data (step 6)
**Flow:**

1. System keeps playing the game, and the agent keeps deciding, unchanged (NFR-029).
2. Presenter records that backend's round as not received, which is not a result about the shape.
3. Use case continues at step 7.

### A6: No intervention can be asked about

**Trigger:** No intervention with an intervention id and a lever that can save the player was applied during the game (step 8)
**Flow:**

1. Presenter records the round as without a question and plays another game in the same shape.
2. Use case continues at step 2.

### A7: The game does not end normally

**Trigger:** The game is force-ended ([UC-027](UC-027.md)) or the game coordinator stops before the game ends (step 7)
**Flow:**

1. System records no ground truth for a game that did not end normally (UC-100 BR-006).
2. Presenter does not count the game and plays another game in the same shape.
3. Use case continues at step 2.

## Postconditions

### Success Postconditions

- For each enabled backend and each of the three shapes, a result (found, found but not correlated, not found) and the backend's answer are recorded next to the ground truth.
- The games were played under the normal game and intervention rules.

### Failure Postconditions

- No intervention is applied, blocked, delayed or changed because of its intervention id: a missing, empty or unreadable id only leaves the moment without one (NFR-061).
- The game loop rate holds (NFR-003), and the agent's inputs are those of a game without the challenge (the agent takes nothing from an intervention moment, BR-010).
- No result is recorded as found unless the backend's answer matches the ground truth.

## Business Rules

### BR-001: The player levers

An intervention moment is recorded for each agent intervention the coordinator applies to one player. Its `intervention.type` is the decision's intervention name, the same value the agent's `agent.intervention.effect` and the coordinator's `game_interventions_total{type}` carry ([decide-contract.md §11](../specs/decide-contract.md#11-from-decision-to-game-effect)):

| `intervention.type` | Lands as | Can save the player | In a real game with `standard` |
|---|---|---|---|
| `grant_shield` | an instant shield, a charge (trigger mode) or energy (hold mode) | yes (instant shields only, BR-007) | yes |
| `grant_group_shield` | one moment per shielded player (A4) | yes | no (group allow-list and `policy.group_grant.real_games`) |
| `toughness_boost` | an armed toughness boost | yes | no |
| `adjust_player_sensitivity` | a changed sensitivity factor, a return to 1.0 included | yes, when it protects | yes |
| `set_player_handicap` | a changed handicap factor, a return to 1.0 included | yes, when it helps | no |
| `revive_player` | a revived player | yes | no (`full`) |
| `soft_penalty` | a warning or a tightened threshold | no | no |
| `eliminate_player` | the player's death | no | no (`full`) |

Every game kind records the moment, shadow and pattern games included (UC-100 BR-002); the levers a real game does not allow show up in shadow games, which use wider allow-lists. Game-wide levers (tempo, pacing, global sensitivity and difficulty, volume, end game), the auto-rubberband boosts (the coordinator picks each boosted player itself, not the agent) and the cosmetic player levers (controller effect, audio cue) record no intervention moment. The booth question (step 8) asks only about a lever that can save the player. The moment is recorded in addition to the lever's own span event (`shield_granted`, `toughness_boost_armed`, ...; a soft-penalty warning has none), which stays as it is ([telemetry.md §3.2](../specs/telemetry.md#32-game-coordinator)).

### BR-002: The intervention moment follows the game's shape

The intervention moment is a moment like the warning: it is sent in the shape the game started with (span, span event, log event or both), with one moment id per moment (shared by its two records in `both`) and the same attributes in every shape (UC-100 BR-001 to BR-003, BR-005). It keeps the name `intervention` in every shape.

### BR-003: The intervention id travels with the write

The agent gives every intervention it writes an intervention id before the write, records it on its decision as `decision.intervention_id`, and sends it with the write. The flag service serves it together with the written value, so the coordinator reads the value and its id in one resolution, with no extra call. A write without an id is served without one. The id is informational on every hop: nothing checks it, and nothing is refused or delayed for it.

### BR-004: The moment carries the intervention id

The intervention moment carries `intervention.id`, `intervention.type`, its own `moment.id` and the moment's identity attributes (the player, the game). `intervention.id` is the id served with the value at the read that found the change, carried per target to the handler that applies it, and left out when there is none. One intervention id is on several moments only for a group shield (A4).

### BR-005: Only an applied intervention is a moment

Only an intervention the coordinator applies to a player is recorded as a moment and in the ground truth, and it is recorded where the handler records the lever's own effect: an intervention whose effect lands late (the game loop was slow) is recorded when it lands. A blocked, refused or failed intervention has none, nor has a write that a later write superseded before the coordinator read it, or one that changed nothing (A2). A deferred intervention (the cross-set gate of [UC-053](UC-053.md) A9) has none while it waits; when the re-evaluation applies it, the moment is recorded then, with the id served at that read. The agent's decision still carries its id, so a backend that finds a decision without a moment is not wrong.

### BR-006: The ground truth comes from the game

The ground truth is what the game coordinator recorded for the game at a normal end (UC-100 BR-006): per applied intervention its id (when it had one), type, player, the time it was applied and the time of that player's first death at or after the apply time (left out when the player did not die from then until the game ended). For `eliminate_player` that death is the one the intervention caused, at the apply time.

### BR-007: Survived means alive 10 s later

A player survived an intervention when the ground truth has no death of that player within 10 s after the intervention was applied: the longest shield the agent can grant (`grant_shield` at most 10 s, [decide-contract.md §2.1](../specs/decide-contract.md#21-magnitude-bounds)). A game that ends within the 10 s without that player's death counts as survived. The rule assumes the lever protects from the moment it is applied, which a shield charge (trigger mode) or shield energy (hold mode) does not, so the challenge is played with instant shields (preconditions).

### BR-008: Only the moment record counts

A backend has found the intervention only when it shows the intervention moment's own record (the name `intervention` with its `moment.id` and `intervention.id`) and joins it to the agent's `agent.decision` with the same `decision.intervention_id`. A join by player and time alone does not count, nor do other records of the same happening: the lever's own span event and the coordinator's `agent_intervention` game event (type, target, blocked; [telemetry.md §5](../specs/telemetry.md#5-game-events)), which carry no intervention id.

### BR-009: The three results

For the asked intervention of a game, a backend's result is:

- **found**: it shows the intervention moment (BR-008), names the agent decision with the same intervention id, and its answer whether the player survived matches the ground truth (BR-007);
- **found but not correlated**: it shows the intervention moment, but names no decision, another decision, or a survival answer that differs from the ground truth;
- **not found**: it shows no record of the asked intervention moment (its `moment.id` and `intervention.id`); another intervention moment of the same player does not count.

Results are shown side by side per backend and shape, never ranked (UC-100 BR-008). A backend that did not receive the game (A5) gets no result for that game.

### BR-010: The agent takes nothing from an intervention moment

The agent ignores the intervention moment in every shape: a `game.intervention` span is skipped like the other moment spans (UC-100 BR-010), and intervention log events are not exported to the agent. Its own decisions and effect measurement stay its source for what it did.
