# Use Case: See the Game State on the Operator Pad

## Overview

**Use Case ID:** UC-016
**Use Case Name:** See the Game State on the Operator Pad
**Primary Actor:** Host
**Goal:** See on the operator pad's own screen, without a laptop and without waiting for a voice line, what the lobby looks like (game state, selected mode, ready and connected controllers, the agent) and, while turning the knob, which setting is being changed and to what
**Trigger:** The pad service attaches to the pad and its display link comes up; the menu status changes; Host holds a layer key and turns the knob, turns the knob alone, or a pad command ends
**Status:** Implemented
**Requirements:** FR-236, FR-237, FR-238, FR-239, FR-240, FR-241, FR-242, NFR-070
**Planned:** FR-243, FR-244, FR-245, FR-256, FR-257, FR-258, FR-259, FR-260, FR-261, FR-262

Phase 2 of the operator pad (#2741): [UC-015](UC-015.md) is phase 1, the keys and the knob with voice, sound and LED cues. This use case adds the pad's 128x64 OLED. The firmware is a Vial keymap for the 0xCB 1337 in the `orange-case/operator-pad` repository (`firmware/`); it draws what the pad service sends over the pad's raw HID interface (BR-002) and holds no game logic. The pad is a rev 5 (RP2040), for which QMK and Vial have no keyboard definition, so the repository brings its own (`keyboard/`, built as `orange_case/operator_pad`); revisions 1 to 4 (ATmega32U4) build the same keymap as `0xcb/1337`. While the screen works it replaces the pad's own voice lines and the volume sound (BR-004, BR-005); every other cue of UC-015 stays. The firmware side of BR-002 is built and bench-tested on a rev 5 pad (`orange-case/operator-pad` #1); the pad service side is built (#2741: `services/operator_pad/`, the menu's `cue` key and `ProcessInputResponse.value`, the `operator-pad` compose service and the udev rule). Only the check on the Pi 5 with the real pad is still pending (the measurement of NFR-070 and the bench check of the link): FR-236 to FR-242 are Implemented, not Verified, until then, and NFR-070 stays Open.

Iteration 2 (Open, #2742): a pad whose firmware answers protocol 2, 3 or 4 (BR-002) gets seven pages in one screen frame (a title bar with the page's place, three rows, a status bar of icons), that the knob scrolls and that turn on their own while the pad is idle, and the internet state in its status bar (A5, A6, BR-006 to BR-010). Protocol 3 (rev 5 only) draws the rows in a medium 8x12 font and a ladder setting as a marker bar; protocol 4 (rev 5 only, planned) adds the vertical wheel that wraps for the mode, the backend and the shield mode, its middle row in a tall 8x16 font; protocol 2 (revisions 1 to 5) draws the same pages with big 12x16 rows. A pad that answers protocol 1 keeps the single status screen of BR-001. The layout follows the maintainer's bench decisions of 2026-11-24. Protocols 2 and 3 are built in the firmware (`orange-case/operator-pad` #3 and #4, merged), protocol 4 is being built there; the pad service side is not built yet. The rows sit where the key rows are; editing a row from its page (the page keys) is #2747.

Iteration 3 (Open, #2747; spec only, nothing built): the page keys. The bench (2026-11-24) showed that UC-015's fixed keys do not line up with the rows (on `HOME`, K2 changes the sensitivity while row 2 shows the volume). With iteration 3 the keys follow the rows: the left key of a row edits its setting, the middle key resets it to its default, K5 (the agent) and K8 (the game) stay fixed on every page, and a long K4 hold locks the pad (A7 to A9, BR-011 to BR-016). This replaces UC-015's key layout (UC-015 BR-011, BR-016) with the display link up or down: without a screen the row keys act as on one fixed page (BR-016). The commands stay UC-015's (UC-015 BR-001 to BR-005, BR-010), plus two planned menu commands (`reset_setting`, `interventions_switch`, [services.md](../specs/services.md) §3.1).

## Preconditions

- **Pre-1:** UC-015 Pre-1 to Pre-3 hold: the `operator-pad` service runs, the pad is attached and the menu is RUNNING.
- **Pre-2:** The pad runs the operator-pad firmware, which answers the hello of BR-002 with protocol version 1 or higher (2 or higher for the pages, A5), and the service can open the pad's raw HID node read-write ([services.md](../specs/services.md) §3.1).
- **Pre-3:** `operator_pad.display_enabled` is on (default on, [flags.md](../specs/flags.md) §10a).

## Main Success Scenario

1. System (the pad service) attaches to the pad, sends the hello and gets protocol version 1 or higher: the display link is up (version 2 or higher: A5).
2. System reads `GetMenuStatus` every `operator_pad.display_poll_ms` (BR-003) and shows the status screen (BR-001; with protocol 2 or higher the pages of BR-006, A5): the game state, the selected mode, the ready and connected controllers, the agent (on, off or unknown, its level and its backend), the settings and the JoustMania version.
3. The menu status changes (a controller connects or readies up, a game starts, someone changes a setting from the dashboard): System redraws the status screen with no key pressed, within NFR-070's bound from the moment `GetMenuStatus` first reports the change (a setting changed elsewhere reaches the status with the menu's own delay, UC-015 BR-018).
4. Host holds a layer key (K1, K2, K3, K5, K6 or K7; planned, #2747: the edit key of a row, A7, BR-011) and turns the knob: from the first step System shows the setting screen (BR-001): which setting is being changed, its value at the press and the value the release would commit, updated per step (the value of the live preview, UC-015 BR-017); the preview speaks nothing (BR-005).
5. Host releases the layer key: UC-015 commits as before (UC-015 BR-005); System shows the result screen (BR-001) for `operator_pad.display_result_ms`, then the status screen.
6. Host turns the knob with no layer key held: System shows the volume screen (BR-001) with the level the turn would commit and plays no sound (BR-004); the commit after the pause is UC-015 step 8. With protocol 2 or higher the knob alone scrolls the pages and press and turn sets the volume (A5, BR-008).

## Alternative Flows

### A1: Display link down or old firmware

**Trigger:** the raw HID node is missing or cannot be opened, the firmware does not answer the hello with a version of 1 or higher, a frame write fails, or `operator_pad.display_enabled` is off (step 1, or any later step)
**Flow:**

1. System keeps every key, knob and cue of UC-015 working as before (FR-240): the display link is never needed to send a command, and a failed frame write never delays or drops a key event. Planned (#2747, FR-262): with the page keys the fixed keys (K4 lock, K5, K8) and the knob work as with the link up, and the row keys act as on the fallback page (BR-016), with UC-015's voice and sound cues.
2. System counts the link as down: the volume plays its short sound and the pad speaks its own voice lines again (BR-004, BR-005), and System retries the hello at the device rescan interval (UC-015 A4), never in a busy loop.
3. The firmware, after 3 s without a frame, shows its own `NO HOST` screen (BR-002); the keys keep sending their F key codes.
4. Use case ends; it starts again at step 1 when the link comes back.

### A2: Status unreadable

**Trigger:** a `GetMenuStatus` read fails or times out (step 2 or 3)
**Flow:**

1. System keeps the last values on the status screen and shows `NO CONNECTION` on its last line (BR-001); it does not queue or retry any command (UC-015 BR-010).
2. Use case continues at step 2 with the next read.

### A3: Refused, limit, cancel or failure

**Trigger:** a pad command of UC-015 ends without a commit: A1 `game_active`, A3 failure, A5 / A10 cancel, A7 limit (step 5)
**Flow:**

1. System shows the result screen with the UC-015 BR-009 word (`NOT POSSIBLE`, `FAILED`, `CANCELLED`, `MAXIMUM`, `MINIMUM`, `NO CONNECTION`) besides the cue, then the status screen.
2. Use case ends.

### A4: A lobby-only layer while the game is live

**Trigger:** Host holds K1, K2, K5 or K6 and turns the knob while the lifecycle is live (step 4; UC-015 A1)
**Flow:**

1. System shows the setting screen with `NOT POSSIBLE` on its last line and no new value; the release is refused as in UC-015 A1.
2. Use case ends.

### A5: Pages and knob scrolling (protocol 2 or higher)

**Trigger:** the firmware answers the hello with version 2 or higher (step 1)
**Flow:**

1. System shows the `HOME` page (BR-006) instead of the status screen, and draws the setting, result, tap and volume screens in the same frame (BR-007); steps 3 to 5 and A2 to A4 apply to the page showing, and the internet check of BR-010 runs.
2. Host turns the knob alone: System shows the next page (clockwise) or the previous one (counter-clockwise), one page per knob step, wrapping, and sends no command (BR-008).
3. Host presses the knob and turns it while it is down: System sets the master volume one variant per step and commits after the pause as in UC-015 step 8, showing the volume screen without a sound (BR-004, BR-008).
4. Host presses the knob and releases it within the tap limit without a turn: System mutes or unmutes (BR-008).
5. Use case continues at step 3.

### A6: Pages turn on their own

**Trigger:** the pages show (A5), no key and no knob press is down and no setting, result, tap or volume screen shows (step 2)
**Flow:**

1. System shows the next page every `operator_pad.display_autopage_ms` (BR-009); with the flag at `off` the page stays.
2. Host scrolls with the knob (A5 step 2): System stops the cycling and keeps the page Host chose.
3. When `operator_pad.display_home_ms` have passed since the last key or knob input and the page is not `HOME` or the cycling has stopped, System shows `HOME` once and the cycling resumes (BR-009).
4. Use case continues at step 3.

### A7: Edit a row from its page (planned, #2747)

**Trigger:** Host presses the edit key of a row (K1, K3 or K6, BR-011) whose setting the page lets the keys change (BR-012) (step 2, or A5)
**Flow:**

1. System draws that row inverted (the highlight, BR-006) while the key is down and the knob has made no step; the page stays for the whole hold (BR-011).
2. Host releases within the tap limit: System shows the tap screen with the row's label and value (BR-007; without a screen UC-015's announcement, BR-016). Use case ends.
3. Host turns the knob while the key is down: System shows the setting's edit screen (BR-007: marker bar, wheel, or NOW and NEW rows) with the live preview of UC-015 BR-017, and nothing is written.
4. Host releases the key: System commits the setting once with the menu command of BR-012 (UC-015 BR-005) and shows the result screen (step 5); a raise of the agent needs the confirmation of A9 first.
5. Use case ends; a refusal, limit or failure is A3, a lobby-only setting while the game is live A4.

### A8: Reset a row to its default (planned, #2747)

**Trigger:** Host presses the reset key of a row (K2, K4 or K7, BR-011) whose setting has a reset (BR-012, BR-013) (step 2, or A5)
**Flow:**

1. System draws the row inverted while the key is down (BR-006).
2. Host releases within the tap limit: System shows the tap screen with the row's label and `DEFAULT` with the default (BR-013); nothing is written. Use case ends.
3. Host holds the key for `operator_pad.hold_reset_ms` (default 1000): System shows the reset screen (BR-007): the setting's label and `RESET?`, `NOW` and the value, `NEW` and the default, the hint `RELEASE TO RESET`.
4. Host releases the key: System sends `reset_setting` for the row's setting ([services.md](../specs/services.md) §3.1) and shows the result screen; a reset that raises the agent needs the confirmation of A9 first.
5. Use case ends. A release between the tap limit and the reset hold does nothing (UC-015 BR-007). A K4 hold that reaches the lock time is the lock instead of the reset (BR-015).

### A9: A raise of the agent waits for a confirmation (planned, #2747)

**Trigger:** in A7 or A8 the value the release would commit raises what the agent may do (BR-014) (step 4)
**Flow:**

1. System shows `CONFIRM?` on the right of the title bar and the hint `PRESS TO CONFIRM` instead of `RELEASE TO SET` / `RELEASE TO RESET`.
2. Host presses the knob while the key is still down: System marks the value showing as confirmed and shows `RELEASE TO SET` (or `RELEASE TO RESET`); a later knob step clears the confirmation.
3. Host releases the key: with the value confirmed System commits it (A7 step 4, A8 step 4); without, it sends nothing and shows `CANCELLED` (the cancel cue, UC-015 BR-009).
4. Use case ends.

## Postconditions

### Success Postconditions

- The pad's screen shows the status screen (a page with protocol 2 or higher, A5) with values no older than NFR-070 allows, or the screen of the gesture in progress. No flag, setting or game state was changed by this use case: it only shows. Planned (#2747): the page keys (A7, A8) send UC-015's commands and the planned `reset_setting` and `interventions_switch`; what they change is UC-015's postconditions.

### Failure Postconditions

- The pad works as in UC-015 (FR-240); the screen shows `NO HOST` (firmware, no frames) or the last values with `NO CONNECTION` (A2).

## Business Rules

### BR-001: Screens

The display is 128x64 pixels, drawn as 8 text lines of 21 characters (the firmware's 6x8 font), numbered 0 to 7 as in BR-002 throughout this use case; line 0 is the title, drawn inverted. The pad service composes every screen; the firmware only draws lines (BR-002). Every value comes from the last `GetMenuStatus` read (BR-003) or, on the setting screen, from the live preview (UC-015 BR-017). A value the status does not tell (an agent state the menu reports as unknown, a missing key in `operator_settings` outside status line 5, no status at all) shows as `?`, never a guess. Sensitivity and teams on status line 5 have one rule: `AUTO` when `operator_settings` reports `automatic` for the setting, otherwise the effective `sensitivity` / `num_teams` of the status in short form, also when the key is missing (the status has no "unknown" for the effective values: for a flag flagd cannot resolve that is the menu's default). The result screen shows the value the menu reports as committed (`ProcessInputResponse.value`, [services.md](../specs/services.md) §3.1), never the pad's own prediction; with no `value` (a menu older than that field, or a command that commits no value) it shows the label and the UC-015 BR-009 word, or `OK` on success. With protocol 1 there are no display pages: one screen shows at a time; with protocol 2 or higher the knob scrolls the pages of BR-006 (iteration 2, #2742). K8's tap stays reserved either way (UC-015 BR-011; planned, #2747: it starts a game, BR-011). Values are written in the short forms below, so that every line fits in 21 characters; a mode is its full name of the mode table (BR-006; planned, #2742: until then its `Games` name in capitals), any value not in the tables is the name in capitals, cut to fit.

| Setting | Short forms |
|---|---|
| Sensitivity (`ultra_slow` to `ultra_fast`) | `AUTO`, `0`, `1`, `2`, `3`, `4` |
| Teams (`two` to `six`) | `AUTO`, `2`, `3`, `4`, `5`, `6` |
| Shield mode | `AUTO`, `INST`, `TRIG`, `HOLD` |
| Volume | `MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX` |
| Agent level | `NONE`, `AMBIENT`, `STANDARD`, `FULL` |
| Backend | `RULES`, `CLAUDE`, `OPENAI`, `JEV` |

| Screen | When | Lines |
|---|---|---|
| Status | default: no layer key held, no result, tap or volume screen showing | 0 `JOUSTMANIA` and the state: `LOBBY`, or `GAME` while the game lifecycle is live (the status does not tell starting, running and ending apart); 1 the selected mode's full name (the mode table of BR-006; planned, #2742: until then its `Games` name in capitals); 2 `READY <ready>/<connected>`; 3 the agent, so the screen never disagrees with what a K3 hold would do: `AGENT ?` when UC-015 BR-013 counts the status as unknown (`agent_enabled_state` or `agent_interventions_enabled_state` not `on` or `off`, or `agent_level` empty or outside the ladder of UC-015 BR-004), else `AGENT OFF` when UC-015 BR-002 counts the agent as stopped (`agent_enabled` off, level `none` or the write gate `off`), else `AGENT ON` and the level's short form; 4 `BACKEND` and its name; 5 `SENS` and `TEAMS` (the line 5 rule above); 6 `SHIELD` and `VOL`; 7 `NO CONNECTION` (A2), else `LOCKED` (UC-015 A6), else the JoustMania version: `V` and the release tag the stack runs (a tag that already starts with `v` or `V` is shown with a single `V`, never `VV`), or `DEV` without one, also for an image tag that is not a release (`latest`, `main`, a commit sha) (FR-241) |
| Setting | a layer key is the only key down and the knob has made at least one step (the UC-015 BR-017 condition) | 0 the setting's label (`GAME`, `SENSITIVITY`, `AGENT LEVEL`, `TEAMS`, `SHIELD MODE`, `BACKEND`); 2 `NOW` and the value read at the press; 4 `NEW` and the value the release would commit; 5 the ladder with the new value marked (`AUTO 0 1 2 [3] 4`) where it fits on one line; 7 `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range (ladder settings only; the mode, the backend and the shield mode wrap, BR-007), or `NOT POSSIBLE` (A4) |
| Volume | a knob turn or press with no layer key held | 0 `VOLUME`; 2 the variant the turn would commit (`MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX`); 4 a bar of the five rungs; 7 `MUTED` while muted, or `MAXIMUM` / `MINIMUM` when a turn hits the end of the range. Shown for `operator_pad.display_result_ms` after the last turn |
| Result | from the release until the menu answers: the label alone, at most the command's deadline; after a commit, a refusal, a cancel or a failure (step 5, A3): the result | 0 the label of the command; 2 empty while the menu has not answered, then the value the menu committed (`ProcessInputResponse.value`, short form), or the UC-015 BR-009 word (`FAILED` for any error without one), or `OK` for a success without a `value`; the result shown for `operator_pad.display_result_ms` (default 1500), then the status screen |
| Tap | after a tap UC-015 announces (K2, K3, K5, K7; UC-015 BR-011) | 0 the label (`SENSITIVITY`, `AGENT`, `TEAMS`, `BACKEND`); 2 the value read at the tap in short form (K3: as status line 3, without `AGENT`), or `?` when the status does not tell it; shown for `operator_pad.display_result_ms`, then the status screen |

A new screen replaces the one showing at once (a new layer step replaces a result still showing). A K3 hold (stop / resume the agent) and a K4 hold (end / force-start) show their result like every command.

This is the layout for a pad that answers protocol 1. A pad that answers protocol 2 or higher gets the pages of BR-006 instead of the status screen and the setting, volume, result and tap screens of BR-007; the values, their sources, the `?` rule and the "When" column above stay, and so do the short forms where a row has no room for the full word.

### BR-002: Display link and frame protocol

The pad service writes to the pad's raw HID interface (the Vial / VIA interface: usage page `0xFF60`, usage `0x61`, 32-byte reports) on the device `operator_pad.device` matches (UC-015 BR-014). Every report starts with the command id `0x50`, which is not a VIA or Vial command id, then an op:

| Op | Bytes | Meaning | Reply |
|---|---|---|---|
| `0x00` hello | none | asks the protocol version | `0x50 0x00 <version>`; version 1 (2, 3 or 4 with protocols 2 to 4, below) |
| `0x01` line | 2: line 0 to 7 (with the medium bit: the medium row 0 to 2, protocol 3); 3: attributes (bit 0 inverted; from protocol 2 bit 1 large, bit 2 underline; from protocol 3 bit 3 medium); 4 to 24: 21 ASCII characters (0x20 to 0x7E, space padded; any other byte draws as `?`) | writes one line into the back buffer | `0x50 0x01 0x00`; a line number of 8 or more, or a medium row above 2: `0x50 0x01 0xFF`, nothing written |
| `0x02` show | 2: frame sequence number | draws the back buffer; also the heartbeat | `0x50 0x02 0x00` |

An unknown op is answered `0x50 <op> 0xFF` and changes nothing. The service sends the 8 lines and a show for each screen that differs from the last one shown, and a show alone at least once a second. The firmware draws only on show, so a half-sent frame is never seen. With no show for 3 s it draws its own `NO HOST` screen; after a power-up it shows `JOUSTMANIA` and `WAITING FOR HOST`. The keys never depend on the link (A1). Vial's own commands keep working, so the Vial app can still read and change the keymap.

**Protocol 2** (#2742; `orange-case/operator-pad` #3, merged; revisions 1 to 5). Everything above holds, with these additions: the hello is answered with version 2; in the `line` op's attribute byte bit 1 means large and bit 2 underline; and the bytes `0x7F` to `0x84` draw glyphs instead of `?`: `0x7F` a full bar block, `0x80` an empty bar block, `0x81` internet, `0x82` agent, `0x83` instructions, `0x84` lock (BR-006). A large line n (0 to 6) draws the first 10 characters of its text in a 12x16 pixel font (each pixel of the 6x8 font doubled) over display lines n and n+1 (pixel columns 0 to 119; columns 120 to 127 stay blank, or are filled when the line is also inverted); the content written to line n+1 is ignored for that frame. A large bit on line 7 draws the line small. An underlined line gets a 1 px line across the full width on its bottom pixel row (a large line n on the bottom row of line n+1), dark when the line is inverted; no glyph uses that row.

**Protocol 3** (#2742; `orange-case/operator-pad` #4, merged; rev 5 only). Everything of protocol 2 holds, with these additions: the hello is answered with version 3, bit 3 of the `line` op's attribute byte means medium, the byte `0x85` draws the marker (a down-pointing triangle), and a new op draws a bar. The ATmega32U4 of revisions 1 to 4 has no flash left for a second font, so its firmware stays at protocol 2: its hello answers 2, it ignores bit 3 and answers `0x50 0x03 0xFF` to the bar op; it draws the marker glyph `0x85` in its small font too.

- **Medium row.** A `line` op with the medium bit addresses medium row r (0 to 2) in its line byte; rows 0, 1 and 2 are rows 1, 2 and 3 of the frame (BR-006). The row is stored as display line 1 + 2r and, like a large line, covers display lines 1 + 2r and 2 + 2r (row 0 lines 1-2, row 1 lines 3-4, row 2 lines 5-6): the content of line 2 + 2r is ignored for that frame, and a later small or large write to line 1 + 2r replaces the row. It draws the first 16 characters of its text in an 8x12 pixel font, 8 px per character across the full 128 px, its 12 pixel rows starting at pixel row 11 + 15r, so 3 px separate the title bar, the rows and the divider. Inverted (bit 0) fills the row's 12 pixel rows (the highlight); underline (bit 2) draws the 1 px divider on the bottom pixel row of the row's slot (pixel row 23, 39 or 55), always lit since it lies below the inverted band; on row 2 it is the divider above the status bar. The large bit is ignored on a medium row. The font is X.Org misc-fixed (public domain) at 8x12, with the same glyphs as the small one: ASCII `0x20` to `0x7E` and `0x7F` to `0x85`.
- **Bar** (op `0x03`; report `0x50 0x03 <row> <rungs> <filled> <marker> <labels>`): byte 2: the bar row r (0 or 1); 3: the rungs (2 to 8; 0 removes the bar); 4: the filled rungs (0 to the rungs, from the left); 5: the marker rung (0 to the rungs - 1, or `0xFF` for no marker); 6 to 31: the rung labels, ASCII separated by `|`, ended by `0x00` or the end of the report, label k under rung k (a missing or empty label stays blank, extra ones are ignored). The bar at row r covers display lines 1 + 2r to 4 + 2r (pixel rows 8 + 16r to 39 + 16r, medium rows r and r + 1); the content of those lines is not drawn. Within those 32 pixel rows, from the top: the marker (the `0x85` shape) on rows 6-9, centred over its rung; the bar on rows 12-20, rungs of equal pitch (128 / rungs px) with a 2 px gap, centred, the first `filled` rungs solid and the rest a 1 px outline; the labels in the small font on rows 23-29, each centred under its rung and kept on screen, never cut: a label wider than its rung (`AUTO` under the first of six rungs) starts at the left edge. An underline on the bar's last line (4 + 2r) is still drawn. The bar is part of the back buffer and is drawn on show. Writing any line it covers (a small, large or medium `line` op) removes it, so the host sends the bar after the lines of its frame. Reply `0x50 0x03 0x00`; any other value out of range: `0x50 0x03 0xFF`, nothing drawn.

**Protocol 4** (planned, #2742; an `orange-case/operator-pad` PR in progress; rev 5 only, revisions 1 to 4 stay at protocol 2). Everything of protocol 3 holds, with these additions; the exact ops, attribute bits and byte layout are those of the firmware's README (`orange-case/operator-pad`, `firmware/`), which this rule does not repeat:

- **Hello** answered with version 4.
- **NOW arrows**: the bytes `0x86` (a right-pointing triangle, ▸) and `0x87` (a left-pointing triangle, ◂) draw glyphs in the small 6x8, the medium 8x12 and the tall font. A firmware below protocol 4 draws `?` for them, like any byte without a glyph.
- **Tall font**: an 8x16 pixel font (Spleen 8x16, BSD-2-Clause) for the middle row of the wheel, up to 16 characters across the 128 px.
- **Centred text**: a small or medium line can be drawn centred, pixel-exact across the full width, instead of flush left (a large line ignores it); the tall row exists only as the wheel's middle entry, which is always centred.
- **Wheel**: one documented scheme (a wheel op or row attributes, the firmware's choice) draws the three entries of the wheel of BR-007 between the title bar and the divider: the entry above in the small font, the middle entry in the tall font, inverted across the full row width, the entry below in the small font, each centred, with even gaps (8 + 16 + 8 pixel rows); NOW is marked by the arrows of its entry.

The pad service treats any version of 1 or higher as the link up and uses a feature only when the hello reports its version: protocol 4 the wheel (BR-007), protocol 3 the medium rows and the marker bar (BR-006, BR-007), protocol 2 the big-font layout of the same pages (large rows, the glyphs, the underline), protocol 1 the screens of BR-001. A version above 4 is used as 4. A pad that answers protocol 3 gets the protocol 3 layout with the NOW and NEW rows instead of the wheel (BR-007); protocols 2 and 1 are as above.

### BR-003: Status refresh

While the display link is up, the pad service reads `GetMenuStatus` every `operator_pad.display_poll_ms` (default 500) besides the reads of UC-015's key presses and releases, and redraws the status screen when a shown value changed. The polled status is for the screen only: a command still uses the status read at its own press or release (UC-015 A5, BR-013).

### BR-004: Volume without a sound

The menu plays the volume step sound of a volume step and of a mute or unmute (its `step_setting` for `audio_volume.master`), so the pad silences it through the menu: while the display link is up, the pad sends that `step_setting` with `cue=none` ([services.md](../specs/services.md) §3.1), the menu skips the volume step sound, and the volume screen (BR-001) shows the level instead. A menu older than the `cue` key ignores it and the sound plays. With the link down (A1) the pad sends no `cue` and the short sound of UC-015 step 8 plays as before, so a pad without a screen still gives feedback.

### BR-005: The pad's own voices with a screen

### BR-007: Setting, volume, result and tap screens (protocol 2 or higher)

With protocol 2 or higher the setting, volume, result and tap screens of BR-001 show when BR-001 says (the volume screen on a volume step or a mute of BR-008 only, never on a page step), for as long as it says, in the frame of BR-006: the status bar stays.

- **Ladder settings**: the sensitivity (rungs `AUTO 0 1 2 3 4`), the teams (`AUTO 2 3 4 5 6`), the agent level (`NONE AMB STD FULL`) and the volume (`MUTE QUIET NORM LOUD MAX`). Protocol 3 or higher: the marker bar (the bar op, BR-002) at bar row 0, over rows 1 and 2, one rung per ladder value: the marker above the rung of the value at the press (NOW; no marker while that value is unknown), the rungs filled up to and including the rung the release would commit (NEW). Labels: the sensitivity, the teams and the agent level a label under every rung (`AUTO|0|1|2|3|4`, `AUTO|2|3|4|5|6`, `NONE|AMB|STD|FULL`); the volume only at the ends, `MUTE` under the first rung and `MAX` under the last (`MUTE||||MAX`). Row 3 (medium row 2) holds the hint `RELEASE TO SET` (empty on the volume screen, which commits after the pause) with the underline as the divider. The service sends the bar after the frame's lines, since a line written over the bar removes it (BR-002). Title bar: the setting's label (`SENSITIVITY`, `TEAMS`, `AGENT LEVEL`, `VOLUME`) left and `EDIT` right; `MAXIMUM` / `MINIMUM` right instead when a step hits the end of the range (the ladder settings stay clamped, UC-015 BR-005, A7), and on the volume screen `MUTED` right while muted. For the volume the value at the press is the level when the turn began.
- **Wheel settings**: the mode (the full names of the mode table of BR-006, in `MODE_LADDER` order), the decision backend (`RULES`, `CLAUDE`, `OPENAI`, `JEV`; `BACKENDS` order) and the shield mode (`AUTO`, `INSTANT`, `TRIGGER`, `HOLD`; `SHIELD_KNOB_LADDER` order), none of them an ordered scale; the shield mode's values are kinds of activation, not levels, so it gets no marker bar. The goal profile has no edit screen: it is read-only on the pad and changes only in Flagsmith (BR-006, FR-226). Protocol 4: a vertical wheel that wraps, drawn by the wheel of BR-002. Title bar: the setting's label left, `EDIT` right; then the divider and the status bar of the frame (BR-006); there is no hint row. Between the title bar and the divider the wheel shows three entries in ladder order, wrapping at both ends (after the last option comes the first, before the first the last), so there is always one entry above and one below the middle; every wheel setting has at least four options. The middle entry is NEW, the option the release would commit, in the tall 8x16 font, centred and inverted across the full row width; the entry before it (above) and the entry after it (below) are in the small 6x8 font, centred, not inverted; the gaps between the title bar, the three entries and the divider are even. Each entry is its full name (no short forms; at most 16 characters in the tall row), so the wheel never looks like a page (label left, value right). The option read at the press (NOW) carries a right-pointing triangle (`0x86`) directly left and a left-pointing triangle (`0x87`) directly right of its centred text (`▸FREE-FOR-ALL◂`, BR-002), in whichever of the three entries it is, drawn dark inside the inverted middle row when NOW is NEW; while NOW is not among the three, or unknown, no entry has them. A full name has at most 14 characters, so the arrows always fit. Each knob step turns the wheel one option, NEW staying in the middle. **Shield `AUTO`**: `AUTO` is a wheel entry like the modes (the `automatic` rung of UC-015 BR-018); with no operator shield value (`operator_settings` reports `automatic`) NOW is `AUTO`, not the effective mode, and the knob starts there; committing `AUTO` clears the operator value (UC-015 BR-018). This changes UC-015 BR-018's knob start for the shield mode only (built with the wrap, #2742; `lib/setting_ladders.py` `knob_start`); sensitivity and teams keep theirs.
- **Wrap**: for the mode, the backend and the shield mode a step past the last option goes to the first, and back past the first to the last, with the display link up or down: the wrap is a property of these settings, not of the screen, so UC-015 changes for them regardless of the link (UC-015 BR-005, A7; built by a UC-015 PR of its own before the pad service's display PR, #2742: the menu's `step_setting` and the pad's preview and backend step over `lib/setting_ladders.py` `step_ladder`, where an explicit per-option set `WRAPPING` names the wrapping options, never a default). The backend wraps in the pad's own step before the absolute `set_backend` (`RULES` back to `JEV`): the wheel shows where the release lands and nothing commits before it. A net turn count that is a whole number of turns of the wheel (n a multiple of the number of options, zero included) is a no-op: nothing is written and no cue plays, never `at_limit` (the menu answers `step_setting` with `ok` and the unchanged value; the pad sends no `set_backend`). They never give `at_limit`, `MAXIMUM` or `MINIMUM`. The ladder settings (sensitivity, teams, agent level, volume) stay clamped, with the marker bar and `MAXIMUM` / `MINIMUM` at the ends; so does the saved-level ladder a stopped agent's K3 + knob moves (UC-015 BR-003), since the level ladders back the kill switch.
- **NOW and NEW rows**: on protocol 2 every setting, on protocol 3 the wheel settings (no wheel below protocol 4), and on any protocol every setting whose step is refused (A4). Rows: 1 `NOW` and the value read at the press; 2 `NEW` and the value the release would commit (empty when refused); 3 the hint `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range (ladder settings only), or `NOT POSSIBLE` (A4). Title bar: the setting's label left, `EDIT` right. On protocol 2 a ladder setting shows its bar of BR-006 as the value where it has one.
- **Result**: title bar the command's label; row 2 the value the menu committed (`ProcessInputResponse.value`), the UC-015 BR-009 word, or `OK` (BR-001), the full word where it fits; row 2 stays empty until the menu answers; rows 1 and 3 empty. On protocol 2 a word over 10 characters takes rows 2 and 3 (`NOT` / `POSSIBLE`, `NO` / `CONNECTION`).
- **Tap**: as the result screen, with the value read at the tap (BR-001).

- **Two-state settings** (planned, #2747: instructions, force all, interventions; BR-012): NOW and NEW rows on every protocol (`OFF` / `ON`; a two-option scale is neither a marker bar nor a wheel), clamped (up is `ON`, a step past either end is `MAXIMUM` / `MINIMUM` as for the ladders).
- **Reset** (planned, #2747; A8, BR-013): from `operator_pad.hold_reset_ms` on, title bar the setting's label left and `RESET?` right, rows `NOW` and the value, `NEW` and the default (BR-013; `?` while unknown), hint `RELEASE TO RESET` (`PRESS TO CONFIRM` while a raise waits, BR-014). On every protocol NOW and NEW rows, never a bar or wheel. On K4, from `operator_pad.hold_lock_ms` on, the lock screen replaces it (BR-015).

The reset screen comes with the page keys of #2747. When a result, tap or volume screen ends, the page that showed before it comes back (`HOME` when BR-009 returns there in the meantime).

### BR-008: The knob with the pages (protocol 2 or higher)

While the display link is up with protocol 2 or higher and no layer key is down, the knob works as follows; a step is a knob step of UC-015 BR-005 (`operator_pad.knob_events_per_step`):

- **Turn alone** (the knob not pressed and no key down at all): one page per step, clockwise (B) to the next, counter-clockwise (A) to the previous, wrapping (`SYSTEM` to `HOME` and back). The page shows at once; a step sends no command, plays nothing and, while a result, tap or volume screen shows, ends it and counts from the page under it.
- **Press and turn**: each step while the knob is down sets the master volume one variant (UC-015 BR-006), committed after the same pause as UC-015 step 8 (UC-015 BR-005), with the volume screen and no sound (BR-004). The release of that press does nothing else.
- **Short press**: a knob press released within the tap limit (`operator_pad.tap_ms`, UC-015 BR-007) with no step while it was down mutes or unmutes, at the release (with protocol 1 or no link the mute fires at the press, UC-015 BR-016). A longer press without a step does nothing.

A locked pad (UC-015 A6) still scrolls the pages, which send nothing; the volume and the mute stay blocked as UC-015 A6 says. With a layer key down the knob is that layer's, as in UC-015 BR-007 and BR-017. With K4 or K8 down (keys without a layer) a turn does nothing: no page step and no volume, as in UC-015 without a display. With protocol 1 the knob is step 6; with the link down it is UC-015 step 8 (FR-240). The K8 tap stays reserved (UC-015 BR-011). Planned (#2747, BR-011): the keys without a layer become the reset keys K2, K4 and K7 and the fixed keys K5 and K8 (a turn with one of them down does nothing; a knob press while a reset key or an edit key is down is the confirmation of BR-014, never a mute), and the K8 tap starts a game.

### BR-009: Auto-paging and return to Home (protocol 2 or higher)

While the pages show, no key and no knob press is down and no setting, result, tap or volume screen shows, the pad shows the next page in the order of BR-006 every `operator_pad.display_autopage_ms` (default 5000) after a page was shown; at `off` (0) the page stays. A page step by the knob (BR-008) stops the cycling. Return to Home: once, `operator_pad.display_home_ms` (default 10000) after the last key or knob input of any kind, and only when the page is not `HOME` or the cycling has stopped, the pad shows `HOME` and the cycling resumes (with `display_autopage_ms` at `off` it shows `HOME` and stays); with no key or knob input since the link came up there is no return. A menu status change neither moves the page nor restarts a timer.

### BR-010: Internet check

While the display link is up with protocol 2 or higher, the pad service checks general internet access itself (not the agent's backend, not Flagsmith): a TCP connect to `operator_pad.internet_check_target` (`host:port`, default `google.com:443`) every `operator_pad.internet_check_ms` (default 30000), with a connect timeout of 3 s. A connect that succeeds counts as reachable and is closed at once with nothing sent; a failed name lookup, a refused connect or the timeout count as down. A TCP connect needs no raw-socket privilege (an ICMP ping would), so the service stays unprivileged. One check runs at a time and never delays a key event, a frame or a status read. The status bar shows the internet icon while the last check succeeded, and `SYSTEM` row 2 shows the state (BR-006); before the first check ends the icon is hidden and the row shows `?`. With the target at `off` no check runs, the icon stays hidden and the row shows `OFF`. A failed read of the target flag keeps the last good value (the default `google.com:443` only before the first good read), so a flaky read never turns a check that was `off` back on ([flags.md](../specs/flags.md) §10a).

### BR-013: Reset and the default (planned, #2747)

A reset sends one `reset_setting` ([services.md](../specs/services.md) §3.1, planned) on the release of a reset hold (A8), whatever the setting's value; it is not a step and has no `steps`.

- **The flag file's default** for the others (`game_instructions`, `force_all_start`, `agent_level` = `interventions_allowed`, `decision.backend`): one clear of the operator's persisted value, so the baseline (or an in-memory stage overlay, which wins while it lasts, [flags.md](../specs/flags.md) §13) applies again. The reset screen's NEW is the baseline default the planned status field `setting_defaults` reports ([services.md](../specs/services.md) §3.1); `?` while it does not report one. The menu says the value now in force with the setting's usual voice line (UC-012, UC-015).
- **A stopped agent's level** (UC-015 BR-002): the reset writes nothing and sets the saved level to the default, as the ladder does (UC-015 BR-003), so a reset never resumes an agent.
- **No reset** for the mode, the volume (decisions D-3, D-4), the interventions switch and every read-only row.
- **Tap** on a reset key: the tap screen with the row's label and `DEFAULT` and the default (`AUTO`, or the `setting_defaults` value, `?` while unknown); without a screen the pad says the label and the default as a UC-015 BR-011 announcement.
- A reset of a setting that has no operator value is a no-op: nothing is written, the menu answers `ok` with the unchanged value and plays nothing (as UC-015 BR-005's net-zero step). A reset that fails is UC-015 A3 (`flag_service_unavailable`).

### BR-014: A raise of the agent needs a confirmation (planned, #2747)

A page-key edit or reset that raises what the agent may do commits only after a knob press while its key is still down (A9; #2050 decision 6); one that lowers it, or leaves it, commits on release as before. A raise is: an `agent_level` edit to a higher rung of UC-015 BR-004's ladder (none, ambient, standard, full), the saved level of a stopped agent included (it is what the K5 resume applies); a level reset whose default is above the level; the interventions switch to `ON`. When the level, its default or the gate is unknown the change counts as a raise (fail closed). The backend, the goal and every game setting are not raises. The confirmation belongs to the value showing at the press: a later knob step clears it. A release without it sends nothing and shows `CANCELLED` (UC-015 BR-009's cancel). The K5 resume is unchanged: it needs no confirmation (UC-015 BR-003). This replaces UC-015 BR-004's "escalation or restriction alike" for the page keys. The check is the pad's: the menu commands take no confirmation field, so an older pad without the page keys behaves as UC-015 says. Without a screen the fallback page has no agent row (BR-016), so no raise can be made blind.

### BR-015: K4: reset, then lock (planned, #2747)

The lock of UC-015 A6 moves from the K8 3 s hold to K4: a K4 hold of `operator_pad.hold_lock_ms` (default 3000) locks or unlocks the pad on release, on every page. K4 is also row 2's reset (BR-011), so a K4 hold goes through two stages:

1. From the press: the row 2 highlight (BR-006).
2. From `operator_pad.hold_reset_ms` (1 s): the reset screen with `RESET?` (BR-007); a release now is row 2's reset (A8).
3. From `operator_pad.hold_lock_ms` (3 s): the reset is cancelled and the lock screen shows: title `PAD` left and `LOCK?` (or `UNLOCK?` while locked) right, hint `RELEASE TO LOCK` / `RELEASE TO UNLOCK`; a release now toggles the lock (UC-015 A6: the Scroll Lock LED, the lock icon of BR-006, the `SYSTEM` row 3; the lock words only without a screen, BR-005).

On a page whose row 2 has no reset (read-only or empty), stage 2 is skipped: a release before 3 s does nothing. While the pad is locked, K4 has no reset stage: only the 3 s hold, which unlocks. `operator_pad.hold_reset_ms` must be below `operator_pad.hold_lock_ms` and above the tap limit; when the timing flags break that, the pad keeps the default timings and logs a warning (UC-015 BR-007). A K4 lock hold changes no setting: the reset is never sent once the 3 s are reached.

### BR-016: Without a screen (planned, #2747)

While the display link is down (A1) or the pad answers protocol 1 (no pages, BR-002), the row keys act as on the fallback page `HOME` (decision D-6; BR-012: K1 / K2 the mode, K3 / K4 the volume, K6 / K7 the sensitivity), and the fixed keys K4 (lock), K5 and K8 and the knob work as with the link up (the knob alone: the volume, UC-015 step 8). The cues are UC-015's: a tap says the row's label and value (UC-015 BR-011 announcements; the labels the voice catalog lacks, "Game mode" and "Volume", are new lines of [UC-031](UC-031.md) BR-007), a hold + knob speaks the live preview (UC-015 BR-017), the volume plays its sound (BR-004), the lock words play (UC-015 A6). The reset hold plays nothing while held; the menu's voice line says the result. With protocol 1 the setting, result and tap screens of BR-001 show as before; there is no highlight. `HOME` is the fallback because it holds the mode, the setting the host changes most (UC-015's goal), and the sensitivity, while the kill switch, the start and end and the volume stay on fixed keys and the knob; teams, the shield mode, instructions, the agent level and the backend are then set from the dashboard or the admin controller (UC-012) until the screen is back. This changes FR-240's "exactly as in UC-015" to "as this layout without a screen" (FR-262).
