# Use Case: See the Game State on the Operator Pad

## Overview

**Use Case ID:** UC-016
**Use Case Name:** See the Game State on the Operator Pad
**Primary Actor:** Host
**Goal:** See on the operator pad's own screen, without a laptop and without waiting for a voice line, what the lobby looks like (game state, selected mode, ready and connected controllers, the agent) and, while turning the knob, which setting is being changed and to what
**Trigger:** The pad service attaches to the pad and its display link comes up; the menu status changes; Host holds a layer key and turns the knob, turns the knob alone, or a pad command ends
**Status:** Implemented
**Requirements:** FR-236, FR-237, FR-238, FR-239, FR-240, FR-241, FR-242, NFR-070

Phase 2 of the operator pad (#2741): [UC-015](UC-015.md) is phase 1, the keys and the knob with voice, sound and LED cues. This use case adds the pad's 128x64 OLED. The firmware is a Vial keymap for the 0xCB 1337 in the `orange-case/operator-pad` repository (`firmware/`); it draws what the pad service sends over the pad's raw HID interface (BR-002) and holds no game logic. The pad is a rev 5 (RP2040), for which QMK and Vial have no keyboard definition, so the repository brings its own (`keyboard/`, built as `orange_case/operator_pad`); revisions 1 to 4 (ATmega32U4) build the same keymap as `0xcb/1337`. While the screen works it replaces the pad's own voice lines and the volume sound (BR-004, BR-005); every other cue of UC-015 stays. The firmware side of BR-002 is built and bench-tested on a rev 5 pad (`orange-case/operator-pad` #1); the pad service side is built (#2741: `services/operator_pad/`, the menu's `cue` key and `ProcessInputResponse.value`, the `operator-pad` compose service and the udev rule). Only the check on the Pi 5 with the real pad is still pending (the measurement of NFR-070 and the bench check of the link): FR-236 to FR-242 are Implemented, not Verified, until then, and NFR-070 stays Open.

## Preconditions

- **Pre-1:** UC-015 Pre-1 to Pre-3 hold: the `operator-pad` service runs, the pad is attached and the menu is RUNNING.
- **Pre-2:** The pad runs the operator-pad firmware, which answers the hello of BR-002 with protocol version 1, and the service can open the pad's raw HID node read-write ([services.md](../specs/services.md) §3.1).
- **Pre-3:** `operator_pad.display_enabled` is on (default on, [flags.md](../specs/flags.md) §10a).

## Main Success Scenario

1. System (the pad service) attaches to the pad, sends the hello and gets protocol version 1: the display link is up.
2. System reads `GetMenuStatus` every `operator_pad.display_poll_ms` (BR-003) and shows the status screen (BR-001): the game state, the selected mode, the ready and connected controllers, the agent (on, off or unknown, its level and its backend), the settings and the JoustMania version.
3. The menu status changes (a controller connects or readies up, a game starts, someone changes a setting from the dashboard): System redraws the status screen with no key pressed, within NFR-070's bound from the moment `GetMenuStatus` first reports the change (a setting changed elsewhere reaches the status with the menu's own delay, UC-015 BR-018).
4. Host holds a layer key (K1, K2, K3, K5, K6 or K7) and turns the knob: from the first step System shows the setting screen (BR-001): which setting is being changed, its value at the press and the value the release would commit, updated per step (the value of the live preview, UC-015 BR-017); the preview speaks nothing (BR-005).
5. Host releases the layer key: UC-015 commits as before (UC-015 BR-005); System shows the result screen (BR-001) for `operator_pad.display_result_ms`, then the status screen.
6. Host turns the knob with no layer key held: System shows the volume screen (BR-001) with the level the turn would commit and plays no sound (BR-004); the commit after the pause is UC-015 step 8.

## Alternative Flows

### A1: Display link down or old firmware

**Trigger:** the raw HID node is missing or cannot be opened, the firmware does not answer the hello with version 1, a frame write fails, or `operator_pad.display_enabled` is off (step 1, or any later step)
**Flow:**

1. System keeps every key, knob and cue of UC-015 working as before (FR-240): the display link is never needed to send a command, and a failed frame write never delays or drops a key event.
2. System counts the link as down: the volume plays its short sound and the pad speaks its own voice lines again (BR-004, BR-005), and System retries the hello at the device rescan interval (UC-015 A4), never in a busy loop.
3. The firmware, after 3 s without a frame, shows its own `NO HOST` screen (BR-002); the keys keep sending their F key codes.
4. Use case ends; it starts again at step 1 when the link comes back.

### A2: Status unreadable

**Trigger:** a `GetMenuStatus` read fails or times out (step 2 or 3)
**Flow:**

1. System keeps the last values on the status screen and shows `NO CONNECTION` on its last line (BR-001); it does not queue or retry any command (UC-015 BR-010).
2. Use case continues at step 2 with the next read.

### A3: Refused, limit, cancel or failure

**Trigger:** a pad command of UC-015 ends without a commit: A1 `game_active`, A3 failure, A5 / A10 cancel, A7 limit (step 5)
**Flow:**

1. System shows the result screen with the UC-015 BR-009 word (`NOT POSSIBLE`, `FAILED`, `CANCELLED`, `MAXIMUM`, `MINIMUM`, `NO CONNECTION`) besides the cue, then the status screen.
2. Use case ends.

### A4: A lobby-only layer while the game is live

**Trigger:** Host holds K1, K2, K5 or K6 and turns the knob while the lifecycle is live (step 4; UC-015 A1)
**Flow:**

1. System shows the setting screen with `NOT POSSIBLE` on its last line and no new value; the release is refused as in UC-015 A1.
2. Use case ends.

## Postconditions

### Success Postconditions

- The pad's screen shows the status screen with values no older than NFR-070 allows, or the screen of the gesture in progress. No flag, setting or game state was changed by this use case: it only shows.

### Failure Postconditions

- The pad works as in UC-015 (FR-240); the screen shows `NO HOST` (firmware, no frames) or the last values with `NO CONNECTION` (A2).

## Business Rules

### BR-001: Screens

The display is 128x64 pixels, drawn as 8 text lines of 21 characters (the firmware's 6x8 font); line 1 is the title, drawn inverted. The pad service composes every screen; the firmware only draws lines (BR-002). Every value comes from the last `GetMenuStatus` read (BR-003) or, on the setting screen, from the live preview (UC-015 BR-017). A value the status does not tell (an agent state the menu reports as unknown, a missing key in `operator_settings` outside status line 6, no status at all) shows as `?`, never a guess. Sensitivity and teams on status line 6 have one rule: `AUTO` when `operator_settings` reports `automatic` for the setting, otherwise the effective `sensitivity` / `num_teams` of the status in short form, also when the key is missing (the status has no "unknown" for the effective values: for a flag flagd cannot resolve that is the menu's default). The result screen shows the value the menu reports as committed (`ProcessInputResponse.value`, [services.md](../specs/services.md) §3.1), never the pad's own prediction; with no `value` (a menu older than that field, or a command that commits no value) it shows the label and the UC-015 BR-009 word, or `OK` on success. Phase 2 has no display pages: one screen shows at a time, and K8's tap stays reserved (UC-015 BR-011); a later iteration (#2742) moves pages to the knob. Values are written in the short forms below, so that every line fits in 21 characters; a mode's name and any value not in the table are the name in capitals, cut to fit.

| Setting | Short forms |
|---|---|
| Sensitivity (`ultra_slow` to `ultra_fast`) | `AUTO`, `0`, `1`, `2`, `3`, `4` |
| Teams (`two` to `six`) | `AUTO`, `2`, `3`, `4`, `5`, `6` |
| Shield mode | `AUTO`, `INST`, `TRIG`, `HOLD` |
| Volume | `MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX` |
| Agent level | `NONE`, `AMBIENT`, `STANDARD`, `FULL` |
| Backend | `RULES`, `CLAUDE`, `OPENAI`, `JEV` |

| Screen | When | Lines |
|---|---|---|
| Status | default: no layer key held, no result, tap or volume screen showing | 1 `JOUSTMANIA` and the state: `LOBBY`, or `GAME` while the game lifecycle is live (the status does not tell starting, running and ending apart); 2 the selected mode; 3 `READY <ready>/<connected>`; 4 the agent, so the screen never disagrees with what a K3 hold would do: `AGENT ?` when UC-015 BR-013 counts the status as unknown (`agent_enabled_state` or `agent_interventions_enabled_state` not `on` or `off`, or `agent_level` empty or outside the ladder of UC-015 BR-004), else `AGENT OFF` when UC-015 BR-002 counts the agent as stopped (`agent_enabled` off, level `none` or the write gate `off`), else `AGENT ON` and the level's short form; 5 `BACKEND` and its name; 6 `SENS` and `TEAMS` (the line 6 rule above); 7 `SHIELD` and `VOL`; 8 `NO CONNECTION` (A2), else `LOCKED` (UC-015 A6), else the JoustMania version: `V` and the release tag the stack runs (a tag that already starts with `v` or `V` is shown with a single `V`, never `VV`), or `DEV` without one, also for an image tag that is not a release (`latest`, `main`, a commit sha) (FR-241) |
| Setting | a layer key is the only key down and the knob has made at least one step (the UC-015 BR-017 condition) | 1 the setting's label (`GAME`, `SENSITIVITY`, `AGENT LEVEL`, `TEAMS`, `SHIELD MODE`, `BACKEND`); 3 `NOW` and the value read at the press; 5 `NEW` and the value the release would commit; 6 the ladder with the new value marked (`AUTO 0 1 2 [3] 4`) where it fits on one line; 8 `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range, or `NOT POSSIBLE` (A4) |
| Volume | a knob turn or press with no layer key held | 1 `VOLUME`; 3 the variant the turn would commit (`MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX`); 5 a bar of the five rungs; 8 `MUTED` while muted, or `MAXIMUM` / `MINIMUM` when a turn hits the end of the range. Shown for `operator_pad.display_result_ms` after the last turn |
| Result | from the release until the menu answers: the label alone, at most the command's deadline; after a commit, a refusal, a cancel or a failure (step 5, A3): the result | 1 the label of the command; 3 empty while the menu has not answered, then the value the menu committed (`ProcessInputResponse.value`, short form), or the UC-015 BR-009 word (`FAILED` for any error without one), or `OK` for a success without a `value`; the result shown for `operator_pad.display_result_ms` (default 1500), then the status screen |
| Tap | after a tap UC-015 announces (K2, K3, K5, K7; UC-015 BR-011) | 1 the label (`SENSITIVITY`, `AGENT`, `TEAMS`, `BACKEND`); 3 the value read at the tap in short form (K3: as status line 4, without `AGENT`), or `?` when the status does not tell it; shown for `operator_pad.display_result_ms`, then the status screen |

A new screen replaces the one showing at once (a new layer step replaces a result still showing). A K3 hold (stop / resume the agent) and a K4 hold (end / force-start) show their result like every command.

### BR-002: Display link and frame protocol

The pad service writes to the pad's raw HID interface (the Vial / VIA interface: usage page `0xFF60`, usage `0x61`, 32-byte reports) on the device `operator_pad.device` matches (UC-015 BR-014). Every report starts with the command id `0x50`, which is not a VIA or Vial command id, then an op:

| Op | Bytes | Meaning | Reply |
|---|---|---|---|
| `0x00` hello | none | asks the protocol version | `0x50 0x00 <version>`; version 1 |
| `0x01` line | 2: line 0 to 7; 3: attributes (bit 0 inverted); 4 to 24: 21 ASCII characters (0x20 to 0x7E, space padded; any other byte draws as `?`) | writes one line into the back buffer | `0x50 0x01 0x00`; a line number of 8 or more: `0x50 0x01 0xFF`, nothing written |
| `0x02` show | 2: frame sequence number | draws the back buffer; also the heartbeat | `0x50 0x02 0x00` |

An unknown op is answered `0x50 <op> 0xFF` and changes nothing. The service sends the 8 lines and a show for each screen that differs from the last one shown, and a show alone at least once a second. The firmware draws only on show, so a half-sent frame is never seen. With no show for 3 s it draws its own `NO HOST` screen; after a power-up it shows `JOUSTMANIA` and `WAITING FOR HOST`. The keys never depend on the link (A1). Vial's own commands keep working, so the Vial app can still read and change the keymap.

### BR-003: Status refresh

While the display link is up, the pad service reads `GetMenuStatus` every `operator_pad.display_poll_ms` (default 500) besides the reads of UC-015's key presses and releases, and redraws the status screen when a shown value changed. The polled status is for the screen only: a command still uses the status read at its own press or release (UC-015 A5, BR-013).

### BR-004: Volume without a sound

The menu plays the volume step sound of a volume step and of a mute or unmute (its `step_setting` for `audio_volume.master`), so the pad silences it through the menu: while the display link is up, the pad sends that `step_setting` with `cue=none` ([services.md](../specs/services.md) §3.1), the menu skips the volume step sound, and the volume screen (BR-001) shows the level instead. A menu older than the `cue` key ignores it and the sound plays. With the link down (A1) the pad sends no `cue` and the short sound of UC-015 step 8 plays as before, so a pad without a screen still gives feedback.

### BR-005: The pad's own voices with a screen

While the display link is up, the pad plays none of its own voice lines: the live preview's label and value (UC-015 BR-017), the tap announcements (UC-015 BR-011; the tap screen), the status words it decides itself (`NOT POSSIBLE`, `MAXIMUM`, `MINIMUM`, `CANCELLED`), the lock words (UC-015 A6) and the spoken "No connection" after the failure cue of a menu the pad cannot reach (UC-015 BR-009; the screen shows `NO CONNECTION`); the screen shows each of them instead (BR-001). The unknown-key cue (UC-015 A4) is a sound, not a voice line, and stays. The menu's voice lines for a command it runs (UC-015 steps 4 to 7 and 9) stay, so the room still hears a committed change; the volume sound is BR-004. The failure cue (two beeps, UC-015 BR-009) stays too, the pad's included, since it warns without a look at the screen. The controllers' LED cues are unchanged. With the link down (A1) the pad speaks as in UC-015.
