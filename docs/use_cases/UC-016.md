# Use Case: See the Game State on the Operator Pad

## Overview

**Use Case ID:** UC-016
**Use Case Name:** See the Game State on the Operator Pad
**Primary Actor:** Host
**Goal:** See on the operator pad's own screen, without a laptop and without waiting for a voice line, what the lobby looks like (game state, selected mode, ready and connected controllers, the agent) and, while turning the knob, which setting is being changed and to what
**Trigger:** The pad service attaches to the pad and its display link comes up; the menu status changes; Host holds a layer key and turns the knob, turns the knob alone, or a pad command ends
**Status:** Draft
**Requirements:** FR-236, FR-237, FR-238, FR-239, FR-240, FR-241, FR-242, FR-243, FR-244, FR-245, FR-256, NFR-070

Phase 2 of the operator pad (Open, #2741): [UC-015](UC-015.md) is phase 1, the keys and the knob with voice, sound and LED cues. This use case adds the pad's 128x64 OLED. The firmware is a Vial keymap for the 0xCB 1337 in the `orange-case/operator-pad` repository (`firmware/`); it draws what the pad service sends over the pad's raw HID interface (BR-002) and holds no game logic. The pad is a rev 5 (RP2040), for which QMK and Vial have no keyboard definition, so the repository brings its own (`keyboard/`, built as `orange_case/operator_pad`); revisions 1 to 4 (ATmega32U4) build the same keymap as `0xcb/1337`. While the screen works it replaces the pad's own voice lines and the volume sound (BR-004, BR-005); every other cue of UC-015 stays. The firmware side of BR-002 is built and bench-tested on a rev 5 pad (`orange-case/operator-pad` #1); the pad service side is not built yet.

Iteration 2 (Open, #2742): a pad whose firmware answers protocol 2 or 3 (BR-002) gets seven pages in one screen frame (a title bar with the page's place, three rows, a status bar of icons), that the knob scrolls and that turn on their own while the pad is idle, and the internet state in its status bar (A5, A6, BR-006 to BR-010). Protocol 3 (rev 5 only) draws the rows in a medium 8x12 font and a ladder setting as a marker bar; protocol 2 (revisions 1 to 5) draws the same pages with big 12x16 rows. A pad that answers protocol 1 keeps the single status screen of BR-001. The layout follows the maintainer's bench decisions of 2026-11-24. Protocols 2 and 3 are built in the firmware (`orange-case/operator-pad` #3 and #4, merged); the pad service side is not built yet. The rows sit where the key rows are; editing a row from its page (the page keys) is #2747.

## Preconditions

- **Pre-1:** UC-015 Pre-1 to Pre-3 hold: the `operator-pad` service runs, the pad is attached and the menu is RUNNING.
- **Pre-2:** The pad runs the operator-pad firmware, which answers the hello of BR-002 with protocol version 1 or higher (2 or 3 for the pages, A5), and the service can open the pad's raw HID node read-write ([services.md](../specs/services.md) §3.1).
- **Pre-3:** `operator_pad.display_enabled` is on (default on, [flags.md](../specs/flags.md) §10a).

## Main Success Scenario

1. System (the pad service) attaches to the pad, sends the hello and gets protocol version 1 or higher: the display link is up (version 2 or higher: A5).
2. System reads `GetMenuStatus` every `operator_pad.display_poll_ms` (BR-003) and shows the status screen (BR-001; with protocol 2 or higher the pages of BR-006, A5): the game state, the selected mode, the ready and connected controllers, the agent (on, off or unknown, its level and its backend), the settings and the JoustMania version.
3. The menu status changes (a controller connects or readies up, a game starts, someone changes a setting from the dashboard): System redraws the status screen with no key pressed, within NFR-070's bound from the moment `GetMenuStatus` first reports the change (a setting changed elsewhere reaches the status with the menu's own delay, UC-015 BR-018).
4. Host holds a layer key (K1, K2, K3, K5, K6 or K7) and turns the knob: from the first step System shows the setting screen (BR-001): which setting is being changed, its value at the press and the value the release would commit, updated per step (the value of the live preview, UC-015 BR-017); the preview speaks nothing (BR-005).
5. Host releases the layer key: UC-015 commits as before (UC-015 BR-005); System shows the result screen (BR-001) for `operator_pad.display_result_ms`, then the status screen.
6. Host turns the knob with no layer key held: System shows the volume screen (BR-001) with the level the turn would commit and plays no sound (BR-004); the commit after the pause is UC-015 step 8. With protocol 2 or higher the knob alone scrolls the pages and press and turn sets the volume (A5, BR-008).

## Alternative Flows

### A1: Display link down or old firmware

**Trigger:** the raw HID node is missing or cannot be opened, the firmware does not answer the hello with a version of 1 or higher, a frame write fails, or `operator_pad.display_enabled` is off (step 1, or any later step)
**Flow:**

1. System keeps every key, knob and cue of UC-015 working as before (FR-240): the display link is never needed to send a command, and a failed frame write never delays or drops a key event.
2. System counts the link as down: the volume plays its short sound and the pad speaks its own voice lines again (BR-004, BR-005), and System retries the hello at the device rescan interval (UC-015 A4), never in a busy loop.
3. The firmware, after 3 s without a frame, shows its own `NO HOST` screen (BR-002); the keys keep sending their F key codes.
4. Use case ends; it starts again at step 1 when the link comes back.

### A2: Status unreadable

**Trigger:** a `GetMenuStatus` read fails or times out (step 2 or 3)
**Flow:**

1. System keeps the last values on the status screen and shows `NO CONNECTION` on its last line (BR-001); it does not queue or retry any command (UC-015 BR-010).
2. Use case continues at step 2 with the next read.

### A3: Refused, limit, cancel or failure

**Trigger:** a pad command of UC-015 ends without a commit: A1 `game_active`, A3 failure, A5 / A10 cancel, A7 limit (step 5)
**Flow:**

1. System shows the result screen with the UC-015 BR-009 word (`NOT POSSIBLE`, `FAILED`, `CANCELLED`, `MAXIMUM`, `MINIMUM`, `NO CONNECTION`) besides the cue, then the status screen.
2. Use case ends.

### A4: A lobby-only layer while the game is live

**Trigger:** Host holds K1, K2, K5 or K6 and turns the knob while the lifecycle is live (step 4; UC-015 A1)
**Flow:**

1. System shows the setting screen with `NOT POSSIBLE` on its last line and no new value; the release is refused as in UC-015 A1.
2. Use case ends.

### A5: Pages and knob scrolling (protocol 2 or higher)

**Trigger:** the firmware answers the hello with version 2 or higher (step 1)
**Flow:**

1. System shows the `HOME` page (BR-006) instead of the status screen, and draws the setting, result, tap and volume screens in the same frame (BR-007); steps 3 to 5 and A2 to A4 apply to the page showing, and the internet check of BR-010 runs.
2. Host turns the knob alone: System shows the next page (clockwise) or the previous one (counter-clockwise), one page per knob step, wrapping, and sends no command (BR-008).
3. Host presses the knob and turns it while it is down: System sets the master volume one variant per step and commits after the pause as in UC-015 step 8, showing the volume screen without a sound (BR-004, BR-008).
4. Host presses the knob and releases it within the tap limit without a turn: System mutes or unmutes (BR-008).
5. Use case continues at step 3.

### A6: Pages turn on their own

**Trigger:** the pages show (A5), no key and no knob press is down and no setting, result, tap or volume screen shows (step 2)
**Flow:**

1. System shows the next page every `operator_pad.display_autopage_ms` (BR-009); with the flag at `off` the page stays.
2. Host scrolls with the knob (A5 step 2): System stops the cycling and keeps the page Host chose.
3. When `operator_pad.display_home_ms` have passed since the last key or knob input, System shows `HOME` and the cycling resumes (BR-009).
4. Use case continues at step 3.

## Postconditions

### Success Postconditions

- The pad's screen shows the status screen (a page with protocol 2 or higher, A5) with values no older than NFR-070 allows, or the screen of the gesture in progress. No flag, setting or game state was changed by this use case: it only shows.

### Failure Postconditions

- The pad works as in UC-015 (FR-240); the screen shows `NO HOST` (firmware, no frames) or the last values with `NO CONNECTION` (A2).

## Business Rules

### BR-001: Screens

The display is 128x64 pixels, drawn as 8 text lines of 21 characters (the firmware's 6x8 font); line 1 is the title, drawn inverted. The pad service composes every screen; the firmware only draws lines (BR-002). Every value comes from the last `GetMenuStatus` read (BR-003) or, on the setting screen, from the live preview (UC-015 BR-017). A value the status does not tell (an agent state the menu reports as unknown, a missing key in `operator_settings` outside status line 6, no status at all) shows as `?`, never a guess. Sensitivity and teams on status line 6 have one rule: `AUTO` when `operator_settings` reports `automatic` for the setting, otherwise the effective `sensitivity` / `num_teams` of the status in short form, also when the key is missing (the status has no "unknown" for the effective values: for a flag flagd cannot resolve that is the menu's default). The result screen shows the value the menu reports as committed (`ProcessInputResponse.value`, [services.md](../specs/services.md) §3.1), never the pad's own prediction; with no `value` (a menu older than that field, or a command that commits no value) it shows the label and the UC-015 BR-009 word, or `OK` on success. With protocol 1 there are no display pages: one screen shows at a time; with protocol 2 or higher the knob scrolls the pages of BR-006 (iteration 2, #2742). K8's tap stays reserved either way (UC-015 BR-011). Values are written in the short forms below, so that every line fits in 21 characters; a mode's name and any value not in the table are the name in capitals, cut to fit.

| Setting | Short forms |
|---|---|
| Sensitivity (`ultra_slow` to `ultra_fast`) | `AUTO`, `0`, `1`, `2`, `3`, `4` |
| Teams (`two` to `six`) | `AUTO`, `2`, `3`, `4`, `5`, `6` |
| Shield mode | `AUTO`, `INST`, `TRIG`, `HOLD` |
| Volume | `MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX` |
| Agent level | `NONE`, `AMBIENT`, `STANDARD`, `FULL` |
| Backend | `RULES`, `CLAUDE`, `OPENAI`, `JEV` |

| Screen | When | Lines |
|---|---|---|
| Status | default: no layer key held, no result, tap or volume screen showing | 1 `JOUSTMANIA` and the state: `LOBBY`, or `GAME` while the game lifecycle is live (the status does not tell starting, running and ending apart); 2 the selected mode; 3 `READY <ready>/<connected>`; 4 the agent, so the screen never disagrees with what a K3 hold would do: `AGENT ?` when UC-015 BR-013 counts the status as unknown (`agent_enabled_state` or `agent_interventions_enabled_state` not `on` or `off`, or `agent_level` empty or outside the ladder of UC-015 BR-004), else `AGENT OFF` when UC-015 BR-002 counts the agent as stopped (`agent_enabled` off, level `none` or the write gate `off`), else `AGENT ON` and the level's short form; 5 `BACKEND` and its name; 6 `SENS` and `TEAMS` (the line 6 rule above); 7 `SHIELD` and `VOL`; 8 `NO CONNECTION` (A2), else `LOCKED` (UC-015 A6), else the JoustMania version: `V` and the release tag the stack runs (a tag that already starts with `v` or `V` is shown with a single `V`, never `VV`), or `DEV` without one (FR-241) |
| Setting | a layer key is the only key down and the knob has made at least one step (the UC-015 BR-017 condition) | 1 the setting's label (`GAME`, `SENSITIVITY`, `AGENT LEVEL`, `TEAMS`, `SHIELD MODE`, `BACKEND`); 3 `NOW` and the value read at the press; 5 `NEW` and the value the release would commit; 6 the ladder with the new value marked (`AUTO 0 1 2 [3] 4`) where it fits on one line; 8 `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range, or `NOT POSSIBLE` (A4) |
| Volume | a knob turn or press with no layer key held | 1 `VOLUME`; 3 the variant the turn would commit (`MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX`); 5 a bar of the five rungs; 8 `MUTED` while muted, or `MAXIMUM` / `MINIMUM` when a turn hits the end of the range. Shown for `operator_pad.display_result_ms` after the last turn |
| Result | after a commit, a refusal, a cancel or a failure (step 5, A3) | 1 the label of the command; 3 the value the menu committed (`ProcessInputResponse.value`, short form), or the UC-015 BR-009 word (`FAILED` for any error without one), or `OK` for a success without a `value`; shown for `operator_pad.display_result_ms` (default 1500), then the status screen |
| Tap | after a tap UC-015 announces (K2, K3, K5, K7; UC-015 BR-011) | 1 the label (`SENSITIVITY`, `AGENT`, `TEAMS`, `BACKEND`); 3 the value read at the tap in short form (K3: as status line 4, without `AGENT`), or `?` when the status does not tell it; shown for `operator_pad.display_result_ms`, then the status screen |

A new screen replaces the one showing at once (a new layer step replaces a result still showing). A K3 hold (stop / resume the agent) and a K4 hold (end / force-start) show their result like every command.

This is the layout for a pad that answers protocol 1. A pad that answers protocol 2 or higher gets the pages of BR-006 instead of the status screen and the setting, volume, result and tap screens of BR-007; the values, their sources, the `?` rule and the "When" column above stay, and so do the short forms where a row has no room for the full word.

### BR-002: Display link and frame protocol

The pad service writes to the pad's raw HID interface (the Vial / VIA interface: usage page `0xFF60`, usage `0x61`, 32-byte reports) on the device `operator_pad.device` matches (UC-015 BR-014). Every report starts with the command id `0x50`, which is not a VIA or Vial command id, then an op:

| Op | Bytes | Meaning | Reply |
|---|---|---|---|
| `0x00` hello | none | asks the protocol version | `0x50 0x00 <version>`; version 1 (2 or 3 with protocols 2 and 3, below) |
| `0x01` line | 2: line 0 to 7 (with the medium bit: the medium row 0 to 2, protocol 3); 3: attributes (bit 0 inverted; from protocol 2 bit 1 large, bit 2 underline; from protocol 3 bit 3 medium); 4 to 24: 21 ASCII characters (0x20 to 0x7E, space padded; any other byte draws as `?`) | writes one line into the back buffer | `0x50 0x01 0x00`; a line number of 8 or more, or a medium row above 2: `0x50 0x01 0xFF`, nothing written |
| `0x02` show | 2: frame sequence number | draws the back buffer; also the heartbeat | `0x50 0x02 0x00` |

An unknown op is answered `0x50 <op> 0xFF` and changes nothing. The service sends the 8 lines and a show for each screen that differs from the last one shown, and a show alone at least once a second. The firmware draws only on show, so a half-sent frame is never seen. With no show for 3 s it draws its own `NO HOST` screen; after a power-up it shows `JOUSTMANIA` and `WAITING FOR HOST`. The keys never depend on the link (A1). Vial's own commands keep working, so the Vial app can still read and change the keymap.

**Protocol 2** (#2742; `orange-case/operator-pad` #3, merged; revisions 1 to 5). Everything above holds, with these additions: the hello is answered with version 2; in the `line` op's attribute byte bit 1 means large and bit 2 underline; and the bytes `0x7F` to `0x84` draw glyphs instead of `?`: `0x7F` a full bar block, `0x80` an empty bar block, `0x81` internet, `0x82` agent, `0x83` instructions, `0x84` lock (BR-006). A large line n (0 to 6) draws the first 10 characters of its text in a 12x16 pixel font (each pixel of the 6x8 font doubled) over display lines n and n+1 (pixel columns 0 to 119; columns 120 to 127 stay blank, or are filled when the line is also inverted); the content written to line n+1 is ignored for that frame. A large bit on line 7 draws the line small. An underlined line gets a 1 px line across the full width on its bottom pixel row (a large line n on the bottom row of line n+1), dark when the line is inverted; no glyph uses that row.

**Protocol 3** (#2742; `orange-case/operator-pad` #4, merged; rev 5 only). Everything of protocol 2 holds, with these additions: the hello is answered with version 3, bit 3 of the `line` op's attribute byte means medium, the byte `0x85` draws the marker (a down-pointing triangle), and a new op draws a bar. The ATmega32U4 of revisions 1 to 4 has no flash left for a second font, so its firmware stays at protocol 2: its hello answers 2, it ignores bit 3 and answers `0x50 0x03 0xFF` to the bar op.

- **Medium row.** A `line` op with the medium bit addresses medium row r (0 to 2) in its line byte; rows 0, 1 and 2 are rows 1, 2 and 3 of the frame (BR-006). The row is stored as display line 1 + 2r and, like a large line, covers display lines 1 + 2r and 2 + 2r (row 0 lines 1-2, row 1 lines 3-4, row 2 lines 5-6): the content of line 2 + 2r is ignored for that frame, and a later small or large write to line 1 + 2r replaces the row. It draws the first 16 characters of its text in an 8x12 pixel font, 8 px per character across the full 128 px, its 12 pixel rows starting at pixel row 11 + 15r, so 3 px separate the title bar, the rows and the divider. Inverted (bit 0) fills the row's 12 pixel rows (the highlight); underline (bit 2) draws the 1 px divider on the bottom pixel row of the row's slot (pixel row 23, 39 or 55), always lit since it lies below the inverted band; on row 2 it is the divider above the status bar. The large bit is ignored on a medium row. The font is X.Org misc-fixed (public domain) at 8x12, with the same glyphs as the small one: ASCII `0x20` to `0x7E` and `0x7F` to `0x85`.
- **Bar** (op `0x03`; report `0x50 0x03 <row> <rungs> <filled> <marker> <labels>`): byte 2: the bar row r (0 or 1); 3: the rungs (2 to 8; 0 removes the bar); 4: the filled rungs (0 to the rungs, from the left); 5: the marker rung (0 to the rungs - 1, or `0xFF` for no marker); 6 to 31: the rung labels, ASCII separated by `|`, ended by `0x00` or the end of the report, label k under rung k (a missing or empty label stays blank, extra ones are ignored). The bar at row r covers display lines 1 + 2r to 4 + 2r (pixel rows 8 + 16r to 39 + 16r, medium rows r and r + 1); the content of those lines is not drawn. Within those 32 pixel rows, from the top: the marker (the `0x85` shape) on rows 6-9, centred over its rung; the bar on rows 12-20, rungs of equal pitch (128 / rungs px) with a 2 px gap, centred, the first `filled` rungs solid and the rest a 1 px outline; the labels in the small font on rows 23-29, each centred under its rung and kept on screen, never cut: a label wider than its rung (`AUTO` under the first of six rungs) starts at the left edge. An underline on the bar's last line (4 + 2r) is still drawn. The bar is part of the back buffer and is drawn on show. Writing any line it covers (a small, large or medium `line` op) removes it, so the host sends the bar after the lines of its frame. Reply `0x50 0x03 0x00`; any other value out of range: `0x50 0x03 0xFF`, nothing drawn.

The pad service treats any version of 1 or higher as the link up and uses a feature only when the hello reports its version: protocol 3 the medium rows and the marker bar (BR-006, BR-007), protocol 2 the big-font layout of the same pages (large rows, the glyphs, the underline), protocol 1 the screens of BR-001. A version above 3 is used as 3.

### BR-003: Status refresh

While the display link is up, the pad service reads `GetMenuStatus` every `operator_pad.display_poll_ms` (default 500) besides the reads of UC-015's key presses and releases, and redraws the status screen when a shown value changed. The polled status is for the screen only: a command still uses the status read at its own press or release (UC-015 A5, BR-013).

### BR-004: Volume without a sound

The menu plays the volume step sound of a volume step and of a mute or unmute (its `step_setting` for `audio_volume.master`), so the pad silences it through the menu: while the display link is up, the pad sends that `step_setting` with `cue=none` ([services.md](../specs/services.md) §3.1), the menu skips the volume step sound, and the volume screen (BR-001) shows the level instead. A menu older than the `cue` key ignores it and the sound plays. With the link down (A1) the pad sends no `cue` and the short sound of UC-015 step 8 plays as before, so a pad without a screen still gives feedback.

### BR-005: The pad's own voices with a screen

While the display link is up, the pad plays none of its own voice lines: the live preview's label and value (UC-015 BR-017), the tap announcements (UC-015 BR-011; the tap screen), the status words it decides itself (`NOT POSSIBLE`, `MAXIMUM`, `MINIMUM`, `CANCELLED`), the lock words (UC-015 A6) and the spoken "No connection" after the failure cue of a menu the pad cannot reach (UC-015 BR-009; the screen shows `NO CONNECTION`); the screen shows each of them instead (BR-001). The unknown-key cue (UC-015 A4) is a sound, not a voice line, and stays. The menu's voice lines for a command it runs (UC-015 steps 4 to 7 and 9) stay, so the room still hears a committed change; the volume sound is BR-004. The failure cue (two beeps, UC-015 BR-009) stays too, the pad's included, since it warns without a look at the screen. The controllers' LED cues are unchanged. With the link down (A1) the pad speaks as in UC-015.

### BR-006: Pages and the screen frame (protocol 2 or higher)

With protocol 2 or higher (BR-002) the status screen of BR-001 becomes seven pages, in this order: `HOME`, `GAME`, `START`, `AGENT`, `INTERV`, `RETRO`, `SYSTEM`. Every page, and every screen of BR-007, uses one frame (the maintainer's bench decisions of 2026-11-24, mock variant B):

- **Title bar** (line 1, small, inverted): the page's name flush left and its place flush right (`HOME` ... `1/7`); on a screen of BR-007 the setting's or command's label left and the screen's word right.
- **Three rows** between the bars. Protocol 3: medium rows of 16 characters (BR-002), the label flush left and the value or bar flush right, with full words where 16 characters allow (`VOLUME`, `SHIELD`, `INSTRUCTIONS ON`) and the short forms of BR-001 otherwise. Protocol 2: large lines on lines 2-3, 4-5 and 6-7 of 10 characters each, with the short labels of the table below.
- **Divider**: a 1 px line across the full width above the status bar (the underline bit on the last row, BR-002).
- **Status bar** (line 8, small, not inverted), the same on every page and screen, with no page indicator: the internet icon (`0x81`) while the internet is reachable (BR-010); the selected mode's short name (at most 5 characters, for example `FFA`; a mode without one is its name in capitals cut to 5); `<ready>/<connected>`; the agent icon (`0x82`) while the agent is on, `?` in its place while it is unknown, nothing while it is off (on, off and unknown by the rule of BR-001 status line 4); the instructions icon (`0x83`) while game instructions are on; the lock icon (`0x84`) only while the pad is locked (UC-015 A6). While the status is unreadable (A2) the status bar is `NO CONNECTION`, inverted, instead.

Every value, its source and the `?` rule are those of BR-001; the agent row uses the rule of BR-001 status line 4, the sensitivity and teams the line 6 rule, the version the line 8 rule. A row's **bar** is one glyph per rung of the setting's ladder, `0x7F` (full) up to and including the value's rung and `0x80` (empty) above it: the volume five rungs (`MUTE` one full, `MAX` five), the sensitivity five rungs (0 to 4; `AUTO` as text when `operator_settings` reports `automatic`), the agent level four rungs (`NONE` one full, `FULL` four); `?` instead of the bar while the value is unknown. A value that does not fit is cut to fit. In the table a row's protocol 2 label is in brackets.

| Page | Row 1 | Row 2 | Row 3 |
|---|---|---|---|
| `HOME` | `MODE` (`MODE`): the selected mode's short name | `VOLUME` (`VOL`): its bar | `SENS` (`SENS`): its bar, or `AUTO` |
| `GAME` | `TEAMS` (`TEAMS`): `AUTO`, `2` to `6` | `SHIELD` (`SHLD`): `AUTO`, `INSTANT`, `TRIGGER`, `HOLD` (protocol 2: the BR-001 short forms) | `INSTRUCTIONS` (`INSTR`): `ON` / `OFF` (`instructions`) |
| `START` | `FORCE ALL` (`FORCE`): `ON` / `OFF` (`force_all_start`) | empty | empty |
| `AGENT` | `AGENT` (`AGENT`): `ON`, `OFF` or `?` | `LEVEL` (`LEVEL`): its bar | `GOAL` (`GOAL`), read-only: the goal profile (`agent/goal.profile`, Flagsmith-only, FR-226), planned field |
| `INTERV` | `BACKEND` (`AI`): the decision backend (`agent_backend`, BR-001 short forms) | `RATE` (`RATE`), read-only for now: `<n>/MIN` (`policy.max_interventions_per_minute`, the intervention budget of NFR-015; not `llm.max_requests_per_minute`, which caps all of the agent's LLM calls together: decide, retro and proposer), planned field | `GROUP` (`GROUP`), read-only for now: `ON` / `OFF` (`policy.group_grant.enabled`), planned field |
| `RETRO` | `RETRO AI` (`RETRO`), read-only for now: `STUB` / `CLAUDE` (`inference.backend`), planned field | `EFFORT` (`EFF`), read-only: `LOW` to `MAX` (`inference.effort`), planned field | `BRIEF` (`BRIEF`), read-only: `ON` while `decision.operator_brief` is set, else `OFF` (its text is never shown), planned field |
| `SYSTEM` | `VERSION` (`V`), read-only: the JoustMania version (FR-241) | `NET` (`NET`), read-only: `OK`, `DOWN`, `?` before the first check, `OFF` with the check off (BR-010) | `LOCK` (`LOCK`): `ON` / `OFF` (the pad's lock, UC-015 A6, set by the K8 hold) |

**Planned status fields.** The values of GOAL, RATE, GROUP, RETRO AI, EFFORT and BRIEF are not in `GetMenuStatus` today; they need the planned status fields of [services.md](../specs/services.md) §3.1. Until the menu reports a field (a menu older than it leaves it empty), its row shows `?`; the row is never left out, so a page keeps its three rows and the key rows stay where they are. A read-only row shows no key hint and, with #2747, no key edits it.

**Rows and keys.** Rows 1, 2 and 3 sit where the pad's key rows are (row 1 K1 / K2, row 2 K3 / K4, row 3 K6 / K7), so a page never has more than three rows (more settings make more pages) and editing a row from its page needs no new layout. That editing (the page keys: edit and reset per row) comes with #2747; until then every key keeps its UC-015 layer whatever page shows. **Highlight** (with #2747): while a row's key is held, before the first knob step, that row is drawn inverted.

When the link comes up the pad shows `HOME`. A page redraws when one of its values changes (BR-003), the internet state included (BR-010).

### BR-007: Setting, volume, result and tap screens (protocol 2 or higher)

With protocol 2 or higher the setting, volume, result and tap screens of BR-001 show when BR-001 says (the volume screen on a volume step or a mute of BR-008 only, never on a page step), for as long as it says, in the frame of BR-006: the status bar stays.

- **Ladder settings**: the sensitivity (rungs `AUTO 0 1 2 3 4`), the teams (`AUTO 2 3 4 5 6`), the agent level (`NONE AMB STD FULL`) and the volume (`MUTE QUIET NORM LOUD MAX`). Protocol 3: the marker bar (the bar op, BR-002) at bar row 0, over rows 1 and 2, one rung per ladder value: the marker above the rung of the value at the press (NOW; no marker while that value is unknown), the rungs filled up to and including the rung the release would commit (NEW). Labels: the sensitivity, the teams and the agent level a label under every rung (`AUTO|0|1|2|3|4`, `AUTO|2|3|4|5|6`, `NONE|AMB|STD|FULL`); the volume only at the ends, `MUTE` under the first rung and `MAX` under the last (`MUTE||||MAX`). Row 3 (medium row 2) holds the hint `RELEASE TO SET` (empty on the volume screen, which commits after the pause) with the underline as the divider. The service sends the bar after the frame's lines, since a line written over the bar removes it (BR-002). Title bar: the setting's label (`SENSITIVITY`, `TEAMS`, `AGENT LEVEL`, `VOLUME`) left and `EDIT` right; `MAXIMUM` / `MINIMUM` right instead when a step hits the end of the range, and on the volume screen `MUTED` right while muted. For the volume the value at the press is the level when the turn began.
- **Other settings**: the mode, the decision backend and the shield mode (none of them an ordered scale; the shield mode's values `AUTO`, `INSTANT`, `TRIGGER` and `HOLD` are kinds of activation, not levels, so it gets no marker bar), on protocol 2 every setting, and every setting whose step is refused (A4). Rows: 1 `NOW` and the value read at the press; 2 `NEW` and the value the release would commit (empty when refused); 3 the hint `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range, or `NOT POSSIBLE` (A4). Title bar: the setting's label left, `EDIT` right. On protocol 2 a ladder setting shows its bar of BR-006 as the value where it has one.
- **Result**: title bar the command's label; row 2 the value the menu committed (`ProcessInputResponse.value`), the UC-015 BR-009 word, or `OK` (BR-001), the full word where it fits; rows 1 and 3 empty. On protocol 2 a word over 10 characters takes rows 2 and 3 (`NOT` / `POSSIBLE`, `NO` / `CONNECTION`).
- **Tap**: as the result screen, with the value read at the tap (BR-001).

A reset screen (title `<SETTING>` and `RESET`, rows `NOW` and the value, `NEW` and the default, hint `RELEASE TO RESET`) comes with the page keys of #2747. When a result, tap or volume screen ends, the page that showed before it comes back (`HOME` when BR-009 returns there in the meantime).

### BR-008: The knob with the pages (protocol 2 or higher)

While the display link is up with protocol 2 or higher and no layer key is down, the knob works as follows; a step is a knob step of UC-015 BR-005 (`operator_pad.knob_events_per_step`):

- **Turn alone** (the knob not pressed): one page per step, clockwise (B) to the next, counter-clockwise (A) to the previous, wrapping (`SYSTEM` to `HOME` and back). The page shows at once; a step sends no command, plays nothing and, while a result, tap or volume screen shows, ends it and counts from the page under it.
- **Press and turn**: each step while the knob is down sets the master volume one variant (UC-015 BR-006), committed after the same pause as UC-015 step 8 (UC-015 BR-005), with the volume screen and no sound (BR-004). The release of that press does nothing else.
- **Short press**: a knob press released within the tap limit (`operator_pad.tap_ms`, UC-015 BR-007) with no step while it was down mutes or unmutes, at the release (with protocol 1 or no link the mute fires at the press, UC-015 BR-016). A longer press without a step does nothing.

A locked pad (UC-015 A6) still scrolls the pages, which send nothing; the volume and the mute stay blocked as UC-015 A6 says. With a layer key down the knob is that layer's, as in UC-015 BR-007 and BR-017. With protocol 1 the knob is step 6; with the link down it is UC-015 step 8 (FR-240). The K8 tap stays reserved (UC-015 BR-011).

### BR-009: Auto-paging and return to Home (protocol 2 or higher)

While the pages show, no key and no knob press is down and no setting, result, tap or volume screen shows, the pad shows the next page in the order of BR-006 every `operator_pad.display_autopage_ms` (default 5000) after a page was shown; at `off` (0) the page stays. A page step by the knob (BR-008) stops the cycling. When `operator_pad.display_home_ms` (default 10000) have passed since the last key or knob input of any kind, the pad shows `HOME` and the cycling resumes (with `display_autopage_ms` at `off` it shows `HOME` and stays). A menu status change neither moves the page nor restarts a timer.

### BR-010: Internet check

While the display link is up with protocol 2 or higher, the pad service checks general internet access itself (not the agent's backend, not Flagsmith): a TCP connect to `operator_pad.internet_check_target` (`host:port`, default `google.com:443`) every `operator_pad.internet_check_ms` (default 30000), with a connect timeout of 3 s. A connect that succeeds counts as reachable and is closed at once with nothing sent; a failed name lookup, a refused connect or the timeout count as down. A TCP connect needs no raw-socket privilege (an ICMP ping would), so the service stays unprivileged. One check runs at a time and never delays a key event, a frame or a status read. The status bar shows the internet icon while the last check succeeded, and `SYSTEM` row 2 shows the state (BR-006); before the first check ends the icon is hidden and the row shows `?`. With the target at `off` no check runs, the icon stays hidden and the row shows `OFF`.
