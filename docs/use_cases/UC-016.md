# Use Case: See the Game State on the Operator Pad

## Overview

**Use Case ID:** UC-016
**Use Case Name:** See the Game State on the Operator Pad
**Primary Actor:** Host
**Goal:** See on the operator pad's own screen, without a laptop and without waiting for a voice line, what the lobby looks like (game state, selected mode, ready and connected controllers, the agent) and, while turning the knob, which setting is being changed and to what
**Trigger:** The pad service attaches to the pad and its display link comes up; the menu status changes; Host holds a layer key and turns the knob, turns the knob alone, or a pad command ends
**Status:** Implemented
**Requirements:** FR-236, FR-237, FR-238, FR-239, FR-240, FR-241, FR-242, FR-243, FR-244, FR-245, FR-256, FR-257, FR-258, FR-259, FR-260, FR-261, FR-262, FR-263, FR-264, NFR-070

Phase 2 of the operator pad (#2741): [UC-015](UC-015.md) is phase 1, the keys and the knob with voice, sound and LED cues. This use case adds the pad's 128x64 OLED. The firmware is a Vial keymap for the 0xCB 1337 in the `orange-case/operator-pad` repository (`firmware/`); it draws what the pad service sends over the pad's raw HID interface (BR-002) and holds no game logic. The pad is a rev 5 (RP2040), for which QMK and Vial have no keyboard definition, so the repository brings its own (`keyboard/`, built as `orange_case/operator_pad`); revisions 1 to 4 (ATmega32U4) build the same keymap as `0xcb/1337`. While the screen works it replaces the pad's own voice lines and the volume sound (BR-004, BR-005); every other cue of UC-015 stays. The firmware side of BR-002 is built and bench-tested on a rev 5 pad (`orange-case/operator-pad` #1); the pad service side is built (#2741: `services/operator_pad/`, the menu's `cue` key and `ProcessInputResponse.value`, the `operator-pad` compose service and the udev rule). Only the check on the Pi 5 with the real pad is still pending (the measurement of NFR-070 and the bench check of the link): FR-236 to FR-242 are Implemented, not Verified, until then, and NFR-070 stays Open.

Iteration 2 (#2742): a pad whose firmware answers protocol 2, 3 or 4 (BR-002) gets seven pages in one screen frame (a title bar with the page's place, three rows, a status bar of icons), that the knob scrolls and that turn on their own while the pad is idle, and the internet state in its status bar (A5, A6, BR-006 to BR-010). Protocol 3 (rev 5 only) draws the rows in a medium 8x12 font and a ladder setting as a marker bar; protocol 4 (rev 5 only) adds the vertical wheel that wraps for the mode, the backend and the shield mode, its middle row in a tall 8x16 font; protocol 2 (revisions 1 to 5) draws the same pages with big 12x16 rows. A pad that answers protocol 1 keeps the single status screen of BR-001. The layout follows the maintainer's bench decisions of 2026-11-24. Protocols 2 to 4 are built in the firmware (`orange-case/operator-pad` #3, #4 and #5, merged) and in the pad service (#2742); the status fields of BR-006 came with the menu of #2755, and the check on the Pi 5 with the real pad is pending as for FR-236 to FR-242. The rows sit where the key rows are; editing a row from its page (the page keys) is iteration 3 (#2747).

Iteration 3 (#2747; built in the menu and the pad service, the check on the Pi 5 with the real pad pending as for iteration 2): the page keys. The bench (2026-11-24) showed that UC-015's fixed keys do not line up with the rows (on `HOME`, K2 changes the sensitivity while row 2 shows the volume). With iteration 3 the keys follow the rows: the left key of a row edits its setting, the middle key resets it to its default, K5 (the agent) and K8 (the game) stay fixed on every page, and a long K4 hold locks the pad (A7 to A10, BR-011 to BR-016). This replaces UC-015's key layout (UC-015 BR-011, BR-016) with the display link up or down: without a screen the row keys act as on one fixed page (BR-016). The commands stay UC-015's (UC-015 BR-001 to BR-005, BR-010), plus two menu commands (`reset_setting`, `interventions_switch`), two guard keys (`agent_switch` `only_if_stopped`, `step_setting` `from`) and two status fields (`setting_defaults`, `pad_commands`) ([services.md](../specs/services.md) §3.1). The rules include the maintainer decisions of 2026-11-24 taken after the review of the build plan: the K5 stop fires at the hold time whatever else is down (BR-011, A10), the resume brings the agent back exactly as it was at the stop (UC-015 BR-003), what a reset puts in force is computed by one menu function and checked at the commit (BR-013), an unknown agent level is refused, never confirmed blind (BR-014), and the K4 reset and lock stages cannot collide (BR-015).

Iteration 4 (#2755; built in the menu, the pad service and the flag service's `if_writer` in scope `stack`, #2757; maintainer decisions D2 to D16 of 2026-11-24 and D17 and D18 of 2026-11-25, of #2755): every row the maintainer defined becomes settable from the pad. The six agent rows that are read-only today get keys: `AGENT` row 3 `GOAL` (`objectives`, D17), `INTERV` row 2 `RATE` (`policy.max_interventions_per_minute`) and row 3 `GROUP` (`policy.group_grant.enabled`), `RETRO` row 1 `RETRO AI` (`inference.backend`), row 2 `EFFORT` (`inference.effort`) and row 3 `BRIEF` (`decision.operator_brief`) (BR-006, BR-007, BR-012); `SYSTEM` stays read-only (D10), and there is no new page (D8). Goal, rate, group, effort and brief are written in memory (their registry rows take no persist), the retro backend persisted like the decision backend (D2). The goal is the agent's `objectives`, from which the goal profile follows by default (`goal.profile` = `from_objectives`, decide-contract §14.4); `goal.profile` itself stays Flagsmith-only (FR-226, D17). A reset clears only the menu's own value of the row and leaves a script's or Flagsmith's value alone (BR-013, D14, replacing D6); Flagsmith stays the reference, so a Flagsmith pull can undo a pad value (D13, BR-012). A change that gives the agent more autonomy (RATE up, GROUP `ON`) or costs more (RETRO AI `CLAUDE`, EFFORT up, and the decision backend of `INTERV` row 1 from the free `RULES` to a paid backend, D12) needs the confirmation of BR-014 (D3). The retro backend is a wheel of two options that does not wrap (D18, BR-007). The brief is a preset wheel; a free text is shown as `CUSTOM`, never overwritten or cleared by the pad (D4, D13). The goal is lobby-only, the others live (D5); no new voice lines (D7). Against a menu older than #2755 (no status fields 22 to 27, no per-option `pad_commands`; [services.md](../specs/services.md) §3.1) these rows show `?` and their keys send nothing and play the refusal cue (BR-011 "Menu too old").

## Preconditions

- **Pre-1:** UC-015 Pre-1 to Pre-3 hold: the `operator-pad` service runs, the pad is attached and the menu is RUNNING.
- **Pre-2:** The pad runs the operator-pad firmware, which answers the hello of BR-002 with protocol version 1 or higher (2 or higher for the pages, A5), and the service can open the pad's raw HID node read-write ([services.md](../specs/services.md) §3.1).
- **Pre-3:** `operator_pad.display_enabled` is on (default on, [flags.md](../specs/flags.md) §10a).

## Main Success Scenario

1. System (the pad service) attaches to the pad, sends the hello and gets protocol version 1 or higher: the display link is up (version 2 or higher: A5).
2. System reads `GetMenuStatus` every `operator_pad.display_poll_ms` (BR-003) and shows the status screen (BR-001; with protocol 2 or higher the pages of BR-006, A5): the game state, the selected mode, the ready and connected controllers, the agent (on, off or unknown, its level and its backend), the settings and the JoustMania version.
3. The menu status changes (a controller connects or readies up, a game starts, someone changes a setting from the dashboard): System redraws the status screen with no key pressed, within NFR-070's bound from the moment `GetMenuStatus` first reports the change (a setting changed elsewhere reaches the status with the menu's own delay, UC-015 BR-018).
4. Host holds the edit key of a row (K1, K3 or K6, A7, BR-011) and turns the knob: from the first step System shows the setting screen (BR-001): which setting is being changed, its value at the press and the value the release would commit, updated per step (the value of the live preview, UC-015 BR-017); the preview speaks nothing (BR-005).
5. Host releases the layer key: UC-015 commits as before (UC-015 BR-005); System shows the result screen (BR-001) for `operator_pad.display_result_ms`, then the status screen.
6. Host turns the knob with no layer key held: System shows the volume screen (BR-001) with the level the turn would commit and plays no sound (BR-004); the commit after the pause is UC-015 step 8. With protocol 2 or higher the knob alone scrolls the pages and press and turn sets the volume (A5, BR-008).

## Alternative Flows

### A1: Display link down or old firmware

**Trigger:** the raw HID node is missing or cannot be opened, the firmware does not answer the hello with a version of 1 or higher, a frame write fails, or `operator_pad.display_enabled` is off (step 1, or any later step)
**Flow:**

1. System keeps every key, knob and cue of UC-015 working as before (FR-240): the display link is never needed to send a command, and a failed frame write never delays or drops a key event. With the page keys (FR-262) the fixed keys (K4 lock, K5, K8) and the knob work as with the link up, and the row keys act as on the fallback page (BR-016), with UC-015's voice and sound cues.
2. System counts the link as down: the volume plays its short sound and the pad speaks its own voice lines again (BR-004, BR-005), and System retries the hello at the device rescan interval (UC-015 A4), never in a busy loop.
3. The firmware, after 3 s without a frame, shows its own `NO HOST` screen (BR-002); the keys keep sending their F key codes.
4. Use case ends; it starts again at step 1 when the link comes back.

### A2: Status unreadable

**Trigger:** a `GetMenuStatus` read fails or times out (step 2 or 3)
**Flow:**

1. System keeps the last values on the status screen and shows `NO CONNECTION` on its last line (BR-001); it does not queue or retry any command (UC-015 BR-010).
2. Use case continues at step 2 with the next read.

### A3: Refused, limit, cancel or failure

**Trigger:** a pad command of UC-015 ends without a commit: A1 `game_active`, A3 failure, A5 / A10 cancel, A7 limit (step 5); a `stale` answer to a guarded page-key command (BR-013, BR-014, A10)
**Flow:**

1. System shows the result screen with the UC-015 BR-009 word (`NOT POSSIBLE`, `FAILED`, `CANCELLED`, `MAXIMUM`, `MINIMUM`, `NO CONNECTION`) besides the cue, then the status screen. A `stale` answer shows `CANCELLED` with the cancel cue: the value changed under the hold, nothing was written, and the host repeats the gesture if still wanted.
2. Use case ends.

### A4: A lobby-only layer while the game is live

**Trigger:** Host holds K1, K2, K5 or K6 and turns the knob while the lifecycle is live (step 4; UC-015 A1)
**Flow:**

1. System shows the setting screen with `NOT POSSIBLE` on its last line and no new value; the release is refused as in UC-015 A1.
2. Use case ends.

### A5: Pages and knob scrolling (protocol 2 or higher)

**Trigger:** the firmware answers the hello with version 2 or higher (step 1)
**Flow:**

1. System shows the `HOME` page (BR-006) instead of the status screen, and draws the setting, result, tap and volume screens in the same frame (BR-007); steps 3 to 5 and A2 to A4 apply to the page showing, and the internet check of BR-010 runs.
2. Host turns the knob alone: System shows the next page (clockwise) or the previous one (counter-clockwise), one page per knob step, wrapping, and sends no command (BR-008).
3. Host presses the knob and turns it while it is down: System sets the master volume one variant per step and commits after the pause as in UC-015 step 8, showing the volume screen without a sound (BR-004, BR-008).
4. Host presses the knob and releases it within the tap limit without a turn: System mutes or unmutes (BR-008).
5. Use case continues at step 3.

### A6: Pages turn on their own

**Trigger:** the pages show (A5), no key and no knob press is down and no setting, result, tap or volume screen shows (step 2)
**Flow:**

1. System shows the next page every `operator_pad.display_autopage_ms` (BR-009); with the flag at `off` the page stays.
2. Host scrolls with the knob (A5 step 2): System stops the cycling and keeps the page Host chose.
3. When `operator_pad.display_home_ms` have passed since the last key or knob input and the page is not `HOME` or the cycling has stopped, System shows `HOME` once and the cycling resumes (BR-009).
4. Use case continues at step 3.

### A7: Edit a row from its page

**Trigger:** Host presses the edit key of a row (K1, K3 or K6, BR-011) whose setting the page lets the keys change (BR-012) (step 2, or A5)
**Flow:**

1. System binds the key to a row of a page it has shown (BR-011, "Which row"; a row key while the link is uncertain is refused there), draws that row inverted (the highlight, BR-006) while the key is down and the knob has made no step; the page stays for the whole hold (BR-011).
2. Host releases within the tap limit: System shows the tap screen with the row's label and value (BR-007; without a screen UC-015's announcement, BR-016). Use case ends.
3. Host turns the knob while the key is down: System shows the setting's edit screen (BR-007: marker bar, wheel, or NOW and NEW rows) with the live preview of UC-015 BR-017, and nothing is written. An agent level whose NOW is unknown, and the interventions switch of an `OFF` agent, show `NOT POSSIBLE` instead and the release sends nothing (BR-012, BR-014).
4. Host releases the key: System commits the setting once with the menu command of BR-012 (UC-015 BR-005; the level with `from`, the level the edit started from, BR-014) and shows the result screen (step 5); a raise of the agent needs the confirmation of A9 first.
5. Use case ends; a refusal, limit, `stale` answer or failure is A3, a lobby-only setting while the game is live A4. A release past `operator_pad.hold_agent_ms` without a knob step plays the transition cue (BR-011).

### A8: Reset a row to its default

**Trigger:** Host presses the reset key of a row (K2, K4 or K7, BR-011) whose setting has a reset (BR-012, BR-013) (step 2, or A5)
**Flow:**

1. System binds the key to a row as in A7 step 1 and draws the row inverted while the key is down (BR-006).
2. Host releases within the tap limit: System shows the tap screen with the row's label and `DEFAULT` with the default (BR-013); nothing is written. Use case ends.
3. Host holds the key for `operator_pad.hold_reset_ms` (default 1000): System shows the reset screen (BR-007): the setting's label and `RESET?`, `NOW` and the value, `NEW` and the value the reset puts in force (`setting_defaults`, BR-013), the hint `RELEASE TO RESET`. For the agent level with NOW or NEW unknown, or NEW off the ladder, the hint is `NOT POSSIBLE` and the release sends nothing (BR-014).
4. Host releases the key: System sends `reset_setting` for the row's setting with `expect`, the NEW it showed ([services.md](../specs/services.md) §3.1), and shows the result screen; a reset that raises the agent needs the confirmation of A9 first. The menu answers `stale` and clears nothing when its own computation now differs from `expect` (A3).
5. Use case ends. A release between the tap limit and the reset hold sends nothing and plays the cancel cue (`CANCELLED`; maintainer decision D5, #2747); a release within the guard band after a stage boundary does the same (BR-011); after `operator_pad.hold_lock_ms` on every row, a row without a reset included. A K4 hold that reaches the lock time is the lock instead of the reset, unless the reset was confirmed (BR-015).

### A9: A raise of the agent waits for a confirmation

**Trigger:** in A7 or A8 the value the release would commit raises what the agent may do (BR-014) (step 4)
**Flow:**

1. System shows `PRESS KNOB` on the right of the title bar and blinks the title bar (inverted and normal in turn, every 500 ms; BR-014), on every edit and reset screen (wheel, marker bar, two-state, NOW and NEW rows); the screens with a hint row show `PRESS TO CONFIRM` instead of `RELEASE TO SET` / `RELEASE TO RESET`. The pad plays one short attention sound when the change first becomes a raise waiting for the press.
2. Host presses the knob while the key is still down: System marks the value showing as confirmed, plays a short confirm sound, and shows `CONFIRMED` on the right of a steady title bar and, where there is a hint row, `RELEASE TO SET` (or `RELEASE TO RESET`), but only when that value has not changed for 250 ms before the press (knob jitter, BR-014); knob turns while the knob is down are ignored; a later knob step clears the confirmation. On K4 a confirmation ends the lock stage for that hold (BR-015).
3. Host releases the key: with the value confirmed System commits it (A7 step 4, A8 step 4); without, it sends nothing and shows `CANCELLED` (the cancel cue, UC-015 BR-009).
4. Use case ends.

### A10: The K5 hold, stop and resume

**Trigger:** Host holds K5 (BR-011), on any page, locked or not (step 2, or A5)
**Flow:**

1. System reads the status at the press (UC-015 BR-013) and times the hold from the press (BR-011, "Timing"). K5's events are handled at once, never queued behind a command still waiting for the menu.
2. K5 has been held `operator_pad.hold_agent_ms` and is still down, and the press read is not `OFF` (BR-011: `ON`, `WATCH` or `?`), or the hold is not clean (another key down, the knob down, a key whose release was lost, the pad locked): System sends the stop at once (UC-015 BR-002), without waiting for the release and without UC-015 A10's cancel, and shows its result. The release does nothing more. Use case ends.
3. Otherwise (a clean hold, press read `OFF`): System waits for the release and reads the status again. Known `OFF`: it sends the resume with the guard `only_if_stopped` ([services.md](../specs/services.md) §3.1); the menu brings the agent back with the level and the gate it had at the stop (UC-015 BR-003), or answers `stale` and writes nothing when the flag service shows it not fully stopped (A3). Known and not `OFF`: System cancels (UC-015 A10, the cancel cue). Unknown: System sends the stop (UC-015 A10, a no-op for a stopped agent, UC-015 A9).
4. Use case ends.

## Postconditions

### Success Postconditions

- The pad's screen shows the status screen (a page with protocol 2 or higher, A5) with values no older than NFR-070 allows, or the screen of the gesture in progress. No flag, setting or game state was changed by this use case: it only shows. The page keys (A7 to A10) send UC-015's commands and `reset_setting` and `interventions_switch`; what they change is UC-015's postconditions.

### Failure Postconditions

- The pad works as in UC-015 (FR-240); the screen shows `NO HOST` (firmware, no frames) or the last values with `NO CONNECTION` (A2).

## Business Rules

### BR-001: Screens

The display is 128x64 pixels, drawn as 8 text lines of 21 characters (the firmware's 6x8 font), numbered 0 to 7 as in BR-002 throughout this use case; line 0 is the title, drawn inverted. The pad service composes every screen; the firmware only draws lines (BR-002). Every value comes from the last `GetMenuStatus` read (BR-003) or, on the setting screen, from the live preview (UC-015 BR-017). A value the status does not tell (an agent state the menu reports as unknown, a missing key in `operator_settings` outside status line 5, no status at all) shows as `?`, never a guess. Sensitivity and teams on status line 5 have one rule: `AUTO` when `operator_settings` reports `automatic` for the setting, otherwise the effective `sensitivity` / `num_teams` of the status in short form, also when the key is missing (the status has no "unknown" for the effective values: for a flag flagd cannot resolve that is the menu's default). The result screen shows the value the menu reports as committed (`ProcessInputResponse.value`, [services.md](../specs/services.md) §3.1), never the pad's own prediction; with no `value` (a menu older than that field, or a command that commits no value) it shows the label and the UC-015 BR-009 word, or `OK` on success. With protocol 1 there are no display pages: one screen shows at a time; with protocol 2 or higher the knob scrolls the pages of BR-006 (iteration 2, #2742). K8's tap starts a game either way (BR-011). Values are written in the short forms below, so that every line fits in 21 characters; a mode is its full name of the mode table (BR-006), any value not in the tables is the name in capitals, cut to fit.

| Setting | Short forms |
|---|---|
| Sensitivity (`ultra_slow` to `ultra_fast`) | `AUTO`, `0`, `1`, `2`, `3`, `4` |
| Teams (`two` to `six`) | `AUTO`, `2`, `3`, `4`, `5`, `6` |
| Shield mode | `AUTO`, `INST`, `TRIG`, `HOLD` |
| Volume | `MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX` |
| Agent level | `NONE`, `AMBIENT`, `STANDARD`, `FULL` |
| Backend | `RULES`, `CLAUDE`, `JEV` |

| Screen | When | Lines |
|---|---|---|
| Status | default: no layer key held, no result, tap or volume screen showing | 0 `JOUSTMANIA` and the state: `LOBBY`, or `GAME` while the game lifecycle is live (the status does not tell starting, running and ending apart); 1 the selected mode's full name (the mode table of BR-006); 2 `READY <ready>/<connected>`; 3 the agent, so the screen never disagrees with what a K3 hold would do: `AGENT ?` when UC-015 BR-013 counts the status as unknown (`agent_enabled_state` or `agent_interventions_enabled_state` not `on` or `off`, or `agent_level` empty or outside the ladder of UC-015 BR-004), else `AGENT OFF` while `agent_enabled` is off or the level is `none` (BR-011's `OFF`), else `AGENT WATCH` and the level's short form while only the write gate is `off`, else `AGENT ON` and the level's short form (BR-011); 4 `BACKEND` and its name; 5 `SENS` and `TEAMS` (the line 5 rule above); 6 `SHIELD` and `VOL`; 7 `NO CONNECTION` (A2), else `LOCKED` (UC-015 A6), else the JoustMania version: `V` and the release tag the stack runs (a tag that already starts with `v` or `V` is shown with a single `V`, never `VV`), or `DEV` without one, also for an image tag that is not a release (`latest`, `main`, a commit sha) (FR-241) |
| Setting | a layer key is the only key down and the knob has made at least one step (the UC-015 BR-017 condition) | 0 the setting's label (`GAME`, `SENSITIVITY`, `AGENT LEVEL`, `TEAMS`, `SHIELD MODE`, `BACKEND`); 2 `NOW` and the value read at the press; 4 `NEW` and the value the release would commit; 5 the ladder with the new value marked (`AUTO 0 1 2 [3] 4`) where it fits on one line; 7 `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range (ladder settings only; the mode, the backend and the shield mode wrap, BR-007), or `NOT POSSIBLE` (A4) |
| Volume | a knob turn or press with no layer key held | 0 `VOLUME`; 2 the variant the turn would commit (`MUTE`, `QUIET`, `NORM`, `LOUD`, `MAX`); 4 a bar of the five rungs; 7 `MUTED` while muted, or `MAXIMUM` / `MINIMUM` when a turn hits the end of the range. Shown for `operator_pad.display_result_ms` after the last turn |
| Result | from the release until the menu answers: the label alone, at most the command's deadline; after a commit, a refusal, a cancel or a failure (step 5, A3): the result | 0 the label of the command; 2 empty while the menu has not answered, then the value the menu committed (`ProcessInputResponse.value`, short form), or the UC-015 BR-009 word (`FAILED` for any error without one), or `OK` for a success without a `value`; the result shown for `operator_pad.display_result_ms` (default 1500), then the status screen |
| Tap | after a tap UC-015 announces (K2, K3, K5, K7; UC-015 BR-011) | 0 the label (`SENSITIVITY`, `AGENT`, `TEAMS`, `BACKEND`); 2 the value read at the tap in short form (K3: as status line 3, without `AGENT`), or `?` when the status does not tell it; shown for `operator_pad.display_result_ms`, then the status screen |

A new screen replaces the one showing at once (a new layer step replaces a result still showing). A K3 hold (stop / resume the agent) and a K4 hold (end / force-start) show their result like every command.

This is the layout for a pad that answers protocol 1. A pad that answers protocol 2 or higher gets the pages of BR-006 instead of the status screen and the setting, volume, result and tap screens of BR-007; the values, their sources, the `?` rule and the "When" column above stay, and so do the short forms where a row has no room for the full word.

### BR-002: Display link and frame protocol

The pad service writes to the pad's raw HID interface (the Vial / VIA interface: usage page `0xFF60`, usage `0x61`, 32-byte reports) on the device `operator_pad.device` matches (UC-015 BR-014). Every report starts with the command id `0x50`, which is not a VIA or Vial command id, then an op:

| Op | Bytes | Meaning | Reply |
|---|---|---|---|
| `0x00` hello | none | asks the protocol version | `0x50 0x00 <version>`; version 1 (2, 3 or 4 with protocols 2 to 4, below) |
| `0x01` line | 2: line 0 to 7 (with the medium bit: the medium row 0 to 2, protocol 3); 3: attributes (bit 0 inverted; from protocol 2 bit 1 large, bit 2 underline; from protocol 3 bit 3 medium); 4 to 24: 21 ASCII characters (0x20 to 0x7E, space padded; any other byte draws as `?`) | writes one line into the back buffer | `0x50 0x01 0x00`; a line number of 8 or more, or a medium row above 2: `0x50 0x01 0xFF`, nothing written |
| `0x02` show | 2: frame sequence number | draws the back buffer; also the heartbeat | `0x50 0x02 0x00` |

An unknown op is answered `0x50 <op> 0xFF` and changes nothing. The service sends the 8 lines and a show for each screen that differs from the last one shown, and a show alone at least once a second. The firmware draws only on show, so a half-sent frame is never seen. With no show for 3 s it draws its own `NO HOST` screen; after a power-up it shows `JOUSTMANIA` and `WAITING FOR HOST`. The keys never depend on the link (A1). Vial's own commands keep working, so the Vial app can still read and change the keymap.

**Protocol 2** (#2742; `orange-case/operator-pad` #3, merged; revisions 1 to 5). Everything above holds, with these additions: the hello is answered with version 2; in the `line` op's attribute byte bit 1 means large and bit 2 underline; and the bytes `0x7F` to `0x84` draw glyphs instead of `?`: `0x7F` a full bar block, `0x80` an empty bar block, `0x81` internet, `0x82` agent, `0x83` instructions, `0x84` lock (BR-006). A large line n (0 to 6) draws the first 10 characters of its text in a 12x16 pixel font (each pixel of the 6x8 font doubled) over display lines n and n+1 (pixel columns 0 to 119; columns 120 to 127 stay blank, or are filled when the line is also inverted); the content written to line n+1 is ignored for that frame. A large bit on line 7 draws the line small. An underlined line gets a 1 px line across the full width on its bottom pixel row (a large line n on the bottom row of line n+1), dark when the line is inverted; no glyph uses that row.

**Protocol 3** (#2742; `orange-case/operator-pad` #4, merged; rev 5 only). Everything of protocol 2 holds, with these additions: the hello is answered with version 3, bit 3 of the `line` op's attribute byte means medium, the byte `0x85` draws the marker (a down-pointing triangle), and a new op draws a bar. The ATmega32U4 of revisions 1 to 4 has no flash left for a second font, so its firmware stays at protocol 2: its hello answers 2, it ignores bit 3 and answers `0x50 0x03 0xFF` to the bar op; it draws the marker glyph `0x85` in its small font too.

- **Medium row.** A `line` op with the medium bit addresses medium row r (0 to 2) in its line byte; rows 0, 1 and 2 are rows 1, 2 and 3 of the frame (BR-006). The row is stored as display line 1 + 2r and, like a large line, covers display lines 1 + 2r and 2 + 2r (row 0 lines 1-2, row 1 lines 3-4, row 2 lines 5-6): the content of line 2 + 2r is ignored for that frame, and a later small or large write to line 1 + 2r replaces the row. It draws the first 16 characters of its text in an 8x12 pixel font, 8 px per character across the full 128 px, its 12 pixel rows starting at pixel row 11 + 15r, so 3 px separate the title bar, the rows and the divider. Inverted (bit 0) fills the row's 12 pixel rows (the highlight); underline (bit 2) draws the 1 px divider on the bottom pixel row of the row's slot (pixel row 23, 39 or 55), always lit since it lies below the inverted band; on row 2 it is the divider above the status bar. The large bit is ignored on a medium row. The font is X.Org misc-fixed (public domain) at 8x12, with the same glyphs as the small one: ASCII `0x20` to `0x7E` and `0x7F` to `0x85`.
- **Bar** (op `0x03`; report `0x50 0x03 <row> <rungs> <filled> <marker> <labels>`): byte 2: the bar row r (0 or 1); 3: the rungs (2 to 8; 0 removes the bar); 4: the filled rungs (0 to the rungs, from the left); 5: the marker rung (0 to the rungs - 1, or `0xFF` for no marker); 6 to 31: the rung labels, ASCII separated by `|`, ended by `0x00` or the end of the report, label k under rung k (a missing or empty label stays blank, extra ones are ignored). The bar at row r covers display lines 1 + 2r to 4 + 2r (pixel rows 8 + 16r to 39 + 16r, medium rows r and r + 1); the content of those lines is not drawn. Within those 32 pixel rows, from the top: the marker (the `0x85` shape) on rows 6-9, centred over its rung; the bar on rows 12-20, rungs of equal pitch (128 / rungs px) with a 2 px gap, centred, the first `filled` rungs solid and the rest a 1 px outline; the labels in the small font on rows 23-29, each centred under its rung and kept on screen, never cut: a label wider than its rung (`AUTO` under the first of six rungs) starts at the left edge. An underline on the bar's last line (4 + 2r) is still drawn. The bar is part of the back buffer and is drawn on show. Writing any line it covers (a small, large or medium `line` op) removes it, so the host sends the bar after the lines of its frame. Reply `0x50 0x03 0x00`; any other value out of range: `0x50 0x03 0xFF`, nothing drawn.

**Protocol 4** (#2742; `orange-case/operator-pad` #5, merged; rev 5 only, revisions 1 to 4 stay at protocol 2). Everything of protocol 3 holds, with these additions; the exact ops, attribute bits and byte layout are those of the firmware's README (`orange-case/operator-pad`, `firmware/`), which this rule does not repeat:

- **Hello** answered with version 4.
- **NOW arrows**: the bytes `0x86` (a right-pointing triangle, ▸) and `0x87` (a left-pointing triangle, ◂) draw glyphs in the small 6x8, the medium 8x12 and the tall font. A firmware below protocol 4 draws `?` for them, like any byte without a glyph.
- **Tall font**: an 8x16 pixel font (Spleen 8x16, BSD-2-Clause) for the middle row of the wheel, up to 16 characters across the 128 px.
- **Centred text**: a small or medium line can be drawn centred, pixel-exact across the full width, instead of flush left (a large line ignores it); the tall row exists only as the wheel's middle entry, which is always centred.
- **Wheel**: one documented scheme (a wheel op or row attributes, the firmware's choice) draws the three entries of the wheel of BR-007 between the title bar and the divider: the entry above in the small font, the middle entry in the tall font, inverted across the full row width, the entry below in the small font, each centred, with even gaps (8 + 16 + 8 pixel rows); NOW is marked by the arrows of its entry.

The pad service treats any version of 1 or higher as the link up and uses a feature only when the hello reports its version: protocol 4 the wheel (BR-007), protocol 3 the medium rows and the marker bar (BR-006, BR-007), protocol 2 the big-font layout of the same pages (large rows, the glyphs, the underline), protocol 1 the screens of BR-001. A version above 4 is used as 4. A pad that answers protocol 3 gets the protocol 3 layout with the NOW and NEW rows instead of the wheel (BR-007); protocols 2 and 1 are as above.

### BR-003: Status refresh

While the display link is up, the pad service reads `GetMenuStatus` every `operator_pad.display_poll_ms` (default 500) besides the reads of UC-015's key presses and releases, and redraws the status screen when a shown value changed. The polled status is for the screen only: a command still uses the status read at its own press or release (UC-015 A5, BR-013).

### BR-004: Volume without a sound

The menu plays the volume step sound of a volume step and of a mute or unmute (its `step_setting` for `audio_volume.master`), so the pad silences it through the menu: while the display link is up, the pad sends that `step_setting` with `cue=none` ([services.md](../specs/services.md) §3.1), the menu skips the volume step sound, and the volume screen (BR-001) shows the level instead. A menu older than the `cue` key ignores it and the sound plays. With the link down (A1) the pad sends no `cue` and the short sound of UC-015 step 8 plays as before, so a pad without a screen still gives feedback.

### BR-005: The pad's own voices with a screen

While the display link is up, the pad plays none of its own voice lines: the live preview's label and value (UC-015 BR-017), the tap announcements (UC-015 BR-011; the tap screen), the status words it decides itself (`NOT POSSIBLE`, `MAXIMUM`, `MINIMUM`, `CANCELLED`), the lock words (UC-015 A6) and the spoken "No connection" after the failure cue of a menu the pad cannot reach (UC-015 BR-009; the screen shows `NO CONNECTION`); the screen shows each of them instead (BR-001). The unknown-key cue (UC-015 A4) is a sound, not a voice line, and stays. The menu's voice lines for a command it runs (UC-015 steps 4 to 7 and 9) stay, so the room still hears a committed change; the volume sound is BR-004. The failure cue (two beeps, UC-015 BR-009) stays too, the pad's included, since it warns without a look at the screen. The controllers' LED cues are unchanged. With the link down (A1) the pad speaks as in UC-015.

### BR-007: Setting, volume, result and tap screens (protocol 2 or higher)

With protocol 2 or higher the setting, volume, result and tap screens of BR-001 show when BR-001 says (the volume screen on a volume step or a mute of BR-008 only, never on a page step), for as long as it says, in the frame of BR-006: the status bar stays.

- **Ladder settings**: the sensitivity (rungs `AUTO 0 1 2 3 4`), the teams (`AUTO 2 3 4 5 6`) and the volume (`MUTE QUIET NORM LOUD MAX`), the quantities with a minimum and a maximum. Protocol 3 or higher: the marker bar (the bar op, BR-002) at bar row 0, over rows 1 and 2, one rung per ladder value: the marker above the rung of the value at the press (NOW; no marker while that value is unknown), the rungs filled up to and including the rung the release would commit (NEW). Labels: the sensitivity and the teams a label under every rung (`AUTO|0|1|2|3|4`, `AUTO|2|3|4|5|6`); the volume only at the ends, `MUTE` under the first rung and `MAX` under the last (`MUTE||||MAX`). Row 3 (medium row 2) holds the hint `RELEASE TO SET` (empty on the volume screen, which commits after the pause) with the underline as the divider. The service sends the bar after the frame's lines, since a line written over the bar removes it (BR-002). Title bar: the setting's label (`SENSITIVITY`, `TEAMS`, `VOLUME`) left and `EDIT` right; `MAXIMUM` / `MINIMUM` right instead when a step hits the end of the range (the ladder settings stay clamped, UC-015 BR-005, A7), and on the volume screen `MUTED` right while muted. For the volume the value at the press is the level when the turn began. Iteration 4 (#2755): two more marker bars, the intervention rate (`RATE`, rungs `1 2 4 8 20`, the declared variants of `policy.max_interventions_per_minute` in value order, a label under every rung, `1|2|4|8|20`) and the retro effort (`EFFORT`, rungs `LOW MED HIGH XHI MAX`, labels `LOW` under the first rung and `MAX` under the last); both clamped, with `MAXIMUM` / `MINIMUM` at the ends. A value off the ladder (a rate written by a script or a fixture, for example 50) has no rung: NOW is then unknown and the edit is refused (`NOT POSSIBLE`, BR-012, D11), never moved to the first rung (these ladders never restart outside).
- **Wheel settings**: the mode (the full names of the mode table of BR-006, in `MODE_LADDER` order), the decision backend (`RULES`, `CLAUDE`, `JEV`; `BACKENDS` order), the shield mode (`AUTO`, `INSTANT`, `TRIGGER`, `HOLD`; `SHIELD_KNOB_LADDER` order) and the agent level (`NONE`, `AMBIENT`, `STANDARD`, `FULL`; `AGENT_POLICY_LEVELS` order), none of them a quantity with a minimum and a maximum; the shield mode's values are kinds of activation and the agent levels are policies, so neither gets a marker bar. **The agent level's wheel does not wrap** (no wrap; empty slot at the ends): it backs the kill switch, so `NONE` to `FULL` in one step is impossible; it stays clamped (UC-015 BR-005, A7, not in `WRAPPING`). At `NONE` the slot above is empty and at `FULL` the slot below (the slot sent as all spaces with no NOW flag, which the firmware draws blank), a step past the end changes nothing, and the title bar shows `MAXIMUM` / `MINIMUM` right instead of `EDIT` as on the ladder settings. Iteration 4 (#2755): three more wheels. The goal (`ENDURANCE`, `BALANCED`, `ACCELERATE`, `CHAOS`, `MIXED`; the declared order of `objectives`, BR-006, D17) wraps like the mode (in `WRAPPING`; objectives are kinds of game, not a quantity). The brief (`OFF`, `UNKILLABLE`, `PROTECT WEAK`; the declared presets of `decision.operator_brief`) does not wrap: it is clamped like the agent level, with the empty slot at the ends and `MAXIMUM` / `MINIMUM`, and it has three options. The retro backend (`STUB`, `CLAUDE`; the ladder of `inference.backend`, BR-012, maintainer decision D18) does not wrap either: with two options it is clamped like the agent level, so at `STUB` the slot above is empty and at `CLAUDE` the slot below, a step past the end changes nothing and the title bar shows `MAXIMUM` / `MINIMUM` right; NOW carries its arrows as on every wheel. A brief whose text is no preset (`CUSTOM`) has no edit: the edit screen shows `NOT POSSIBLE` and the release sends nothing, so a free text is never overwritten by a knob step (D4); its reset is a no-op that leaves the text (BR-013, D13). Protocol 4: a vertical wheel that wraps for the options in `WRAPPING` (the agent level's does not), drawn by the wheel of BR-002. Title bar: the setting's label left, `EDIT` right; then the divider and the status bar of the frame (BR-006); there is no hint row. Between the title bar and the divider the wheel shows three entries in ladder order, wrapping at both ends for the wrapping wheels (after the last option comes the first, before the first the last), so there is always one entry above and one below the middle (the ends of the non-wrapping wheels excepted, see above); every wrapping wheel has at least four options; the non-wrapping wheels are the exceptions to this rule: the agent level's, the brief's (three options) and the retro backend's (two options, D18). The middle entry is NEW, the option the release would commit, in the tall 8x16 font, centred and inverted across the full row width; the entry before it (above) and the entry after it (below) are in the small 6x8 font, centred, not inverted; the gaps between the title bar, the three entries and the divider are even. Each entry is its full name (no short forms; at most 16 characters in the tall row), so the wheel never looks like a page (label left, value right). The option read at the press (NOW) carries a right-pointing triangle (`0x86`) directly left and a left-pointing triangle (`0x87`) directly right of its centred text (`▸FREE-FOR-ALL◂`, BR-002), in whichever of the three entries it is, drawn dark inside the inverted middle row when NOW is NEW; while NOW is not among the three, or unknown, no entry has them. A full name has at most 14 characters, so the arrows always fit. Each knob step turns the wheel one option, NEW staying in the middle. **Shield `AUTO`**: `AUTO` is a wheel entry like the modes (the `automatic` rung of UC-015 BR-018); with no operator shield value (`operator_settings` reports `automatic`) NOW is `AUTO`, not the effective mode, and the knob starts there; committing `AUTO` clears the operator value (UC-015 BR-018). This changes UC-015 BR-018's knob start for the shield mode only (built with the wrap, #2742; `lib/setting_ladders.py` `knob_start`); sensitivity and teams keep theirs.
- **Wrap**: for the mode, the backend and the shield mode a step past the last option goes to the first, and back past the first to the last, with the display link up or down: the wrap is a property of these settings, not of the screen, so UC-015 changes for them regardless of the link (UC-015 BR-005, A7; built by a UC-015 PR of its own before the pad service's display PR, #2742: the menu's `step_setting` and the pad's preview and backend step over `lib/setting_ladders.py` `step_ladder`, where an explicit per-option set `WRAPPING` names the wrapping options, never a default). The backend wraps in the pad's own step before the absolute `set_backend` (`RULES` back to `JEV`): the wheel shows where the release lands and nothing commits before it. A net turn count that is a whole number of turns of the wheel (n a multiple of the number of options, zero included) is a no-op: nothing is written and no cue plays, never `at_limit`. The pad treats it alike on all three wheels: when the release would commit the value the knob started at, it sends nothing (no `step_setting`, no `set_backend`) and clears the result screen. A `step_setting` that still arrives for one (a pad that could not read the start) the menu answers with `ok` and the unchanged value, writing nothing. They never give `at_limit`, `MAXIMUM` or `MINIMUM`. The ladder settings (sensitivity, teams, volume) stay clamped, with the marker bar and `MAXIMUM` / `MINIMUM` at the ends, and so does the agent level on its non-wrapping wheel; so does the saved-level ladder a stopped agent's K3 + knob moves (UC-015 BR-003), since the level ladders back the kill switch.
- **NOW and NEW rows**: on protocol 2 every setting, on protocol 3 the wheel settings (no wheel below protocol 4), and on any protocol every setting whose step is refused (A4). Rows: 1 `NOW` and the value read at the press; 2 `NEW` and the value the release would commit (empty when refused); 3 the hint `RELEASE TO SET`, `MAXIMUM` / `MINIMUM` at the end of the range (the clamped settings only: the ladder settings and the non-wrapping wheels), or `NOT POSSIBLE` (A4). Title bar: the setting's label left, `EDIT` right. On protocol 2 a ladder setting shows its bar of BR-006 as the value where it has one; its 10-character rows show the hint as `RELEASE`, and `NOT POSSIBLE` over rows 2 and 3 (`NOT` / `POSSIBLE`, NEW being empty when refused). A goal or brief value too long to sit beside `NOW` / `NEW` (6 characters on protocol 2, 12 on protocol 3) shows its row form: the goal `ENDUR`, `BAL`, `ACCEL`, `CHAOS`, `MIXED`, the brief `OFF`, `UNKILL`, `PROTEC` (`CUSTOM` as it is), so no two values look alike.
- **Result**: title bar the command's label; row 2 the value the menu committed (`ProcessInputResponse.value`), the UC-015 BR-009 word, or `OK` (BR-001), the full word where it fits; row 2 stays empty until the menu answers; rows 1 and 3 empty. On protocol 2 a word over 10 characters takes rows 2 and 3 (`NOT` / `POSSIBLE`, `NO` / `CONNECTION`).
- **Tap**: as the result screen, with the value read at the tap (BR-001).

- **Two-state settings** (instructions, force all, interventions; BR-012): NOW and NEW rows on every protocol (`OFF` / `ON`; a two-option scale is neither a marker bar nor a wheel), clamped (up is `ON`, a step past either end is `MAXIMUM` / `MINIMUM` as for the ladders). Iteration 4 (#2755): the group shield is two-state too (`OFF` / `ON`, up is `ON`); the retro backend has two options as well but is a non-wrapping wheel (`STUB`, `CLAUDE`, up is `CLAUDE`; maintainer decision D18, see the wheel settings), on protocol 2 and 3 its NOW and NEW rows as for every wheel; up is the next option of the row's ladder (BR-012), never the flag file's declared order (`policy.group_grant.enabled` is declared `on`, `off`).
- **Reset** (A8, BR-013): from `operator_pad.hold_reset_ms` on, title bar the setting's label left and `RESET?` right (`PRESS KNOB`, blinking, while a raise waits for its press, `CONFIRMED` after it, BR-014), rows `NOW` and the value, `NEW` and the default (BR-013; `?` while unknown), hint `RELEASE TO RESET` (`PRESS TO CONFIRM` while a raise waits, BR-014; `NOT POSSIBLE` for a lobby-only setting while the game is live, A4, as on the edit screen, and for a reset BR-013 or BR-014 refuses). On every protocol NOW and NEW rows, never a bar or wheel (protocol 1: the 8-line layout of BR-016). On K4, from `operator_pad.hold_lock_ms` on, the lock screen replaces it (BR-015).

When a result, tap or volume screen ends, the page that showed before it comes back (`HOME` when BR-009's return fell due in the meantime).

### BR-008: The knob with the pages (protocol 2 or higher)

While the display link is up with protocol 2 or higher and no layer key is down, the knob works as follows; a step is a knob step of UC-015 BR-005 (`operator_pad.knob_events_per_step`):

- **Turn alone** (the knob not pressed and no key down at all): one page per step, clockwise (B) to the next, counter-clockwise (A) to the previous, wrapping (`SYSTEM` to `HOME` and back). The page shows at once; a step sends no command, plays nothing and, while a result, tap or volume screen shows, ends it and counts from the page under it.
- **Press and turn**: each step while the knob is down sets the master volume one variant (UC-015 BR-006), committed after the same pause as UC-015 step 8 (UC-015 BR-005), with the volume screen and no sound (BR-004). The release of that press does nothing else.
- **Short press**: a knob press released within the tap limit (`operator_pad.tap_ms`, UC-015 BR-007) with no step while it was down mutes or unmutes, at the release (with protocol 1 or no link the mute fires at the press, UC-015 BR-016). A longer press without a step does nothing.
- **Push jitter**: the encoder can send a stray raw turn event as the knob is pushed; at one event per step (the default) that would be a volume step and cancel the mute. Raw turn events in the first 150 ms after the knob press goes down are therefore ignored (no volume step, no count toward one); the volume counts from then on as above.

A locked pad (UC-015 A6) still scrolls the pages, which send nothing; the volume and the mute stay blocked as UC-015 A6 says. With an edit key down the knob is that row's setting, as in UC-015 BR-007 and BR-017. With a reset key (K2, K4, K7), K5 or K8 down a turn does nothing: no page step and no volume; a knob press while a reset key or an edit key is down is the confirmation of BR-014, never a mute, and turns while it is down are ignored; a knob press while K5 is down never blocks the K5 stop (BR-011). With protocol 1 the knob is step 6; with the link down it is UC-015 step 8 (FR-240). The K8 tap starts a game (BR-011). The service drives one screen: with several pads attached, the first raw node of the matching device gets it (BR-002), and the knob of any attached pad scrolls its pages.

### BR-009: Auto-paging and return to Home (protocol 2 or higher)

While the pages show, no key and no knob press is down and no setting, result, tap or volume screen shows, the pad shows the next page in the order of BR-006 every `operator_pad.display_autopage_ms` (default 5000) after a page was shown; at `off` (0) the page stays. A page step by the knob (BR-008) stops the cycling. Return to Home: once, `operator_pad.display_home_ms` (default 10000) after the last key or knob input of any kind, and only when the page is not `HOME` or the cycling has stopped, the pad shows `HOME` and the cycling resumes (with `display_autopage_ms` at `off` it shows `HOME` and stays); with no key or knob input since the link came up there is no return. The return waits while a key or the knob press is down or a setting, result, tap or volume screen shows (it never changes the page under a held key) and comes as soon as none is. A menu status change neither moves the page nor restarts a timer.

### BR-010: Internet check

While the display link is up with protocol 2 or higher, the pad service checks general internet access itself (not the agent's backend, not Flagsmith): a TCP connect to `operator_pad.internet_check_target` (`host:port`, default `google.com:443`) every `operator_pad.internet_check_ms` (default 30000), within 3 s in all: IPv4 addresses first, and with several addresses each tries for its share of what is left, so a dead first address never keeps a later one from being tried. A connect that succeeds counts as reachable and is closed at once with nothing sent; a failed name lookup, a refused connect or the timeout count as down. A TCP connect needs no raw-socket privilege (an ICMP ping would), so the service stays unprivileged. One check runs at a time and never delays a key event, a frame or a status read. The status bar shows the internet icon while the last check succeeded, and `SYSTEM` row 2 shows the state (BR-006); before the first check ends the icon is hidden and the row shows `?`. With the target at `off` no check runs, the icon stays hidden and the row shows `OFF`. A failed read of the target flag keeps the last good value (the default `google.com:443` only before the first good read), so a flaky read never turns a check that was `off` back on ([flags.md](../specs/flags.md) §10a).

- **Agent states, "always stop"** (maintainer decision 2026-11-24). `OFF`: fully stopped, `enabled` off or the level `none` (the stop's no-op test, UC-015 A9). `WATCH`: `enabled` on and the level not `none`, but the write gate `interventions_enabled` off, so the agent observes and decides but may not act (the interventions switch, BR-012). `ON`: `enabled` on, the level not `none` and the gate on. `?`: the unknown rule of BR-001 status line 3. The K5 hold's direction is the state read at the press (UC-015 BR-013): `ON`, `WATCH` and `?` stop, only `OFF` resumes (A10). **The stop** (maintainer decision 2026-11-24, after the plan review) fires as soon as K5 has been held `operator_pad.hold_agent_ms` while it is still down, timed from the press, not on the release; it is exempt from chords, from the knob being down, from the lock and from a key whose release was lost, and under any of those it only ever stops, never resumes. A stop is idempotent (UC-015 A9), so it is never cancelled: UC-015 A10's cancel applies only to a resume. **The resume** needs a clean hold (no other key or the knob down, the pad not locked, the press read `OFF`) and fires on the release, as today; the read on release must be known `OFF` too, a known other state cancels (UC-015 A10), an unknown one sends the stop. `?` is outside that disagreement test: an unknown read at either end never cancels, it stops (UC-015 A10 step 2). `ON` against `WATCH` is no disagreement either, both stop. The pad sends the resume with the guard `only_if_stopped`, so the menu refuses it (`stale`, nothing written) when the flag service shows the agent not fully stopped, and the resume brings the agent back exactly as it was at the stop, its level and its gate (UC-015 BR-003): a watching agent comes back watching. So a K5 hold stops the agent whenever any part of it runs and never opens the gate of a watching agent; the pad opens the gate only with `AGENT` row 1 and the confirmation of BR-014. K5's press, hold time and release are handled at once, in their order, never queued behind a command still waiting for the menu. While a stop is still in flight, a further K5 hold is stop-only. The stop at the hold time never waits for the press's status read: one not in yet counts as unknown, which stops. Test hooks: a K5 hold with `enabled` on and the gate closed sends the stop, never the resume, locked or not; the stop fires at the hold time with the knob already down, with K3 down, with a stuck K1 and on a locked pad with the knob down (a mutation "a chord blocks K5" fails).

The binding holds for the whole hold, even if the link changes during it: no page step happens while a key is down (BR-008), the paging stops before the press's status read, and the auto-paging and the return to `HOME` wait until every key is up (BR-009). A key pressed while a result, tap or volume screen shows acts on the page under it. Between 1.5 s and 3 s after the last acknowledged frame (the link uncertain: the pad's screen may still show the frame) a row key is refused with the refusal cue and sends nothing; the fallback page of BR-016 applies only once the firmware shows `NO HOST` (more than 3 s, BR-002). Only the input node of the pad whose display link is up binds to the pages; the keys of any other pad act on the fallback page (BR-016), which has no agent rows; with more than one possible pad attached (a node whose USB device cannot be resolved counts as one more), every key acts on the fallback page, and the knob of one pad (press or turn) never acts on a key held on another. The binding uses the key event's time, not when the service gets to it. While row keys are refused (the uncertain link), the K4 lock and the transition cue still work: they act on no row.
- **Timing.** The press time and a snapshot of the timing flags taken at the press go with the key: the gesture stages and the screen stages (the highlight, the reset screen, the lock screen) of that hold use the same press time and the same snapshot, so the screen never shows a stage the release would not do. For 150 ms after each stage boundary (the tap limit, `operator_pad.hold_reset_ms`, `operator_pad.hold_lock_ms`, `operator_pad.hold_end_ms`) a release does nothing and plays the cancel cue. A key, or the knob press, whose release was lost counts as up after 30 s without an event for it, so a stuck key cannot block the other keys for ever. Each event is timed and its gesture settled as it arrives, before any status read, so a release is never decided late by a slow read; lost input events (SYN_DROPPED) reset every gesture in progress except a K5 hold, which stays and becomes stop-only.
- **Rows without keys.** A read-only row and an empty row have no keys (BR-012): their edit and reset keys send nothing, play no cue and draw no highlight; a K4 hold still reaches the lock (BR-015), and two cues stay on every row: the transition cue (below) and the cancel cue of a K4 release in the guard band after `operator_pad.hold_lock_ms`. A row whose setting has no reset (BR-013) has an edit key only; its reset key is silent like a read-only row's.
- **Chords.** UC-015 BR-007 holds: while two keys are down every key is blocked until all are up, except the K5 stop (above).
- **Lobby only.** The lobby-only settings (mode, sensitivity, teams, shield, instructions, force all; UC-015 A1) refuse an edit or a reset while the game lifecycle is live (`game_active`, A4); the volume, the agent rows and the backend do not. Known limits (accepted, #2755): lobby-only follows the menu's real game lifecycle only; the agent reads the goal profile once at game end, asynchronously, so a goal change right after a game ends can score that ended game against the new profile, and shadow or fallback games that run while the menu is in the lobby see the change mid-game; `objectives` is part of `pattern.flag_digest`, so a change starts a new experiment round, as one from Flagsmith or a script does (no extra guard, D17); the rate, the group shield and the `RETRO` rows are live (their readers take a change on the next cycle, request or retro).
- **Locked** (BR-015): the pad sends nothing except a K5 hold, which always sends the stop at the hold time (UC-015 A6 with K5 in place of K3), and the K4 hold that unlocks; the knob still scrolls the pages (BR-008). A restart of the pad service comes back unlocked (UC-015 A6) and sets the Scroll Lock LED off when it attaches.

Iteration 4 (#2755): the six new rows go per option: the pad enables a row's edit only when `pad_commands` lists `step_setting:<option>` and its reset only when it lists `reset_setting:<option>` (for example `step_setting:inference.effort`); when the entry is missing the edit or reset sends nothing and plays the refusal cue (`NOT POSSIBLE`), as for the commands above, and the row still shows its value, so a menu that knows some of the options never gets a command it would answer with `bad_option`. ### BR-013: Reset and the default

A reset sends one `reset_setting` ([services.md](../specs/services.md) §3.1) on the release of a reset hold (A8), whatever the setting's value; it is not a step and has no `steps`. It carries `expect`, the NEW the pad showed, and for the agent's level `from`, the level the reset replaces as the pad showed it (BR-014); the menu recomputes the value the reset would put in force at the commit (for the agent's level under its agent lock) and, when it differs, answers `stale` and clears nothing (A3), so a value that changed during the hold (a dashboard write, a stage overlay, the agent stopped or resumed) never commits unseen.

- **`AUTO`** for the settings with an automatic rung (`sensitivity`, `num_teams`, `shield.activation`): the same clear of the persisted operator value as the knob's `automatic` rung (UC-015 BR-018: `DELETE ?persist=true`, the "Automatic" voice line and the double white flash on the lobby controllers); the reset screen's NEW is `AUTO`.
- **The default** for the others (`game_instructions`, `force_all_start`, `agent_level` = `interventions_allowed`, `decision.backend`): one clear of the operator's persisted value, so the value below it applies again. What the reset puts in force is computed by one menu function, the same for the status field `setting_defaults` (the reset screen's NEW, the tap's `DEFAULT`) and for the command (maintainer decision D2): an in-memory stage overlay while it lasts, else the real overlay, else the baseline (the flag file's default; [flags.md](../specs/flags.md) §13). An operator value masked by a stack overlay is never cleared: the reset is then a no-op (`ok`, the value in force unchanged), so a reset never removes an admin value the host cannot see while the overlay wins. `?` while `setting_defaults` does not report the option. The menu says the value now in force with the setting's usual voice line (UC-015).
- **The agent's level** by the states of BR-011: for an `OFF` agent (`enabled` off or the level `none`) the reset writes nothing and sets the saved level the resume applies (UC-015 BR-003) to the baseline default when it is a saved level (`ambient`, `standard`, `full`), else to `ambient` (maintainer decision D4), so a reset never resumes an agent; `setting_defaults` reports that saved value for an `OFF` agent. A `WATCH` agent (only the gate closed) is not stopped here, as for the ladder (UC-015 BR-002): like an `ON` one, the reset clears the operator's persisted value of the live `interventions_allowed` level, and `setting_defaults` reports the value in force after it (as above). A default off the ladder of UC-015 BR-004 (`probe`, `shadow_experimental`) is refused (`NOT POSSIBLE` on the pad; `bad_option` from the menu), as is a level or default the pad does not know (BR-014). The raise check of BR-014 compares that value with the level the reset replaces: the live level for `ON` and `WATCH`, the saved level for `OFF`.
- **Clear the menu's own value** (iteration 4, #2755, maintainer decision D14, replacing D6; built in the menu and the flag service's `if_writer` in scope `stack`, #2757) for the in-memory rows (`objectives`, `policy.max_interventions_per_minute`, `policy.group_grant.enabled`, `inference.effort`, `decision.operator_brief`): their registry rows take no persisted value, so the reset clears the row's stack overlay only when the menu wrote it (writer `menu`; `DELETE` without `persist`, with the compare-and-delete `if_writer=menu`, [services.md](../specs/services.md) §3.1). A stage script's overlay (`talk-stage.sh`'s `aggressive` rate, which the pre-flight checks), an experiment script's (`agent-group-ab.sh`'s group shield during a run) or Flagsmith's stays, and the reset is a no-op `ok`: `setting_defaults` then reports that value, the reset screen's NEW, so the host sees before the release that nothing changes. After a clear the baseline applies again (no `agent` row of these takes a `real` overlay). `expect` is required for these options and guards as above, and a reset whose NEW is unknown is refused (BR-014). A free brief text (`CUSTOM`) is never the menu's (the menu writes presets only), so its reset is always a no-op: no clear, nothing pushed to Flagsmith, so the reference write of FR-227 never replaces a typed text in Flagsmith (maintainer decision D13). The retro backend (`inference.backend`) takes the default reset of `decision.backend` above (its persisted value cleared; a value masked by a stack overlay never). A reset is a raise whenever its NEW is above its NOW on a raise row, computed for every reset (BR-014). The decision backend's reset (#2755) carries `from=<backend at the press>` (BR-014).
- **No reset** for the mode, the volume (maintainer decisions, #2747), the interventions switch and every read-only row.
- **Tap** on a reset key: the tap screen with the row's label and `DEFAULT` and the default (`AUTO`, or the `setting_defaults` value, `?` while unknown); without a screen the pad says the label and the default as a UC-015 BR-011 announcement.
- A reset of a setting that has no operator value is a no-op: nothing is written, the menu answers `ok` with the unchanged value and plays nothing (as UC-015 BR-005's net-zero step). A reset that fails is UC-015 A3 (`flag_service_unavailable`). A successful reset always answers with its `value`, never empty, so the pad never shows `OK` for a reset it cannot see.

### BR-014: A raise of the agent needs a confirmation (of what it may do or spend)

A page-key edit or reset that raises what the agent may do commits only after a knob press while its key is still down (A9; #2050 decision 6); one that lowers it, or leaves it, commits on release as before. A raise is: an `agent_level` edit to a higher rung of UC-015 BR-004's ladder (none, ambient, standard, full), the saved level of an `OFF` agent included (it is what the K5 resume applies), the live level of an `ON` or `WATCH` one; a level reset whose default is above that level (BR-013); the interventions switch to `ON`. **Unknown values** (maintainer decision 2026-11-24): an agent level edit or reset whose NOW is unknown, and a level reset whose default is unknown or off the ladder, are refused (`NOT POSSIBLE`, nothing sent), never offered for a confirmation the host cannot judge; the interventions switch to `ON` with the gate unknown stays a raise to confirm, since its NEW (`ON`) is known. The backend, the goal and every game setting are not raises. Iteration 4 (#2755, D3): a raise is also a change that gives the agent more autonomy or costs more: in autonomy the intervention rate to a higher rung (an edit, or a reset whose baseline is above NOW) and the group shield to `ON`; in cost the retro backend to `CLAUDE` (remote calls and egress) and the retro effort to a higher rung (an edit or a reset above NOW). Their NOW, and for a reset its NEW, must be known (BR-012). Every reset of a raise row (the six, the level, the decision backend) is checked by computing whether its NEW is above its NOW on the row's ladder; no reset is assumed to lower. **Decision backend** (#2755, maintainer decision D12, the cost rule): the backends that call a paid remote API are paid, `claude` and `jev` (each with its API key: `ANTHROPIC_API_KEY`, `JEV_API_KEY`; jev is a hosted API, `decision.jev.base_url`), and `rules` is free (no model call). A raise is free → paid only: the `INTERV` row 1 edit from `RULES` to `CLAUDE` or `JEV`; an edit to `RULES` or between paid backends applies at once; the backend reset is a raise only when the flag file's default is paid and NOW is `rules` (computed as above). The pad judges the target and the raise from the press read (the wheel steps from NOW at the press, never from a read at the release) and, when the menu lists `set_backend.from`, sends every `set_backend` with `from=<NOW at the press>`; the menu answers `stale` when the backend in force differs (services.md §3.1), so a backend changed during the hold never turns a paid-to-paid switch into an unconfirmed free-to-paid one. A backend edit or reset with NOW unknown is refused, whatever its NEW, never confirmed blind. The backend reset carries `from=<backend at the press>` too: the pad always sends it when the menu lists `reset_setting.from:decision.backend` (the menu answers `stale` on a mismatch and clears nothing), and refuses a backend reset to a paid default without that capability (the refusal cue), as it refuses a backend edit to a paid backend without `set_backend.from`. D12 is the pad's (maintainer decision D16): the dashboard, voice and older pads still switch the backend without a confirmation, and the menu's `from` stays optional for them (a follow-up in #2755). The goal and the brief stay no raises. The confirmation covers what the pad commits: a Flagsmith pull can still bring back a higher value (D13, BR-012). The confirmation belongs to the value showing at the knob press and is taken only when that value has not changed for 250 ms before the press; while the knob is down with an edit or reset key held its turns are ignored, so the jitter of the press cannot move the value; a later knob step clears it. A release without it sends nothing and shows `CANCELLED` (UC-015 BR-009's cancel). **On the screen and by ear** (maintainer bench decision, #2747): a raise waiting for its press shows `PRESS KNOB` at the right of the title bar, which blinks (the service redraws it inverted and normal in turn every 500 ms, a display-only timer that ends with the key or the screen; no firmware change), on every edit and reset screen of protocols 2 to 4, the wheel and the marker bar included, which have no hint row; the NOW and NEW rows also keep the hint `PRESS TO CONFIRM`. The pad plays one short attention sound (`SFX_JOIN`) when a held edit or reset first becomes a raise waiting for the press (again only after a knob step cleared a confirmation), and a distinct short sound (`SFX_SHIELD_UP`) when the press is taken; both are sounds, so they play with a screen too (BR-005). After the press the title bar is steady with `CONFIRMED` on the right and the hint, where there is one, `RELEASE TO SET` / `RELEASE TO RESET`. The commit gate is an explicit check in the pad's actions (never an `assert`, which `python -O` strips), and the only code that builds an `interventions_switch` `on` or a raising level command takes the confirmation as input (#2755: also every raising command of the rows above, the raising `set_backend` and backend reset included: `_row_step`, `_set_backend`, `_reset_send`). The menu guards against a value that changed under the hold: a level edit carries `from` (the level it started from) and a reset carries `expect` (BR-013) and, for the level, `from` (the level it replaces, so a level that dropped under the hold never turns the lowering the pad judged into a raise); the menu answers `stale` when any differs (A3). An agent-row edit or level reset whose press read failed is refused; a level step past `FULL` or `NONE` sends nothing and gives the limit word. The K5 hold is no way around it (maintainer decision 2026-11-24, "always stop", BR-011): it stops an `ON` or `WATCH` agent and resumes only an `OFF` one, so it never opens the gate of an agent that still runs; the resume of an `OFF` agent brings back the level and the gate it had at the stop, never more, with no confirmation (UC-015 BR-003), as the undo of the kill switch. This replaces UC-015 BR-004's "escalation or restriction alike" for the page keys. The check is the pad's: the menu commands take no confirmation field, so an older pad without the page keys behaves as UC-015 says. Without a screen the fallback page has no agent row (BR-016), so no raise can be made blind.

### BR-015: K4: reset, then lock

The lock of UC-015 A6 moves from the K8 3 s hold to K4: a K4 hold of `operator_pad.hold_lock_ms` (default 3000) locks or unlocks the pad on release, on every page. K4 is also row 2's reset (BR-011), so a K4 hold goes through two stages:

1. From the press: the row 2 highlight (BR-006).
2. From `operator_pad.hold_reset_ms` (1 s): the reset screen with `RESET?` (BR-007); a release now is row 2's reset (A8).
3. From `operator_pad.hold_lock_ms` (3 s): the reset is cancelled and the lock screen shows: title `PAD` left and `LOCK?` (or `UNLOCK?` while locked) right, hint `RELEASE TO LOCK` / `RELEASE TO UNLOCK`; a release now toggles the lock (UC-015 A6: the Scroll Lock LED, the lock icon of BR-006, the `SYSTEM` row 3; the lock words only without a screen, BR-005).

**Reset and lock never collide** (maintainer decision 2026-11-24): once the host has confirmed a row 2 reset with the knob press (A9) during a K4 hold, that hold has no lock stage: it stays the reset, and its release commits the confirmed reset even after `operator_pad.hold_lock_ms`. Reaching the lock stage drops any confirmation still pending. For 150 ms after each stage boundary a release does nothing and plays the cancel cue (BR-011, "Timing"), so a release just past 1 s or 3 s never does the stage the screen had no time to show. `operator_pad.hold_lock_ms` minus `operator_pad.hold_reset_ms` must be at least the confirmation window of 1500 ms, the time to read the reset screen and press the knob ([flags.md](../specs/flags.md) §10a).

On a page whose row 2 has no reset (read-only or empty), stage 2 is skipped: a release before 3 s does nothing. While the pad is locked, K4 has no reset stage: only the 3 s hold, which unlocks. `operator_pad.hold_reset_ms` must be below `operator_pad.hold_lock_ms` by that window and above the tap limit; when the timing flags break that, the pad keeps the default timings and logs a warning (UC-015 BR-007). An unconfirmed K4 hold that reaches the lock stage changes no setting: the reset is never sent once the 3 s are reached.

### BR-016: Without a screen

While the display link is down (A1; for the row keys: the firmware shows `NO HOST`, more than 3 s after the last acknowledged frame, BR-011 "Which row"), the pad answers protocol 1 (no pages, BR-002), or the key comes from a pad whose display link is not up (BR-011), the row keys act as on the fallback page `HOME` (maintainer decision, #2747; BR-012: K1 / K2 the mode, K3 / K4 the volume, K6 / K7 the sensitivity), and the fixed keys K4 (lock), K5 and K8 and the knob work as with the link up (the knob alone: the volume, UC-015 step 8). With the link down the cues are UC-015's: a tap says the row's label and value (UC-015 BR-011 announcements; the labels "Game mode" and "Volume" are in the voice catalog already, the K5 tap's "Watching" is a new line of [UC-031](UC-031.md) BR-007), a hold + knob speaks the live preview (UC-015 BR-017), the volume plays its sound (BR-004), the lock words play (UC-015 A6). The volume row (maintainer decision D6): the catalog has no voice for a volume value, so its tap says "Volume" alone and K3 + knob speaks no preview; the release commits the volume with `step_setting` without `cue=none` (never while the link is down, BR-004), so the menu's volume step sound at the new level is the feedback. The reset hold plays nothing while held; the menu's voice line says the result. With protocol 1 the link is up and the pad is quiet (BR-005): the setting, result and tap screens of BR-001 show as before, and the page keys add three screens in BR-001's 8-line layout: the reset tap is the tap screen with line 0 the row's label and line 2 `DEFAULT` and the default (`AUTO`, the `setting_defaults` value, or `?`); the reset screen (from `operator_pad.hold_reset_ms`) has line 0 the label, line 2 `NOW` and the value, line 4 `NEW` and the default, line 7 `RELEASE TO RESET`; the lock screen (from `operator_pad.hold_lock_ms`, BR-015) has line 0 `PAD`, line 2 `LOCK?` or `UNLOCK?`, line 7 `RELEASE TO LOCK` or `RELEASE TO UNLOCK`. There is no highlight, and no raise to confirm (the fallback page has no agent row, BR-014). `HOME` is the fallback because it holds the mode, the setting the host changes most (UC-015's goal), and the sensitivity, while the kill switch, the start and end and the volume stay on fixed keys and the knob; teams, the shield mode, instructions, the agent level and the backend are then set from the dashboard or the flag-service scripts until the screen is back (the controller admin mode, [UC-012](UC-012.md), is gone since #2819). This changes FR-240's "exactly as in UC-015" to "as this layout without a screen" (FR-262).
