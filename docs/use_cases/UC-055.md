# Use Case: See Runtime Flag Changes in Flagsmith

## Overview

**Use Case ID:** UC-055
**Use Case Name:** See Runtime Flag Changes in Flagsmith
**Primary Actor:** Operator, Presenter
**Secondary Actors:** Flagsmith, Agent, Host
**Goal:** See in hosted Flagsmith, for every runtime flag, the value the stack runs and for which scope, without slowing down any local write
**Trigger:** A writer of [UC-053](UC-053.md) changes a runtime flag in the flag service, or a runtime value ends (time-to-live, game end, delete)
**Status:** Tested
**Requirements:** [FR-207, FR-211, FR-212, FR-213, NFR-050, NFR-057, C-015, C-016, C-030, C-036, C-037](../requirements.md)

Known gap (live SaaS only, non-blocking per maintainer decision D1, 2026-11-15): the link is tested against an in-process fake Flagsmith in the service tier ([TC-021](../test_cases/TC-021-operator-steers-stack-from-flagsmith.md), [TC-022](../test_cases/TC-022-flag-service-restart-with-flagsmith-link.md)) and the Go tests of `services/flag-service/flagsmith/`; edge-document identity overrides, the timing of audit-log authorship, the `__future__` feature-state API and the request limits under 8 live games are not yet checked against the hosted Flagsmith SaaS (#2592).

## Preconditions

- The flag service serves the stack's flags to flagd ([UC-053](UC-053.md)).
- The stack is linked to its own Flagsmith environment, and every flag of the mutable-flag registry is a feature there ([UC-054](UC-054.md) BR-002).

## Main Success Scenario

1. The host, a presenter script, the operator or the agent changes a runtime flag in the flag service, or a runtime value ends.
2. The flag service applies the change locally first, exactly as in UC-053, and answers the writer; Flagsmith is not on the path of the write (BR-001).
3. The flag service sends the change to Flagsmith in the background, in the form of its scope (BR-002); the send is recorded with the local writer (BR-002).
4. Changes to the same flag and scope that arrive faster than Flagsmith accepts them are merged, so Flagsmith receives the latest value (BR-001).
5. Flagsmith confirms the change; the flag service records the value as the last state seen from Flagsmith for that flag and scope, so the change never comes back as a new change from Flagsmith (UC-054 BR-004).
6. The operator sees in Flagsmith the value the stack runs and its scope, and the change in the flag's history.

## Alternative Flows

### A1: Game starts

**Trigger:** The game coordinator registers a game with the flag service (step 1)
**Flow:**

1. The flag service registers the game as in UC-053 step 1 without waiting for Flagsmith.
2. The flag service lists the game in Flagsmith in the background, and shows each player on the player's own controller, which Flagsmith keeps across games and which names the game it plays in now; before a player value of the game is shown, the controller is cleared of the values of any other game (BR-004). Each player of a shadow game is listed for that game only, never on a controller. So the operator can see their values and set a value for the game or one of its players ([UC-054](UC-054.md) step 1).
3. Use case continues at step 6.

### A2: Game ends

**Trigger:** The game coordinator reports the end of a game, or the flag service drops a game whose end was never reported (UC-053 A11) (step 1)
**Flow:**

1. The flag service drops the game scope locally (UC-053 step 7).
2. The flag service removes the game and its values from Flagsmith in the background; each controller of the game stays in Flagsmith but loses the game's values and no longer names the game, unless it plays in another live game already, which then owns it (BR-004); a shadow game's players are removed; the flag's history in Flagsmith keeps the changes (BR-003).
3. Use case continues at step 6.

### A3: Flagsmith not reachable

**Trigger:** The flag service cannot reach Flagsmith, or Flagsmith does not answer within 5 seconds (step 3)
**Flow:**

1. The local change stays in force; the flag service marks the link as offline and keeps the latest unsent value per flag and scope in memory.
2. The flag service tries again with growing waits, up to 60 seconds between two tries.
3. When Flagsmith answers again, the flag service reconciles both sides ([UC-054](UC-054.md) A2) and sends the values still unsent.
4. Use case continues at step 5.

### A4: Flagsmith refuses the change

**Trigger:** Flagsmith refuses a change the flag service sends: the environment requires an approved change request, the feature does not exist, the credentials are wrong or the request limit is reached (step 3)
**Flow:**

1. The local value stays in force; the flag service records the refusal with its reason and marks the flag as out of sync.
2. A refusal for the request limit is retried after the wait Flagsmith asks for; every other refusal is not retried until the next local change of that flag to a different value (a re-save of the same value does not retry) or a restart of the flag service.
3. Use case ends.

### A5: Flag service restarts with unsent changes

**Trigger:** The flag service restarts while changes wait to be sent (step 4)
**Flow:**

1. The unsent changes are lost, because the flag service keeps them in memory only (UC-054 BR-007).
2. At start the flag service brings Flagsmith in line with the restart rule ([UC-054](UC-054.md) A3, BR-006).
3. Use case ends.

## Postconditions

### Success Postconditions

- Flagsmith shows, for every runtime flag and every live game and player, the value the stack runs.
- Flagsmith shows no game, no shadow player and no controller value of a game that is not live; a controller stays in Flagsmith without values while it plays in no game.
- The send is recorded as a sync span naming the flag, scope and writer, and counted in the Flagsmith link metrics.

### Failure Postconditions

- The local value is in force and unchanged by the failure; a failure of Flagsmith never delays, refuses or changes a local write.
- The game keeps playing.
- A flag whose value Flagsmith does not show is recorded as out of sync.

## Business Rules

### BR-001: Local first, Flagsmith in the background

A local write is applied and answered before it is sent to Flagsmith (NFR-057). Sends run in the background, the latest value per flag and scope, within Flagsmith's request limit.

### BR-002: Every scope is shown

A stack-wide overlay is the feature's environment value: switched on with the value, switched off when no overlay is set (the baseline applies). A game value is a value for that game in Flagsmith, a player value a value on that player's controller while it plays in that game (BR-004), or, in a shadow game, a value for that player in that game; an experiment-arm, `real` or fraction value is a value for its scope. A one-shot event list is shown as its latest value. The local writer label is not stored in Flagsmith: Flagsmith's history names an API-key change, not which writer of the stack made it (architecture note F7); the writer is on the send's span (telemetry.md §10.4).

### BR-003: Games live in Flagsmith only while they run

A game and its shadow players are listed in Flagsmith from their registration to the end of the game, and a real game's values stay on its controllers only while it runs, so Flagsmith never shows, and never drives, a game that has ended (UC-053 BR-003). Their changes stay in the flag's history.

### BR-004: One identity per controller

Each Move controller is one identity in Flagsmith (`controller:<serial>`), kept across games and never removed by the flag service; it names the game it plays in (`game_id`, `game_kind`, `coordinator_instance`), so a person can address "the controllers in game X". A controller belongs to one live real game at a time, the one registered last when two hold it, and carries only that game's player values: before the game's first player value is shown, any other value on the controller (another game's, or one set while it played in no game) is removed, except right after a restart of the flag service when the controller still names that same game; when the controller leaves the game, the game's values are removed and the game is no longer named. A shadow game never touches a controller (architecture note §2.2).
