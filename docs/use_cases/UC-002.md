# Use Case: Connect a Controller and Join the Lobby

## Overview

**Use Case ID:** UC-002
**Use Case Name:** Connect a Controller and Join the Lobby
**Primary Actor:** Player
**Secondary Actors:** Operator
**Goal:** Get a paired controller connected and shown as present in the lobby
**Status:** Tested
**Requirements:** FR-002, FR-003, FR-004, FR-006, FR-265, FR-275, NFR-001, NFR-002, NFR-054, NFR-055, NFR-056

## Preconditions

- The controller was paired (UC-001).
- The controller manager runs with a backend set that includes a real adapter (`backend` flag, read at startup; default `rust`, also used when the flag is empty or cannot be read, BR-003). The mock adapter is always added.
- The menu is running.

## Main Success Scenario

1. Player presses the PS button.
2. System's HID backend opens the device and streams sensor data (≈ 1 kHz); a controller manager reader that lags still gets fresh samples (median age under 100 ms at the NFR-056 load).
3. System discovers the controller on its next discovery check (1 Hz) and routes it to one adapter (the first non-mock adapter that found it). Discovery is the only path that adds or removes a route. A pass that finishes after the backend shut down installs no routes and closes the handles it opened. The routed controller's HCI adapter (from rust-hid's sysfs walk, none for mock and USB; rust-hid resolves it once when it opens the device, on a discovery pass and on an on-demand `Open` alike) is exported as `controller_adapter_info{serial,adapter}` and shown on the dashboard card (UC-035 BR-009).
4. System assigns the controller a stable name (generated from the serial on first sight, persisted).
5. System publishes a connect event on the button stream.
6. System's menu registers the controller as CONNECTED and lights its LED in the selected game mode's colour at 30 % brightness.

## Alternative Flows

### A1: Controller disconnects

**Trigger:** The serial disappears from the backend (step 6, or any time later), or the controller stays listed but sends no fresh report for `silent_disconnect_seconds` (a silent link, BR-007). A failed or timed-out discovery pass of an adapter is not a disappearance: the adapter keeps its controllers until 3 passes in a row have failed (about 3 s when the HID service refuses at once, about 15 s when each 5 s call times out), then they all disconnect here; a successful pass resets the count.
**Flow:**

1. System removes it from the lobby and publishes a disconnect event.
2. System sets `controller_connected` to 0 for that serial and removes its `controller_info{serial,name}` series.
3. During a game, System also reports the disconnect to the game, which eliminates the player (UC-020 A2). A game gets only the disconnects of its own stream and of its roster controllers that dropped and are not back when that stream opens (BR-004).
4. System ends the controller's feedback in the controller manager: the running effect, the shield, charge and hold layers with their cues, the background rumble and the rumble stop timers. The reconnect rebuilds the LED from the owner (A4, BR-008).
5. Use case ends.

### A2: Operator renames the controller

**Trigger:** Operator calls RenameController (gRPC / connect-proxy; the dashboard has no rename UI) (step 4, or any time later)
**Flow:**

1. System stores the new name in the names file.
2. For a connected controller, System replaces its `controller_info{serial,name}` series: the old label set is removed, so only the current name is exported (the agent names targeted players from it, UC-041).
3. The controller manager's roster (`GetConnectedControllers`) shows the new name, and games started after the rename use it on player spans (state_builder copies the tracked name into the gameplay frame and the game fills `player.name` from it). A game already running keeps the old name.
4. Use case ends.

### A3: Lobby idle

**Trigger:** No button press for `idle.timeout_minutes` (default 15) (step 6)
**Flow:**

1. System switches connected controllers to IDLE (LED off) and animates up to `sentinel.count` sentinel controllers (UC-010 A2).
2. Use case ends.

### A4: Controller reconnects

**Trigger:** A controller that was connected earlier in this controller-manager run connects again (step 3)
**Flow:**

1. System runs steps 4 and 5 (name, connect event), then writes the controller's LED with the colour its current owner gives (BR-008): a player the running game eliminated for its disconnect gets the out state, a live player its game colour, any other controller its last lobby colour if one was set before (the serial is in `base_colors`); the colour is written after the event is published, and sent again even when it did not change (BR-008). A controller that came back from a silent link (BR-007) registers here the same way. When the controller comes back on another adapter, the adapter label moves with it; a rediscovery that reports no adapter name clears the stored adapter, so the old `hciN` is not kept (UC-035 BR-009).
2. Use case continues at step 6.

### A5: Button stream reconnects

**Trigger:** The menu's button stream to the controller manager drops and reconnects (step 5, or any time later)
**Flow:**

1. System clears all lobby state (controller states, ready flags, button and battery state), so every READY player is un-readied.
2. The controller manager sends a connect event for every connected controller again.
3. Use case continues at step 6.

### A6: Ghost controller

**Trigger:** A connect or disconnect event lists the connected controllers, and the lobby holds a controller that is not in that list (step 5, or any time later)
**Flow:**

1. System removes the ghost from the lobby as if it had disconnected.
2. Use case continues at step 6.

### A7: rust-hid stops answering

**Trigger:** rust-hid's gRPC server does not answer its own health check 5 times in a row (one probe every 3 s, 3 s each), or its device-manager loop polls no input for 15 s, also when it is busy only on queued commands (step 2, or any time later; NFR-054)
**Flow:**

1. rust-hid flushes its logs, traces and metrics (at most 1 s, so traces and metrics reach the collector; the trip reason line is read in `docker logs rust-hid`, since the OTLP log ends in the collector's debug exporter) and exits with code 70; the compose restart policy starts it again (compose does not act on `unhealthy` by itself). On SIGTERM / SIGINT (`docker stop`) rust-hid first switches every controller's LED and rumble off (each writer sends its off; waits at most 2 s), flushes the same way off the runtime workers, and exits 0; a stop that has not ended after 5 s is cut short by a plain thread.
2. The controller manager's `StreamIO` stream to rust-hid ends; its next discovery pass after the restart opens the stream and the controllers again (the same recovery as a manual `docker restart joustmania-rust-hid`); `close_all()` cancels the adapter's `StreamIO` call, and a reader that ends for any other reason (the stream failed, a frame it could not convert) cancels its own call before the adapter can reopen, so rust-hid never keeps serving a stream the controller manager has dropped; rust-hid gives each `StreamIO` registration an id, so the late end of an old call never unregisters the reopened stream (only the newest registration streams), and a stream whose call ended without an unregister is unregistered on the device loop's next pass instead of being polled for nobody; a new registration first drains every open controller's queued input reports without sending them, so the stream starts with fresh input, never with reports (or a press) queued while no stream read them; `close_all()` (shutdown) is final: a discovery pass that races it opens no stream afterwards, and a command (an LED colour, a rumble) that a stopping stream took from the queue but never sent is sent first by the next stream, never twice, and never after a newer command: the next stream merges its queue only once the stopping stream's take is done, so an old colour never follows the new one; commands still queued when the stream ended are coalesced per serial before the next stream opens: the LED colour is state and the latest queued colour wins (no older colour replays before it; a full queue of 256 refuses the newest command; the controller manager's 20 Hz LED batch counts an output (colour + rumble) as sent only once the queue took it, so it sends it again on its next tick), while rumble changes stay in order and carry that latest colour; controllers missed by a discovery pass during the restart go through A1 and come back through A4. A rust-hid that hangs at controller-manager startup does not hold the start: the startup Discover / Open calls run in a worker thread, the adapters start concurrently, at most 8 s in all (`INIT_ADAPTER_TIMEOUT_S`), so the event loop stays free and the server's 10 s startup wait can fire; an adapter past the bound starts with no controllers and the 1 s discovery check finds them once rust-hid answers. Cost of a restart during a game: every controller goes through A1 at once, so the game aborts with no winner (BR-009), and the controllers come back through A4 in the lobby. `joustmania-status` names a rust-hid that is still running but unhealthy as FAIL with `docker restart joustmania-rust-hid` (UC-060 BR-005).
3. Use case continues at step 6.

### A8: A controller's battery is low in the lobby

**Trigger:** The menu holds a battery level at or below the low threshold (BR-010) for a CONNECTED or READY controller while the lobby runs (step 6, or any time later in the lobby)
**Flow:**

1. System (the menu) sends the controller a `LOW_BATTERY` effect (red and dim red twice, 150 ms each; [services.md](../specs/services.md) §6) within about 1 s, then again at most once every 20 s (`LOW_BATTERY_BLINK_INTERVAL_S`, a code constant) while it stays low. The effect ends on the controller's base colour, so the controller goes back to its lobby state (dim CONNECTED or bright READY, in the selected mode's colour), and a ready or mode change during the blink is kept. The blink never takes the LED from a running effect (an identify, a battery display, a mode pulse): the controller manager skips it and the next period sends it again.
2. The pad's `START` page shows how many connected controllers are low (`LOW`, [UC-016](UC-016.md) BR-006), from `GetMenuStatus` `low_battery_count` ([services.md](../specs/services.md) §3.1).
3. Use case continues at step 6.

### A9: The pairing daemon is about to restart Bluetooth

**Trigger:** The pairing daemon calls the menu's `WarnBluetoothRestart` before a planned bluetoothd restart ([UC-001](UC-001.md) BR-011) while the lobby runs (step 6, or any time later in the lobby)
**Flow:**

1. System (the menu) plays the warning cue (BR-011): one loud beep (`SFX_BEEP_LOUD`) and a 3 s white pulse (`GAME_EFFECT_PULSE`) on every CONNECTED or READY controller, and answers the daemon with `warned` and `lead_ms` 3000.
2. After the cue, as the last step before the restart, the daemon asks again with `check_only`; the menu plays nothing and answers whether a game has gone live meanwhile; when none has, it refuses new starts for the next 5 s, the time the restart needs to drop the controllers (BR-011, [UC-001](UC-001.md) BR-011).
3. Unless a game went live, the daemon restarts bluetoothd: every controller goes through A1 at once, and its player presses PS to come back through A4.
4. Use case continues at step 6.

## Postconditions

### Success Postconditions

- The controller is tracked by the controller manager and shown CONNECTED in the lobby.

### Failure Postconditions

- The controller is not in the roster; no lobby state exists for it.

## Business Rules

### BR-001: One adapter per controller

Each controller is served by exactly one adapter per discovery cycle; routing changes apply on the next cycle without a reconnect.

### BR-002: Reserved mock controllers are hidden

Mock controllers reserved for shadow games never appear in the lobby roster.

### BR-003: rust-hid is the default Bluetooth backend

Real controllers are read through rust-hid by default: the `backend` flag defaults to `rust` (the controller manager adds `mock`), and every compose stack that reads real hardware (`docker-compose.yml`, `docker-compose.lite.yml`) starts the rust-hid service; it is the only HID backend. A stale `joustmania-python-hid` container from an older install is an orphan of the compose project, which the Pi start removes (`--remove-orphans`). `scripts/talk-preflight.sh` FAILs when the `backend` flag names `rust` and the rust-hid container is not running and healthy, and skips the check (INFO) when docker is unreachable.

### BR-004: A game only gets disconnects from its own stream

The controller manager reports a disconnect to every game stream (a gameplay stream that sent player colours) open when the controller drops, once each, in the stream's next frame. A disconnect from before a game stream opens reaches no game: a controller that dropped, reconnected and joined the next game is not eliminated at that game's first frame. A roster controller (one in the stream's colours config) that was reported disconnected and is not connected again when the stream opens is still reported, in the stream's first frame, so a player who drops before the stream opens (during the instructions clip, or while the game reconnects its stream) is still eliminated (UC-020 A2). A roster controller the controller manager has not discovered yet (a freshly added mock) is not a disconnect. A game stream that opens while another is running (a shadow game) does not take the running game's pending disconnects.

### BR-005: Controller output never blocks rust-hid

rust-hid writes LED and rumble reports from one writer thread per controller, never from the device loop or a gRPC worker. Each controller keeps one pending value: the LED colour is the last one asked for, rumble keeps the highest value since the last write (a short pulse is not lost) and the latest follows in the next write. A controller gets at most `rust_hid.output_rate_hz` reports per second (flag, default 20), so effects and lobby repaints cannot fill the Bluetooth output queue (the kernel's "Output queue is full"). Identical values are still sent: the controller manager's 2 s LED keep-alive keeps the LED lit. Pairing calls (GetUSBControllers, PairController) run off the gRPC workers (NFR-055). A queued Discover or Open whose caller already gave up (its reply channel closed) is skipped, so an abandoned command enumerates and opens nothing (NFR-055). A write stuck in the kernel holds its controller's device, so that controller's input freezes while rust-hid stays healthy: a write in flight for more than 1 s is logged once (WARN, then INFO once the write returned or the controller was closed) and shown as `rust_hid_output_write_in_flight_seconds{serial}`; it is reported only, never a watchdog restart (NFR-055).

### BR-006: A discovery pass opens a controller once and never reads a polled one

A rust-hid discovery pass enumerates the attached controllers (so a new one is found on the next 1 Hz check, step 3) but opens only those that are not open yet and not claimed by another adapter; an open controller is never reopened. While the controller manager's input stream is registered, a pass reads no report from an open controller (every report goes to the stream); the device loop's own poll marks a controller whose read fails, and the next pass drops it (A1) before it enumerates, so a controller that reconnected is opened again in that same pass. Without a registered stream, a non-forced pass reads each open controller once to find the dead ones; a stream whose call has ended no longer counts as registered once the device loop has unregistered it (A7 step 2). While a stream is registered, a Discover request's `force` flag has no effect (nothing is read either way) and `verify_only` still skips the enumeration.

### BR-007: A silent link is a disconnect

A tracked controller that sends no fresh report (a poll that returns a new sample) for `silent_disconnect_seconds` (`controller` flag, default 3 s, clamped to 1 to 10 s, read live on every discovery pass; flags.md §6) is disconnected as in A1, although the Bluetooth link is still up and the backend still lists it (out of range). The normal report gap is 20 to 50 ms (p95), so the limit never trips on a working link. The silence is measured in the 1 Hz discovery step from the connection-quality gap window (UC-035 BR-005), up to the last 100 Hz poll batch and with the poll loop's own stalls subtracted, so a late or stalled poll loop never disconnects a controller; the 100 Hz poll pays nothing for it. During a game the disconnect reaches the game (A1 step 3), which eliminates the player (UC-020 A2), so a player cannot stay in the game by walking out of range and a dead link does not keep a player alive. While the backend still lists it, the controller manager polls the silenced controller on each discovery pass; once the poll returns a new sample it registers again (A4). A silenced controller the backend stops listing comes back through the normal discovery path. A silent drop also forgets the controller's stored LED colour and rumble in the backend (its route stays because the backend still lists it), so its next registration never replays a stale game or death colour. A HID stream outage longer than the limit (rust-hid stalled but still listing its controllers) disconnects every controller at once, which in a game aborts it with no winner, as a rust-hid restart does (A7, BR-009).

### BR-008: The LED is written on every (re)registration, by its current owner

When a controller registers (step 3 or A4) the controller manager writes its LED and does not skip the write as unchanged: the backend sends the output again on its next 20 Hz LED tick, whatever it sent before the re-open, and once more 0.5 s later (`LED_RESEND_DELAY_S`), so a first write that the re-opened device dropped or that raced its readiness is repeated. The colour comes from the controller's current owner, never from a colour cached for another owner: a player of an open game stream's roster whose disconnect that stream was handed (BR-004) and that the game no longer lists alive (its last alive filter) was eliminated by it (UC-020 A2), so it gets the out state (LED off) once, not its game colour; the off is not stored as its base colour, so the game's own effects can still repaint it. A roster player that registers for the first time after the stream opened, or whose disconnect the game dropped because its frames came back during the intro (BR-004, the player stays alive), gets its game colour. Any other controller gets its last lobby colour, and the menu repaints it on the connect event (step 6). The delayed resend is cancelled when the controller disconnects again or the controller manager stops. When a game stream closes, the game colours of its players that are not connected are dropped, so a player who dropped during a game and comes back in the lobby never shows the old game colour; so is an output the game wrote to them while they were away (below).

An LED or rumble write that reaches the backend for a controller with no adapter route (it is disconnected; in practice an effect's restore or a shield or cue rumble, and a base-colour write only in the moment between the discovery swap and the drop, since game effects and base colours for an untracked controller are refused before the backend) is not lost: the backend keeps it as the wanted output. Nothing is sent to the controller before it has registered again: once routed again, the LED batch skips it and any further write to it is held the same way; the registration releases the output just before the owner's colour is written, which is newer and wins; a controller whose registration fails keeps its LED unwritten, not stale. A dead player stays off when it reconnects: the death effect marks its base colour off from its first moment (not only after the red hold), and a (re)opened game stream configures a dead player's colour as off (UC-030 BR-006), so a reconnect before the game's next alive filter or after a stream reopen (whose new stream was handed no disconnect) restores off, never the game colour. A silent drop (BR-007) cancels the running effect; the effect's end does not write the game colour back, because the controller is no longer tracked.

### BR-009: A mass disconnect aborts the game with no winner

A rust-hid restart (A7), a lost Bluetooth dongle or a HID stream stall (BR-007) disconnects many controllers at once. That is an infrastructure fault, not play, so the game declares no winner. In every mode, the game counts the disconnects it is handed (BR-004) of players alive when a window opens and still alive when they disconnect; a player who died inside the window (or waits to respawn) and then switches off does not count. In Non-Stop Joust a player waiting to respawn is not alive, so it counts neither among the disconnects nor among the players alive at the window's start ([UC-026](UC-026.md) A2). The window opens at the first such disconnect and lasts 1.5 s of game time (`MASS_DISCONNECT_WINDOW_S`). Disconnects reach the game on the controller manager's 1 Hz discovery pass (A1, BR-007), so one window covers two consecutive passes: a fault whose drops are split across two passes still counts as one. Disconnects buffered during the countdown and the EMA warm-up count as one batch. The game aborts when at least 2 players of one window disconnected (`MASS_DISCONNECT_MIN_PLAYERS`) and either:

- more than half of the players alive at the window's start disconnected, or
- every player alive at the window's start on one Bluetooth adapter disconnected, and that adapter had at least 2 of them. The game learns each player's adapter from `GameplayData.bt_adapter` during the EMA warm-up (UC-030 BR-003). A controller with no adapter name (mock, USB) belongs to no adapter.

The check runs before the frame's disconnects are processed, so no player of the batch that trips it is eliminated and no win check runs (UC-020 BR-001). The abort shows no winner: no `game_winner`, no rainbow and no "congratulations". System plays "Cancelled." (`status_cancelled`), logs the counts and ends the game through the frame-error path (UC-030 BR-006). That path publishes `game_error` with error `mass_disconnect: <n> of <alive> players disconnected` (with `on adapter <hciN>` for the adapter case), and the session counts outcome `error` (UC-020 BR-003). The menu restores the lobby (UC-020 failure postcondition), and the controllers come back through A4. A disconnect that does not trip the rule eliminates its player as before (UC-020 A2). A player eliminated earlier in the window stays eliminated, and a single disconnect never aborts. The limits are constants, not flags. Pausing the game until the players reconnect was the alternative not taken: a rust-hid restart or a dongle loss takes several seconds and does not always bring every controller back. A controller-manager restart during a game ends it the same way (no winner, "Cancelled.", `game_error`, the lobby comes back), but not through this rule: the game sees its gameplay stream die or go silent, not disconnects, and ends once the stream's reconnect budget is spent (UC-030 BR-006). Non-Stop Joust's own game loop recovers its stream the same way ([UC-026](UC-026.md) BR-003).

### BR-010: A low battery warns in the lobby only

A controller is low when its last known battery, read on the scale of [UC-035](UC-035.md) BR-007 (`battery_to_pct`: a 0-5 level times 20, a value above 5 already a percentage), is 20 % or less: level 0 or 1 on the 0-5 scale, 0 or 20 on the Rust HID percentage. Charging and charged report 100 and are never low. The menu learns the level from its button stream: the connect event and every button event carry it, so the level is as fresh as the controller's last button press. The controller manager marks a real reading (`ButtonEvent.battery_reported`), so a reported 0 counts as an empty battery; without the marker (an older controller manager, a disconnect) a 0 means not read and is dropped. The menu clears its levels when the button stream reconnects, after every game too; the controller manager's connect replay then restores each controller's current level, so a controller that ran down to 0 during the game is low in the next lobby. The blink (A8) runs only in the lobby: its loop starts and stops with the idle monitor (A3), so the menu sends none while a game is starting or running, and when a game claims a controller (its gameplay stream configuration) the controller manager ends a blink still running on it, as it ends an identify (UC-004 BR-003), so the game's colour is never painted over. A battery that dies during a game still counts as a disconnect that eliminates the player (UC-020 A2). IDLE controllers (LED off, A3) are not blinked, but they count for the pad's `LOW`. There is no voice line: none of the generated voice assets says it and the audio service has no speech synthesis.

### BR-011: The lobby hears and sees a Bluetooth restart coming

The menu answers `WarnBluetoothRestart` (A9, [services.md](../specs/services.md) §3.2) without waiting for the cue: the beep request is sent detached and the pulses are only queued on the button stream, so the answer reaches the pairing daemon well inside its 2 s timeout. It plays the cue only while the menu runs (`RUNNING`), no game is live (no game lifecycle starting, running or restoring the lobby, no boot lookup of a game still live after a menu restart, [UC-010](UC-010.md) A16, and no `reset_menu` recovery; [UC-010](UC-010.md) BR-008) and at least one controller is connected in any state. A `check_only` request never plays the cue; it only answers `game_live`, and one that answers no live game within 15 s of the menu's own cue starts the 5 s start hold of [UC-001](UC-001.md) BR-011. IDLE controllers (LED off, A3) get no pulse, but they hear the beep. With a live lifecycle it plays nothing and answers `game_live`, so the daemon defers the restart; when stopped or with no controller connected it plays nothing and answers `warned` false, so the daemon restarts at once. A pulse never takes the LED from an effect the mode pulse yields to (an identify, a battery display; [UC-004](UC-004.md) BR-005); the beep still plays. The cue uses existing assets only: there is no voice line that tells the players to press PS after the restart ([UC-001](UC-001.md) BR-011).
