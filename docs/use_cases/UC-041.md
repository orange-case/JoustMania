# Use Case: Observe a Game

## Overview

**Use Case ID:** UC-041
**Use Case Name:** Observe a Game
**Primary Actor:** Agent
**Goal:** Know each live game's state from telemetry alone
**Trigger:** A game service exports a span or metric batch over OTLP, or a batch of the agent's own log events (A8)
**Status:** Tested
**Requirements:** FR-040, FR-041, FR-218, FR-250, FR-251, FR-252, FR-253, NFR-024, C-001

## Preconditions

- The collector fans traces and OTLP metrics and the log events marked for the agent (A8) out to the agent over OTLP/HTTP on port 4318 (NFR-024).

## Main Success Scenario

1. System (game services) export spans and metrics over OTLP to the collector; the game coordinator also sends the agent its own log events in every game (A8; without a flag).
2. The collector forwards them to the agent (best effort: 2 s timeout, no retries; A6 when a batch is lost).
3. The agent skips its own telemetry (resources whose `service.name` is its own).
4. The agent extracts per-player and per-game signals from known metrics (acceleration, playstyle, alive, battery, skill, movement variance, thresholds, tempo, game active, duration) and from span attributes, and each elimination from `game_player_elimination_order` alone, whatever the booth's moment shape (BR-008, BR-009) (every game mode feeds the per-player movement and skill metrics, BR-006), and keeps each controller's display name from `controller_info` (used to name targeted players on its decision spans) and the game's trace ids only from the trace context of its own log events (BR-004, A8). Signals without a game id are handled in A5.
5. The agent partitions the signals by `game_id` into one context per game and normalises `game_kind` (a legacy `primary` → `real`; `shadow`, empty and unknown kinds pass through unchanged and never count as real: fail closed, FR-041); the game-state gauges (tempo, thresholds, sensitivity, mode, loop rate) carry `game_kind, game_id`, so each reaches its own game's context.
6. The agent evaluates the game when it is active and has a fresh player, one whose last signal arrived within `lifecycle.player_ttl_seconds` (default 5 s) (UC-040).
7. When the game ends (`game_active` 1 → 0, A4, or the `game.end` log event, A8), the agent records in the game's context which signal ended it (its end reason: `zero`, `root_span`, `end_event` (a normal end like `zero` and `root_span`) or `stale`; not the coordinator's `game.end_reason`) and runs, in order, once per game: experiment conclusion, retro, game summary, proposer (UC-042, UC-043; BR-005); a game that ended `stale` gets only the experiment release (A4 step 3).

## Alternative Flows

### A1: Infrastructure signals

**Trigger:** A `controller.bluetooth_health` span arrives (~1 Hz) (step 4)
**Flow:**

1. The agent ignores the span (its infrastructure loop was retired with UC-050). The span carries no game id or player attribute, so it changes no game's context and triggers no game evaluation.
2. Use case continues at step 1 with the next batch.

### A2: Stale data

**Trigger:** A player or session sends nothing for `lifecycle.player_ttl_seconds` / `lifecycle.session_grace_seconds` (step 5)
**Flow:**

1. At its eviction tick (`lifecycle.evict_interval_seconds`, default 1 s) the agent evicts the player (default TTL 5 s) or resets the session's state (default grace 15 s); a game context with no players, no active game and its grace over is dropped, unless a log record opened it less than 60 s ago (BR-010). All three values are hot-reloaded flags.
2. A later signal of an evicted player recreates it; a later signal for an ended game id that was dropped recreates a context that stays ended (BR-005). A player evicted for silence while its game is active keeps its whole-game aggregates until the game ends, and a signal that recreates it brings them back (BR-007).
3. Use case continues at step 4 with the next batch.

### A3: Duration gauge missing or stale

**Trigger:** During an active game, `game_duration_seconds` has not been received or its value has not advanced for 5 s (step 4)
**Flow:**

1. The agent derives the elapsed game time from when it saw `game_active` go 0 → 1, never below the last gauge value (BR-003).
2. Use case continues at step 5.

### A4: The `game_active` 0 never arrives

**Trigger:** An active game's `game_active` 0 datapoint is not exported, for example because retire or force-end removed the series first (step 7)
**Flow:**

1. When the game's root span reaches the agent (it is exported when the game's session ends), the agent ends the game. Its duration bracket closes at the span's end time. A later `game_active` 1 for that game id does not start it again.
2. If neither the 0 nor the root span arrives and the game's `game_active` series stays silent for 60 s (a fixed value, not a flag), the agent ends the game at its next eviction tick (A2), with the duration bracket closed at the last `game_active` datapoint. No telemetry for a live game means the agent's telemetry broke, so ending the game is the safe default; the end is counted in `agent_game_end_stale_total`.
3. A game ended this way (its context's end reason is `stale`) has incomplete data, so it is excluded from experiments: an experiment game is released without a fitness sample (UC-043) and its slot is refilled, and a pattern pair reruns as [UC-046](UC-046.md) BR-015 defines for a stale end; a real game adds no recent-real fitness sample, and the retro, game summary and proposer skip it (UC-042).
4. The game stays ended for the agent even if its `game_active` series resumes (the game may still be running): the agent runs no further evaluation, decisions or interventions for that game id (BR-005).
5. Use case continues at step 7 (BR-005); the game's context is then evicted as in A2.

### A5: Signals without a game id

**Trigger:** A datapoint or span carries no `game_id` (step 5)
**Flow:**

1. The agent puts it into one shared fallback context. Controller signals without a game id (battery, connection) always land there; id-less signals of two games running at the same time mix in it, which is why no intervention is ever written for it (A5 step 3).
2. A `game_active` 0 → 1 in the fallback context starts a new game there with a synthetic id `session-<n>`; a second 1 while that game is active changes nothing. The fallback context is never dropped and keeps no ended-id record, so a later 0 → 1 starts `session-<n+1>`.
3. The agent may evaluate the fallback context (UC-040), but the intervention writer refuses its `session-<n>` id ([UC-040](UC-040.md) BR-002), so nothing reaches any game.
4. A `game_active` 0 or a silent series (A4 step 2) ends the fallback game and runs the game-end chain (step 7); a root span never does, because it carries a game id.
5. Use case continues at step 6.

### A6: A telemetry batch is lost while the agent runs

**Trigger:** The collector cannot deliver a batch to the agent within 2 s, the delivery fails (also while the agent is not running), or its queue of 1000 batches is full (step 2)
**Flow:**

1. The collector drops the batch without a retry; the agent does not notice and counts nothing (only the collector's own metrics show the drop).
2. Gauges are exported again at every export interval (flag `metrics_export_interval_ms`, 100 ms for the game coordinator), so a lost `game_active` or elimination-order datapoint is restored by the next batch; a lost `game_active` 1 starts the game one interval later. The coordinator publishes no `game_trace_correlation` gauge, so a lost `game.start` or `game.phase.start` record is not restored and the agent parents that game's spans as BR-004 says.
3. Span data is exported once and is not restored: a lost root span leaves the game's end to the `game_active` 0 or to the stale end (A4).
4. After the agent was unreachable (not started yet, restarting), the collector delivers every signal again from the first batch after the agent listens (NFR-024). What was sent meanwhile is lost as in step 1: an agent that (re)starts after a game's `game.start` and `game.phase.start` records holds no trace ids for that game, and its decisions there are parented as BR-004 says.
5. Use case continues at step 4 with the next batch.

### A7: A moment arrives as a log event - Obsolete

**Status:** Obsolete. The agent reads no moment in any shape: the collector forwards no moment log event to it (`filter/agent_events`), and eliminations come from `game_player_elimination_order` alone (BR-008, BR-009). The flow below is kept for history only.
**Trigger:** A player's warning or death arrives as a log event (moment shape `log_event`, [UC-100](UC-100.md) BR-001) (step 4)
**Flow:**

1. The collector forwarded to the agent the log events named `death_warning` or `player_death` that carried a moment id.
2. The agent read a `player_death` log event like its span event, once per moment id; a `death_warning` changed nothing.
3. A moment log event for a game the agent held no context for opened that game's context and held it (BR-010).
4. Use case continues at step 5.

### A8: The agent's own log events

**Trigger:** the game coordinator sends a log event marked for the agent (step 1), in every game ([UC-100](UC-100.md) BR-012; without a flag)
**Flow:**

1. The collector forwards the records marked for the agent (`orangecase.audience` = `agent`) to the agent only (a `game.start`, `game.end` or `game.phase.start` without the marker never reaches it); the gateway to the external backends drops them (UC-100 BR-012). The marker is on the record itself, because the collector decides on each record alone and never sees its span.
2. A `game.start` log event opens the game's context from its `game.id` and holds it (BR-010) when the agent holds none yet, and fills in the context's `game.kind` (normalised as the span attribute: a legacy `primary` becomes `real`) and `game.mode` while they are unknown; it never changes a known kind or mode. A `game.start` or `game.end` without the marker or a game id changes nothing. It does not make the game active: `game_active` stays the source of that (BR-001).
3. No moment is sent to the agent, marked or not (BR-009): a `game.start`, `game.end` or `game.phase.start` is the only record it reads.
4. A `game.end` log event is an end signal like the root span (BR-005). For an active game it ends the game with end reason `end_event` and runs the game-end chain (step 7); the game's end time is the record's timestamp (else its observed timestamp, else its arrival), kept between the game's start and now, as for the root span. For a game that is not active, or that the agent holds no context for (a context is then opened and held, BR-010), it only marks the game ended, so a later `game_active` 1 never starts it and no game-end chain runs, as the root span does.
5. A `game.start` log event, and a `game.phase.start` log event sent when the game's `game.phase.gameplay` or `game.cycle` span opens, give the agent the game's trace ids from their trace context when it is sampled, its only source of them; a `game.phase.start` also gives the game's trace id when `game.start` was lost (BR-004). A `game.phase.start` for a game the agent holds no context for opens that context from its `game.id` and `game.kind` and holds it, as `game.start` does (BR-010).
6. Use case continues at step 5.

## Postconditions

### Success Postconditions

- The agent holds a current context per live game id, built only from OTel signals: its active flag, players and game state are those of the last batch received, except that a game that has ended stays ended (BR-005).

### Failure Postconditions

- The game services and the collector never wait for the agent (best effort, no retry), telemetry still reaches Jaeger and VictoriaMetrics, and signals labeled with one game id never enter another game's context. An agent that was down rebuilds its contexts from the signals that arrive after it returns.

## Business Rules

### BR-001: Metrics are timely, spans are late

Metrics carry the live picture: they arrive within about a second and each batch that changes a live game can trigger an evaluation. A span batch also wakes the evaluation and adds span-derived state to the game context: `game.mode`, `game.kind` and the experiment id and arm. Decisions may use that state (the LLM eligibility check reads the game kind). Player spans close at game end and the collector batches traces, so span-derived state lags the game; spans also serve audit. The elimination order (rules R1/R2 read it) comes from the `game_player_elimination_order` gauge on the metric path (BR-008, BR-009), within about a second of the death in every mode and every moment shape, and a lost datapoint is restored by the next export (A6). In every game, the `game.start` log event brings `game.mode` and `game.kind` at game start instead of with the spans (A8).

### BR-002: Game summaries are not durable

Game summaries are not written to disk. Their game-level aggregates live only in the agent's in-memory cross-game window and are lost when the agent restarts (UC-042 BR-004, BR-005).

### BR-003: Elapsed game time is live

The game coordinator refreshes `game_duration_seconds` every 1 s while a game is RUNNING (real and shadow games) and sets its final value when the game ends. The agent uses the gauge while it is fresh; otherwise it falls back as in A3. The in-game elapsed time never decreases within a game. At game end the agent uses the larger of the gauge and its own start → end time, so every game-end consumer sees the same duration.

### BR-004: The game's trace ids reach the agent as log trace context

The game coordinator publishes no `game_trace_correlation` gauge (FR-253).

The ids reach the agent as the trace context of its own log events: the trace id and root span id of `game.start`, and the span id of the `game.phase.start` record the coordinator sends when the `game.phase.gameplay` or `game.cycle` span opens (a mode without a `game.cycle` span sends only the first). These records are the agent's only source of the ids; each arrives with its record shortly after its span opens (the coordinator flushes it at once, still about 1 s of collector batching), so the agent's earliest in-game spans may be their own roots. The agent takes the game's trace id from `game.start` or, when that record was lost, from any `game.phase.start`: the `game.phase.gameplay` and `game.cycle` spans belong to the game's trace, so their records carry the same trace id, and a phase record never replaces a trace id already known. The root span id comes only from `game.start`, each phase span id only from its own `game.phase.start`. A record with an invalid or unsampled trace context sets no id, and taking an id refreshes no update time (BR-010). A lost record is not restored: a lost `game.phase.start` leaves that span's id unknown, and a lost `game.start` leaves the root span id unknown while a phase record still gives the trace id. The agent then parents its in-game spans on the first span id it knows in the order of UC-040 BR-013 (`game.cycle`, `game.phase.gameplay`, the game root span); only when no record gave the trace id are those spans their own roots, as in a process without OTLP logging, which sends none. With the root span id unknown, `agent.decision` has no Link to the game root and the agent's spans carry no `game.trace_span_id`. Both losses are accepted. The first ids arrive with `game.start`, sent and flushed once the game is built (BR-001), so the agent's earliest in-game spans may be their own roots until it arrives (accepted).

Per FR-253 (maintainer decision 2026-11-25: hard cut, no migration) the log events of A8 are sent in every game, without a flag (a process without OTLP logging still sends none, and a game that fails before it is built sends no `game.start`), so every game gives the agent its trace ids as above.

### BR-005: A game ends exactly once

A game ends for the agent on whichever end signal arrives first: the `game_active` 1 → 0 datapoint, the game root span, a silent `game_active` series (A4) or the `game.end` log event (A8, end time: the record's timestamp). The game-end chain (step 7) runs once per game; the later signals change nothing. Game ids are unique per game start and never reused, so once a game id has ended, a later `game_active` 1 for it (out-of-order delivery, or a series that resumes after a stale end) does not start it again, also after its context was evicted. The agent keeps the ids of the last 512 ended games in memory only: after an agent restart a late `game_active` 1 for a game that ended before the restart starts it again (accepted limit). Signals without a game id follow A5. The game's duration at the end, and the start → end bracket of its timeline, close at the game's own end as the agent saw it: the time the 0 arrived, the root span's end time, the `game.end` record's time (A8), or the arrival of the last `game_active` datapoint (A4). A game that has ended no longer keeps its context from being evicted.

### BR-006: Every game mode produces the per-player movement and skill inputs

Every game mode gives each player a movement tracker when the game starts (while `analytics.enabled` is on), so the per-player gauges the agent decides on (`game_player_accel_magnitude`, `game_player_movement_zone`, `game_player_peak_accel`, `game_player_playstyle`, `game_player_movement_variance`, `game_player_skill_level`, `game_player_movement_variance_aggregate`) and, at game end, one `player_analytics` summary per player and the `analytics.*` attributes on the player span's end event exist in all ten modes, not only in Free-for-All, Teams, Random Teams and Non-Stop. A sample is taken on each frame whose motion the mode checks for a death: in Fight Club and Tournament only the two fighters' frames count, so a waiting player's tracker does not advance until it fights, and its `survival_time_ms` in the end summary is the time it spent fighting, not the time it was in the game. While a Fight Club or Tournament player waits (before its first round or match, and between its fights), it exports no `game_player_*` gauge: the coordinator removes them, `game_player_alive` included, when it goes back to waiting, and sets `game_player_alive` 1 again when it is seated for its next fight, whose frames bring the other gauges back; a Tournament loser keeps `game_player_alive` 0 and its elimination order. The tracker keeps its samples, so the end summary covers every fight. Werewolf and Zombies span events carry the attributes only for players alive at the end, as Free-for-All and Teams do.

### BR-007: A player evicted mid-game keeps its whole-game aggregates

A player evicted for silence (A2) while its game is active, in practice a Fight Club or Tournament player waiting for its fight (BR-006), is remembered for the rest of the game with its whole-game aggregates: skill level, peak accel and cumulative movement variance (`game_player_skill_level`, `game_player_peak_accel`, `game_player_movement_variance_aggregate`), at most 64 players per game. While remembered it is listed as waiting in the game's context ([UC-040](UC-040.md) A49, BR-038) and is not a player of the context, so no rule acts on it. The game-end context (step 7) holds it again, as waiting, with those aggregates and no alive state, so the game-end consumers (the experiment fitness of [UC-043](UC-043.md) step 4, with the balanced skill gap and spike survival, the game summary and the retro) see every player of the game. A signal that recreates the player (it is seated for its next fight) makes it a live player again, starting from the remembered aggregates until the coordinator's gauges replace them. A waiting player who disconnects leaves the memory the same way: in the game's partition its `game_player_alive` 0 (Fight Club takes it out of the rotation, Tournament eliminates it) recreates it as a player that is not alive, so the game-end context holds it as out, not as waiting. The disconnect signal itself (`controller_connected`) carries no game id and reaches only the fallback partition, never the game's. A player evicted after its game ended is not remembered; the memory is reset when the next game starts on the context and when the session's grace ends, and is lost on an agent restart.

### BR-008: Only a player who is out of the game is an elimination

In every mode the game's elimination sequence (from `game_player_elimination_order`, step 4, BR-009) holds only the players who are out of the game. A death that keeps the player in the game is not an elimination: a Fight Club round loss sets no `game_player_elimination_order` (its `player_death` record, which the agent does not read, carries `death.eliminated` false for the backends; [UC-025](UC-025.md)). A Fight Club player who leaves the rotation for good (A4 there: a disconnect) gets its elimination order when it leaves, 1 for the first player out; when that disconnect is a death (the kill path), its `player_death` carries `death.eliminated` true. A round loser that disconnects while its loss is still finishing leaves without a second death, so only the elimination-order gauge records it, once. A Tournament match loser is out of the bracket and is an elimination. The coordinator sets the gauge in every moment shape ([UC-100](UC-100.md) BR-001), so the sequence is the same whatever the shape. The game's own teardown leaves the gauge in place; the session removes it with the game's other series a few export intervals after the end ([telemetry.md §6](../specs/telemetry.md#6-metrics)), so a kill just before the end still reaches the agent.

The modes where a death keeps the player in the game apply the same rule:

- NonStop ([UC-026](UC-026.md) BR-004): a respawn death sets no elimination order and its `player_death` carries `death.eliminated` false. A disconnect takes the player out for good: a disconnect death carries `death.eliminated` true and records the order; a player who disconnects while waiting to respawn gets its order when it disconnects, without a second death, so only the elimination-order gauge records it.
- Zombies ([UC-023](UC-023.md) BR-007): no death is an elimination. A human turning zombie keeps playing, a zombie death respawns, and a disconnect goes through the same kill path and keeps the player in the game (UC-023 step 3). Every Zombies `player_death` carries `death.eliminated` false and no Zombies death sets an elimination order.
- Swapper ([UC-024](UC-024.md) BR-005): a swap sets no elimination order and its `player_death` carries `death.eliminated` false. A disconnected player is eliminated (A1 there): its order is recorded once, when it is taken out, and a disconnect death carries `death.eliminated` true.

In FFA, Teams, Random Teams, Traitor and Werewolf every death is final (revive is denied there by the intervention capability matrix), so their `player_death` carries no attribute and every death is an elimination.

### BR-009: Deaths come from one channel

The agent learns of an elimination only from `game_player_elimination_order`. It reads no moment ([UC-100](UC-100.md) BR-001) in any shape: the `player_death` span event changes nothing, every span that carries `moment.id` is skipped like the shield charge span (UC-100 BR-010), and the case collector forwards no moment log event (C-001). So the agent keeps no moment ids and counts no moments; the booth's moment shape changes only what the backends get. The only log records the agent takes are the game coordinator's log events marked for the agent (A8), which the case collector filters (C-001); the services' ordinary log lines never reach it.

### BR-010: A log record is never a live signal

A context opened by a log record (A8 step 2, A8 step 5) holds no player and no active game: a log record adds no player, refreshes no player's last signal and never sets the game active, so the evaluation gate (step 6) never fires on log records alone. Such a context is not dropped at the eviction tick (A2) for 60 s after the log record that opened it, so what it read before the game's metrics and spans (kind, mode, trace ids) is still there once they arrive. The 60 s is a fixed value, not a flag, like the stale end of A4: it only bounds how long an otherwise empty context waits. Only the opening record starts the hold: a later log record does not extend it, and a later metric or span does not cancel it, it only gives the context state of its own. When nothing else arrives within the 60 s, the context is dropped as in A2. When the game then starts (`game_active` 0 → 1), eliminations read before the start stay in the game's elimination sequence instead of being reset with it; this holds only for the first game of a game id context. An ended game stays ended (BR-005): a log record for an ended game id recreates a context that stays ended and is held like any other log-opened context.
