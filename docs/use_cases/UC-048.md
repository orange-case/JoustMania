# Use Case: Apply an Agent Shield

## Overview

**Use Case ID:** UC-048
**Use Case Name:** Apply an Agent Shield
**Primary Actor:** Agent
**Secondary Actors:** Player
**Goal:** Protect a player the agent chose for a bounded time, in the game's shield mode, so that the player and the room can see and feel it
**Trigger:** The agent decides a `grant_shield` for a player, or a `grant_group_shield` for a set of alive players, in a running game ([UC-040](UC-040.md) step 11)
**Status:** Tested
**Requirements:** FR-052, FR-053
**Planned:** FR-160 (Implemented: A3 to A5, BR-004 to BR-006; stays here, not under Requirements, until the hardware check #1465 lets it be Verified, because a Tested use case would derive Verified), FR-161 and FR-162 (#2096, In Progress: the pool, grants, refusals and latch (A8, A9, A10, A11, BR-008, BR-009, BR-011), the `hold` variant of `shield.activation`, the controller feedback (BR-010), the dashboard bar (UC-035 BR-008) and the agent's view and ledger checks (A9 step 1) are implemented; `shield_energy_full` for a recharge (A10 step 3) is not; FR-162 is Implemented: the experiment catalog and the promotion, UC-043 A17), FR-202 (Implemented: A13, A14, BR-014; stays here until the experiment and a hardware check let it be Verified)

## Preconditions

- The game is running and the agent may write interventions for it ([UC-040](UC-040.md) preconditions).

## Main Success Scenario

1. The agent decides a `grant_shield` for a player ([UC-040](UC-040.md) steps 1 to 10, rules or remote) and stamps the shield length on it (BR-012).
2. The agent's shield ledger passes the grant in the permission chain ([UC-040](UC-040.md) step 11): in trigger mode the agent gave the player no charge in the current window (A4), the player is below the per-game cap and out of the cooldown (A6, BR-007), and in a hold game the pool has room and the budget is not used up (A9).
3. The agent writes the grant for the game and the player (`shield_seconds`, [UC-040](UC-040.md) step 12).
4. The game coordinator picks the grant up ([UC-040](UC-040.md) step 13) and checks, before it writes anything, that the player is alive and the game is not ending (A12 step 3), then the single grant's refusals in order: in a hold game the budget, then the pool (A9); in trigger mode `already_charged` (A4); then the cap, then the cooldown (A7, BR-007).
5. The coordinator applies the grant in the game's activation mode (BR-004): `instant` protects the player now (a protection that already lasts longer is kept), `trigger` stores a charge the player activates (A3), `hold` adds energy to the player's pool (A8). The grant counts against the cap and starts the cooldown (BR-007).
6. The coordinator sends the helped cue (A12), then the shield's own feedback: in instant mode the shield LED schedule, the `shield_up` sound, the `player_shielded` event and the dashboard badge (A1, BR-001, BR-003).
7. The protection ends: the controller shows the player's base colour again and the shield end grace window follows (BR-015). The agent records the decision and measures its effect ([UC-040](UC-040.md) step 14).

## Alternative Flows

### A1: Shield feedback for the player

*In trigger mode the feedback is the charge of A3 and the activation of UC-030 A6.*

**Trigger:** The coordinator grants or extends a `grant_shield` or `toughness_boost` for a player (step 6)
**Flow:**

1. For a `grant_shield`, System first sends the helped cue (A12, BR-013). System sends the player's controller a `GAME_EFFECT_SHIELD` (`grant_shield`) or `GAME_EFFECT_TOUGHNESS_BOOST` (`toughness_boost`) with `duration_ms` = the remaining protection; the controller manager renders the LED schedule itself (BR-001, BR-002). For a `GAME_EFFECT_SHIELD` it also gives an "ending soon" double pulse about 1 s before the protection ends (BR-006).
2. System plays the shield sound `shield_up` (full volume for `grant_shield`, half volume for `toughness_boost`) (UC-040 BR-007).
3. System publishes the game event `player_shielded` (`serial`, `kind` = `full` or `toughness_boost`, `seconds`, `until_ms`; the dashboard also renders the older kind `partial` as the toughness boost badge, so an older coordinator never shows as an immune full shield) and records the span event `shield_feedback` on the player's span.
4. The dashboard tile of the player shows the live LED colour and a shield badge counting down the event's `seconds` from the browser's monotonic receipt time (`performance.now()`); `until_ms` is never compared with the browser clock, so a Pi/browser clock skew (a Pi without an RTC) neither hides nor prolongs the badge. An event without a usable `seconds` falls back to `until_ms` against the browser clock.
5. When the protection ends, the controller restores the player's current base colour. For a `grant_shield` the shield end grace window follows the protection (BR-015); a `toughness_boost` opens none.
6. Use case continues at step 7.

### A2: Shield feedback ends early

*A held shield charge ends the same way, A5.*

**Trigger:** The shielded player dies, wins (winner rainbow), disconnects, or the game ends while the shield of A1 runs (step 7)
**Flow:**

1. On death or the winner rainbow the controller manager ends the shield layer before that effect starts; on game end System sends `GAME_EFFECT_SHIELD` with `duration_ms=0` to every player with a full shield or a toughness boost still running, before the winner effects; this ends both shield layers (BR-003).
2. The controller manager cancels the shield renderer (no task is left) and shows the death effect, the rainbow or, at game end, the current base colour; the dashboard clears the badge on `player_death`, `game_ended` and `game_force_ended`.
3. Use case ends.

### A3: Shield charge granted

**Trigger:** A `grant_shield` is applied while the game's activation mode is `trigger` (BR-004) and the player holds no charge (step 5)
**Flow:**

1. System stores one charge for the player with the granted seconds and an expiry (`shield.charge_expiry_seconds`, read now; 0 = none) and leaves `grace_until` unchanged: the player is not protected yet.
2. System sends `GAME_EFFECT_SHIELD_CHARGE` to the player's controller with a bounded `duration_ms` and re-sends it while the charge is held (BR-006). The controller breathes the player's colour and plays the charge rumble pattern: a grant pattern, a reminder pulse every few seconds while the charge is held, and a double pulse shortly before it expires (BR-006).
3. System publishes the game event `player_shield_charged` (`serial`, `seconds`, `expires_ms`, `"0"` = never), records the span event `shield_charge_granted` on the player's span and starts the span `game.shield_charge`.
4. The dashboard tile of the player shows a "Charged" badge, with the seconds to expiry when there is one (UC-035, FR-084). A browser clock that disagrees with the coordinator (an `expires_ms` in the past or more than 130 s ahead) shows "Charged" without a countdown.
5. The player activates the charge with the trigger (UC-030 A6), or it ends unused (A5). An activated charge's protection is followed by the shield end grace window (BR-015); a charge that ends unused opens none. A press inside a window activates a held charge at once.
6. Use case continues at step 6.

### A4: Grant to a player who holds a charge

**Trigger:** A `grant_shield` targets a player who already holds a shield charge (step 2 or step 4; BR-005)
**Flow:**

1. In trigger mode only (BR-004), the agent gives a player at most one shield charge per window: it blocks a `grant_shield` as `already_charged` when its own charge ledger holds a grant to that player in this game. Trigger mode for the agent means a Free-for-All game (`game.mode` `FFA`), a real game, and `shield.activation` resolving to `trigger` for this game when the agent reads it from the `game` flag set with `gameId` and `game_kind=real`. The coordinator's grant read carries the game's context as well (UC-040 BR-018), but targeting on these two flags may use only `gameId` and `game_kind` (flags.md §4), and the agent reads them only for a real game, so both resolve the same value. A `hold` read follows the coordinator's latch (BR-004, BR-011): the agent remembers, per game, the first mode it read (for at most 1 h; an unreadable read records nothing), and it makes that first read when it first sees the game (its first signal, a few seconds after the start), not at its first `grant_shield` decision, and a later `hold` read in a game it first read as `trigger` stays trigger, so a flip to `hold` mid-game does not make the ledger inert while the coordinator keeps the game in trigger mode. A game the agent first reads as `hold` is a hold game: the ledger never applies in it, also to a later `trigger` read (fail open; the hold checks are A9). The window is `min(shield.charge_expiry_seconds, 20 s)` (20 s when the expiry is 0) plus 2 s for the write to reach the coordinator, so at most 22 s. The block comes before the rate limit: no budget is charged, nothing is written and the coordinator sees nothing. Fail open: any other mode, an unknown mode, a shadow game, or a `game` flag set the agent cannot read means no block, and the coordinator decides (step 2). The ledger is the agent's own record, in memory only, so within the window it also refuses a grant the coordinator would accept (BR-005) and it is lost when the agent restarts (step 2). The ledger mechanics (reserve, release, repeats, warnings) are in [decide-contract.md](../specs/decide-contract.md) §4.5 step 4. The decide state marks a player `shield_charged` while the ledger would refuse a `grant_shield` to them at the moment the state is built, so a remote backend sees the refusal before it spends a call (NFR-011). The rules engine drops a `grant_shield` candidate whose target is `shield_charged` before ranking, without moving to another player. The window is a pacing rule: an activation, an expiry or a death does not end it early. After an operator flips `shield.activation` from `trigger` to `instant` mid-game, or while the `game` flag set cannot be read (the refusal then fails open, but the state marker and R4 read the ledger directly), entries written before that point stay live for up to 22 s: the state still says `shield_charged`, R4 skips that player and an instant `grant_shield` to them does not count as `shielded`, although the ledger no longer refuses. This errs towards fewer shields.
2. If a write goes out anyway (the ledger missed it, for example after an agent restart), the coordinator applies nothing, sends no feedback and publishes `agent_intervention` with `blocked=true`, `block_reason=already_charged` (UC-040 A22). The backstop reservation it made for the write is refunded. The agent's own tally still counts that write as applied; the coordinator's `game_interventions_total{blocked="true", block_reason="already_charged"}` is the truth.
3. Use case ends.

### A5: Charge ends unused

**Trigger:** The expiry passes, the player dies or disconnects, or the game ends while a charge is held (step 5)
**Flow:**

1. System drops the charge (reason `expired`, `death` or `game_end`), publishes `player_shield_charge_ended` (`serial`, `reason`), records `shield_charge_ended` on the player's span and ends `game.shield_charge` with `shield.charge_outcome` = the reason.
2. The controller stops breathing and its charge rumble pattern stops at once, a pulse in progress included (BR-006): on expiry, death and game end the coordinator sends `GAME_EFFECT_SHIELD_CHARGE` with `duration_ms` 0 and stops re-sending it; a disconnected controller drops its layers and pattern in the controller manager. At game end a running shield is ended separately by `GAME_EFFECT_SHIELD` 0 (A2), so a charge holder with no running shield gets only `GAME_EFFECT_SHIELD_CHARGE` 0.
3. The dashboard clears the badge on `player_shield_charge_ended` (any reason), on a death, at `game_start` and game end, and when its game event stream is lost (UC-035 A4).
4. Use case ends.

### A6: Agent refuses a shield on the cap or the cooldown

**Trigger:** The agent decides a `grant_shield` (rules, rules fallback or a remote answer) for a player it already gave the per-game shield cap, whose last agent shield ended less than the cooldown ago, or to whom another grant is still being written (step 2; BR-007)
**Flow:**

1. System reads `policy.max_shields_per_player_per_game` and `policy.shield_cooldown_seconds` (`agent` flag set, flags.md §3) with the cycle's live flags; a read error or a negative value gives the default (3 / 15 s), 0 means unlimited / off.
2. The shield ledger, after the allow-list and battery and, in trigger mode, after `already_charged` (A4), refuses the grant `shield_cap_reached` when the player's agent shields in this game (written plus in flight) reached the cap, else `shield_cooldown` while now is before the end of the last one (write + granted seconds + 2 s) plus the cooldown, or while another grant to the player is in flight. The refusal comes before the rate limit: no budget is charged, rank-order admission continues, nothing is written. The ledger mechanics are in [decide-contract.md](../specs/decide-contract.md) §4.5 step 4.
3. System records the decision as blocked with that reason (UC-040 A10); `invoke_agent joustmania-agent` carries `decide.blocked` / `decide.block_reason` on the remote path. A repeat is quiet (UC-040 A21).
4. The rules engine drops a `grant_shield` candidate to such a player before ranking, so R4 does not take a decision slot every second for a refused shield. The player is then not one of R4's candidates, and R4 may shield another candidate instead (decide-contract.md §15.2). From the same ledger snapshot the decide state marks the player `shield_limited` ([UC-040](UC-040.md) step 4), so a remote backend sees the refusal before it spends a call (NFR-011).
5. A grant the agent did not write (rate-limit block, gated write UC-040 A11, failed write UC-040 A27) does not count and starts no cooldown. A new game starts with no shields counted.
6. Use case ends.

### A7: Coordinator refuses a shield on the cap or the cooldown

**Trigger:** A `grant_shield` targets a living player who has reached the per-game shield cap, or whose last agent shield ended less than the cooldown ago (step 4; BR-007)
**Flow:**

1. The coordinator reads `policy.max_shields_per_player_per_game` and `policy.shield_cooldown_seconds` (`agent` flag set, flags.md §3) at the grant. It checks after the alive check and, in trigger mode, after `already_charged` (A4): first the cap, then the cooldown.
2. It applies nothing: no grace change, no charge, no feedback. It records the span event `shield_refused` on the player's span and publishes `agent_intervention` with `blocked=true` and `block_reason` `shield_cap_reached` or `shield_cooldown` (UC-040 A22). The backstop reservation is refunded.
3. The next game starts with no shields counted.
4. Use case ends.

### A8: Shield energy granted (hold mode)

**Trigger:** A `grant_shield` is applied in a game latched to `hold` (BR-004, BR-011) to a living player whose pool has room and whose budget is not used up (step 5)
**Flow:**

1. After the alive check, the pool checks (A9) and the shield limits (BR-007, A7), System adds `min(seconds, min(cap, budget remaining) - energy)` to the player's energy (BR-008). `grace_until` is not touched: the player is protected only while holding the trigger (UC-030 A7).
2. During an active hold the added energy moves the running deadline (`hold_until`) out; in the minimum-burst tail of a release it only adds to the pool.
3. System records `shield_energy_granted` (`shield.seconds_requested`, `shield.seconds_added`, `shield.energy_s`) on the player's span and, when the pool reaches full (`min(cap, budget remaining)`), `shield_energy_full` (`shield.energy_source` = `agent`). The grant counts against BR-007 (it added more than 0) and its cooldown runs from the grant (grant time + the requested seconds, also when a partial top-up added fewer: the conservative choice), as in trigger mode.
4. Feedback (BR-010): the coordinator sends the player's new energy (`GAME_EFFECT_SHIELD_ENERGY`, or `GAME_EFFECT_SHIELD_HOLD` with the new end during a hold); the controller plays the charge grant pattern (BR-006) when the grant fills the pool and a single pulse for a partial top-up, and its LED shows the new level. The dashboard bar (UC-035 BR-008) follows the `player_shield_energy` event with `source` = `agent`.
5. Use case continues at step 6.

### A9: Grant into a full pool or an exhausted budget

**Trigger:** A `grant_shield` in a hold game targets a living player whose energy is already at `min(cap, budget remaining)` (less than 0.05 s of room), or whose budget remaining is below the minimum burst (step 2 or step 4; BR-008)
**Flow:**

1. Agent side ([decide-contract.md](../specs/decide-contract.md) §4.5 step 4): the agent's shield ledger blocks the grant `shield_budget_exhausted` (budget remaining below the minimum burst) or `shield_pool_full` (energy plus the seconds of the agent's grants in flight at least `min(cap, budget remaining)` minus 0.5 s) from the coordinator's hold gauges (the decide-state values), in a game whose `game_shield_activation_mode` says `hold`, before the rate limit, after the allow-list and battery and before the cap and cooldown. The pool margin is deliberately stricter than the coordinator's (step 2 refuses only with less than 0.05 s of room), so the agent may refuse a small top-up the coordinator would accept: the safe direction. For a player whose shield is active only the pool check is skipped (the energy gauge then over-reads the draining pool); the budget check stays. Both fail open when the values are missing. Repeats are quiet (as UC-040 A21: `agent.decision_shield_pool_full_repeat`, `agent.decision_shield_budget_exhausted_repeat` at debug level).
2. Coordinator side: the coordinator checks after the alive check and before the shield limits, first the budget, then the pool. It applies nothing, records `shield_refused` (`shield.refusal_reason` = `shield_budget_exhausted` or `shield_pool_full`) on the player's span and publishes `agent_intervention` with `blocked=true` and that `block_reason` (UC-040 A22). The backstop reservation is refunded and the grant does not count against BR-007.
3. Use case ends.

### A10: Passive recharge

**Trigger:** `shield.recharge_per_second` is above 0 in a hold game while a player lives and no activation runs (step 5; BR-009)
**Flow:**

1. While the player is alive and no activation runs, the energy rises at the latched rate from the start of the game loop, up to `min(cap, budget remaining)`. It never rises during an activation or its minimum-burst tail; it restarts at the end of the activation.
2. The coordinator keeps no timer: the energy is computed from the time when it is read (an activation, a grant, a death, the game end).
3. Reaching full gives the charge grant pattern (BR-006) once: the controller manager detects it from the level, rate and full level of the last `GAME_EFFECT_SHIELD_ENERGY` (BR-010), so the coordinator sends nothing for a recharge. The dashboard bar computes the same from the `player_shield_energy` rate (UC-035 BR-008). The `shield_energy_full` span event for a recharge is planned (see Planned extensions).
4. Recharge is pure game balance: it counts against the budget only when it is spent, never against BR-007, and it adds nothing once the budget is used up.
5. Use case ends.

### A11: Shield energy ends

**Trigger:** An activation runs out (empty or budget used up) while held, the player dies or disconnects, or the game ends (step 7; BR-008)
**Flow:**

1. Empty or budget used up while held: the protection ends at the deadline (UC-030 A7 step 4); `game.shield_hold` ends with `empty` or `budget_exhausted` (with `shield.end_grace_s`); when the budget is used up, `shield_budget_exhausted` is recorded on the player's span once. The shield end grace window follows (BR-015): for `shield.end_grace_seconds` (default 0.75 s), at most the activation's cost, after the deadline movement cannot kill, then the first unprotected frame primes the EMA (UC-030 BR-009). A release (`released`, the minimum-burst tail included) opens no window.
2. Death or disconnect (the kill path, also `eliminate_player`, which ignores the hold, BR-005) and game end: System drops the pool and ends an open `game.shield_hold` with `death` or `game_end`, once at the start of the kill path and again after its awaits, so energy granted while the kill awaited is dropped too.
3. Nothing carries into the next game, and a respawn never restores the pool.
4. Feedback (BR-010): when an activation ends because the energy or the budget ran out, the controller gets `GAME_EFFECT_SHIELD_HOLD` 0 and the idle energy layer with the "empty" cue; the LED shows the empty state (the base colour). In ramp mode (the default) the rumble, which rose to `shield.hold_rumble_max_intensity` as the energy drained, stops cleanly and no empty pulse plays; in flat mode the controller plays the single empty pulse. Death and game end end every shield layer on the controller (A2, A5). With the trigger still held past empty and a death right after it, the controller plays the single empty pulse in flat mode (cut short by the death rumble when the death comes first; in ramp mode no pulse), then the death effect: after the death the rumble is 0 (the hold rumble, flat or ramped, does not come back after the death rumble) and the LED ends off, never the shield colour, also when the controller has no shield layer left to end.
5. Use case ends.

### A12: The helped player sees a cue before the shield

**Trigger:** The coordinator applies a `grant_shield` for a player, in any shield mode (step 6; BR-013)
**Flow:**

1. After the grant is in place (instant mode: the protection, A1; trigger mode: the stored charge, A3; hold mode: the energy added to the pool, A8), System sends the player's controller a `GAME_EFFECT_PULSE` in magenta (255,0,192), 500 ms at speed 4 (two pulses), on the game's gameplay stream.
2. System then sends the shield's own LED command as before: `GAME_EFFECT_SHIELD` (A1), `GAME_EFFECT_SHIELD_CHARGE` (A3) or, from the hold feedback task, `GAME_EFFECT_SHIELD_ENERGY` / `GAME_EFFECT_SHIELD_HOLD` (BR-010). The controller manager plays the pulse as an overlay effect over every shield layer, so the shield colour shows when the pulse ends; the protection itself starts at the grant, not after the pulse.
3. A grant that applies nothing sends no cue: a refusal (`already_charged` A4, `shield_cap_reached` / `shield_cooldown` A7, `shield_pool_full` / `shield_budget_exhausted` A9), a kept grant inside a longer running shield, or a dead or unknown player. Once the game is ending (its outcome is latched at the win, it was force-ended, or its state is ENDING or ENDED) System refuses the grant itself with `game_ending` (blocked, nothing applied, the backstop reservation refunded, UC-040 A22) in every shield mode, so no shield layer and no cue appear over the winner effect: a `GAME_EFFECT_PULSE` would take over the winner rainbow in the controller manager. The cue write re-checks the same condition, so a latch that lands while a grant runs still sends no cue. A toughness boost, a player's own hold activation and an activated charge send no cue.
4. The cue is best-effort: a failed write is logged as a warning and the grant stands. A game whose gameplay stream is not open sends nothing. A shadow game has a gameplay stream to the controller manager like a real game (its pattern controllers are mock controllers, UC-046 step 4), so its cue is written to a mock controller and no physical LED shows it.
5. Use case continues at step 7.

### A13: A group shield is applied to the chosen alive players

**Trigger:** The coordinator reads a new `group_shield` event in the game's event list (`interventions` set, payload `{"serials":"A,B,C","seconds":"5"}`, flags.md §13.1) and the intervention type `grant_group_shield` passes its chain (allow-list, global backstop; no capability-matrix row, so every mode) (step 4; BR-014). The agent writes the event for a `grant_group_shield` decision (agent half below); only the opt-in `interventions_allowed` variants `standard_group` and `shadow_group` name the lever, every other variant refuses it `not_allowed` (UC-040 A10, UC-040 A22).

**Agent half**, before the event exists:

- The lever is offered as in [UC-040](UC-040.md) step 4. A remote backend may answer it with a group option of `ffa.target`; the agent resolves the option against the request's alive players into the decision's set (sorted). The lever with `none` or a serial, or a group option on any other lever, is an invalid answer: the rules decide (UC-040 A2).
- When the answer lands, a target no longer present discards the group `stale` with detail `target_gone` (UC-040 A7).
- The permission chain checks, before the rate limit: the allow-list, the gate and the set (`group_disabled`, `group_real_game`, `group_bad_set`: not 2 to `max_targets` distinct alive players), the battery of every target, then the shield ledger reserves every target with the single grant's checks (A4, A6, A9) and one group slot of the game (`group_cap_reached` at `max_per_game`), all or nothing; a refused target names `decision.group.refused_serial`. The group costs 1 in the rate limit (UC-040 BR-014) and counts as one decision of the cycle.
- Every group decision (applied or refused) is also noted for the game summary: whether it was a rescue (a target `near_threshold` in the game context at the moment the decision lands, which for a remote answer is the re-validated landing-time context, not the request state the backend saw), its outcome and the decider's own reason text (an answer that came without one adds none: the loop's "decided by <backend>" fallback is never exported). The game summary then carries `group_grants` (`applied`, `blocked`, `non_rescue`, `rescue_refused`, and `rationales`, the reason texts with no arm and no backend label so a rater cannot tell the arms apart; [telemetry.md](../specs/telemetry.md) §4 `agent.game.summary`, entity model GAME_SUMMARY); the same texts are emitted as one `summary.group.rationale` event each on the `agent.game.summary` span, so a rater can read them in Jaeger. The noted decisions are kept in memory for a bounded number of games, and a decision noted after its game's summary took them is dropped. Observation only: it never changes a decision.
- The writer posts one `group_shield` event with the set and the length (the `shield_seconds` default variant, BR-012); a set of fewer than 2 is a failed write (UC-040 A27). Each target counts as one agent shield in the ledger once written (BR-007).

**Flow:**

1. The handler reads the four `policy.group_grant.*` flags (`agent` set, no targeting, flags.md §3) in the game's flag context, at the event.
2. The group passes the game-level checks of A14 step 1: the gate is open (`enabled` on, and the game is a shadow game or `real_games` is on), the set holds 2 to `max_targets` distinct serials and the length is 1 to 10 s, every serial is an alive player of the game with a battery not below `policy.battery_threshold`, the game is not ending, and the game has applied fewer than `max_per_game` group shields.
3. System checks every target with the single grant's checks, in the single grant's order, before it writes anything (A4, A7, A9: in hold mode the budget, then the pool; in trigger mode `already_charged`; then the cap, then the cooldown). Every target passes.
4. System commits every target in the same game-loop turn, with no await between the first check and the last write: in instant mode the protection (A1) and its end grace (BR-015), in trigger mode the stored charge (A3), in hold mode the energy added to the pool (A8). Each target counts as one agent shield for the cap and the cooldown (BR-007). In instant mode a target already protected longer (admin invincibility or a running shield) is kept: it counts as success and is not counted, as for a single grant. Then the game's group count goes up by one.
5. Per covered player, System sends the helped cue (A12) and the shield's own feedback (A1, A3, BR-010), best-effort: a failed write is logged and the shields stand. A kept target gets no cue.
6. System publishes one `agent_intervention` with `type` = `grant_group_shield`, `blocked=false` and an empty `target`, and counts one `game_interventions_total{type=grant_group_shield}`.
7. Use case continues at step 7.

### A14: A group shield is refused as a whole

**Trigger:** A `group_shield` event reaches the handler (A13 step 1) and one of its checks fails (step 4; BR-014). The agent refuses a group before it writes on the same grounds (A13 agent half: `group_disabled`, `group_real_game`, `group_bad_set`, `battery_threshold`, `group_cap_reached`, or a target's ledger reason), blocked and recorded like any other refusal (UC-040 A10); nothing is reserved for any target.
**Flow:**

1. Game-level checks, in this order, each refused with `group_refused:<reason>`: `disabled` (`enabled` off, unreadable, or `max_targets` unreadable or 0), `real_game` (the game is not a shadow game and `real_games` is off; any kind but shadow counts as real), `bad_set` (fewer than 2 or more than `max_targets` serials, a repeat, an empty entry, or a length that is not a number from 1 to 10 s), `target_gone` (a serial that is not an alive player of the game), `low_battery` (a target below `policy.battery_threshold`), `game_ending` (outcome latched, force-ended, ENDING or ENDED), `cap_reached` (the game already applied `max_per_game` group shields; 0, the default, allows none).
2. Per-target checks (A13 step 3): the first refused target refuses the group with `group_refused:` and the single grant's reason (`already_charged`, `shield_pool_full`, `shield_budget_exhausted`, `shield_cap_reached`, `shield_cooldown`).
3. Nothing is applied for any target: no protection, charge or energy, no count, no cue, and the group count does not move. The hold mode is latched as by a single grant (BR-011).
4. System publishes `agent_intervention` with `blocked=true` and that `block_reason` (UC-040 A22), refunds the backstop reservation. When a target caused the refusal, it records `shield_refused` with `shield.refusal_reason` = the block reason on that player's span and logs the serial.
5. Use case ends.

## Postconditions

### Success Postconditions

- The player is protected, or holds a charge or energy, for at most the granted seconds plus the shield end grace, and the player's controller and the dashboard show it.

### Failure Postconditions

- Nothing is applied to any player and no shield is counted (A4, A7, A9, A14); a refused grant charges the agent no budget and the coordinator refunds its backstop reservation.

## Business Rules

### BR-001: Shield LED schedule

For `GAME_EFFECT_SHIELD` with duration T: the LED shows the shield colour (white, as in spawn protection) and its brightness falls linearly from 100 % to 30 % over the first T − 1 s; in the last 1 s it blinks at 4 Hz between full shield colour and off; at T it shows the player's current base colour. A shield of 1 s or less blinks for its whole duration. The controller manager renders the schedule at its effect rate (20 Hz) as a pure function of the time since the grant; the coordinator sends one command per grant, not a colour stream.

### BR-002: Toughness boost is the weaker variant

For `GAME_EFFECT_TOUGHNESS_BOOST` with duration T: the shield colour breathes slowly (0.5 Hz) between 10 % and 50 % brightness until the last 1 s, then blinks at 4 Hz between 50 % and off, then restores the base colour.

### BR-003: Feedback follows the protection, never the other way round

Feedback starts only when the grant changes the protection: a grant that extends the shield restarts the LED schedule with the new remaining time; a grant that is kept (the effective grace, `max(agent shield, admin invincibility)`, already lasts longer) sends no feedback. The shield sound plays only on the transition from unprotected to protected; an extension restarts the LED silently. The LED effect, the sound and the `player_shielded` event are sent independently: one failing never skips the others. Feedback never changes `grace_until`, `invincible_until` or the toughness boost factor, and a feedback failure never fails the intervention; the coordinator keeps no timer or task for it.

On the controller the shield is a persistent **layer**, not a replaceable effect:

- Effects that do not touch the LED (rumble) neither end nor hide the shield.
- Short LED effects (death warning flash, agent pulse / flash, battery display) are drawn over the shield; when they end, the shield schedule continues at the point it has reached by then.
- A new base colour (a team or colour change during the game) does not end the shield; it is the colour shown when the shield ends.
- Death, the winner rainbow, a disconnect and `GAME_EFFECT_SHIELD` with `duration_ms=0` (game end) end the shield, the full and the toughness boost layer alike.
- A full shield and a toughness boost can be active together; the full one is shown, and when it ends while the toughness boost is still active its schedule continues. `GAME_EFFECT_TOUGHNESS_BOOST` with `duration_ms=0` ends only the toughness boost layer.

### BR-004: Shield activation mode

- The `game` flag `shield.activation` (`instant` | `trigger` | `hold`; `hold` with its controller feedback, BR-010) is read at each `grant_shield` in instant and trigger games; a malformed value gives `instant`. A game whose flag resolves to `hold` at the start of its game loop or at its first `grant_shield`, whichever comes first, is latched to hold for its whole life (BR-011); a `hold` read mid-game in a game that was not latched to hold resolves to the mode that game read at that latch (`instant` or `trigger`): a flip to `hold` never changes the mode of a running game. The stack default is `trigger`, which only Free-for-All honours; every other mode and every shadow game stays `instant`. The code fallback and the CI baseline stay `instant`. Rollback: set the flagd `defaultVariant` back to `instant`, live. `hold` is not the default; an operator selects it (a stage overlay, flags.md §13.3), and since FR-162 the agent may experiment toward it in shadow games (UC-043 A17). It is not latched in instant and trigger games, so it has no `real` scope and the agent never promotes it (UC-043 A17 step 3, flags.md §13); operator flips keep applying per grant.
- `trigger` and `hold` apply to Free-for-All only (an allow-list). Every other mode, including Fight Club, Zombies (the trigger is the weapon), Traitor and Werewolf (UC-022: rumble is the hidden-role signal), is always `instant` whatever the flag says.
- A shadow game is `instant` unless its pattern controllers press the trigger by themselves: it honours `trigger` and `hold` (including the hold latch, BR-011) only when its start carries `pattern_trigger_policy`, which the agent sets when the installed archetype declares a `trigger_policy` (UC-046 BR-018), so an experiment on `shield.activation` can compare trigger against hold, not instant against hold. The coordinator binds the field only to a shadow session, like `rng_seed`: a real (menu-origin) start that carries it ignores it. The Free-for-All allow-list applies to shadow games too. Nothing in this changes how a real game reads the flag. Whether a shadow game plays sound or rumble is not governed by this rule.
- A flip applies to the next grant. A held charge stays activatable in either mode, and an `instant` grant to a player who holds a charge applies the shield at once and leaves the charge alone.
- The agent never writes `shield.activation` or `shield.charge_expiry_seconds` stack-wide (C-034); they are human flags (stage overlay, flags.md §13.3). Since FR-162, `shield.activation` and the seven hold parameters are experiment+arm and `real` values the agent may write under UC-043 A17; `shield.charge_expiry_seconds` and the charge cue flags (BR-006) stay human-only (C-034).

### BR-005: One charge per player

- Trigger mode only (a hold game has a pool instead, BR-008). A player holds at most one charge. The coordinator refuses a `grant_shield` while a charge is held as `already_charged` (A4); it is authoritative. A grant while a shield is active and no charge is held is accepted by the coordinator: the charge then waits under the active shield. The agent's ledger (A4 step 1) allows at most one agent charge per player per window, so it may refuse such a grant within its window.
- The granted seconds become the shield duration at activation. The expiry is fixed at grant time, so a flag flip never changes a held charge.
- Death, disconnect (a death in every mode, UC-020 A2), game end and expiry discard the charge. A respawn never restores it. `eliminate_player` still eliminates a player who holds a charge or an active shield.
- The coordinator keeps no timer for the charge: it checks the expiry in the frame path, only for players that hold one.

### BR-006: Charge and activation feedback

- Charge layer (`GAME_EFFECT_SHIELD_CHARGE`): the player's current base colour breathing between 60 % and 100 % at 0.5 Hz, rendered at 5 to 10 Hz (or only on a visible change) to spare the battery. It is the lowest-priority shield layer: the full shield and the toughness boost draw over it. Short LED effects overlay it.
- `duration_ms` is capped at 120 s. While a charge is held the coordinator re-sends the command before it runs out, which also covers an expiry of `never` (0). The controller manager ends the shield layers, charge and active `SHIELD` alike, of a game stream's controllers when that stream closes (serials snapshotted before the stream is released), so a coordinator crash leaves no breathing controller in the lobby. After a mid-game coordinator reconnect the coordinator re-sends `GAME_EFFECT_SHIELD_CHARGE` for every held charge, and `GAME_EFFECT_SHIELD` and `GAME_EFFECT_TOUGHNESS_BOOST` with the time left for every running shield and toughness boost; the cleanup is delayed about 7 s (longer than the coordinator's 1, 2, 3 s reconnect backoff) and cancelled when a new game stream claims the serial, so the re-send finds the layers intact.
- Charge rumble pattern, run by the controller manager per charge layer, so the coordinator sends nothing extra and its frame path is unchanged:
  - Grant: when a charge layer starts (not when a re-send extends it), 3 pulses of `shield.charge_rumble_pulse_ms` (default 150 ms) at `shield.charge_rumble_intensity` (default 255) with 100 ms gaps.
  - Reminder: one such pulse every `shield.charge_reminder_seconds` (default 5 s, counted from the grant) while the charge is held; 0 turns the reminders off.
  - Pre-expiry: a double pulse (two pulses, 100 ms gap) `shield.charge_pre_expiry_seconds` (default 3 s, at most 8 s) before the charge layer ends; the last cue, no reminder after it. The layer's end is the expiry: the coordinator sends the time to expiry, capped at 120 s, and re-sends 10 s before a cap that is not the expiry, so an expiry of `never` (0) or one more than 120 s ahead never gives the pulse early. A charge shorter than the grant pattern plus the lead gets no pre-expiry pulse. 0 turns it off.
  - The four flags are read when the charge layer starts and fixed for that charge (flags.md §4). Intensity 0 turns the whole pattern off.
  - A charge pulse plays only when the rumble slot is free: while another rumble runs (the warning, the death rumble, the swell, an agent `RUMBLE`), a cue waits up to 1 s for the slot and is skipped if it is still taken. Any later rumble replaces a running charge pulse. The pattern stops at once, a pulse in progress included, when the charge layer ends: activation (`GAME_EFFECT_SHIELD_CHARGE` 0), expiry, death, game end, stream close or disconnect.
- Shield ending soon: an active shield (a `GAME_EFFECT_SHIELD` layer: an instant shield or an activated charge) gives a double pulse (2 x 150 ms at 255, 100 ms gap) `shield.ending_rumble_seconds` (default 1 s, 0 to 3, 0 = off) before its layer ends, so the player knows the protection is about to end. The lead is read each time the layer starts or restarts; a restart (a re-grant or a re-send after a reconnect) moves the pulse to the new end. A shield no longer than the lead gets no pulse. The toughness boost (not a protection) gets none. Same rules as the charge pulses: only in a free rumble slot (waits up to 1 s), any later rumble replaces it, and it stops at once when the shield layer ends early: death, game end (`GAME_EFFECT_SHIELD` 0), stream close or disconnect.
- Activation swell (`GAME_EFFECT_SHIELD_SWELL`): a rumble ramping 0, 180, 0 over 600 ms. It is a rumble only: it neither ends nor hides an LED layer.
- The charge pulses, the ending pulse and the swell are distinct from the death warning (200 ms flat) and the death rumble (1000 ms at 255). Any later rumble (warning, death, agent `RUMBLE`) replaces a running charge pulse, ending pulse or swell; the death rumble is never shortened.
- `GAME_EFFECT_SHIELD_CHARGE` with `duration_ms=0` ends only the charge layer; `GAME_EFFECT_SHIELD` 0 ends every shield layer.

### BR-007: Shields per player per game are capped and paced

- Two operator flags in the `agent` set bound the agent's shields per player per game: `policy.max_shields_per_player_per_game` (default 3, 0 = unlimited) and `policy.shield_cooldown_seconds` (default 15 s, 0 = off). The agent never writes them (C-034). A read error or a negative value gives the default, so the limits stay on. They carry no targeting, so every reader resolves the same value.
- Count: the agent shields applied to that player (by serial) in this game. An instant grant that moved the player's shield counts, in trigger mode a stored charge counts, and in hold mode a grant that added energy counts, a partial add included (A8); a refusal for a full pool or a used-up budget does not (A9). A kept grant (the player's protection already lasts longer, step 5) and a refused grant do not count. A revive does not reset the count; the next game starts at 0.
- Cooldown: a grant is refused while now is before the end of the player's last agent shield plus the cooldown. The end is the shield's own (grant time + requested seconds), never `grace_until`, which other graces share. In trigger and hold mode the cooldown runs from the grant: charge stored (or energy added) + the requested seconds (a partial top-up in hold mode still books the full requested cooldown), whenever the player uses it. In trigger mode the cooldown and the count are recorded when the charge is stored, before its feedback, so a charge whose feedback fails or is cancelled still counts. The flag is read at each grant and added to the stored end, so a flip applies to the next grant.
- With a cooldown set, a running agent shield is never extended (the cooldown refuses it); cooldown 0 restores extend-not-shorten.
- The coordinator is the authority (A7). The agent enforces the same limits first (A6), so a refused shield costs no budget and is not written. The agent's count is an upper bound of the coordinator's: it counts every write it made, also one the coordinator refused (`already_charged` after an agent restart, a dead target, the mode, its own cooldown) or kept, so the agent errs towards fewer shields, never more. Its ledger is in memory: an agent restart, or a game whose Loop was evicted, starts again at 0, and the coordinator's count still holds.

### BR-008: Shield energy pool and budget (hold mode)

- Each player of a hold game has a pool of shield energy in seconds. Cap `shield.energy_max_seconds` (default 5, 1 to 10). Budget `shield.energy_budget_seconds` (default 15, 3 to 30): the active shield time actually used per player per game, summed over every activation, whatever filled the pool. Minimum burst `shield.min_burst_seconds` (default 0.3, 0.1 to 1). Starting energy `shield.energy_initial_seconds` (default 0, 0 to 5), clamped to the cap and the budget. All are `game` flags latched at the start of the game loop or at the first `grant_shield`, whichever comes first (BR-011, flags.md §4).
- One activation costs `max(held, minimum burst)` and never more than the usable energy at its start, `min(energy, budget remaining)`; the protection lasts exactly the cost. An activation needs a usable energy of at least the minimum burst, so a remainder below it never buys a full burst.
- The energy shown and stored is clamped to the budget remaining, so it never shows energy that cannot be used. Once the budget remaining is below the minimum burst the shield cannot activate again in that game, and grants (A9) and recharge (A10) add nothing.
- Bound: total protected time per player per game ≤ budget + the sum of the run-out windows, each at most `min(shield.end_grace_seconds, the cost of the activation that ran out)` (BR-015), so ≤ 2 × budget; the protection of one activation ≤ `min(budget remaining, energy at the start + grants landing during the hold)`, followed by at most one window of `shield.end_grace_seconds`.

### BR-009: Energy sources

- Agent grants add energy (A8); passive recharge, `shield.recharge_per_second` (default 0 = off, at most 0.5), adds energy while no activation runs (A10). The pool never fills by itself otherwise.
- Recharge is pure game balance: it counts against the budget only when spent and never against BR-007.

### BR-010: Hold feedback

- The controller shows the shield energy on the LED and as rumble, so the player knows it without looking (LED is the primary feedback; audio only reinforces). Two shield layers of the controller manager carry it ([services.md](../specs/services.md) §4 and §6 "LED states"): `GAME_EFFECT_SHIELD_ENERGY`, the idle pool, and `GAME_EFFECT_SHIELD_HOLD`, the running activation, which draws over it.
- LED states. Each idle state uses the player's current base colour; none uses red or off (death), and only the active state uses white (protected, as every shield, BR-001):
  - empty (usable energy below the minimum burst, so the shield cannot activate; also once the budget is used up): the base colour, steady, as in a game without a shield;
  - low (usable, below a third of the cap): the base colour breathing from 100 % down to 20 % at 1 Hz;
  - charged (from a third of the cap up to below full): the base colour breathing 60 % to 100 % at 0.5 Hz, the look of a held charge in trigger mode (BR-006);
  - full (the energy at `min(cap, budget remaining)`): the base colour breathing towards white, between the base colour and a 50 % white blend at 0.5 Hz;
  - active (held): white, dimming as the energy drains: the brightness is `floor + (1 − floor) × fill²`, with `fill` the energy left above the last second as a share of the activation's energy above it (the energy at the start of the activation plus any grant during it, not the cap), so every activation starts at 100 % and reaches `shield.hold_led_floor_percent` (default 20 %, never below 10 %; 100 = no fade) when the last second starts; the last second blinks at 4 Hz, as a shield does (BR-001). The colour stays white (dimming, not desaturating), so white, then the blink, then the player's own colour is the change the room sees.
  The controller computes the idle level from the last command (energy, recharge rate, full level), so a recharge moves the LED through the states with no further command.
- Rumble:
  - active: a continuous rumble kept as a background level that the controller manager restores after every one-shot rumble (warning, cue pulses, swell); it stops when the activation ends. Death ends every shield layer and the background level with it, also when no layer is left, so the death rumble keeps the motor and stops at 0. Ramp mode (`shield.hold_rumble_max_intensity` above `shield.hold_rumble_intensity`, the default): the level rises with the energy used, `hold_rumble + (max − hold_rumble) × (1 − energy left / activation energy)`, from `shield.hold_rumble_intensity` (default 70) at the start of an activation to `shield.hold_rumble_max_intensity` (default 200, below the death rumble's 255) when the energy runs out. The controller manager computes it in its shield renderer from the time left and the activation energy the command carries, and writes it only when it moved by at least 8 (or reaches the top) and at least 100 ms after the last write (at most 10 rumble writes per second per holding controller). A grant during the hold raises the activation energy, so the level steps back down; a re-send after a reconnect lands at the level of the time left. Flat mode (`shield.hold_rumble_max_intensity` at or below `shield.hold_rumble_intensity`, or `shield.hold_rumble_intensity` at 0): the level stays at `shield.hold_rumble_intensity`; a hold rumble of 0 means no hold rumble, so it never ramps from silence. The ramp top stays below the death rumble (at most 230, the registry range and the code clamp);
  - ending soon (flat mode only): the shield-ending double pulse (BR-006) `shield.ending_rumble_seconds` before the energy runs out while held (the existing flag, no new one); a grant during the hold moves it. In ramp mode the ramp is the warning and no ending pulse plays;
  - empty (flat mode only): one pulse of `shield.empty_pulse_ms` (default 400) at the cue intensity when an activation ends because the energy or the budget ran out. In ramp mode the end is a clean stop of the rumble plus the LED change from white to the empty state; the coordinator still sends the empty cue (telemetry and dashboard keep its meaning) and the controller manager plays no pulse for it;
  - full: the charge grant pattern (3 pulses, BR-006) when a grant fills the pool, or when the recharge fills it (detected by the controller from the recharge rate, once per fill); a partial top-up by a grant gives a single pulse. A pool that starts the game with energy (`shield.energy_initial_seconds`) plays no pattern at game start; the LED shows it.
  - Every cue pulse follows the slot rules of BR-006: it waits up to 1 s for a busy rumble slot and is skipped after that; death and the warning keep the slot.
- Sound only reinforces: `shield_up` plays on an activation at most once per 2 s per player, so a bouncing or mashed trigger never queues sound RPCs.
- The coordinator latches the cue values with the hold values (BR-011): `shield.charge_rumble_intensity`, `shield.charge_rumble_pulse_ms`, `shield.ending_rumble_seconds`, `shield.hold_rumble_intensity`, `shield.empty_pulse_ms`, `shield.hold_rumble_max_intensity` and `shield.hold_led_floor_percent`. It ships them with each command, and with `SHIELD_HOLD` also the activation energy (`ShieldHoldState.activation_ms`, the usable energy at the start of the activation plus any grant during it), so the controller plays what the game latched; the controller manager falls back to its own read when they are absent.
- One ordered outbound task per hold game sends the commands; the frame path only marks the player and never awaits (UC-030 BR-008). The game's gameplay stream carries one write at a time (grpc allows one write in flight per call): the task, the frame path's warning and death effects, the intervention handlers and the end-of-game effects all write through one lock per call, so a frame waits at most for the one write in flight, as long as its own write takes (the agent cue to several players writes one pulse after the other, never a batch ahead of a frame). A write that started is never cancelled, because cancelling a grpc write ends the whole call: a cancel of the writer (the game end stopping the task) leaves its write to finish, and the next write waits for it. After the game end the task is stopped for good: a late grant or re-send sends nothing after `SHIELD` 0. The task sends the player's state at the time it runs, so changes between two sends coalesce:
  - the start of the game loop: `SHIELD_ENERGY` for every player;
  - an activation: `SHIELD_HOLD` with the energy left;
  - the end of an activation: `SHIELD_HOLD` 0, then `SHIELD_ENERGY` (with the empty pulse after `empty` or `budget_exhausted`);
  - a grant: `SHIELD_ENERGY` with the full or top-up cue, or, during a hold, `SHIELD_HOLD` with the new end and the cue;
  - a release inside the minimum-burst tail sends nothing; a dead or disconnected player gets nothing (the death effect and the disconnect end the layers);
  - after a mid-game reconnect the state of every living player is sent again (BR-006).
- A hold activation does not publish `player_shielded`, so the dashboard's shield badge never shows a protection a release already ended; the energy bar reads `player_shield_energy` (UC-035 BR-008).
- Whether the default hold rumble is felt on a moving controller, and whether the rumble ramp and the LED dimming read on stage, is a stage check on the Pi (#1465) before `hold` becomes a default.

### BR-011: Hold parameters are latched per game

- `shield.activation` (when it resolves to `hold`) and every hold and cue parameter are read once, at the start of the game loop or at the first `grant_shield`, whichever comes first, in the game's flag context (the read sees the experiment arm, as `windows` does), and are fixed for that game.
- A stage overlay, an experiment write or a promotion (and a kill-switch revert of a promotion, UC-045) applies from the next game; a running game keeps its values. A promotion of a hold sub-parameter is written at once; `shield.activation` is never promoted (UC-043 A17 step 3). A game not latched to hold keeps reading `shield.activation` per grant (BR-004), but a `hold` read there gives the mode it read at the latch, so a flip to `hold` never changes the mode of a running game.
- The game carries the latched values in telemetry (`game.shield_hold` span and the `game_shield_hold_setting` per-game gauge), the decide state and the retro (UC-042 BR-007).

### BR-012: The agent's shield length is the `default` variant of `shield_seconds`

- A `grant_shield` that carries no value (every rules decision, a remote answer without a magnitude) is written with the value of the variant named `default` of the `interventions` flag `shield_seconds` (5 s in the baseline). The flag's `defaultVariant` stays `none` (0): it is what a player the agent never granted resolves. A remote answer's magnitude (3 to 10 s) is kept.
- The agent reads it at use time, through the flag service (`GET /interventions/shield_seconds`), when it runs the permission chain for a grant the allow-list permits; one read serves the whole agent for at most 1 s. It stamps the value on the decision before the shield ledger, so the ledger's cooldown end and in-flight seconds (BR-007, A6, A9) and the write use the same length.
- Fail closed: a read that fails or times out (200 ms), a missing variant, or a value that is not a number from 3 to 10 (the `grant_shield` magnitude bounds, so the recorded answer is the written length) gives 5 s and logs `agent.shield_seconds_unreadable` (at most every 30 s). No new flag (C-035). The flag service reads its baseline file at start, so an edited variant applies after a flag-service restart.
- The rules record's `ffa.magnitude` answer reports the stamped length (decide contract §2.1), so `decide.answers` on the `invoke_agent joustmania-agent` span and the decision's value agree.

### BR-013: An agent shield is visible to the room

- Every applied `grant_shield` pulses the helped controller magenta (255,0,192) before the shield colour (A12), so a shield reads as the agent helping a struggling player, not as chance. The "agent acted" cue for HARD-class interventions ([UC-040](UC-040.md) step 13) is the same magenta, so both read as the agent acting; the two are told apart by what they target (the helped controller before its shield, versus the intervention's target or every active player).
- The cue is told apart by its timing, not by its colour alone: a short pulse (two pulses in 500 ms) on the one helped controller, just before that controller's shield appears (the white shield in instant mode, the player's base colour breathing in trigger and hold mode). Magenta can match a player's own colour: it is the second team colour in the team modes (`teams_base.py` `TEAM_COLORS`, so every game with two or more teams has a magenta team), and close to the hue of the last players in a Free-for-All of 8 or more ([services.md](../specs/services.md) palettes).
- `grant_shield` is written only by the agent (the `shield_seconds` flag, W1, [flags.md](../specs/flags.md) §13.1), so every grant the coordinator applies is an agent grant. A `grant_group_shield` (the `group_shield` event, also W1) pulses each player it covers once, in the order of its set (A13). Admin invincibility (`invincible_until`), a player's own hold activation and the activation of a charge are not grants and get no cue.
- The LED is the cue (LED is the primary feedback); no voice line is added. The cue is not behind `agent_intervention_cue`: that toggle mutes the operator cue of HARD-class interventions, and `grant_shield` is MEDIUM-class, so the two cues never both fire for one grant.
- A cue pulse may cut a running 200 ms warning flash short in trigger and hold mode (the overlay takes over the LED); the warning rumble still plays, and the next warning flashes again.

### BR-014: A group shield is all or nothing and shadow-first

- A group shield covers 2 to `policy.group_grant.max_targets` alive players with one decision (the `group_shield` event, flags.md §13.1). It is applied to all of them or to none (A13, A14): every target passes the same per-target checks as a single `grant_shield` (the C-034 bounds: BR-007 cap and cooldown, BR-005 charge, BR-008 pool and budget) before any target is written, and the writes happen in one game-loop turn with no await between the first check and the last write.
- Each target counts as one shield for those limits, so a group behaves like N single grants for the caps, the cooldown windows and the shield end grace (BR-015). In instant mode a target already protected longer is kept: success, not counted, as for a single grant. One helped cue per covered player (BR-013).
- It costs one intervention in the rate limit and is not a protective lever (UC-040 BR-015). At most `policy.group_grant.max_per_game` group shields per game: the coordinator counts them per game (in memory, per game-mode instance), so a new event seq or an agent restart does not reset it; the agent checks it too (A13 agent half: written plus in flight, in memory per game). The default 0 allows none: enabling needs `max_per_game` of at least 1 as well as `policy.group_grant.enabled` = `on`.
- Shadow-first: a game that is not a shadow game also needs `policy.group_grant.real_games` = `on`; any other kind, an unknown one included, counts as real. The coordinator re-reads the flags at the event, so switching `enabled` off also refuses an event already written. A missing or unreadable flag reads off (fail closed). The four flags carry no targeting: the agent and the coordinator read them in different contexts and must see one value (`test_group_grant_flags_carry_no_targeting`, `handler_flag_reads.py`).
- The payload is checked twice: by the flag service (`serial_set`, `float 1 10`) and again by the coordinator (2 to `max_targets` distinct alive players, 1 to 10 s, each battery at or above `policy.battery_threshold`).
- Dashboard: the Agent tab shows a decision whose `ffa.target` choice starts with `group:` as a badge, "Group: all" for `group:all` and "Group: all but one" for `group:all_except:<serial>` (the serial is not shown, also not in the badge tooltip, which reads `group:all_except`), and any other `group:<x>` choice as "Group", not the raw choice string.
- Opt-in on every layer: only the `interventions_allowed` variants `standard_group` (`standard` plus the lever) and `shadow_group` (`shadow_experimental` plus the lever) name it (`test_only_the_group_variants_name_grant_group_shield`); `max_per_game` defaults to 0; `enabled` and `real_games` default off; the kill switch and the landing re-read apply as for any decision. The lever is a capability: no rule proposes it, the lever text describes its effect only (both prompt profiles), and a remote backend decides whether to use it.

### BR-015: Shield end grace

- When a shield ends, the player gets a short window in which movement cannot kill, so a player who moved freely under the shield has time to settle. Length `shield.end_grace_seconds` (default 0.75 s in the stack file and the code fallback; 0 in the CI baseline; 0 to 2; 0 = no window), a `game` flag latched once per game in every mode, at the start of the game loop or at the first `grant_shield`, in the game's flag context (BR-011), stack-only and human-only (C-034: it lengthens every agent shield).
- A window opens after: a hold activation that ran out (`empty` or `budget_exhausted`, A11), from its deadline, and at most as long as that activation's cost (`min(shield.end_grace_seconds, cost)`), so a minimum-burst run-out buys at most its own cost again and run-outs never chain with the recharge into continuous protection (the recharge during such a window, at most 0.5/s × the cost, stays below the cost, so each re-hold is shorter than the last); an instant `grant_shield` (A1), from the end of its protection, known at the grant; an activated shield charge (A3, UC-030 A6), from the end of its protection. Instant and charge windows have the full length.
- No window after: a voluntary release in hold mode (`released`, the minimum-burst tail included, so a tap never buys more than its cost; a gameplay stream reopen force-releases a held activation as `released` at its last held frame, UC-030 BR-008, so it opens no window either, even when the player meant to hold it to empty); a charge that ends unused (A5); a `toughness_boost`; the match-start grace (UC-030 BR-003); a spawn, respawn or revive grace; admin invincibility (`invincible_until`) and NonStop spawn protection.
- In the window the frame is handled as UC-030 A1: the EMA is reset and the warning and death checks are skipped. The window is not part of the effective grace (`max(grace_until, invincible_until, hold_until)`): a re-hold inside it starts the activation at once and closes the window, and a charge press inside it activates the charge. The first unprotected frame after the window primes the EMA with `min(raw sample, effective warning threshold)` (UC-030 BR-009), so a sustained hard movement still kills a few frames later.
- No stacking: the window is assigned, never added; only a new shield end opens a new one, and an activation closes it. Kills that do not pass the frame gate still apply in the window (`eliminate_player`, a disconnect, a mode's own kill such as the Tournament time limit); the kill path and a revive close it, so a respawn never inherits one.
- Feedback: none of its own. The end of the shield (the clean stop of the hold rumble and the LED change from white to the player's colour, BR-010, or the end of the shield LED, A1) starts the window.
- Telemetry: `shield.end_grace_s` on `game.shield_hold` (the window's length: 0 when none opened, at most the cost after a run-out) and on the `shield_granted` and `shield_activated` span events; `shield.since_end_ms` on `player_death` when the player's last shield ended less than 3 s before; `game_shield_hold_setting{setting="shield.end_grace_seconds"}` in hold games ([telemetry.md](../specs/telemetry.md)).
