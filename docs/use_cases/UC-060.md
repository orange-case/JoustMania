# Use Case: Operate the Stage Pi

## Overview

**Use Case ID:** UC-060
**Use Case Name:** Operate the Stage Pi
**Primary Actor:** Operator
**Goal:** The Pi comes up on its own into a known, pinned version of the full stack, the game works even when observability or the network does not, and a version change is one command that can be undone
**Trigger:** The Pi boots (the autostart unit runs), or the operator runs the upgrade command or its rollback option
**Status:** Implemented
**Requirements:** FR-180, FR-182, FR-181 (Obsolete, #2785), FR-183 (Obsolete, #2785), FR-188 (Obsolete, #2785), NFR-026, NFR-027, C-040, C-041, C-042

Simplification (#2785, spec-simplification epic #2818): the host-OS detail of this use case (the systemd unit and its hooks, the start phases and timeouts, the pin floor, the status command, the ACT LED, the first-time install and the development setup) moved without a behaviour change to the ops spec [stage-host.md](../specs/stage-host.md), §1 to §5, with an acceptance checklist (SH-1 to SH-10, SH-16, SH-17). This use case keeps its goal and the flows of FR-180 (offline start) and FR-182 (upgrade and rollback); the other flows and every rule are retired here, their ids kept, and live on in the ops spec under their former ids.

## Preconditions

- **Pre-1:** The Pi runs Docker and the autostart is installed (`scripts/setup/install_autostart.sh`).
- **Pre-2:** The checkout is pinned (C-040): a release tag or an exact commit sha at or after `MIN_PINNABLE`, with `.env.local` carrying the keys (UC-070 Pre-2) and no `IMAGE_TAG` ([stage-host.md](../specs/stage-host.md) §2).

## Main Success Scenario

1. System (the autostart unit) runs the start script at boot ([stage-host.md](../specs/stage-host.md) §1).
2. System checks the pin and exports the image tag derived from the checkout; it pulls nothing and contacts no registry, so a boot without network starts the same version.
3. System starts the game services from the images on the Pi, then the observability services; observability that does not come up leaves the game running.
4. System shows the state (`starting`, `ok`, `degraded` or `failed`) on `joustmania-status` and the ACT LED ([stage-host.md](../specs/stage-host.md) §3, C-042).
5. Use case ends.

### A2: Upgrade

**Trigger:** Operator runs the upgrade command with a target release tag or exact commit sha, which changes the pin (step 2)
**Flow:**

1. System refuses `latest`, a branch name and a target older than `MIN_PINNABLE` (C-040), and changes nothing.
2. System pulls the target's images while the old version keeps running, switches the checkout to the target and restarts the unit.
3. System checks the new version as in main steps 3 and 4 and removes superseded images only once it is healthy ([stage-host.md](../specs/stage-host.md) §2, SH-5, SH-7).
4. Use case ends. A failed pull changes nothing. The upgrade never writes host files: once the new version is healthy it names a host file the operator must install, such as a missing or outdated operator pad udev rule, with the command that installs it ([stage-host.md](../specs/stage-host.md) §2, SH-17, #2858).

### A3: Rollback

**Trigger:** The new version is not healthy after A2 step 3 (automatic), or the operator runs the upgrade command with the rollback option (step 2)
**Flow:**

1. System switches the checkout back to the previous recorded version and restarts the unit with the images still on the Pi, with no network needed ([stage-host.md](../specs/stage-host.md) §2, SH-6).
2. System reports that the upgrade was rolled back, with the state of main step 4; after `--rollback` it names host files to install as in A2 step 4, and writes none.
3. Use case ends. With `--no-rollback` the failed new version is left in place for inspection.

## Postconditions

### Success Postconditions

- The pinned version of the full stack runs; the state is `ok` or `degraded`, shown by the ACT LED and `joustmania-status`.
- A reboot with unchanged images and configuration recreated 0 containers (NFR-026).

### Failure Postconditions

- The state is `failed`; no container was removed that was running before the boot, and the checkout still names a pinned version.
