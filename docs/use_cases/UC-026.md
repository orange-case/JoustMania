# Use Case: Play Non-Stop Joust

## Overview

**Use Case ID:** UC-026
**Use Case Name:** Play Non-Stop Joust
**Primary Actor:** Player
**Goal:** Die least often before the time limit
**Status:** Tested
**Requirements:** FR-026, FR-027, FR-030, FR-033

The game lifecycle is the base of [UC-020](UC-020.md) (BR-005 to BR-009 there); this use case states only the Non-Stop Joust delta (BR-005) and its own flows and rules.

## Preconditions

- A NonStop game was started with at least two players (UC-010).
- Lobby: selecting NonStop announces the mode by voice (`MENU_VOX_NONSTOP_JOUST`) and shows the pink lobby colour.

## Main Success Scenario

1. System starts the game and counts deaths per player; `score` stays 0 during play.
2. A player whose movement exceeds the threshold dies (`player_death`), the death is counted (it is no elimination, BR-004), and the player respawns once `nonstop.respawn_seconds` (default 3 s) of wall-clock time have passed since the death, on the first gameplay frame after that deadline, with `nonstop.spawn_protection_seconds` (default 2 s) of protection (`player_respawned`). The respawn time does not depend on the gameplay frame rate or on how many frames the game loop processes. While the player waits, the controller LED shows the time left: grey above 2 s, yellow above 1 s, green for the last second, with a beep at each colour change. `nonstop.respawn_seconds` = 0 respawns the player on the next gameplay frame. The game loop processes each frame as it arrives and does not sleep between frames: the controller manager paces the stream (NFR-004).
3. Before `nonstop.time_limit_seconds` (default 180 s, BR-006) is reached, System announces the time left at the 60 s, 30 s and 10 s marks: `time_announcement` with `seconds_remaining` plus the matching voice line ("1 minute", "30 seconds", "10 seconds left"; the Zombies lines, UC-023 step 2). A mark fires once, on the first frame at or past it; a mark at or above the time limit is skipped. No announcement follows the latch. When `nonstop.time_limit_seconds` is reached, measured from the first gameplay frame after the warm-up, System latches the outcome `completed` (BR-003), computes each score as max(0, base − deaths × penalty) (`nonstop.scoring`, default base 100, penalty 10), picks the highest (ties: fewest deaths; still level: A4), sends the winner rainbow, plays the congratulations voice, publishes `game_winner`, shows the winner for 2 s and publishes `player_analytics` for each player (when `analytics.enabled` is on; UC-041 BR-006) and `game_ended` (`outcome` `completed`, `winner` = the winner's serial). The gameplay stream stays open until the end-game step is done (UC-030 BR-006).

## Alternative Flows

### A1: Unlimited time

**Trigger:** `nonstop.time_limit_seconds` is set to 0 (step 3)
**Flow:**

1. No time is announced and the game never ends by itself; an operator ends it (UC-027). No winner is declared (BR-003): no `game_winner`, no rainbow, no congratulations voice; `game_ended` carries `outcome` `force_ended`, `reason` and `winner` `none`.
2. Use case ends.

### A2: Controller disconnects

**Trigger:** A controller disconnects during the game (step 2), including during the countdown or the EMA warm-up; such a disconnect is handled at the start of the game loop, before the first gameplay frame
**Flow:**

1. System counts a death through the normal death path (`player_death`, death effect; no motion involved), as in UC-020 A2, after the mass-disconnect check of UC-002 BR-009 (a player waiting to respawn is not alive there; a batch that trips the rule ends the game with `game_error`, no winner and "Cancelled."). A player who disconnects while waiting to respawn gets no extra death; the pending respawn is cancelled.
2. The player does not respawn for the rest of the game, and an agent revive (`revive_player`) of the player is refused (BR-003). The player stays in the winner ranking with its final score (BR-001). The disconnect is the player's elimination (BR-004).
3. Use case continues at step 2 for the other players.

### A3: Instructions on

**Trigger:** The host has switched spoken instructions on (`game_instructions`, FR-014, the pad's K6, UC-015 BR-011) when the game starts (step 1)
**Flow:**

1. Non-Stop Joust has no instruction recording, so it has no clip: System records `game.instructions` = `no_clip` (UC-020 A5 step 3), plays nothing and does not wait.
2. Use case continues at step 1.

### A4: Tie at the time limit

**Trigger:** At the time limit two or more players share the highest score and the fewest deaths (step 3)
**Flow:**

1. System publishes `game_tie` instead of `game_winner` and shows the tie cue (UC-020 BR-010: white flash on every player and the tie sound) instead of the rainbow, the congratulations voice and the 2 s winner hold. `player_analytics` reports `winner` false for every player; `game_ended` carries `outcome` `completed` and `winner` `none` (UC-020 BR-006).
2. Use case ends.

## Postconditions

### Success Postconditions

- After a time-limit end (step 3) the highest scorer is in the event stream, or `game_tie` when the top is shared (A4); after a force-end or a stream end (A1, BR-003) `game_ended` carries `winner` `none`. The session is ENDED.

### Failure Postconditions

- `game_error` ends the session.

## Business Rules

### BR-001: Scoring

Score = max(0, base − deaths × penalty), computed once at game end (`nonstop.scoring`, default base 100 and penalty 10; `services/game_coordinator/games/nonstop_joust.py` `_end_game_impl`).

### BR-002: Root-span outcome - Obsolete

Obsolete. The root-span outcome is the base rule UC-020 BR-006; the Non-Stop values are in BR-005. The ID is kept so it is not reused.

### BR-003: Force-end and winner

The base rule is UC-020 BR-007; the Non-Stop delta is the latch at the time limit and the stream end below.

- A winner (`game_winner`, the winner rainbow, `VOX_CONGRATULATIONS` and the 2 s winner hold) is declared only when the time limit ended the game (step 3), the latched outcome is not `force_ended` and one player leads alone; a shared lead is a tie (A4).
- The outcome is latched when the game loop detects the time limit, before the loop exits. A force-end recorded earlier in the same frame (before the time-limit check) wins: the outcome is `force_ended` and there is no winner. A force-end after the latch (during the 2 s hold or the teardown) keeps the winner and its effects; the hold ends early.
- No winner in every other end: a force-end while the game runs (A1, or before the time limit), and a gameplay stream that the controller manager ends before the time limit. NonStop opens its own gameplay stream in its game loop and recovers it as the base game loop does (UC-030 BR-006): a stream that fails, ends with a non-OK gRPC status or goes silent (no frame for 1 s of waiting for one) is opened again after 1 s, 2 s, then 3 s. A stream that is back within those three reconnects resumes the game: deaths, scores and the time limit carry on, and a respawn whose deadline passed during the outage happens on the first frame after it. After three reconnects without a healthy stream in between the game ends with one `game_error` (`gameplay_stream_lost`), no winner and "Cancelled." (`tests/test_nonstop_stream_error.py`). A server-side end of the stream with an OK status ends the game with outcome `completed`, no winner, no error and no effect sent to the finished stream (a shield-end write that the base still attempts fails silently).
- Without a winner, scores are still computed, `player_analytics` reports `winner` false for every player, and `game_ended` carries `winner` `none`, `outcome` and, for `force_ended`, `reason`.
- No kill is taken once the outcome is latched (UC-030 step 9): an `eliminate_player` during the end-game step is refused (`eliminate_refused`, UC-040 A22) and adds no death, so the winner computed from the deaths is the leader at the time limit.
- A respawn or an agent revive (`revive_player`) is refused once the game is no longer RUNNING, the outcome is latched or the gameplay stream is closed, and for a player whose controller disconnected (A2): it returns false with no state change and no LED write.

### BR-004: A respawn death is no elimination

The base rule is UC-020 BR-008: a death the player respawns from, also an `eliminate_player` death, is no elimination but still counts (`deaths`, the score, `game_player_deaths_total`, `dead_count`); a disconnect takes the player out for good (A2) and is its elimination. Non-Stop delta: a player who disconnects while waiting to respawn gets its order at the disconnect, once, with no second death and no `player_death`. No order is recorded once the outcome is latched or the game was force-ended (the kill gate, UC-030 step 9).

### BR-005: Delta from the base lifecycle

| Row | Non-Stop Joust |
|---|---|
| Win condition | `nonstop.time_limit_seconds` (default 180 s, BR-006) reached: highest score, ties broken by fewest deaths (step 3, BR-001), still level: `game_tie` (A4); time limit 0: never by itself (A1) |
| Teams | none |
| Thresholds | the tempo-driven thresholds (UC-030) |
| Start cues | the countdown; the respawn countdown LED (grey, yellow, green, with beeps) while a player waits (step 2); the time-left voice lines at 60, 30 and 10 s (step 3) |
| Result event and end cues | `game_winner` + rainbow + congratulations voice + 2 s winner hold, only on a time-limit end (BR-003); `game_tie` + the tie cue (UC-020 BR-010) on a shared lead (A4) |
| No-winner value in `game_ended` | `winner` `none` |
| Instruction clip (A3) | none (`no_clip`, no wait) |
| Streamed intro | no |
| `run()` | base, with its own game loop and gameplay stream (the base loop's frame-gap check and reconnect, BR-003) |
| Mode grace | `nonstop.spawn_protection_seconds` (default 2 s) after a respawn (step 2) |
| Eliminations | a disconnect only (A2, BR-004); a respawn death is none |

Outcome (UC-020 BR-006): `completed` (a winner or a tie) or `force_ended`; the latch is at the time limit (BR-003).

### BR-006: The game ends by itself by default

`nonstop.time_limit_seconds` defaults to 180 s (flagd default variant `three_min`; the menu's fallback when the flag cannot be read is also 180), so a round ends with a result without an operator. 0 keeps the unlimited game (A1). The value is per game: the menu reads it into `NonstopConfig.time_limit_seconds` at game start (UC-012 BR-001).
