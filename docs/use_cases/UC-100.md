# Use Case: Find a Game Moment in Every Shape

## Overview

**Use Case ID:** UC-100
**Use Case Name:** Find a Game Moment in Every Shape
**Primary Actor:** Presenter
**Secondary Actors:** Player, Observability Backend
**Goal:** Show, per observability backend, whether it still finds and correlates the same game moments (a player's warning and death) when they arrive as a span, a span event or a log event
**Trigger:** Presenter starts the "Where did it go?" booth challenge
**Status:** Draft
**Requirements:** [FR-216, FR-217, FR-218, FR-219, NFR-060, NFR-029, NFR-003](../requirements.md)

Booth challenge 3 of the Orange Case (epic #2569, #2658). Use cases UC-100 to UC-199 are the booth challenges, one per challenge. One match per shape; the case records the ground truth, every enabled backend gets the same match through the gateway, and the results are shown side by side, never ranked.

## Preconditions

- The gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter chooses the shape of the game moments for the next match: span, span event or log event.
2. Presenter starts a match ([UC-010](UC-010.md)).
3. System fixes the moment shape for the whole match and records it on the match's trace.
4. Players play; each time a player is warned and each time a player dies ([UC-030](UC-030.md)), System records that moment in the chosen shape, with the same moment identity and the same attributes in every shape.
5. System sends the moments with the rest of the match's telemetry through the gateway to every enabled backend.
6. System records, for the match, each player's warning times and death time as the ground truth.
7. Presenter picks an eliminated player and asks each backend when that player's last warning was and how long before the death.
8. Presenter compares each answer with the ground truth and records, per backend: found, found but not correlated, or not found.
9. Presenter repeats steps 1 to 8 for the other two shapes and shows the results of the three matches side by side.

## Alternative Flows

### A1: The moment shape cannot be read

**Trigger:** The shape flag is absent, holds an unknown value, or flagd cannot be reached when the match starts (step 3)
**Flow:**

1. System uses today's shape, span event, for the whole match and records that shape on the match's trace (BR-004).
2. Use case continues at step 4.

### A2: The shape changes during a match

**Trigger:** Presenter or anyone else changes the shape flag while a match runs (step 4)
**Flow:**

1. System keeps the shape the match started with; the new shape applies from the next match (BR-002).
2. Use case continues at step 4.

### A3: A backend does not receive the match

**Trigger:** The gateway or a backend cannot be reached or refuses the data (step 5)
**Flow:**

1. System keeps playing the match and keeps feeding the in-case backends and the agent unchanged (NFR-029).
2. Presenter records that backend's round as not received, which is not a result about the shape.
3. Use case continues at step 6.

### A4: No player can be asked about

**Trigger:** No eliminated player had a warning before the death (step 7)
**Flow:**

1. Presenter records the round as without a question and plays another match in the same shape.
2. Use case continues at step 2.

## Postconditions

### Success Postconditions

- For each enabled backend and each of the three shapes, a result (found, found but not correlated, not found) and the backend's answer are recorded next to the ground truth.
- The matches were played under the normal game rules.

### Failure Postconditions

- The game is never affected by the challenge: same rules, same warnings and deaths, the game loop rate holds (NFR-003, NFR-060).
- The in-case backends and the agent receive the real game telemetry as without the challenge.
- No result is recorded as found unless the backend's answer matches the ground truth.

## Business Rules

### BR-001: The two moments and their shapes

The moments are a player's **warning** (today the `death_warning` span event on the player span) and a player's **death** (today the `player_death` span event on the player span). Each can be sent as:

- **span**: a span of its own under the player span. For the warning it covers the warning window (the time in which the flash blocks a repeat warning), so the shape has a real duration; for the death it marks the moment of death;
- **span event**: an event on the player span (today's shape);
- **log event**: a log record with the moment's name as its event name, carrying the player span's trace context;
- **both**: span event and log event, with the same identity (BR-005). Not a booth round.

The exact names and attributes are in [telemetry.md §3.2](../specs/telemetry.md#32-game-coordinator).

### BR-002: One shape per match

System reads the shape once, when the match starts, and keeps it for the whole match, so every moment of a match has one shape and no answer depends on a flip in the middle of a match.

### BR-003: Same identity and attributes in every shape

Every copy of a moment carries the same moment id and the same attributes (the player, the game, the moment's own values), whatever its shape, so answers can be compared across shapes.

### BR-004: Unchanged by default

With the flag absent, unreadable, or at its default, every moment is emitted exactly as before this use case existed (NFR-060).

### BR-005: Both shapes count once

In the both shape a moment is sent twice with one moment id. Any reader that counts moments, the agent included, counts it once (FR-218: planned as an alternative flow of [UC-041](UC-041.md) in #2658 slice 2). Both doubles the volume of these moments: it is for moving a reader from one shape to another, not a booth round.

### BR-006: The ground truth comes from the game

The ground truth is what the game coordinator recorded for the match (warning times and death time per player), not what any backend holds. The case keeps no log store, so a log-event round can only be checked this way.

### BR-007: The death keeps its shape until the agent reads every shape

The agent confirms eliminations from the death moment ([UC-041](UC-041.md), [telemetry.md §4.4](../specs/telemetry.md#44-what-the-agent-ingests)). Until it reads deaths in every shape (FR-218), only the warning changes shape and the death stays a span event.

### BR-008: Results are never ranked

Results are shown side by side per backend and shape, as found, found but not correlated or not found, with the answer next to the ground truth. No score, no ranking.
