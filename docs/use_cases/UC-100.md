# Use Case: Find a Game Moment in Every Shape

## Overview

**Use Case ID:** UC-100
**Use Case Name:** Find a Game Moment in Every Shape
**Primary Actor:** Presenter
**Secondary Actors:** Player, Gateway, Observability Backend
**Goal:** Show, per observability backend, whether it still finds a player's warning and correlates it with the player's death when the warning and the death arrive as a span, a span event or a log event
**Trigger:** Presenter starts the "Where did it go?" booth challenge
**Status:** Implemented
**Requirements:** [FR-216, FR-217, FR-218, FR-219, FR-250, FR-253, NFR-060, NFR-029, NFR-003](../requirements.md)

Booth challenge 3 of the Orange Case. Use cases UC-100 to UC-199 are the booth challenges, one per challenge. One game per shape; the case records the ground truth, every enabled backend gets the same game through the gateway, and the results are shown side by side, never ranked. Steps 1 to 6 are system behaviour that tests check; steps 7 to 9 are the presenter's check at the booth, done by hand. Known gaps, no CI test: A4, BR-008, BR-009, BR-011, Post-S-1 and Post-F-3 are booth checks; BR-007's persistence is checked only at the booth; Post-F-2's "metrics are those of a game without the challenge" has no test.

## Preconditions

- The gateway export is on and forwards to the backends taking part (FR-086, UC-035 A7).
- The selected game mode is Joust Free-for-All, so every death is an elimination and each player dies at most once.
- Enough controllers are connected for a game (UC-010 preconditions).

## Main Success Scenario

1. Presenter chooses the moment shape for the next game: span, span event or log event.
2. Presenter starts a game ([UC-010](UC-010.md)).
3. System fixes the moment shape for the whole game and records it on the game's trace.
4. Players play; each time a player is warned or dies ([UC-030](UC-030.md)), System records the moment in the chosen shape (BR-007); every record of a moment carries the moment's identity and the same attributes whatever its shape.
5. System sends the moments with the rest of the game's telemetry through the gateway to every enabled backend.
6. When the game ends, System records on the game's trace each player's warning times and death time as the ground truth.
7. Presenter picks an eliminated player and asks each backend when that player's last warning before the death was, and how long before the death.
8. Presenter compares each answer with the ground truth and records, per backend, one of the three results (BR-008, BR-009, BR-011).
9. Presenter repeats steps 1 to 8 for the other two shapes, shows the results of the three games side by side, and sets the shape back to the default after the booth (BR-007).

## Alternative Flows

### A1: The game runs in another shape than chosen

**Trigger:** The shape flag is absent, holds an unknown value, or could not be read when the game started (flagd not reachable within the admission deadline, [UC-010](UC-010.md) A5), or the shape needs a telemetry channel the process does not have, so the shape recorded on the game's trace differs from the chosen one (step 3)
**Flow:**

1. System uses the default shape, span event, for the whole game and records that shape on the game's trace (BR-004).
2. Presenter sees the recorded shape differ from the chosen one; the game is played to its end and is not counted.
3. Use case continues at step 1 for the next game.

### A2: The shape changes during a game

**Trigger:** Presenter or anyone else changes the shape flag while a game runs (step 4)
**Flow:**

1. System keeps the shape the game started with; the new shape applies from the next game (BR-002).
2. Use case continues at step 4.

### A3: A backend does not receive the game

**Trigger:** The gateway or a backend cannot be reached or refuses the data (step 5)
**Flow:**

1. System keeps playing the game and keeps feeding the in-case backends and the agent unchanged (NFR-029).
2. Presenter records that backend's round as not received, which is not a result about the shape.
3. Use case continues at step 6.

### A4: No player can be asked about

**Trigger:** No eliminated player had a warning before the death (step 7)
**Flow:**

1. Presenter records the round as without a question and plays another game in the same shape.
2. Use case continues at step 2.

### A5: The game does not end normally

**Trigger:** The game is force-ended ([UC-027](UC-027.md)) or the game coordinator stops before the game ends (step 6)
**Flow:**

1. System records no ground truth for a game that did not end normally (BR-006).
2. Presenter does not count the game and plays another game in the same shape.
3. Use case continues at step 2.

### A6: The shape is set to both - Obsolete

**Status:** Obsolete. The value `both` is retired: no challenge used it, and its only reader across shapes, the agent, reads no moment any more ([UC-041](UC-041.md) BR-009). The flag no longer offers it; a game that finds it anyway runs as an unknown value, in the span event shape (A1). The steps below are kept for history only.
**Trigger:** The shape flag held both when the game started (step 3)
**Flow:**

1. System sent each warning and each death as a span event and as a log event, each moment with one moment identity, and recorded the shape both on the game's trace.
2. Presenter did not count the game, because both was not a booth round.
3. Use case continues at step 1 for the next game.

## Postconditions

### Success Postconditions

- For each enabled backend and each of the three shapes, a result (found, found but not correlated, not found) and the backend's answer are recorded next to the ground truth.
- The games were played under the normal game rules.

### Failure Postconditions

- The game is never affected by the challenge: same rules, same warnings and deaths, and the game loop rate holds (NFR-003, NFR-060).
- The metrics are those of a game without the challenge, and the agent's game context holds the same eliminations in every shape: from the elimination-order gauge alone (BR-007, BR-010, [UC-041](UC-041.md) BR-009).
- No result is recorded as found unless the backend's answer matches the ground truth.

## Business Rules

### BR-001: The two moments and their shapes

The moments are a player's **warning** (`death_warning`) and a player's **death** (`player_death`), each an event on the player span in the default shape. A moment can be sent as:

- **span**: a span of its own under the player span, recorded at once with its whole duration. For the warning the duration is the warning window (the time in which the flash blocks a repeat warning); a death is a point in time;
- **span event**: an event on the player span (the default shape);
- **log event**: a log event with the moment's name, carrying the player span's trace context. It is sent whatever the log level, and a process without a log channel uses the span event instead (A1).

The moment keeps its name in every shape. Names, attributes and export timing are in the booth profile, [telemetry.md appendix A](../specs/telemetry.md#appendix-a-booth-profile).

### BR-002: One shape per game

System reads the shape once, when the game starts, and keeps it for the whole game, so every moment of a game has one shape and no answer depends on a change in the middle of a game. Every game follows the shape, shadow and pattern games included.

### BR-003: Same identity and attributes in every shape

Every record of a moment carries the same moment id and the same attributes (the player, the game, the moment's own values), whatever its shape, so answers can be compared across shapes. The moment id is unique within the game, also when a player record is recreated.

### BR-004: Unchanged by default

With the flag absent, unreadable, or at its default, every moment keeps today's name, shape, parent and attributes; it only gains its identity attributes (the moment id, the player, the game) (NFR-060).

### BR-005: Both is not a booth round - Obsolete

Obsolete. The both shape (each moment sent twice, as a span event and as a log event with one moment id) was for moving a reader from one shape to another, not for a booth round. It is retired with that reader, the agent's moment ingest ([UC-041](UC-041.md) BR-009); a booth round never used it (A6).

### BR-006: The ground truth comes from the game

The ground truth is what the game coordinator recorded for the game (each player's warning times and death time, on the game's trace at game end), not what any backend holds and not the agent's game summary. Only a game that ends normally has a ground truth (A5). The case keeps no log store, so a log-event round can only be checked this way.

### BR-007: The death follows the shape like the warning

The death is a moment in the game's shape, like the warning: a span event, a span `game.player_death` (a point in time) or a log event. The agent reads no moment in any shape: its elimination order comes from the elimination-order gauge alone, which the game coordinator sets in every shape ([UC-041](UC-041.md) BR-008, BR-009). A booth round therefore asks a backend to correlate a warning and a death sent in the same shape, and the shape never changes what the agent sees.

The chosen shape stays in effect for every later game, shadow and pattern games included, also after a restart of the game coordinator, until it is changed or the flag service restarts (the shape is held in the flag service's memory, not persisted). After the booth the presenter sets it back to the default, so that later games send the moments as they do off the booth.

### BR-008: Results are never ranked

Results are shown side by side per backend and shape, as found, found but not correlated or not found, with the answer next to the ground truth. No score, no ranking.

### BR-009: Only the moment record counts

A backend has found a moment only when it shows the moment's own record: the moment's name with its moment id. Other records about the same happening do not count: the log lines the game writes for a warning or a death, the event-bus game event (it reaches stream subscribers only), and the controller manager's effect records.

### BR-010: The agent takes nothing from a moment span

A moment sent as a span carries the player and the game but is no sign that the player is alive or that the game runs: the agent ignores every span that carries a moment id, as it ignores the shield charge span ([telemetry.md §4.4](../specs/telemetry.md#44-what-the-agent-ingests)). The agent's elimination order comes from the elimination-order gauge alone, in this shape as in every other (BR-007).

### BR-011: The three results

For the asked player of a game, a backend's result is:

- **found**: it shows that player's warning record (BR-009), and the time it gives from the last warning to the death matches the ground truth within 0.1 s;
- **found but not correlated**: it shows that player's warning record, but gives no time to the death or a time that differs from the ground truth by more than 0.1 s;
- **not found**: it shows no warning record of that player in that game.

A backend that did not receive the game (A3) gets no result for that game.

### BR-012: The agent's own log events never reach a backend

In every game the game coordinator also sends the agent its own log events (without a flag, FR-253: `telemetry.agent_log_events` is retired and the game's trace records no such attribute): the game's start and end (`game.start`, `game.end`), and the opening of its `game.phase.gameplay` and `game.cycle` spans (`game.phase.start`, UC-041 BR-004); no moment is copied to the agent ([UC-041](UC-041.md) BR-009). A coordinator without OTLP logging sends none of them. The game's start is sent once the game is built and its end only after its start was sent, so the agent never gets an end without a start, and a game that fails before it is built sends neither.

Every such record carries the marker `orangecase.audience` = `agent`, and the case collector drops every marked record on the way to the gateway: a backend gets the moments only in the game's shape. The collector decides on the record alone, never on its span, which usually ends after the record has passed. The records change nothing a backend can find (BR-009); they only change how soon and how reliably the agent sees the game ([UC-041](UC-041.md) A8, BR-010). There is no on/off comparison: the agent's game trace ids come from these records ([UC-041](UC-041.md) BR-004), so an off state would only be a broken agent, not an agent without logs.
